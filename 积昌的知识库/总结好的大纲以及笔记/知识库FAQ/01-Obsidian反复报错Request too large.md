# 🔴 Obsidian 反复报错 "Request too large (max 32MB)"

> [!summary] 📊 报错统计速览（截至 2026-09-30）
> 🔥 **本文档共记录 <span style="color:#e74c3c">4 次报错事件</span>**（2026-07-28/08-01 首发 1 次；2026-09-11 复发 1 次；2026-09-24 复发 1 次——批量读取 JSID 论文 PDF 时整份读取返回 `[Unsupported Document]`，改用 `pages` 参数分页读取即恢复；2026-09-30 复发 1 次——读取 b′/c′ 模块论文 PDF 时整份读取返回 `[Unsupported Document]`，带 `pages` 参数读取即恢复）。主根因为 **「PDF 渲染体积超限（Request too large）」**，同案涉及次生根因 **「poppler 缺失」**（环境层缺依赖）与 **「PDF 渲染管线瞬时故障」**（文件/环境均正常，重试或分页自愈）。
>
> | 根因 | 台账累计 | 主要发生地 |
> |------|:---:|------|
> | 🟠 PDF 渲染体积超限（Request too large） | **1** | 01 |
> | 🟠 poppler 缺失（pdftoppm failed） | **1** | 01 |
> | 🟠 PDF 渲染管线瞬时故障（正常文件，重试即恢复） | **3** | 01 |
>

## 错误信息

```
Error: invalid_requestRequest too large (max 32MB). Try with a smaller file.
```

## 现象

在 Obsidian 中通过 realclaudian 插件与 Claude 交互时，**反复弹出**此错误。即使没有主动操作，错误也会出现。删除 vault 中的大文件**无法解决**此问题。

## 正确原因

**⚠️ 此错误与 vault 中的文件大小无关。** 真正的来源是：

> **Anthropic API（Claude）的 HTTP 请求体上限为 32MB。当 realclaudian 插件发送的请求体超过此限制时，API 网关拒绝请求并返回此错误。**

### 为什么请求体会超过 32MB？

realclaudian 插件每次与 Claude API 通信时，会发送：

| 请求体组成 | 内容 | 说明 |
|-----------|------|------|
| **System Prompt** | 系统指令 + CLAUDE.md × 2 + 所有 Skill 描述 + 所有工具定义 + 系统上下文 | 每次请求都携带，固定较大 |
| **Messages** | 整段对话历史（用户消息 + AI 回复 + 工具调用 + 工具结果） | **随对话轮次增加不断累积** |
| **Tools** | 所有可用工具的完整 JSON Schema 定义 | 每次请求都携带 |

当对话进行多轮后，尤其是涉及大量**文件读取、Agent 搜索、长篇幅回复**时，累积的消息体量会不断增长。最终序列化为 JSON 后突破 32MB 限制。

### 为什么 "一直在报"？

因为每次插件重试或用户继续对话，都会再次发送同样大的请求体 → 再次被拒绝 → 再次报错 → 形成死循环。

### 为什么删除大文件没用？

因为错误**不是**插件在扫描 vault 文件时触发的，而是**API 通信层面**的问题。删除 vault 中的文件不会减少请求体的大小。

## 解决方案

### 方案一：清理旧会话 + 重启 Obsidian（首选）

```bash
# 1. 备份后删除所有旧会话的 meta.json 文件（释放插件缓存）
#    （注意：这会丢失所有历史会话记录）
rm -rf "F:\积昌的知识库 - 副本\.claudian\sessions\"

# 2. 重启 Obsidian（让插件以全新状态初始化）
```

### 方案二：开启新对话

如果不想清除所有历史，也可以：
1. 在 realclaudian 插件中开启一个**全新的对话**
2. 新对话的上下文从零开始，请求体很小，不会触发 32MB 限制

### 方案三：减少单次请求的数据量

- 避免在同一个对话中连续进行大量文件读取
- 避免在同一个对话中多次调用 Agent 进行全库搜索
- 长对话完成后及时开启新对话

## 验证修复

1. 执行清理后重启 Obsidian
2. 如果错误不再弹出 → ✅ **已修复（原因是旧会话积累的数据已清除）**
3. 如果仍报错 → 可能是插件本身存在问题，需检查 realclaudian 插件更新

## 根本原因总结

| 项目 | 结论 |
|------|------|
| ❌ 不是 vault 文件过大 | 删除大文件后错误依旧 |
| ❌ 不是飞书智能助手 | 用户未调用飞书功能 |
| ✅ 是 **API 请求体超限** | realclaudian 插件 → Anthropic API 的请求 JSON 超过 32MB |
| ✅ 根本驱动因素 | **单次对话中累积了大量工具调用结果**（文件读取、Agent 搜索、Grep 结果等） |

## 预防措施

| 措施 | 说明 |
|------|------|
| **定期开新对话** | 长对话（超过 10-15 轮高强度交互）完成后及时开启新会话 |
| **避免过量文件读取** | 需要读取大量文件时，分批进行或使用摘要而非全文 |
| **清理旧会话** | `.claudian/sessions/` 中的旧 .meta.json 文件会积累到 ~17MB，定期清理无用的历史会话 |

## 诊断命令

```bash
# 查看会话文件总大小

# 查看最大的历史会话
ls -lhS "F:\积昌的知识库 - 副本\.claudian\sessions\" | head -10

# 删除所有会话（谨慎！会丢失历史记录）

```

## 🔁 复发记录（2026-09-11 20:35）：正常 PDF 读取返回 Unsupported Document（瞬时故障，重试即恢复）

> 📌 **报错场景**：使用 Read 工具读取 `源文件/pdf文件/学术裁缝课程/充电视频010-顶会如何阅读（1）.pdf`（612.7 KB，9 页）失败，返回 `[Unsupported Document]`。**同一任务此前读取同目录其他 PDF**（如 `补充：科研trick.pdf`、`3.4如何写大论文.pdf`）**均正常**。

**报错原文**

```
[Unsupported Document]
```

**三层诊断结果**

| 层级 | 检查项 | 结果 | 判据 |
|:---|:---|:---|:---|
| ① 文件层 | `pdf_diagnose.py`（页数 / 文字层 / 内嵌图片 / 渲染体积） | ✅ 正常 | 9 页、可选中文字 18836 字符、内嵌图片 0、渲染体积 1x=1.9MB / 1.5x=3.7MB / 2x=4.9MB，风险判定 **✅ 安全**（远低于 32MB 上限） |
| ② 环境层 | `where pdftoppm` | ✅ 正常 | poppler 已安装：`C:\Users\asus\AppData\Local\Microsoft\WinGet\Packages\oschwartz10612.Poppler_...\poppler-25.07.0\Library\bin\pdftoppm.exe` |
| ③ 工具 / 会话层 | 同目录小文件对照 + 重试 | ✅ 正常 | 同目录其他 PDF 读取正常；**带 `pages` 参数重试即成功** |

**根因**

> 🔥 **<span style="color:#e74c3c">PDF 渲染管线瞬时故障</span>**——文件本身、poppler 环境、会话图片投递**三层全部正常**，首次读取时渲染管线偶发失败、返回 `[Unsupported Document]`，**重试即恢复正常**。**与文件体积无关**（该文件仅 612.7 KB、1x 渲染体积仅 1.9MB，远低于上限）。

**修复方法**

> 💡 **<span style="color:#2980b9">直接重试读取即可</span>**：对同一 PDF **再次调用 Read**（本次带 `pages: "1-9"` 参数）→ 成功读取全部 9 页内容。**无需备份、无需分卷、无需重装 poppler。**

**与其他 PDF 报错形态的区别（避免误判）**

| 报错形态 | 根因 | 处置 |
|:---|:---|:---|
| `Request too large (max 32MB)` | 渲染体积超请求上限 | 备份 → `pdf_fix_split.py` 分卷 → 验证 |
| `pdftoppm failed: Command 'pdftoppm' not found` | 机器缺 poppler | winget 安装 → **重启会话** |
| **`[Unsupported Document]`（本记录）** | **渲染管线瞬时故障（文件 / 环境均正常）** | **直接重试读取；多次失败再走三层诊断** |

> ⚠️ 提示：若重试多次仍失败，再按三层诊断逐层排查——**先查文件渲染体积，再查 poppler，最后查会话图片投递**。

**验证结果**

- 带 `pages: "1-9"` 重试 → ✅ 成功读取 9 页全文，后续整理任务（充电视频010 笔记）正常完成。

**遗留事项**

- **无**。该故障为瞬时性问题，无需长期处置；但**再次遇到 `[Unsupported Document]` 时优先「重试一次」，不要第一时间做分卷/重装等重操作**。

## 🔁 复发记录（2026-09-24 00:04）：批量读取 JSID 论文 PDF 返回 Unsupported Document（分页读取即恢复）

> 📌 **报错场景**：确定基准模型 A 的任务中，需**逐篇深度阅读** `总结好的大纲以及笔记/学校/科研/学术裁缝/第一篇论文/论文/A基准模型/A基准模型四区论文/` 下的 6 篇 JSID 论文与 `A基准模型一区论文/` 下的 9 篇论文。**整份一次性读取** `1.jsid.1305.pdf`（2 MB，9 页）失败，返回 `[Unsupported Document]`；随后**多篇 PDF 整份读取同样失败**，任务一度卡死。

**报错原文**

```
[Unsupported Document]
```

**三层诊断结果**

| 层级 | 检查项 | 结果 | 判据 |
|:---|:---|:---|:---|
| ① 文件层 | `pdf_diagnose.py`（页数 / 文字层 / 内嵌图片 / 渲染体积） | ✅ 正常 | 9 页、可选中文字 23246 字符、渲染体积 1x=1.4MB / 1.5x=2.7MB / 2x=3.5MB，风险判定 **✅ 安全**（远低于 32MB 上限） |
| ② 环境层 | `where pdftoppm` | ✅ 正常 | poppler 已安装：`C:\Users\asus\AppData\Local\Microsoft\WinGet\Packages\oschwartz10612.Poppler_...\poppler-25.07.0\Library\bin\pdftoppm.exe` |
| ③ 工具 / 会话层 | 同目录小文件对照 + 重试 | ✅ 正常 | 同目录 txt 与几 KB 小 png 读取正常；**带 `pages` 参数重试即成功** |

**根因**

> 🔥 **<span style="color:#e74c3c">PDF 渲染管线瞬时故障</span>（批量读取场景放大）**——文件本身、poppler 环境、会话图片投递**三层全部正常**，**整份多页 PDF 一次性渲染**时渲染管线偶发失败、返回 `[Unsupported Document]`；**与文件体积无关**（该文件仅 2 MB、1x 渲染体积仅 1.4 MB）。批量连续读取多篇论文时该故障**更易连续触发**，导致任务看起来"卡死"。

**修复方法**

> 💡 **<span style="color:#2980b9">改用 `pages` 参数「分页读取」即可</span>**：对同一 PDF **再次调用 Read 并带 `pages` 参数**（如 `pages: "1-3"`）→ 成功读取；随后各篇论文均按分页方式读取、全部通过。**无需备份、无需分卷、无需重装 poppler。**
>
> 📌 **实操建议**：**深度阅读多页论文时，从一开始就带 `pages` 参数按 3–5 页分段读取**，既规避渲染管线偶发失败，也避免单次请求体过大。

**验证结果**

- `1.jsid.1305.pdf` 带 `pages: "1-3"` 重试 → ✅ 成功读取，后续其余 14 篇论文按分页方式读取全部通过，基准模型 A 的确定任务正常完成。

**遗留事项**

- **无**。该故障为瞬时性问题，无需长期处置；强化既有经验：**遇到 `[Unsupported Document]` 优先「带 `pages` 参数重试」，不要第一时间做分卷/重装等重操作**。
