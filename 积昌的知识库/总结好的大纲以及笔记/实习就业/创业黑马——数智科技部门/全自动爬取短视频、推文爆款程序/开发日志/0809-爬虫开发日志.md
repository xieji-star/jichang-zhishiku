## 1. 项目目标与真实边界

### 1.1 要解决的问题

平台的目标不是单纯“爬几个视频”，而是建立一套可持续扩展的短视频数据工作台：

- 按指定抖音账号自动获取作品，而不是依赖团队手工填写新视频链接。
- 支持固定矩阵账号，也支持临时添加其他达人或对标博主。
- 可以按视频发布时间查询，也可以查看某个账号的全部视频。
- 保留采集时间作为高级筛选条件，用于追踪数据快照变化。
- 采集视频链接、标题、标签、发布时间和互动指标，并为后续爆款分析提供基础数据。
- 支持 Excel 导出，并为飞书云文档、飞书多维表格导出预留能力。
- 通过 MediaCrawler 获得作品元数据，再通过 pyvideotrans 或可替换的 ASR 引擎生成口播稿。
- 最终可以部署到云端，供本人和小组成员共同使用。

🔥 **<span style="color:#e74c3c">项目当前不是一个已经全部交付的成品，而是一个“数据层和后端核心能力已经进入可发布阶段、前端和云端采集闭环仍在建设”的持续开发项目。</span>**

### 1.2 使用范围

- 使用者：本人及内部小组成员。
- 使用目的：日常工作、内容分析、对标账号研究和内部协作。
- 商业化：目前明确不考虑对外售卖或商业化交付。
- 运行方式：由使用者决定何时发起采集，不要求个人电脑长期保持开机。
- 数据范围：默认关注矩阵账号，但系统必须具备批量分析和动态新增账号的能力。

## 2. 当前总体架构

### 2.1 为什么使用飞书妙搭

妙搭不是爬虫本体。它承担的是多人可访问的网站、账号管理、查询、导出和业务数据展示层。选择它的原因包括：

- 已经具备可公开或组织内访问的互联网网址，不需要个人电脑直接暴露端口。
- 自带前后端托管、数据库、登录鉴权和角色能力，减少独立维护网站服务器的工作量。
- 与飞书组织、权限和后续文档/多维表格能力衔接更自然。
- 对小组内部工具而言，能减少域名、证书、前端静态托管和基础认证的运维成本。

💡 **<span style="color:#2980b9">妙搭解决的是“平台入口和业务管理”，MediaCrawler 解决的是“抖音数据采集”，pyvideotrans 解决的是“本地媒体转录”。三者不能互相替代。</span>**

### 2.2 推荐的云端分层

```text
用户浏览器 / 手机
        ↓
飞书妙搭：登录、权限、账号库、筛选、分页、导出、任务状态
        ↓
业务后端与持久任务队列：任务分阶段、重试、幂等、状态同步
        ↓
常驻 CPU 采集节点：MediaCrawler、Chromium、登录态、视频元数据与临时下载
        ↓
按需转录 Worker：Python 3.10、FFmpeg、pyvideotrans / 可替换 ASR
        ↓
结构化结果：视频指标、口播稿、SRT、任务状态
```

推荐保留妙搭作为业务平台，一台小型常驻 CPU 节点维持浏览器登录和采集任务，转录任务按需启动 CPU 或 GPU Worker（工作进程）。这比常驻 GPU 便宜，也比所有功能塞进一台服务器更容易恢复故障。

### 2.3 数据闭环

1. 用户在妙搭选择固定账号或新增达人。
2. 用户按需发起采集任务。
3. 采集节点根据稳定账号 ID 获取作品元数据和视频下载地址。
4. 基础数据先写入业务数据库，采集成功不依赖转录成功。
5. 需要口播稿的视频进入持久任务队列。
6. 下载器将媒体流式保存到任务专属临时目录。
7. pyvideotrans 独立子进程读取本地媒体，生成 SRT（字幕文件）和纯文本口播稿。
8. 结果校验并写库。
9. 口播稿完整入库后，自动删除原视频、WAV、`.part` 和任务临时目录。
10. 前端显示完成、失败、等待人工登录或可重试状态。

⚠️ **<span style="color:#e74c3c">视频临时文件不是业务资产。口播稿和必要字幕成功入库后必须删除媒体，避免云盘持续膨胀。</span>**

## 3. 开发历程与关键决策

### 3.1 第一阶段：需求和爆款标准梳理

早期工作围绕矩阵账号、历史数据和爆款分级展开，形成了 [[矩阵号爆款数据分析与标准定义]]。这一阶段确认了：

- 账号需要按华哥、七哥、鱼哥分组管理。
- 爆款不能只看一个绝对点赞数，应结合账号自身基线和互动指标。
- 系统结构必须配置化，方便增加账号、字段、评分规则和后续平台。
- 不要求立即分析全部历史视频，但数据模型必须能承接批量分析。

### 3.2 第二阶段：付费 API 路线评估

项目最初尝试第三方抖音 API。实际使用中暴露了几个问题：

- 单次调用价格偏高，套餐和余额的跨月规则不够直观。
- 部分平台只能用美元充值，个人使用成本和支付体验较差。
- 某些调用延迟过高，出现等待较长仍拿不到数据的情况。
- 通过抖音号或主页链接批量获取作品的能力、个人主体能否申请、调用频控等存在不确定性。

因此，项目转向开源采集方案。[[MediaCrawler深度分析与结合改进方案]] 记录了替换第三方付费 API 的详细理由和字段结合方式。

### 3.3 第三阶段：采用 MediaCrawler

MediaCrawler 被放入：

`D:\全自动爬取短视频、推文爆款程序\MediaCrawler`

选择它的主要原因：

- 能采集抖音作品元数据，降低按次 API 成本。
- 已有浏览器登录、作品数据和数据库存储能力。
- 数据库中已经保存 `video_download_url`，可以作为后续转录入口。
- 与业务平台解耦后，未来仍能替换为官方或获得授权的数据源。

但它不是“永久稳定的免费官方接口”。登录态、风控、验证码、平台页面变化和开源许可都要求保留数据源适配器边界。

### 3.6 第六阶段：品牌前端与 UI 方向

前端视觉方向以“图灵学术 Turing Academy”Logo 为基础：

- 主色：深蓝、科技蓝。
- 辅色：青绿、水绿色。
- 视觉语言：学术、可信、理性，同时保留山峰、路径和成长感。
- 页面要求：有层次感，信息密度高但不拥挤，兼顾桌面和移动端。

现有线上版本已完成一轮品牌化界面，但新增“达人账号库、日期筛选、全部视频和真实分页”后，需要继续改造仪表盘交互，不能只在旧页面上堆按钮。

### 3.7 第七阶段：动态账号与视频查询重构

随着“临时添加其他达人”和“查询任意日期、全部视频”的需求加入，原有以账号名称作为选择键的做法不再可靠。原因是：

- 显示名称可能重复。
- 博主可能改名。
- 归档后仍需要保留历史数据。
- 同名账号会导致导入、筛选和更新指向错误对象。

因此系统改为稳定 UUID（通用唯一标识符）作为 `accountId`，显示名称只作为可变信息。对应实施计划位于 D 盘项目：

`docs/superpowers/plans/2026-08-09-dynamic-accounts-video-query.md`

账号主页绑定采用已确认的 **A2 半自动识别 + A1 手动粘贴兜底**：平台优先从抖音主页链接中识别稳定身份；自动识别失败、平台页面变化或用户只掌握部分信息时，允许管理员手动粘贴抖音号、主页链接或稳定标识。两条路径最终都要落到同一 `accountId`，不能因为识别方式不同而创建重复账号。

### 3.8 第八阶段：口播稿一站式闭环设计

pyvideotrans 已存放在：

`D:\全自动爬取短视频、推文爆款程序\pyvideotrans`

实际审查发现，pyvideotrans 的 CLI（命令行接口）不接受视频网址，它只接受已经存在的本地音频或视频文件。因此正确链路不是“把 URL 直接传给 pyvideotrans”，而是：

`MediaCrawler 下载地址 → 受控下载到临时文件 → pyvideotrans 转录 → 校验 SRT → 提取口播稿 → 写库 → 删除临时媒体`

这一结论与 [[口播稿转录]] 中“链接直出本质上仍发生下载”的分析一致。

知识库中已有 [MediaCrawler 到 pyvideotrans 的参考脚本](mediacrawler_to_pyvideotrans.py)，可用于理解字段和流程衔接；它属于研究/原型材料，不能替代后端所需的持久任务队列、安全下载、输出校验和失败恢复。

## 6. 遇到的困难、根因与解决过程

### 6.1 第三方 API 成本高、延迟不稳定

**现象：** 调用价格高，套餐规则难判断，部分服务需要美元充值，等待时间也不理想。

**根因：** 抖音数据属于高风控数据，第三方需要承担账号、代理、维护和失败重试成本；低价平台通常在稳定性、字段完整度或合规性上让步。

**处理：** 采用 MediaCrawler 作为内部研究和工作使用的数据源，业务层保留 Provider（数据提供者）接口，以后可替换为官方或获得授权的供应商。

**更好办法：** 不把整个项目绑定到某一家第三方或某一个开源采集器；对不同数据源做统一字段映射和健康检查。

### 6.2 临时公开链接被 Cloudflare 拦截

**现象：** `chatgpt.site` 页面提示访问被阻止。

**根因：** 共享域名、访问来源、Cloudflare 安全规则或隧道特征触发拦截；这类临时地址也不适合长期团队使用。

**处理：** 改用妙搭托管地址，平台登录、角色和发布由妙搭承担。

**更好办法：** 如果未来脱离妙搭，使用正式域名、HTTPS、反向代理和国内备案后的云服务，不继续依赖临时共享域名。

### 6.3 F 盘写入慢

**现象：** 依赖安装、构建、数据库和大量小文件写入速度慢。

**根因：** F 盘介质或挂载性能不适合 Node.js、Python 和 Git 高频小文件操作。

**处理：** 代码和运行数据统一迁移到 D 盘；F 盘保留知识库文档。

**更好办法：** 云端也采用本地 SSD 临时盘处理媒体，结果写数据库，避免在低性能网络盘直接运行依赖和浏览器用户目录。

### 6.4 数据抓下来全是 0

**现象：** 早期页面能够显示记录，但互动数据为 0 或测试数据与真实采集混淆。

**根因方向：** 采集链尚未真正闭环、字段映射不完整、媒体采集关闭、业务库只保留部分字段，以及页面默认值把缺失值显示成 0。

**处理原则：** 页面不能把“未知/未采集”伪装成 0；数据源、采集状态、失败原因和最近采集时间必须可见。当前后端已加强字段契约和真实数据库测试，但云端真实采集仍未完成。

⚠️ **<span style="color:#e74c3c">因此，现在线上看到 0 不能被解释为真实业务指标；必须等云端采集节点、字段同步和任务状态完整上线后再验收。</span>**

### 6.5 账号名称不能作为主键

**现象：** 增加临时达人后，名称可能重复或改变。

**根因：** 显示名称是业务属性，不是稳定身份。

**处理：** 引入稳定 UUID `accountId`；导入兼容旧数据时才回退到抖音号或唯一旧名称。

**更好办法：** 前端所有选择器、URL 参数、导出和任务记录统一使用 `accountId`，仅在显示层使用账号名称。

### 6.6 数据库迁移存在 dev/online DML 缺口

**现象：** 最初计划想在开发环境执行结构和数据回填，再靠结构差异发布到线上。

**根因：** 妙搭的数据库环境差异发布只同步 Schema（表结构），不会把开发环境的 DML（数据更新语句）自动复制到线上。

**处理：** 改为三阶段迁移：

1. Expand：先增加可空字段并上线。
2. Backfill：开发和线上分别执行幂等回填并验零空值。
3. Contract：兼容双写代码上线并经过线上探针后，再加非空和外键约束。

**更好办法：** 每个阶段都要有备份、发布 ID、线上回读、停止条件和恢复预案，不能把结构收紧与应用代码更新挤在一次发布里。

### 6.7 兼容写入与约束收紧之间存在竞态

**现象：** 如果先把 `video.account_id` 设为非空，再发布写入 `account_id` 的新代码，旧接口会在中间窗口写入失败。

**处理：** 必须先发布兼容双写代码，验证新增和 upsert 都能写出 `account_id`，重新全量回填并确认线上零空值，再执行 Contract 迁移。

### 6.8 Jest 没有真正发现前端测试

**现象：** 指定前端测试文件时命令退出码为 0，但实际测试列表为空。

**根因：** 根 `package.json` 的 `testMatch` 只包含服务端测试目录。

**处理：** 将客户端测试纳入 Jest 发现范围，并要求 RED 阶段必须看到真实失败，GREEN 阶段必须报告实际测试数量。

### 6.9 Nest 装饰器测试编译失败

**现象：** 控制器测试尚未执行断言，先在 TypeScript 编译阶段报装饰器错误。

**根因：** Jest 读取了前端 TypeScript 配置，缺少后端需要的 `experimentalDecorators` 和 `emitDecoratorMetadata`。

**处理：** 新增 `tsconfig.jest.json`，明确装饰器配置、CommonJS 模块和路径别名。

### 6.10 真实数据库集成测试曾超时

**现象：** 使用完整 `AppModule` 加载集成测试时，120 秒没有 Jest 输出。

**根因：** 平台模块和数据库初始化范围过大，测试在进入业务断言前就阻塞。

**处理：** 使用更窄的数据库模块组装测试，同时通过环境变量控制真实数据库用例是否运行；发布门禁必须显式执行 `npm run test:radar:db`。

### 6.11 PostgreSQL UUID 数组转换报错

**现象：** Drizzle/PostgresJS 将 `${ids}::uuid[]` 展开为 record，数据库报 `cannot cast type record to uuid[]`。

**根因：** 参数数组被驱动展开为记录类型，并非预期的 PostgreSQL UUID 数组。

**处理：** 改为逐项参数化 `ARRAY[$1::uuid, ...]`，分页和导出同步修复，并用真实数据库测试验证。

### 6.12 OpenAPI 使用 oneOf 导致合法请求被拒

**现象：** 导入数据同时提供 `accountId` 和 `accountName` 时，运行时允许并按优先级解析，但 OpenAPI 的 `oneOf` 认为请求同时命中多个分支而无效。

**根因：** `oneOf` 要求只命中一个条件，实际业务要求是三个标识至少提供一个，也允许同时提供多个。

**处理：** 改为 `anyOf`，并增加“多标识合法、无标识非法”的 Schema 测试。

### 6.13 摘要最新采集时间取错

**现象：** `latestCapturedAt` 从按发布时间排序后的第一条视频中取值，不一定是账号全部视频里的最大采集时间。

**处理：** 对所有非空 `capturedAt` 独立求最大值，并增加发布时间与采集时间交叉排序的真实数据库测试。

### 6.14 pyvideotrans 不能直接读取 URL

**现象：** 原设想是把 MediaCrawler 得到的视频链接直接交给 pyvideotrans。

**根因：** pyvideotrans 的 `--name` 是本地文件路径，代码使用 `Path.exists()` 校验；URL 会被判为文件不存在。

**处理：** 新增受控下载器，将视频下载到任务临时目录，再用独立子进程转录。

### 6.15 Python 版本冲突

**现象：** 根后端和 MediaCrawler 使用 Python 3.12.4，而 pyvideotrans 要求 Python 3.10.x。

**处理：** 为 pyvideotrans 建立独立 Python 3.10 环境或容器，后端只通过参数数组调用子进程，`shell=False`，不直接 import。

### 6.16 MediaCrawler 自带下载器不适合直接做生产批处理

**现象：** 现有实现一次将完整响应读入内存，超时固定、失败重试不足，再一次性写盘。

**风险：** 大文件或并发任务会增加内存、磁盘和失败恢复压力。

**更好办法：** 在业务后端实现流式下载、大小限制、MIME 检查、ffprobe 校验、`.part` 临时扩展、原子改名、指数退避和任务专属目录。

### 6.17 妙搭技能同步在 Windows 失败

**现象：** `skills sync --local` 先因 `spawnSync npm ENOENT` 失败，修正 Windows 下 `npm.cmd` 调用后又遇到创建符号链接 `EPERM`。

**进一步核查：** 手动检查 `@lark-apaas/coding-steering@0.1.29` 后确认包中实际没有计划要求的 `table-skill` 和 `forms-skill`。

**处理：** 已恢复被部分修改的 `.agents` 目录，停止新前端 Task 6，没有伪造不存在的技能合同。

**更好办法：** 获得用户批准后，使用现有 shadcn 组件、妙搭 `plugin-guide` 的 table 参考，以及知识库中的前端设计技能继续实现；并把这一偏差记录在实施说明中。

## 10. 云端部署与成本优化建议

### 10.1 推荐方案

“妙搭 + 常驻小型 CPU 采集节点 + 按需转录 Worker”综合性价比最高。

| 组件 | 推荐配置 | 成本策略 |
|---|---|---|
| 妙搭 | 继续托管业务前端和数据库 | 复用现有能力，减少自建网站运维 |
| 采集节点 | Linux 4 核 8 GB 起步，实测后调整 | 常驻低配 CPU，不买常驻 GPU |
| 转录 Worker | 默认单并发 CPU；积压后再启按需 GPU | 有任务才付费 |
| 临时媒体 | 本地 SSD 临时盘或私有临时对象存储 | 成功后立即删除 |
| 模型缓存 | 持久云盘或对象存储 | 避免 Worker 每次重新下载模型 |
| 数据库 | 妙搭现有数据库，未来量大再迁 PostgreSQL | 先低运维，后按瓶颈迁移 |

### 10.2 为什么不建议一开始买常驻 GPU

- 采集任务不需要 GPU。
- 视频转录并非全天持续运行。
- 常驻 GPU 空闲时仍持续计费。
- 驱动、显存和模型环境会增加维护复杂度。
- 当前最需要验证的是数据源稳定性和单条转录闭环，而不是峰值吞吐量。

### 10.3 临时文件节省策略

🔥 **<span style="color:#e74c3c">媒体文件默认零长期保留：成功入库即删，失败按短期重试窗口保留，超龄后统一清理。</span>**

建议策略：

- 下载到 `jobs/<job_uuid>/input.part`。
- 校验完成后原子改名为内部文件名，不使用外部标题做文件名。
- 转录成功并完成数据库事务后删除视频和中间 WAV。
- SRT 与纯文本写库；是否保存 SRT 文件做配置开关。
- 失败任务保留 6—24 小时，便于重试和排障。
- 服务启动时清理超龄 `.part` 和孤儿任务目录。
- 每日记录临时空间峰值、清理文件数和释放空间。

## 11. 安全、合规与使用边界

### 11.1 浏览器和登录态

- Cookie、浏览器 Profile、同步密钥不能写入代码仓库、妙搭数据库或普通日志。
- 浏览器 Profile 使用加密持久云盘，且同一 Profile 同时只能被一个浏览器进程使用。
- CDP 调试端口只监听本机，不向公网开放。
- noVNC/RDP 只在需要人工验证码时临时开启，完成后立即关闭。
- 不能承诺完全无人值守；抖音可能要求扫码、滑块或短信验证。

### 11.2 下载安全

- 只允许 HTTPS。
- 下载地址使用域名白名单，每次重定向都重新检查。
- 拒绝 localhost、私网和链路本地地址，防止 SSRF（服务端请求伪造）。
- 限制响应大小、视频时长、MIME 类型和总下载时间。
- `subprocess` 使用参数数组并设置 `shell=False`。
- 日志不输出完整下载 URL、Cookie 和本地敏感路径。

### 11.3 开源许可

- pyvideotrans 根许可证为 GPLv3，并有附加说明；内部自用与对外分发的责任不同，若以后改变用途，应重新核查。
- MediaCrawler 明确限制商业用途和大规模抓取。
- 当前用户已说明仅用于本人和小组工作，不考虑商业化，但仍需遵守平台规则、开源许可证和合理采集边界。

📌 **<span style="color:#e67e22">内部使用不等于没有许可义务，也不等于可以无限规模采集；云端部署后尤其需要控制频率和账号数量。</span>**

## 13. 复盘：为什么这样做，以及还能怎样更好

### 13.1 先做稳定身份，再做动态账号

如果继续用账号名称做键，新增达人功能会立刻把系统带入同名、改名和历史数据错配问题。先引入稳定 UUID，看似增加迁移成本，实际是在为分页、导出、任务队列和云端协作打地基。

### 13.2 先让基础数据成功，再异步转录

转录耗时长、依赖模型和媒体下载，失败概率高于元数据采集。如果把两者绑成一个事务，转录失败会让已获取的视频数据也丢失。更好的方式是分阶段提交：采集成功即入库，转录单独排队并可重试。

### 13.3 先真实分页，再开放全部视频

客户端一次加载全部数据在 9 条测试数据时看不出问题，但在数千条视频时会增加传输、内存和渲染压力。服务端分页和准确总数是“全部视频”能力的必要条件。

### 13.4 先低成本 CPU 实测，再决定 GPU

没有真实视频时长、日任务量和模型速度数据，直接购买 GPU 是用费用掩盖不确定性。正确顺序是单条和小批量基准测试，确认队列积压后再启按需 GPU。

### 13.5 把临时文件清理当作业务流程的一部分

“转录完成后删视频”不能只靠一条 `delete` 命令。必须以数据库提交成功为删除门槛，并有重试保留、启动清理和空间监控，否则要么误删导致无法恢复，要么云盘长期堆积。

### 13.6 更好的长期方向

- 保持数据源、下载器和 ASR 都是可替换 Provider。
- 用 PostgreSQL 持久任务表实现租约和重启恢复，初期不额外引入 Redis。
- 将口播稿、SRT、OCR 和爆款分析分成独立阶段，各阶段可重试。
- 给每条任务记录模型版本、配置版本、耗时和错误码，便于评估成本。
- 云端上线前用住宅网络和云 IP 做对照测试；若云 IP 高频触发风控，保留本地采集代理或更换合规数据源。
- 前端把任务状态放在行级状态和详情抽屉，不把转录/OCR 状态挤进账号品牌总览。
