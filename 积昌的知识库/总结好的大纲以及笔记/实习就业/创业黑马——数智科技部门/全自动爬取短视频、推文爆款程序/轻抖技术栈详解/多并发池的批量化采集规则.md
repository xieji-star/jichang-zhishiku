# 🏗️ 多并发池的批量化采集规则：同时采集"不同账号"可以吗？该怎么采？

> [!summary] 概要
> 本文档回答一个关键疑问：**"如果同时采集不同账号的数据可以吗？目前的测试都是在采集相同账号的多个不同视频。"** 结论先行：**当前代码不能，而且是有意设计的"稳定优先"**——现有批采是"账号严格串行、单账号内视频并发 3"，不是多账号并行。技术上"同时采集不同账号"**完全可行**，但要先翻过三座大山（**登录态隔离 / 浏览器 CDP / 数据库并发写**）外加**风控放大**。正确姿势不是"复制 N 路并联"，而是按 [[多worker并发池设计思路]] 的"稳定优先"铁律，把账号级也做成**受控并发池**：账号并发 2~3 路 + 全局限速 + 每账号独立隔离 + 失败隔离。本文给出：当前三重串行锁的代码级证据 → 为什么现在是"单账号多视频" → 多账号并发必须解决的四个问题 → 推荐升级路径（账号级受控并发池）→ 给 Codex 的实施清单与验收标准。

## 1. 结论先行：现在能不能"同时采集不同账号"？

> 🔥 **<span style="color:#e74c3c">一句话答案：当前代码不能，而且这是"稳定优先"的有意设计；技术上"同时采集不同账号"完全可行，但要先解决登录态隔离、浏览器 CDP、数据库并发写三座大山，外加应对风控放大。</span>**

- 📌 **<span style="color:#e67e22">现状：项目现在采集的是"同一账号的多个不同视频"（creator 模式扫一个创作者主页），12 个矩阵账号之间是严格串行的——一个账号采完，才轮到下一个。</span>**
- ✅ **<span style="color:#2980b9">实测佐证：最近批采"4 轮全部 completed、视频 60/60 落库"，正是在"账号串行 + 单账号 3 并发"下跑出来的（见 [[0811-开发日志]] 与 [[0814-还没配置好的内容]]）。</span>**

## 2. 当前实现拆解：三重"串行锁"

> 代码证据全部在 `D:\全自动爬取短视频、推文爆款程序\backend\app\services\collection.py` 与 `backend\app\providers\mediacrawler.py`：

| 层级 | 当前并发度 | 代码证据 |
|:--:|:--:|------|
| **任务级** | **1** | `CollectionService.__init__` 里 `ThreadPoolExecutor(max_workers=1)`；`start()` 里 `if active: raise CollectionBusyError` —— 同一时刻只允许一个采集任务 |
| **账号级** | **1（串行）** | `_run()` 里 `for index, name in enumerate(accounts)` —— 12 个账号挨个处理，一个账号失败会 `continue` 到下一个 |
| **视频级（单账号内）** | **3** | `MediaCrawlerProvider.collect_account()` 起一个 MediaCrawler 子进程，参数 `--max_concurrency_num 3` —— 这只是"该账号内视频请求并发 3" |

### 2.1 关键代码行

```python
# collection.py —— 任务级单实例锁
self.executor = ThreadPoolExecutor(max_workers=1, thread_name_prefix="collector")
...
if active:
    raise CollectionBusyError(f"已有采集任务正在运行：{active['id']}")

# collection.py —— 账号级串行循环
for index, name in enumerate(accounts):
    self._wait_control(task_id, name)
    try:
        self._collect_account(task_id, name, ...)
    except Exception as exc:
        failed_accounts.append(name)   # 单账号失败，继续下一个

# mediacrawler.py —— 单账号子进程 + 账号内并发 3
command = [python, "main.py", "--platform", "dy", "--lt", "qrcode",
           "--type", "creator", "--creator_id", creator_url,
           "--max_concurrency_num", "3", "--headless", "no", ...]
```

> 💡 **<span style="color:#2980b9">注意：`--max_concurrency_num 3` 是"同账号内多条视频请求并发 3"，不是"3 个账号并行"。多账号并行需要的是**多个 MediaCrawler 进程/浏览器实例**同时跑，这是当前代码没有的。</span>**

## 3. 为什么现在的主形态是"单账号多视频"

- 🎯 **<span style="color:#2980b9">MediaCrawler 的 CLI 是"一次一个账号（creator）"的模型：`--type creator --creator_id <sec_user_id>` = 抓取该创作者主页的全部作品，内部并发 3。</span>**
- `backend\config\accounts.json` 里 12 个账号，每个都有 `name / group / douyin_id / creator_url / enabled`；`creator_url` 就是该账号主页的 `sec_user_id`（达人唯一标识）；
- 所以一次采集 = **选定一个账号主页 → 扫它的多个视频 → 逐条转录**。这就是你测试时看到的"相同账号的多个视频"；
- 账号之间为什么串行？因为当前 `content_mode=creator/all` 时 `_collect_account` 每次只处理一个 `creator_url`，而 `_run` 用 for 循环逐个账号调用——**串行是代码结构决定的，不是临时限制**。

> ⚠️ **<span style="color:#e67e22">注意 0811 实证：即使串行，最新批采仍有 5/12 账号失败（人机验证/登录态/接口问题），说明"单账号串行"已经够折腾；直接上多账号并发，失败面会成倍放大。</span>**

## 4. "同时采集不同账号"可行吗？——可行，但有前提

### 4.1 架构上为什么可行

- ✅ **provider 抽象**：后端通过 `MediaCrawlerProvider` 隔离采集源，每个账号独立 `_collect_account`，天然可按账号拆分任务；
- ✅ **账号数据独立**：`accounts.json` 账号是独立的，采集结果按账号落库，互不覆盖；
- ✅ **单账号失败已隔离**：`_run` 里单账号异常会被捕获并 `continue`，不会拖垮整批。

### 4.2 但有四个硬前提（翻不过去就别开）

| # | 前提 | 缺了会怎样 |
|:--:|------|-----------|
| ① | **登录态隔离** | 多账号共用一个登录态 → Cookie 串味、风控一锅端、账号间数据张冠李戴 |
| ② | **浏览器 CDP 隔离** | 当前单一 Edge + 9222 端口，多进程抢同一浏览器 → 互踢、验证码互相干扰 |
| ③ | **数据库并发写安全** | 多进程同时写 `sqlite_tables.db` → `database is locked`，任务崩溃 |
| ④ | **风控缓解** | 多账号同时高频访问抖音 → 人机验证概率成倍上升（关联 [[如何解决人机验证问题]]） |

## 5. 三座大山：多账号并发必须解决的四个问题

### 5.1 登录态隔离（最核心）

- MediaCrawler 的登录态（二维码扫码 / Cookie）是"**一份浏览器配置一份登录态**"；
- 当前单一 Edge 实例 + 单一 `runtime\browser_data\cdp_dy_user_data_dir`；
- 🔥 **<span style="color:#e74c3c">多账号并发必须做到"每账号独立浏览器配置"（独立 user-data-dir + 独立 CDP 端口），否则账号 A 的请求带着账号 B 的 Cookie，数据会串、账号会出问题。</span>**

### 5.2 浏览器 / CDP 隔离

- 当前 `start.ps1` 只启动**一个** Edge（`--remote-debugging-port=9222`）；
- 多账号并行需要**多个浏览器上下文或实例**（多端口如 9222/9223/9224）；
- 📊 **<span style="color:#e67e22">0812 开发日志已明确：当前 MediaCrawler 集成用"单一 Playwright Chromium 配置"，真正的多浏览器并行需隔离浏览器配置、隔离写入队列/数据库、去重和独立调度器——这些还没做（见 [[0814-还没配置好的内容]] 第 2/7 章）。</span>**

### 5.3 数据库并发写

- MediaCrawler 进程写共享 `MediaCrawler\database\sqlite_tables.db`；
- 多进程同时写 → SQLite 锁冲突；
- ✅ 方案：`PRAGMA journal_mode=WAL` + `busy_timeout` + **所有写入走集中串行队列**（见 [[多worker并发池设计思路]] 3.6 与 5.5）。

### 5.4 风控放大（最危险、最容易被忽视）

- 多账号**同时**高频访问，抖音风控（Argus）判定"同一 IP/同一设备大量异常请求"的概率成倍上升；
- 最坏结果：**多个账号同时被要求人机验证**，甚至被临时限制；
- 🛡️ **<span style="color:#e74c3c">应对：账号级受控并发（2~3 路起步）+ 跨账号全局限速（aiolimiter 全局 1 req/s 起步）+ 随机错峰启动，绝对不要"复制 10 路并联"（这正是 [[自研平台批量化处理路线]] 的结论）。</span>**

## 6. 正确姿势：账号级"受控并发池"

> 不是"10 个账号 10 路并联"，而是"**账号也排队叫号、一次放 2~3 个进去**"——与 [[多worker并发池设计思路]] 完全同构，只是把"单条视频"换成"单个账号"。

### 6.1 目标架构

```
用户提交 N 个账号
        ↓
① 账号任务入队（SQLite tasks 表，status: pending）
        ↓
② 调度器（主循环，从 pending 取账号任务）
        ↓
③ 账号级受限并发池  asyncio.Semaphore(2~3)
   每个账号 worker 内部 = 原 _collect_account（单账号 3 并发）
   ├─ 每账号独立浏览器配置（user-data-dir + CDP 端口）
   ├─ 每账号独立登录态（Cookie/扫码）
   ├─ 全局限速 aiolimiter（跨账号共享 1 req/s 起步）
   └─ 结果写集中串行写队列 → 业务库
        ↓
④ 全部完成 → 汇总（各账号成功/失败清单）
```

### 6.2 关键设计点

| 组件 | 做法 | 对应红线（[[多worker并发池设计思路]] 第 6 节） |
|------|------|:--:|
| 账号级并发控制 | `asyncio.Semaphore(2~3)`，**2 起步** | 红线 1 |
| 跨账号全局限速 | `aiolimiter.AsyncLimiter(1, 1)`，全局共享 | 红线 2 |
| 指数退避重试 | `tenacity` 1s→2s→4s，最多 3 次 | 红线 3/4 |
| 账号状态落盘 | tasks 表 pending/doing/done/failed | 红线 5/6 |
| 每账号隔离 | 独立 user-data-dir、独立临时目录 `job-<账号>/` | 红线 9 |
| 数据库串行写 | WAL + 写入集中主循环 | 红线 8 |
| 失败隔离 | `return_exceptions=True`，单账号失败不拖整批 | 红线 11 |
| 保守参数起步 | 账号并发 2、全局限速 1/s，全绿再放宽 | 红线 14 |

> 💡 **<span style="color:#2980b9">为什么账号并发只建议 2~3？因为账号级并发的本质是"把 N 个账号的请求叠加到同一 IP/设备"，叠加越多风控越严。账号并发 2~3 + 账号内 3，等于最高 6~9 路请求，已经是"稳定优先"的天花板附近。</span>**

## 7. 给 Codex 的实施清单与验收标准

> 对齐 [[Codex对话迁移方案]] 与 [[0814-还没配置好的内容]]；模块全部走"独立 venv/独立进程"，不污染主环境。

### 7.1 模块拆分

1. **`accounts/browser_profiles.py`** — 每账号独立 `user-data-dir` + CDP 端口分配（9222/9223/9224…），登录态隔离的地基；
2. **`concurrency/account_pool.py`** — 账号级 `asyncio.Semaphore(2~3)` 受控并发池；
3. **`concurrency/global_limiter.py`** — `aiolimiter` 跨账号全局限速（共享漏桶，天然公平分配）；
4. **`db/wal_queue.py`** — SQLite `journal_mode=WAL` + 集中串行写队列（worker 只算不写库）；
5. **`collection/multi_account_runner.py`** — 调度器：账号任务入队 → 分配 worker → 收结果 → 汇总；
6. **`risk/verification_detector.py`** — 人机验证检测升级（URL 关键字 + DOM 双重确认，见 [[如何解决人机验证问题]] 第 6 章），多账号并发下尤其需要。

### 7.2 分阶段验收（稳定优先，逐级放开）

| 阶段 | 动作 | 验收标准 |
|:--:|------|---------|
| **P0** | 保持现状：单账号串行 + 单账号内 3 并发 | 连续 3 轮零崩溃、无锁冲突（当前已达标） |
| **P1** | 实现账号级并发池框架 + 每账号独立浏览器配置 | 2 个账号并行 × 各 3 并发，跑 3 轮：无人机验证卡死、无 `database is locked`、登录态不串味 |
| **P2** | 接入全局限速 + 指数退避 + 断点续跑 | 同一批账号重跑，已完成的秒跳；偶发 429/超时自动退避成功 |
| **P3** | 风控检测升级（URL+DOM）+ 失败隔离汇总 | 单账号失败不影响其他账号；全局限速生效（日志可证） |
| **P4（可选）** | 账号并发放开到 3~4 | 需先验证 P1~P3 全绿；否则维持 2 |

### 7.3 验收红线（多账号专属）

- ✅ 2 账号并行，各自 Cookie/登录态互不影响（账号 A 的请求绝不带账号 B 的登录态）；
- ✅ 全局请求速率受控：`aiolimiter` 生效，日志无瞬时并发尖峰；
- ✅ 多账号同时段无人机验证误报升级（检测升级后"真验证 vs 误报"区分准确）；
- ✅ SQLite 无 `database is locked`，业务库账号数据无串行污染；
- ✅ 任一账号失败，其余账号照常完成，最终失败清单准确。

## 8. 结论与建议

> 🔥 **<span style="color:#e74c3c">一句话总结："同时采集不同账号"可以，但不是现在直接放开——先把"单账号串行 + 账号内 3 并发"跑稳，再按"账号级受控并发池"逐步放开到 2 路、3 路，每步验收通过再前进。稳定永远优先于速度。</span>**

- 🎯 **<span style="color:#2980b9">给用户的直白建议：保持现状继续跑几轮，收集稳定性数据；如果确实需要"多账号并行提升整体吞吐"，按第 7 章的 P1→P2→P3 顺序升级，先 2 账号并行试水，别一上来 12 个账号全并行。</span>**
- 📌 **<span style="color:#e67e22">最大的隐藏风险不是技术，是风控：多账号并发的本质是把多个账号的请求叠加到同一 IP/设备，叠加越多越容易被抖音判定异常。控制并发 + 全局限速 + 登录态隔离，是"安全多账号采集"的三条命脉。</span>**
