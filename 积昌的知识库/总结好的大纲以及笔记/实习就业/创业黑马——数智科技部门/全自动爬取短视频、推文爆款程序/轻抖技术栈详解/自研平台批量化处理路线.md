# 🔧 自研平台批量化处理路线：从"单条秒出"到"一次 10~20 条"的方案评审与落地

> [!summary] 概要
> **一句话结论：你的"复制 10 个闭环并联"思路方向是对的（多 worker 并发是行业标准做法），但落地方式很危险，大概率会把你现在的"批量 0% 成功"放大成"永远 0% 成功"。** 因为你的闭环现在是"字幕直取"（秒级），属于 **API/网络请求型**任务——这种任务最怕的就是"同一瞬间并发太多"，平台一限流，10 路并联等于 10 倍瞬时请求，直接全被拒。**真正正确的做法是"受控并发（2~3 路）+ 限速 + 指数退避重试 + 缓存 + 任务队列断点续跑"**，把"一次提交 20 条"做成"排队的作业流"，而不是"20 个同时开枪"。本文先评审你的方案，再给出最佳落地方案，最后盘点市面上能批量抓口播稿的工具/平台/开源项目及其技术栈。

## 1. 先复述问题与目标

### 1.1 现状

- ✅ **单条：已经能做到像轻抖一样的秒级出稿**，成功率大幅提升（说明你的闭环已经走通了"字幕直取"或"缓存命中"这条最快路径）
- ❌ **批量：2 条及以上直接失败，成功率 0%**——这不是"变慢"，是"整体失败"
- 💡 **<span style="color:#2980b9">关键信号：从"单条秒级"这个事实可以推断，你的主路径是"字幕直取 / 缓存"（API 请求型），不是"下载 + 本地识别"（算力型）——这个定性决定了下面的所有判断。</span>**

### 1.2 目标

- 一次最多获取 **10 条**视频的口播稿，理想上限 **20 条**
- 用户体验：像"提交一个任务"一样，批量拿到结果，最好还能看进度

### 1.3 你的初步思路

> "将已经闭环的口播采集路线进行复制，并且进行并联的操作，通过并联 10 个这样的模式来进行批量化口播稿件采集"

**本质 = 复制 10 份处理单元，让它们并行跑。** 这就是业界常说的"多 worker 并发池"。方向没错，但"直接复制并联"这四个字里有大坑，下面逐条拆。

## 2. 方案评审：复制 10 个闭环并联，可行吗？

### 2.1 结论先行

🔥 **<span style="color:#e74c3c">结论：方向对（并发池是标准架构），但"无脑复制 10 路并联"是错误落地方式，极可能把现在的"批量 0% 成功"变成"永久 0% 成功"。</span>**

并发（parallelism）本身没有错，错的是**并发度、限速、共享状态、失败恢复**这四件事一个都没设计。

### 2.2 先回答最关键的判断：你的瓶颈是什么性质？

同样的"批量失败"，在不同性质的链路里，解法完全不同。先判断你的闭环属于哪一类：

| 瓶颈类型 | 典型特征 | 并联 10 路的效果 | 正确解法 |
|---------|---------|:---:|---------|
| **A. API/网络限流**（解析接口 / 字幕接口按 IP 或 Token 限速） | 单条秒级；一并发就 429 / 403 / 风控 / 签名失效 | ❌ **适得其反**，10 倍瞬时请求直接全拒 | 限速串行 + 小并发 + 退避重试 |
| **B. 算力不足**（本地 CPU/GPU 做 ASR） | 单条几十秒；CPU 打满 | ✅ 有收益（多核并行） | 提高并发度 + 上 GPU |
| **C. 共享状态竞态**（同一个 Session / Cookie / Token / 临时目录 / SQLite） | 单条正常；两条一起就崩，报错是"会话已过期""数据库被锁""文件已存在" | ❌ 并发越多崩得越狠 | 单会话 + 令牌互斥 + 每任务隔离 |
| **D. 本地代码 Bug**（循环复用变量 / 会话用完即关 / DB 连接非线程安全） | 批量必然失败，错误可复现 | ❌ 复制 10 份还是同一个 Bug | 先写最小复现，修 Bug |

💡 **<span style="color:#2980b9">判断依据：你现在"单条秒级"→ 说明主路径是 A（字幕直取）而不是 B（本地识别）。所以你的批量失败，第一怀疑对象是 A（平台限流），第二是 C（共享状态竞态），第三是 D（本地 Bug）。</span>**

### 2.3 "复制 + 并联"会踩的四个坑

1. ⚠️ **<span style="color:#e74c3c">坑一：平台限流被 10 倍放大</span>**
   - 字幕接口 / 解析接口通常有 QPS（每秒请求数）限制，按 IP 或 Token 计
   - 10 路同时发 = 同一瞬间 10 个请求打到同一个 IP → 平台判定为异常 → **全部拒绝（403/风控/封 Token）**
   - 这正好解释你现在的现象：单条正常，两条一起就全挂——不是算力问题，是"瞬间请求太多"

2. ⚠️ **<span style="color:#e74c3c">坑二：共享 Cookie / Token 的竞态</span>**
   - 如果 10 个 worker 共用一个登录 Cookie 或一个签名 Token，并发时 Token 刷新会发生竞态：两个线程同时刷新 → 前一个刷新把后一个的 Token 顶掉 → 全部 401
   - 复制"代码"容易，但复制出来的 10 份如果还共享同一个会话，等于 10 个人抢一把钥匙

3. ⚠️ **<span style="color:#e74c3c">坑三：临时目录 / 数据库写冲突</span>**
   - 如果每个 worker 写同一个临时目录、同一个 SRT 文件名、同一个 SQLite → 文件覆盖、`database is locked`
   - SQLite 尤其怕并发写，10 路并发写同一张表基本必锁

4. ⚠️ **<span style="color:#e74c3c">坑四：没有限速 / 退避 / 断点，一次失败全盘失败</span>**
   - 并联后如果其中一路触发限流，其余路往往跟着被连坐；没有"退避后重试"和"失败隔离"，一个失败就拖垮整批

### 2.4 那什么情况下并联才是对的？

📊 **<span style="color:#e67e22">并联只对"算力型"任务（本地 ASR）有明确收益；对"API 请求型"任务（字幕直取）反而是负收益。</span>**

- 你现在的主路径是字幕直取（API 型）→ **并联不是你的杠杆，限速排队才是**
- 只有当某条视频无字幕、必须走本地 ASR 兜底时，那一小步才值得并行——但那是另一个层面的优化（多核识别），和"抓字幕的并联"完全是两回事

> 🔥 **<span style="color:#e74c3c">一句话：轻抖的"批量"也不是真并行，而是"逐个请求 + 命中缓存"。你真正要复刻的是它这种"排队 + 缓存"的作业流，而不是"10 路齐发"。</span>**

## 3. 根因定位：先别急着改，先看三组日志

> 任何优化前，先花 30 分钟确认"批量到底死在哪个环节"。不要凭感觉改架构。

### 3.1 要看的三个信号

| 信号 | 说明 | 指向 |
|------|------|------|
| **HTTP 状态码** | 429（限流）/ 403（风控）/ 401（Token 失效）/ 404（签名过期） | 平台限流或凭证问题 |
| **失败阶段** | 是"解析链接"失败，还是"取字幕"失败，还是"写库"失败？ | 精确定位环节 |
| **失败时间点** | 是否恰好发生在第 2 条、第 3 条同时发出的瞬间？ | 并发触发限流 |

### 3.2 三组最小实验

1. **2 条串行**（中间加 1 秒间隔）→ 如果成功：说明是"并发"触发限流 → 走方案 A（限速）
2. **2 条并发**（同时发）→ 如果失败且报 429/403：确认是平台限流 → 千万不要再加大并发
3. **10 条串行**（每条间隔 0.5~1s）→ 测出"单位时间内最多能安全发几条"→ 据此定并发度

> 💡 **<span style="color:#2980b9">用这三组实验，你能把"批量 0% 成功"拆成三种不同原因，再对症下药。绝大多数情况下，你会走到"限速 + 排队 + 缓存"这条路，而不是"并联"。</span>**

## 4. 最佳方案：受控并发 + 限速队列 + 缓存 + 断点续跑

### 4.1 推荐架构

```
用户一次提交 10~20 条链接
        ↓
任务队列（SQLite / Redis，落盘可断点续跑）
        ↓ 逐条取出（受控并发 2~3，不是 10）
先查缓存（video_id 是否已转写过？）
   ├─ 命中 → 直接返回（秒级）
   └─ 未命中 →
        解析链接（失败 → 指数退避重试 1~3 次）
        → 字幕直取（限速间隔 0.3~1s，失败退避）
        → 无字幕才走 ASR 兜底（本地 GPU/CPU 或云端）
        → 结果写缓存 + 落库
        ↓
全部处理完 → 汇总返回（成功/失败/跳过清单 + 进度）
```

### 4.2 五个落地要点

1. **受控并发而非全开**：用 `asyncio.Semaphore(2~3)` 或 `ThreadPoolExecutor(max_workers=2~3)` 把并发钉死在 2~3 路。并发度先按你第 3 节实验测出的安全值来定，宁可小不可大
2. **限速 + 指数退避重试**：每条请求之间加 0.3~1s 间隔；遇到 429/403/超时，按 `1s → 2s → 4s` 指数退避重试，最多 3 次；重试仍失败就标记该条失败，**绝不拖垮整批**
3. **单会话 + 令牌互斥刷新**：全局只用一个 Session；Token/Cookie 刷新用 `asyncio.Lock()`（互斥锁，保证同一时刻只有一个线程刷新）保护，防止并发把 Token 顶掉
4. **每任务彻底隔离**：每条视频用唯一任务 ID，建独立临时目录（`job-<id>/`），SRT/TXT 用 `video_id` 命名，避免文件覆盖；SQLite 用队列串行写，或加 `WAL` 模式（允许并发读）减少写锁
5. **队列 + 断点续跑 + 缓存**：任务状态落盘（pending/doing/done/failed），程序中断后从 pending 接着跑；结果用 `video_id` 做键写缓存，第二次命中秒回

> 🔥 **<span style="color:#e74c3c">核心转变：把"批量"从"10 个同时开枪"改成"一个排队作业流"。对用户来说体验一模一样（提交 N 条 → 拿到 N 条结果），但对平台的请求却是温和、可控、可重试的——这才是轻抖们真正在后台做的事。</span>**

### 4.3 预期耗时（10~20 条）

| 场景 | 单条约耗 | 10 条总耗时 | 20 条总耗时 |
|------|:---:|:---:|:---:|
| 全部命中缓存 | ~0.3s | ~3s | ~6s |
| 混合（部分需抓字幕，间隔 0.5s） | ~1.5~2s | ~20s | ~40s |
| 全部无字幕走本地 CPU ASR 兜底 | ~30~90s | 5~15 分钟 | 10~30 分钟 |

> 📊 **<span style="color:#e67e22">前两种场景（字幕直取 + 缓存）就是你的主力，20 条也能压进 1 分钟内。只有"全无字幕 + 本地 CPU 识别"才是真正的耗时黑洞——那不是批量架构的问题，是算力问题（建议上 GPU 或云端 ASR，见 [[口播稿转录]] 第五节）。</span>**

### 4.4 补充：如果并发后确认是"按 Token 限速"

- 平台若按单 Token 限 QPS，可以**准备多个 Cookie/Token 做轮询**（Round-robin 轮流用），把总 QPS 翻几倍
- ⚠️ **<span style="color:#e74c3c">但多账号轮询属于灰色地带，容易触发平台风控封号，务必用低权重小号、控制频率（合规边界见 [[MediaCrawler深度分析与结合改进方案]] 第七章）</span>**

## 6. 这些产品的内部技术栈拆解

> 把上面所有工具/平台/开源项目去重后，技术栈高度趋同，就是下面五层。你完全可以按这套拼出自己的批量版。

### 6.1 五层技术栈

| 层 | 主流选型 | 说明 |
|----|---------|------|
| **① 解析层**（链接 → 直链/音频） | yt-dlp / F2 签名 / 移动端 UA + 页面 SSR JSON / Playwright 渲染 / 第三方 API（TikHub、RedFox） | 抖音短链解析、无水印直链还原 |
| **② 字幕直取层**（最快路径） | 平台字幕接口（抖音 AI 字幕 / B 站 CC 字幕） | 有字幕直接抄，零算力，秒级 |
| **③ ASR 层**（无字幕兜底） | faster-whisper / Whisper / SenseVoice / sherpa-onnx / FunASR / 火山引擎 / 阿里云 ASR | 中文口播首选 SenseVoice/FunASR（见 [[口播稿转录]] 第五节） |
| **④ 并发/任务层** | asyncio + aiohttp / ThreadPoolExecutor / Celery + Redis / RQ Worker / FastAPI | 受控并发 + 任务队列 + 断点续跑（就是本文第 4 节的核心） |
| **⑤ 存储/缓存层** | SQLite（WAL 模式）/ Redis 缓存 | `video_id` 键缓存，命中秒回 |

### 6.2 批量产品真正"批量"的秘密

📌 **<span style="color:#e67e22">所有成熟批量产品都不是"同时抓 N 条"，而是"排队抓 N 条 + 缓存兜底 + 失败隔离"：**

- 并发度通常很小（2~5），因为平台限流是硬约束
- 大量请求命中缓存（别人已抓过），所以"看起来瞬间完成"
- 每条独立重试、独立失败，进度可实时上报
- 这正是你应该抄的作业，而不是"10 路并联"

## 8. 总结与落地路线

> 🔥 **<span style="color:#e74c3c">一句话总结：你的"并联"思路方向对，但应该实现成"受控并发 + 限速队列 + 缓存 + 断点续跑"的作业流，而不是"复制 10 路齐发"。批量失败 0% 的根因大概率是平台限流 / 共享状态竞态，先做三组实验定位，再按第 4 节架构落地。</span>**

### 8.1 落地路线（按顺序）

1. **定位根因（半天）**：按第 3 节做三组小实验，确认是限流、竞态还是本地 Bug
2. **改造成作业流（1~2 天）**：任务队列 + 受控并发 2~3 + 限速间隔 + 指数退避重试 + 每任务隔离
3. **加缓存（半天）**：`video_id` 做键，结果落库，二次命中秒回
4. **本地 ASR 兜底并发优化（按需）**：无字幕视频走 GPU（你们有 RTX 5060）或云端 ASR，别用 CPU int8 硬扛
5. **开源参考（0 成本）**：参考 [[mediacrawler_to_pyvideotrans.py]] 的幂等/断点设计，以及 pyvideotrans CLI 的批量参数；需要"批量体验 + 字幕优先"时看 chubbyskills / video-batch-download / douyin-creator-toolkit 的实现

> 📌 **<span style="color:#e67e22">给老板/同事的直白版：别让 20 个人同时去柜台办业务（并联），那样只会把柜台挤爆（限流）。正确做法是排号叫号（任务队列），一次放 2~3 个进去（受控并发），办过的人留档（缓存），下次来直接拿结果。</span>**
