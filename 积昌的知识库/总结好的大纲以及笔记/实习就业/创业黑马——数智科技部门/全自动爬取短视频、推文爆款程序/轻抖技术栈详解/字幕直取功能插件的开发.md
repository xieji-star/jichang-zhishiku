## 1. 背景与目标

### 1.1 为什么需要字幕直取

- 现状：口播稿 100% 由 **ASR（语音识别）** 生成（route2 下载+GPU ASR 为主力），单条耗时 **15~44 秒**（中位 15s、P90 63s），且占用 GPU。
- 抖音视频普遍带**平台 AI 自动字幕**（真人出镜口播类尤其），这些字幕文本藏在 detail 接口响应的 `video.subtitles` 字段里——**"抄"回来去时间轴就是口播稿**，预期 <2 秒/条。
- 文档 [[3条线路设计]] 的线路1"字幕直取"就是此意；但此前实测发现：现有 platform_subtitle（yt-dlp 拉标准字幕轨道）**28 次尝试 0 成功**（抖音无标准字幕轨道），route1 douyin-mcp **无字幕提取能力**，GitHub 上也不存在高 star 的现成"字幕直取"项目（最高 star 的 douyin-mcp-server 1.2k 已集成且无此能力）——因此走 **C1 自研**（扩展 MediaCrawler fork 采集 subtitles 字段）。

### 1.2 价值边界（诚实定位）

- 🎯 字幕直取是**提速优化项**，不是管线刚需：ASR 兜底已实测 10 轮 100% 正确率，直取的价值是"省时省 GPU"而非"提升正确率"。
- 🛑 **止损线前置**：Phase 0 实测若 subtitles 存在率 <20%，则不投产（执行 Plan B 字段监测器），零损失退出。

## 3. 三方案对比与代码总监审校过程

### 3.1 三方案摘要

| 方案 | 设计 | 核心特点 |
|------|------|---------|
| **A（fork 内扩展）** | fork core.py 解析 detail 响应中已有的 `video.subtitles` → douyin_aweme 加列 → backend 新增 DouyinSubtitleProvider 插第 0 顺位 | **零新增请求面**、速度满分、低侵入（fork 3 文件 + backend 2 处） |
| **B（backend 独立模块）** | backend 复制 fork 签名（help.py+douyin.js 到 vendor/）+ 对每视频**额外调 detail 接口** | 独立可控，但**请求面翻倍** + 签名链路断裂风险 |
| **C（渐进式混合）** | Phase 0 实测止损 → Phase 1 最小接线（三重质量闸门+灰度）→ Phase 2 固化 | **验证先行、兜底恒在**、止损线前置 |

### 3.2 代码总监第一轮审校：硬伤清单

1. 🔴 **B 签名链路断裂**：fork `help.py:37` 是 `execjs.compile(open('libs/douyin.js'))` 相对路径（依赖 cwd）——复制到 backend/vendor/ 后必然 FileNotFoundError。
2. 🔴 **B 风控火上浇油**：当前正被 Argus 拦截；B 对每视频额外调 detail（请求面翻倍）且独立调用指纹缺 search_id/referer 上下文。
3. 🟡 **A/B 共同硬伤**：subtitles 存在率未经实测（预估 30~70%），A 无止损线 → 嫁接 C 的 Phase 0。
4. 🟡 **C 无独立架构**：C 是纯策略，必须嫁接 A（零请求面）。

**结论**：A、C 可行，B 有致命硬伤（仅保留为"覆盖率不足时的低频补采"备胎，风控解除前禁上线）。

### 3.3 代码总监第二轮终审：ON-TRACK（通过）

- 上轮两个致命硬伤已闭合（请求面零新增 / B 降备胎并留档）
- 剩余 2 条前置条件（见 [[#8. 前置条件与开放问题（终审遗留）]]）
- **最终判定：通过，批准进入 Phase 0 实施**

## 4. 最终方案：A+C 整合版

### 4.1 Phase 0：实测验证（前置止损，零线上改动，1~2 天）

- **采样**：300 条（≥10 位达人 × 3 档时长 × 近 90 天发布，排除图文 aweme_type=163）；其中 50 条并行跑 ASR（route2 GPU ASR 为统一基准）作对比组。
- **探针实现（终审修正版）**：⚠️ <span style="color:#e67e22">raw detail 响应从不入库（store 只落盘解析后字段子集）——探针**不能**"事后读 douyin_aweme 拿 detail"。</span>二选一：
  - (a) 独立有界采样器：复用 fork `client.py` 的签名机制自行拉 300 条 detail（≤15 次/分钟、实验室隔离、结束后删除探针脚本）；
  - (b) 在 fork `core.py` 的 `get_aweme_detail` 挂临时日志钩子跑一轮采集。
- **判定标准**：subtitles **存在率 ≥20%** 且（剔除含 BGM 标签样本后）字幕 vs ASR 文本**相似度 ≥0.85** → 进 Phase 1；否则 **Plan B**：不投产，保留"字段监测器"（每周抽样 50 条探测字段是否回归），ASR 维持。
- **交付物**：覆盖率报告 + 字幕格式样例 + 质量结论。

### 4.2 Phase 1：最小接线（达标后做，3~4 天）

**fork 改动（3 文件）**：
1. `core.py`：`get_aweme_detail` 成功分支解析 `aweme_detail["video"]["subtitles"]`（结构 `[{language, subtitle_id, format:"webvtt", url}]`）
2. 新增 `media_platform/douyin/subtitles.py`：有 url 则**限 1 次 GET 拉 vtt**（CDN 域、1~2 次/s/账号、失败即弃不重试、限 10MB）→ 去 WEBVTT 头/时间轴/尖括号标签 → 拼全文
3. `store/douyin/_store_impl.py`：写入 `douyin_aweme` 新列 `subtitle_text` + `subtitle_meta`（json：id/url/格式/提取时间）；迁移用现有 `PRAGMA table_info` + `ALTER TABLE` 幂等模式（多账号独立库随各实例启动自动迁移）

**backend 改动（2 处）**：
1. 新增 `DouyinSubtitleProvider`（读业务库 subtitle_text → 清洗校验 → `RoutedTranscript`，source=`douyin_subtitle`），实现 `TranscriptProvider` 协议，插为转录管线**第 0 顺位**；命中走 `SQLiteTranscriptCache`（7 天 TTL）
2. `videos` 表导入字幕列（照 media_kind 幂等迁移模式）

**配置开关**：`SUBTITLE_DIRECT_ENABLED`（**默认 false**）——一键回滚即回退现有 4 级链路。

**灰度**：按视频 ID 哈希 20% → 50% → 100%，每级 3 天。

### 4.3 Phase 2：优化固化（持续）

- 覆盖率/质量周报；熔断器（连续 20 败 → 冷却 30 分钟 → 半开 10% 试探）
- 签名维护 SOP（fork 上游升级后同步 + Phase 0 小样本回归）
- 失败账号自动剔除 1 小时（疑似风控命中）

## 5. 三重质量闸门（防 BGM 假成功）

> 🔴 **<span style="color:#e74c3c">历史教训驱动（第 5 轮迭代发现）：</span>** pyvideotrans 曾把图文笔记的背景音乐歌词当"口播稿"入库（两条不同视频产出相同歌词）——字幕直取若不设闸门，会把字幕里的 BGM 歌词/特效标签混入口播稿，毁掉下游爆款分析。

| 闸门 | 规则 | 不过的后果 |
|:--:|------|------|
| ① 非空且长度达标 | ≥20 字（终审建议：10~15 字 + 中文占比检查，避免误杀短口播，以 Phase 0 实测定稿） | 降级 ASR |
| ② 无音乐标签 | 不含 BGM / 原声 / ♪ 等音乐标识 | 降级 ASR |
| ③ 标题关键词交叉验证 | **终审定死规则**：字幕语言=zh 且去停用词后标题实词与字幕文本交集 ≥1 且 cue 数 ≥3 | 降级 ASR |

> 📌 **<span style="color:#e67e22">闸门③是无规格的重灾区：</span>** 过严 → 过闸率永远 <70%，灰度永不晋级，功能名存实亡；过松 → 假成功复发。实现时必须把上述规则连同闸门①的阈值**一并写进测试用例**。

## 6. 并发与预算设计

| 维度 | 设计 | 依据 |
|------|------|------|
| **接口请求面** | **零新增**：字幕寄生在已获取的 detail 响应里 | 代码总监实码验证 client.py:220-221 |
| vtt 下载 | CDN 域非接口域，1~2 次/s/账号，失败即弃不重试，限 10MB | 不进入风控画像的主因是"不增加接口域请求" |
| REQUEST_BUDGET | detail 36 / total 60 **不变**（采集主链路绝不挤占） | 字幕直取是优化项 |
| 多账号并发池 | 字幕列迁移随各账号独立采集库幂等执行；backend 导入单消费者；provider 只读 + 缓存线程安全 | 已落地架构 |
| 失败账号 | 疑似风控命中 → 自动剔除 1 小时 | 防连累 |

## 7. 验收标准与灰度策略

| 阶段 | 进入条件 | 退出/晋级条件 |
|:--:|---------|-------------|
| Phase 0 | 无（实验室探针） | 存在率 ≥20% 且相似度 ≥0.85 |
| Phase 1 灰度 20% | Phase 0 达标 | 过闸成功率 ≥70%、ASR 触发量下降 ≥25%、采集主链路 detail 错误率零上升 |
| 灰度 50% → 100% | 上一级达标 | 同上，每级 3 天 |
| Phase 2 | 100% 稳定 | 连续 4 周稳定 |

**A/B 验收**：50 条对比组——正确率（人工抽检 + 文本相似度）与耗时（预期 <2s vs 15~44s）。

**回归清单**：采集主链路、图文 163 跳过、4 级管线逐级触发、多账号池、预算不超、argus 拦截率不升、字幕列随增量导入进业务库。
