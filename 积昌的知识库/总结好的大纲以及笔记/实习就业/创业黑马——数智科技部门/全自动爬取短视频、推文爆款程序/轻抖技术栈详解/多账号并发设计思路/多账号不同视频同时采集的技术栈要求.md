## 1. 改造目标与总体架构

> 🔥 **<span style="color:#e74c3c">一句话目标：把账号级从"一个账号采完才轮到下一个"改成"账号也排队叫号、一次放 2~3 个进去同时采各自的多个视频"——其余两层锁保持不变。</span>**

### 1.1 改造前后对比

| 层级 | 改造前（现状） | 改造后（目标） |
|:--:|------|------|
| **任务级** | `ThreadPoolExecutor(max_workers=1)` + `CollectionBusyError`，同一时刻只允许一个采集任务 | **保持不变**（仍是单任务，任务内部才并发账号） |
| **账号级** | `for index, name in enumerate(accounts)` 严格串行 | **账号级受控并发池**：`Semaphore / ThreadPoolExecutor(2~3)`，一次放 2~3 个账号 |
| **单账号内视频级** | `--max_concurrency_num 3`（一个 MediaCrawler 子进程内并发 3） | **保持不变**（每账号仍是一个子进程、内部并发 3） |
| **浏览器/登录态** | 单一 Edge + 9222 + 单一 `cdp_dy_user_data_dir` | **每账号独立** user-data-dir + 独立 CDP 端口 |
| **采集库** | 多进程共用 `MediaCrawler\database\sqlite_tables.db` | **每账号独立采集库**（或按账号隔离读取） |
| **业务库写入** | 各账号各自 `save_video_snapshot` | **集中串行写队列**，worker 只算不写库 |
| **限速** | 无跨账号全局限速 | **全局 RateLimiter** 跨账号共享（1 req/s 起步） |

### 1.2 为什么任务级锁不能动

- 📌 **<span style="color:#e67e22">`start()` 里的 `get_active_task()` + `CollectionBusyError` 是"单任务互斥"，防止两个任务同时写同一个 `collection_tasks` 任务表和同一批账号数据。</span>**
- 多账号并发是"**一个任务内部**的并发"，不是"两个任务同时跑"——所以任务级锁**必须保留**，否则两个任务都调度同一批账号会重复采集、重复落库、进度互相覆盖。

### 1.3 目标架构图

```
用户提交 N 个账号（仍是 1 个采集任务，任务级锁保留）
        ↓
① 任务入队 collection_tasks（status: pending）——不变
        ↓
② 多账号调度器 runner.run_accounts(task_id, accounts, payload)
        ↓
③ 账号级受控并发池  ThreadPoolExecutor(max_workers=2~3)
   每个账号 worker = 原 _collect_account + 账号隔离：
   ├─ allocate_profile(name) → 独立 user-data-dir + CDP 端口 + 独立采集库
   ├─ 启动独立 MediaCrawler 子进程（内部仍 --max_concurrency_num 3）
   ├─ 全局 RateLimiter.acquire() 跨账号限速
   ├─ 转录走全局转录池（上限 4，防账号×视频超限）
   └─ 结果提交集中串行写队列 → 业务库
        ↓
④ 全部完成 → 汇总（各账号成功/失败清单 + 进度）——沿用现有 result_json 计数
```

> 💡 **<span style="color:#2980b9">本质：把 [[多并发池的批量化采集规则]] 第 6 章画的"账号级 Semaphore"架构落地成具体代码。复杂度全部收敛在"账号级这一层"，任务级与视频级两层一行不用动。</span>**

### 4.1 browser_profiles.py —— 登录态隔离的地基（最核心）

**职责：** 为每个账号分配独立的浏览器数据目录、CDP 端口、独立采集库路径，并登记/回收，防止两个账号用同一份登录态或同一个端口。

```python
"""每账号独立浏览器 profile + CDP 端口 + 独立采集库（登录态隔离的地基）。"""
import re
import threading
from dataclasses import dataclass
from pathlib import Path

from ..config import (
    MEDIACRAWLER_BROWSER_DATA_DIR,
    MEDIACRAWLER_BROWSER_BASE_PORT,
    MEDIACRAWLER_ROOT,
)

@dataclass(frozen=True)
class BrowserProfile:
    account_name: str
    user_data_dir: Path     # runtime\browser_data\cdp_<key>_user_data_dir
    cdp_port: int           # 9222 / 9223 / 9224 ...
    mc_db_path: Path        # MediaCrawler\database\<key>_sqlite_tables.db

_profiles_root = Path(MEDIACRAWLER_BROWSER_DATA_DIR)
_port_lock = threading.Lock()
_used_ports: set[int] = set()

def allocate_profile(account_name: str) -> BrowserProfile:
    key = re.sub(r"[^\w一-鿿]", "_", account_name)   # 中文账号名安全转文件名
    with _port_lock:
        port = int(MEDIACRAWLER_BROWSER_BASE_PORT)           # 从 9222 起找空闲端口
        while port in _used_ports:
            port += 1
        _used_ports.add(port)
    return BrowserProfile(
        account_name=account_name,
        user_data_dir=_profiles_root / f"cdp_{key}_user_data_dir",
        cdp_port=port,
        mc_db_path=Path(MEDIACRAWLER_ROOT) / "database" / f"{key}_sqlite_tables.db",
    )

def release_profile(profile: BrowserProfile) -> None:
    with _port_lock:
        _used_ports.discard(profile.cdp_port)
```

> 🔥 **<span style="color:#e74c3c">这条是"登录态不串味"的唯一保证：账号 A 的请求绝不带账号 B 的 Cookie。没有它，多账号并发=数据张冠李戴+风控一锅端。</span>**

### 4.2 account_pool.py —— 账号级受控并发池

**职责：** 用线程池把账号并发度钉死在 2~3 路（先 2 起步），每个账号一个 worker。

```python
"""账号级受控并发池：ThreadPoolExecutor(2~3) + 全局限速。"""
from concurrent.futures import ThreadPoolExecutor, as_completed
from ..config import MEDIACRAWLER_CONCURRENT_ACCOUNTS
from .global_limiter import global_limiter

class AccountPool:
    def __init__(self, max_accounts: int | None = None):
        self.max_accounts = max_accounts or int(MEDIACRAWLER_CONCURRENT_ACCOUNTS)
        self.executor = ThreadPoolExecutor(
            max_workers=self.max_accounts, thread_name_prefix="account"
        )

    def run(self, jobs: list[callable]) -> list:
        """jobs: list of callable，每个代表一个账号任务。
        单账号失败必须在内部捕获并记录，不向这里冒泡（失败隔离）。"""
        futures = [self.executor.submit(job) for job in jobs]
        return [f.result() for f in as_completed(futures)]   # 每个 result 是 {name: status}
```

> ⚠️ **<span style="color:#e74c3c">账号并发 2~3 + 账号内视频并发 3 = 最高 6~9 路请求，已经是"稳定优先"天花板附近。绝不要"12 个账号 12 路并联"（[[自研平台批量化处理路线]] 的结论）。</span>**

### 4.3 global_limiter.py —— 跨账号全局限速

**职责：** 一个全局共享的同步漏桶，所有账号的"发起平台请求前"都调 `acquire()`，保证跨账号总请求速率受控（默认 1 req/s 起步）。

```python
"""跨账号全局限速：同步漏桶，线程安全，约 30 行。
（若走异步化路线，可换成 aiolimiter.AsyncLimiter）"""
import threading
import time
from ..config import MEDIACRAWLER_GLOBAL_RATE_PER_SECOND

class RateLimiter:
    def __init__(self, rate_per_second: float = 1.0):
        self.min_interval = 1.0 / max(0.1, rate_per_second)
        self._lock = threading.Lock()
        self._last = 0.0

    def acquire(self) -> None:
        with self._lock:
            now = time.monotonic()
            wait = self._last + self.min_interval - now
            if wait > 0:
                time.sleep(wait)
                now = time.monotonic()
            self._last = now

global_limiter = RateLimiter(float(MEDIACRAWLER_GLOBAL_RATE_PER_SECOND))
```

> 💡 **<span style="color:#2980b9">漏桶是全局的，天然"公平分配"——2 个账号并发时，谁先到谁先用，不会出现一个账号连发把额度吃光。这就是"全局限速"和"每账号各自限速"的本质区别。</span>**

### 4.4 wal_queue.py —— SQLite 集中串行写队列

**职责：** 所有写业务库的操作（`save_video_snapshot` / `save_video_comments` / 任务计数）提交到单线程消费队列，worker 只算不写库——彻底避免 `database is locked`。

```python
"""SQLite WAL + 集中串行写队列：worker 只算，写库单线程。"""
import queue
import threading
from ..db import connect

_write_queue: queue.Queue = queue.Queue()
_thread = None

def submit_write(fn, *args, **kwargs) -> None:
    """fn 签名统一为 fn(con, *args, **kwargs)，con 由写线程提供。"""
    _write_queue.put((fn, args, kwargs))
    _ensure_worker()

def _ensure_worker() -> None:
    global _thread
    if _thread is None or not _thread.is_alive():
        _thread = threading.Thread(target=_write_worker, daemon=True, name="db-write")
        _thread.start()

def _write_worker() -> None:
    while True:
        fn, args, kwargs = _write_queue.get()
        try:
            with connect() as con:
                fn(con, *args, **kwargs)
        except Exception:
            pass                                   # 单条写失败不影响队列
        finally:
            _write_queue.task_done()

def drain() -> None:
    _write_queue.join()
```

> 🔥 **<span style="color:#e74c3c">这是业务库 `data\radar.sqlite3` 在多账号并发下"不锁死"的命门。现有 `save_video_snapshot` 是独立事务，2 个账号同时写就有排队风险——包进串行队列后写锁零竞争。</span>**

### 4.5 runner.py —— 多账号调度器（替代 `_run` 里的 for 循环）

**职责：** 账号任务入队 → 分配 profile → 提交账号池 → 收结果 → 汇总到 `result_json`。

```python
"""多账号调度器：替代 collection.py _run 里的 for 串行循环。"""
from ..db import add_log, increment_task_result
from .browser_profiles import allocate_profile, release_profile
from .account_pool import AccountPool
from .wal_queue import drain

def run_accounts(task_id: str, accounts: list[str], payload: dict,
                 collect_one: callable) -> dict:
    """collect_one(task_id, name, profile, payload) -> None（单账号失败内部捕获）。
    返回 {"succeeded": [...], "failed": [...]}。"""
    pool = AccountPool()
    results = {"succeeded": [], "failed": []}

    def one(name: str):
        profile = allocate_profile(name)
        try:
            add_log(task_id, f"账号 {name} 分配 profile：端口 {profile.cdp_port}，目录 {profile.user_data_dir}")
            collect_one(task_id, name, profile, payload)
            results["succeeded"].append(name)
            increment_task_result(task_id, accounts_succeeded=1)
        except Exception as exc:
            results["failed"].append(name)
            increment_task_result(task_id, accounts_failed=1)
            add_log(task_id, f"{name} 采集失败，已继续其他账号：{exc}", "error")
        finally:
            release_profile(profile)

    pool.run([lambda n=name: one(n) for name in accounts])
    drain()                                  # 等所有串行写落库
    return results
```

> 📌 **<span style="color:#e67e22">`collect_one` 就是改造后的 `_collect_account`（加了 profile 参数）。这样 `_run` 主流程的进度/暂停/取消/汇总逻辑一行都不用改，只把 for 循环换成 `run_accounts(...)`。</span>**

## 7. 多账号专属风控对抗技术栈

> 🔥 **<span style="color:#e74c3c">多账号并发的本质：把 N 个账号的请求叠加到同一 IP/设备，叠加越多越容易被抖音 Argus 判定异常。以下五条是"安全多账号采集"的命脉。</span>**

| # | 对抗层 | 要求 | 落地 | 关联文档 |
|:-:|-------|------|------|---------|
| ① | **登录态隔离**（最核心） | 每账号独立 user-data-dir + 独立 CDP 端口 | `browser_profiles.py`；独立扫码登录，互不串 Cookie | [[多并发池的批量化采集规则]] 5.1 |
| ② | **跨账号全局限速** | 全局 1 req/s 起步，跨账号共享漏桶 | `global_limiter.py`；测过安全 QPS 再放宽 | [[多worker并发池设计思路]] 红线 2 |
| ③ | **随机错峰启动** | 账号与账号之间随机延迟 20~60s，避免机械节奏 | runner 内 `one()` 开头 `time.sleep(random.uniform(20, 60))`（仅首个账号除外） | [[如何解决人机验证问题]] 第 7 章 |
| ④ | **代理/指纹（可选）** | 干净 IP 代理池 + 浏览器指纹伪装 | proxy_pool + CloakBrowser/patchright（独立环境）；数据中心 IP 反而触发更高风控 | [[3条线路设计]] 6 章 |
| ⑤ | **验证码检测升级** | URL + DOM 双重确认，真验证 vs 误报分离 | `verification_detector.py`；真验证才置 `awaiting_verification`，误报不阻断账号 | [[如何解决人机验证问题]] 第 6 章 |

> ⚠️ **<span style="color:#e74c3c">合规红线：降低触发概率 + 人工完成真验证可以，任何"自动破解验证码 / 硬扛风控"都禁止。多账号并发把风控面放大了，更要把频率与隔离做到位，而不是去对抗平台。</span>**

## 9. 分阶段实施清单（P0→P4）

> 🔥 **<span style="color:#e74c3c">铁律：每一阶段跑稳、验收过了，才进下一阶段。永远不要"一次性写满并发"（[[多worker并发池设计思路]] 5 节）。</span>**

| 阶段 | 做什么 | 怎么做 | 验收标准 |
|:--:|------|--------|---------|
| **P0** | 保持现状 + 补稳定依赖 | 主 venv 补装 tenacity（+自研 RateLimiter 或 aiolimiter）；跑现有串行批采 | 连续 3 轮零崩溃、无锁冲突（当前已达标，勿破坏） |
| **P1** | 账号级并发框架 + 每账号独立浏览器配置 | 建 `multi_account` 包：browser_profiles / account_pool / global_limiter / wal_queue；`_collect_account` 加 profile 参数；start.ps1 改方案 A | **2 账号并行 × 各 3 并发**跑 3 轮：无人机验证卡死、无 `database is locked`、登录态不串味（账号 A 请求绝不带账号 B Cookie） |
| **P2** | 全局限速 + 指数退避 + 断点续跑 | 全局 RateLimiter 接入每个账号请求前；tenacity `@retry(1s→2s→4s, 3次)` 包瞬态错误；`account_tasks` 表登记状态支持断点 | 同一批账号重跑，已完成账号秒跳；偶发 429/超时自动退避成功；`account_tasks` 状态可恢复 |

### 9.1 每次放量前的安全自检（三组实验，来自 [[自研平台批量化处理路线]] 3 节）

3. **逐级放量**：2 → 3 → 4，每级稳定跑 2~3 轮再放宽，出现异常立即回退一级。

- ✅ 2 账号并行，各自 Cookie/登录态互不影响（账号 A 的请求绝不带账号 B 的登录态）；
- ✅ 全局请求速率受控：日志无瞬时并发尖峰，`RateLimiter` 生效；
- ✅ 多账号同时段无人机验证误报升级（检测升级后"真验证 vs 误报"区分准确）；
- ✅ 业务库 `data\radar.sqlite3` 无 `database is locked`，账号数据无串行污染；
- ✅ 任一账号失败，其余账号照常完成，最终失败清单准确（`result_json.accounts_failed`）；
- ✅ 采集库层面无多进程写锁死（每账号独立 `sqlite_tables.db` 或已隔离）；
- ✅ 任务级互斥仍生效：并发进行中发起第二个任务 → `CollectionBusyError`。
