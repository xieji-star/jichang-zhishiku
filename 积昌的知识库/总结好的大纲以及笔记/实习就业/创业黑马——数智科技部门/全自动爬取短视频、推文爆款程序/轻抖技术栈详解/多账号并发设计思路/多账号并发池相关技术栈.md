## 1. 结论先行：两条路——对标现成 vs 零依赖自研

> 🔥 **<span style="color:#e74c3c">一句话总括：市面所有"多账号并发采集"成熟方案的技术栈，抽象到最后就三件事——账号隔离、全局限速、受控并发。这三件事本项目用 Python 标准库 + 现有 SQLite WAL 就能全部实现，零新增依赖。</span>**

- 🧭 **<span style="color:#e67e22">路 A（对标现成）**：照抄成熟软件/开源项目的技术栈，如 MediaCrawlerPro 的"账号池 + IP 代理池 + 断点续爬"、AdsPower 的"每账号独立指纹浏览器 + CDP"、xhs_matrix_system 的"账号级任务表 + FastAPI + Redis"——这些项目已在 GitHub 开源，名字和地址见 [[#3. 对照技术栈的 GitHub 高Star项目清单（名字 + 地址，暂不下载）]]，本次只登记不下载；</span>
- ✅ **<span style="color:#2980b9">路 B（零依赖自研）**：不装 aiolimiter、tenacity、Redis、proxy_pool、CloakBrowser，仅用 `concurrent.futures.ThreadPoolExecutor`（项目已在用）+ `threading` + `time` + `queue` + 现有 SQLite WAL，自研"账号级受控并发池 + 全局限速漏桶 + 指数退避重试 + 串行写队列"，落地细节见 [[#6. 新增模块（纯标准库）：6 个文件 + 代码骨架]] 与 [[#7. 现有文件逐文件改动点（交给 Codex 的分步清单）]]。</span>

> 💡 **<span style="color:#2980b9">两条路不冲突：路 A 是"参考别人怎么造"，路 B 是"自己用最省的方式造"。本文推荐先用路 B 把"账号并发 2 路"跑稳，再按需在 P2+ 补路 A 的代理池/指纹等外挂（见 [[#10. 分阶段实施与验收（P0→P4）]]）。</span>**

## 2. 现成多账号并发采集软件/小程序：技术栈调研

> 调研范围：目前市面上能"多账号并发采集/矩阵运营"的软件、小程序、开源工具（2026-08-14 WebSearch）。重点看它们**怎么解决账号隔离、并发控制、风控对抗**三件事。

| 软件/小程序 | 形态 | 核心技术栈 | 多账号做法 | 对本项目的启发 |
|------|------|-----------|-----------|----------------|
| **轻抖** | 微信小程序 | 短链解析 + 字幕直取 + 缓存 + ASR 兜底（"四板斧"） | 接口层单账号逐条，靠缓存秒回 | 字幕直取 = 线路1；**页面层并发最易风控**（见 [[轻抖VS我们的项目]]） |
| **MediaCrawlerPro** | Python CLI | Python + aiohttp + 账号池(Excel/MySQL) + IP 代理池 + 断点续爬 + 签名服务；**去 Playwright 依赖** | 账号池轮换 + 代理池 + 降频 | 多账号 = 账号池 + 代理池 + 断点；浏览器自动化特征越少越稳 |
| **TikHub** | API SDK | httpx + pydantic v2，内置限速/退避/重试 | 平台级多 Key 轮换 | 接口层封装 + 内置频控，是"全局限速"的现成参照 |
| **获客宝** | 桌面 App | Electron 33 + Vue3 + Element Plus + SQLite | 多账号并行、多浏览器窗口 | 壳是 Electron，业务在 JS；与自家无关，仅参考"账号级并发 UI" |
| **CrawlerCLI** | Python CLI | Playwright，按平台/账号隔离 Chrome profile | **每账号独立 profile** | 账号隔离 = 独立 user-data-dir（与本方案 `browser_profiles.py` 完全同构） |
| **ZTWZ-Douyin-MCP** | MCP Server | Spring AI MCP + 临时浏览器（Ephemeral Browser） | 每会话临时浏览器，用完即焚 | MCP 化 + 临时上下文，避免登录态残留 |
| **Alien 店群** | Python 脚本 | DrissionPage + CDP + 浏览器指纹重写 | 多指纹多环境并发 | 指纹伪装 + CDP 控制，是"指纹对抗"的参照 |
| **AdsPower** | 桌面 App | Chromium/Firefox 双内核 + Local API(`localhost:50325`) 返回 CDP ws_url | **每账号独立指纹环境**，API 启动/停止 | 指纹隔离 + CDP 自动化 + **并发建议 2~3 路**（官方实测 8 路会超时）——与本方案并发上限完全一致 |
| **MatrixMedia** | 桌面 App | Vue + Electron + Puppeteer；HTTP API(30088) + MCP | 多平台批量发布 | Electron + Puppeteer 壳；HTTP API 化思路可参考 |
| **xhs_matrix_system** | Web 全栈 | FastAPI + SQLAlchemy + PostgreSQL + Redis + Vue3 + Element Plus | 多账号管理 + 代理 IP 地区隔离 + 定时发布 | **账号级任务表 + 代理隔离 + 状态监控**，与本方案 `account_tasks` 表同思路 |
| **kebenxiaoming/matrix** | Python 脚本 | Python3 + Playwright + MySQL + Redis | 任务队列轮询 + 多平台分发（抖音/快手/视频号/小红书） | 数据库驱动的任务队列（`mx_publish_task_video_queue` 状态机 0=待发/1=发布中/2=成功/3=失败） |

> 🔥 **<span style="color:#e74c3c">调研共性结论：没有一家靠"复制 N 路并联"成功——全部是"账号隔离 + 受控并发 + 频控"三件套。连 AdsPower 官方都实测"同时开 8 个环境会超时、建议线程池 max_workers=2~3"，这正好印证 [[多并发池的批量化采集规则]] 与 [[自研平台批量化处理路线]] 的"稳定优先"铁律。</span>**

## 4. 仅用现有配置能否实现？——可以，零新依赖

> 🔥 **<span style="color:#e74c3c">直接回答用户的核心问题：不需要任何额外插件，仅用本项目已有配置 + Python 标准库，就能完整实现"多账号并发池采集"。</span>**

### 4.1 关键认识：原方案的两个 pip 依赖都能被标准库替代

| 原计划依赖（姊妹篇 [[多账号不同视频同时采集的技术栈要求]] 第 3 章） | 零依赖替代 | 替代代码量 | 说明 |
|------|-----------|:--:|------|
| **tenacity**（指数退避重试） | 自研 `with_retry()`：`time.sleep + random.jitter` | ~20 行 | 只需要"退避重试 + 只重试瞬态错误"两个能力，标准库三行逻辑即可 |
| **aiolimiter**（跨账号全局限速） | 自研 `RateLimiter`：`threading.Lock + time.monotonic` 同步漏桶 | ~25 行 | 项目是同步线程模型，`aiolimiter` 只支持 async 反而要重写调用链；同步漏桶零侵入 |
| **asyncio / 异步化** | 不引入，沿用 `ThreadPoolExecutor`（项目已在用） | 0 | 同步线程模型已足够支撑账号并发 2~3 |
| **Redis 队列** | 现有 SQLite `collection_tasks` + 新增 `account_tasks` 表 | 0 | 账号级状态落 SQLite 即可，Redis 是 P2+ 可选项 |
| **proxy_pool / CloakBrowser / patchright** | 暂不接；靠全局限速 + 随机错峰 + 登录态保鲜降低风控 | 0 | 属 P2 风控对抗外挂，不是并发池的必需品 |

### 4.2 为什么可行：项目已有的三块地基

- ✅ **`ThreadPoolExecutor` 已在用**：`collection.py` L168 任务级单 worker 已用它；同款线程池加 `max_workers=2~3` 就是账号级并发池，**零新语法**；
- ✅ **SQLite WAL 已开**：`db.py` `initialize()` 已 `PRAGMA journal_mode=WAL`，`connect()` 已 `busy_timeout=15000`——并发读 + 集中串行写的基础已就绪；
- ✅ **账号数据独立**：`accounts.json` 14 个账号各自独立 `creator_url`，采集结果按账号落库，天然可按账号拆分任务（见 [[多并发池的批量化采集规则]] 第 4 章）。

### 4.3 唯一必须"新写"的，是账号隔离的地基

> 📌 **<span style="color:#e67e22">零依赖 ≠ 零代码。并发池框架本身可以标准库造，但"每账号独立浏览器配置 + 独立 CDP 端口 + 独立采集库"（登录态隔离）必须新写——这正是 [[多并发池的批量化采集规则]] 第 5 章的"三座大山"里最核心的那座，绕不开。</span>**

> 💡 **<span style="color:#2980b9">一句话总结可行性：并发池（标准库能造）+ 限速（标准库能造）+ 重试（标准库能造）+ 写库（现有 WAL 能扛）都齐了，剩下的唯一新增工作是"把账号和账号的浏览器/端口/采集库隔开"——这是 200 行内的新增模块，见下一章。</span>**

## 5. 改动总览：一张图看清 7 个改动点

```
用户提交 N 个账号（仍是 1 个采集任务，任务级锁保留）
        ↓
① 任务入队 collection_tasks（status: pending）——不变
        ↓
② 多账号调度器 runner.run_accounts(task_id, accounts, payload, collect_one)
        ↓
③ 账号级受控并发池  ThreadPoolExecutor(max_workers=2~3)   ← 自研，标准库
   每个账号 worker = 原 _collect_account + 账号隔离：
   ├─ allocate_profile(name) → 独立 user-data-dir + CDP 端口 + 独立采集库   ← 自研，标准库
   ├─ global_limiter.acquire() 跨账号全局限速（同步漏桶）                   ← 自研，标准库
   ├─ with_retry() 指数退避（429/超时才重试）                               ← 自研，标准库
   ├─ 启动独立 MediaCrawler 子进程（内部仍 --max_concurrency_num 3）
   └─ 结果提交 wal_queue.submit_write() 集中串行写 → 业务库                 ← 自研，标准库
        ↓
④ 全部完成 → drain() 等写库 → 汇总（各账号成功/失败清单）——沿用现有 result_json
```

## 6. 新增模块（纯标准库）：6 个文件 + 代码骨架

> 全部放 `backend\app\services\multi_account\` 包下。**只 import 标准库 + 项目内已有模块，不新增任何 pip 依赖。** 对齐 [[Codex对话迁移方案]] 的"模块独立"约定。

```
backend\app\services\multi_account\
├── __init__.py            # 空文件
├── browser_profiles.py    # ① 每账号独立 user-data-dir + CDP 端口 + 独立采集库
├── global_limiter.py      # ② 跨账号全局限速（自研同步漏桶，替代 aiolimiter）
├── retry.py               # ③ 指数退避重试（自研，替代 tenacity）

├── wal_queue.py           # ⑤ SQLite 集中串行写队列
```

### 6.1 browser_profiles.py —— 登录态隔离的地基（最核心）

**职责：** 为每个账号分配独立的浏览器数据目录、CDP 端口、独立采集库路径，并登记/回收。**这是"账号 A 的请求绝不带账号 B 的 Cookie"的唯一保证。**

```python
"""每账号独立浏览器 profile + CDP 端口 + 独立采集库（登录态隔离的地基）。纯标准库。"""
import re
import threading
from dataclasses import dataclass
from pathlib import Path

from ..config import (
    MEDIACRAWLER_BROWSER_DATA_DIR,
    MEDIACRAWLER_BROWSER_BASE_PORT,
    MEDIACRAWLER_ROOT,
)

@dataclass(frozen=True)
class BrowserProfile:
    account_name: str
    user_data_dir: Path     # runtime\browser_data\cdp_<key>_user_data_dir
    cdp_port: int           # 9222 / 9223 / 9224 ...
    mc_db_path: Path        # MediaCrawler\database\<key>_sqlite_tables.db

_profiles_root = Path(MEDIACRAWLER_BROWSER_DATA_DIR)
_port_lock = threading.Lock()
_used_ports: set[int] = set()

def allocate_profile(account_name: str) -> BrowserProfile:
    key = re.sub(r"[^\w一-鿿]", "_", account_name)   # 中文账号名安全转文件名
    with _port_lock:
        port = int(MEDIACRAWLER_BROWSER_BASE_PORT)           # 从 9222 起找空闲端口
        while port in _used_ports:
            port += 1
        _used_ports.add(port)
    return BrowserProfile(
        account_name=account_name,
        user_data_dir=_profiles_root / f"cdp_{key}_user_data_dir",
        cdp_port=port,
        mc_db_path=Path(MEDIACRAWLER_ROOT) / "database" / f"{key}_sqlite_tables.db",
    )

def release_profile(profile: BrowserProfile) -> None:
    with _port_lock:
        _used_ports.discard(profile.cdp_port)
```

> 🔥 **<span style="color:#e74c3c">这条是"登录态不串味"的唯一保证：没有它，多账号并发 = 数据张冠李戴 + 风控一锅端（[[多并发池的批量化采集规则]] 5.1）。</span>**

### 6.2 global_limiter.py —— 跨账号全局限速（替代 aiolimiter）

**职责：** 一个全局共享的同步漏桶，所有账号"发起平台请求前"都调 `acquire()`，保证跨账号总请求速率受控（默认 1 req/s 起步）。**同步版，零 async 改造。**

```python
"""跨账号全局限速：自研同步漏桶（替代 aiolimiter），纯标准库，约 25 行。
漏桶是全局的，天然"公平分配"——2 个账号并发时谁先到谁先用。"""
import threading
import time
from ..config import MEDIACRAWLER_GLOBAL_RATE_PER_SECOND

class RateLimiter:
    def __init__(self, rate_per_second: float = 1.0):
        self.min_interval = 1.0 / max(0.1, rate_per_second)
        self._lock = threading.Lock()
        self._last = 0.0

    def acquire(self) -> None:
        with self._lock:
            now = time.monotonic()
            wait = self._last + self.min_interval - now
            if wait > 0:
                time.sleep(wait)
                now = time.monotonic()
            self._last = now

global_limiter = RateLimiter(float(MEDIACRAWLER_GLOBAL_RATE_PER_SECOND))
```

### 6.3 retry.py —— 指数退避重试（替代 tenacity）

**职责：** 只对**瞬态错误**（超时/429/5xx）退避重试，业务失败直接抛给上层——防止把"账号真的被风控"也当瞬态错误无限重试。

```python
"""自研指数退避重试（替代 tenacity），纯标准库，约 20 行。
只重试瞬态错误（Timeout/429/5xx），业务失败直接抛给上层。"""
import random
import time

def with_retry(fn, *, attempts=3, base=1.0, factor=2.0, max_delay=8.0,
               retryable=(TimeoutError, ConnectionError), logger=None):
    delay = base
    for i in range(1, attempts + 1):
        try:
            return fn()
        except retryable as exc:
            if i == attempts:
                raise
            jitter = random.uniform(0, 0.5) * delay          # 随机抖动，避免机械节奏
            time.sleep(delay + jitter)
            delay = min(delay * factor, max_delay)           # 1s → 2s → 4s
            if logger:
                logger.warning("第 %d/%d 次重试：%s", i, attempts, exc)
```

### 6.4 account_pool.py —— 账号级受控并发池

**职责：** 用线程池把账号并发度钉死在 2~3 路（先 2 起步），每个账号一个 worker。**与项目现用的 `ThreadPoolExecutor` 同款，零新语法。**

```python
"""账号级受控并发池：ThreadPoolExecutor(2~3) + 全局限速。纯标准库。"""
from concurrent.futures import ThreadPoolExecutor, as_completed
from ..config import MEDIACRAWLER_CONCURRENT_ACCOUNTS
from .global_limiter import global_limiter
from .retry import with_retry

class AccountPool:
    def __init__(self, max_accounts: int | None = None):
        self.max_accounts = max_accounts or int(MEDIACRAWLER_CONCURRENT_ACCOUNTS)
        self.executor = ThreadPoolExecutor(
            max_workers=self.max_accounts, thread_name_prefix="account"
        )

    def run(self, jobs: list[callable]) -> list:
        """jobs: list of callable，每个代表一个账号任务。
        单账号失败必须在内部捕获并记录，不向这里冒泡（失败隔离）。"""
        futures = [self.executor.submit(job) for job in jobs]
        return [f.result() for f in as_completed(futures)]   # 每个 result 是 {name: status}
```

> ⚠️ **<span style="color:#e74c3c">账号并发 2~3 + 账号内视频并发 3 = 最高 6~9 路请求，已经是"稳定优先"天花板附近。绝不要"12 个账号 12 路并联"（[[自研平台批量化处理路线]] 的结论）。</span>**

### 6.5 wal_queue.py —— SQLite 集中串行写队列

**职责：** 所有写业务库的操作（`save_video_snapshot` / `save_video_comments` / 任务计数）提交到单线程消费队列，worker 只算不写库——彻底避免多账号并发下的 `database is locked`。

```python
"""SQLite WAL + 集中串行写队列：worker 只算，写库单线程。纯标准库。"""
import queue
import threading
from ..db import connect

_write_queue: queue.Queue = queue.Queue()
_thread = None

def submit_write(fn, *args, **kwargs) -> None:
    """fn 签名统一为 fn(con, *args, **kwargs)，con 由写线程提供。"""
    _write_queue.put((fn, args, kwargs))
    _ensure_worker()

def _ensure_worker() -> None:
    global _thread
    if _thread is None or not _thread.is_alive():
        _thread = threading.Thread(target=_write_worker, daemon=True, name="db-write")
        _thread.start()

def _write_worker() -> None:
    while True:
        fn, args, kwargs = _write_queue.get()
        try:
            with connect() as con:
                fn(con, *args, **kwargs)
        except Exception:
            pass                                   # 单条写失败不影响队列
        finally:
            _write_queue.task_done()

def drain() -> None:
    _write_queue.join()
```

> 🔥 **<span style="color:#e74c3c">这是业务库 `data\radar.sqlite3` 在多账号并发下"不锁死"的命门。现有 `save_video_snapshot` 是独立事务，2 个账号同时写就有排队风险——包进串行队列后写锁零竞争。</span>**

### 6.6 runner.py —— 多账号调度器

**职责：** 账号任务入队 → 分配 profile → 提交账号池 → 收结果 → 汇总。**`_run` 主流程的进度/暂停/取消/汇总逻辑一行不用改，只把 for 循环换成 `run_accounts(...)`。**

```python
"""多账号调度器：替代 collection.py _run 里的 for 串行循环。纯标准库。"""
import random
import time
from ..db import add_log, increment_task_result
from .browser_profiles import allocate_profile, release_profile
from .account_pool import AccountPool
from .wal_queue import drain

def run_accounts(task_id: str, accounts: list[str], payload: dict,
                 collect_one: callable) -> dict:
    """collect_one(task_id, name, profile, payload) -> None（单账号失败内部捕获）。
    返回 {"succeeded": [...], "failed": [...]}。"""
    pool = AccountPool()
    results = {"succeeded": [], "failed": []}

    def one(name: str):
        if results["succeeded"] or results["failed"]:        # 非首个账号：随机错峰 20~60s
            time.sleep(random.uniform(20, 60))
        profile = allocate_profile(name)
        try:
            add_log(task_id, f"账号 {name} 分配 profile：端口 {profile.cdp_port}，目录 {profile.user_data_dir}")
            collect_one(task_id, name, profile, payload)
            results["succeeded"].append(name)
            increment_task_result(task_id, accounts_succeeded=1)
        except Exception as exc:
            results["failed"].append(name)
            increment_task_result(task_id, accounts_failed=1)
            add_log(task_id, f"{name} 采集失败，已继续其他账号：{exc}", "error")
        finally:
            release_profile(profile)

    pool.run([lambda n=name: one(n) for name in accounts])
    drain()                                  # 等所有串行写落库
    return results
```

> 📌 **<span style="color:#e67e22">`collect_one` 就是改造后的 `_collect_account`（加了 profile 参数）。随机错峰 20~60s 是风控缓解的关键（见 [[如何解决人机验证问题]] 第 7 章）——避免多个账号同一瞬间启动的"机械节奏"。</span>**

## 9. 风控红线：多账号并发的三条命脉

> 🔥 **<span style="color:#e74c3c">多账号并发的本质：把 N 个账号的请求叠加到同一 IP/设备，叠加越多越容易被抖音 Argus 判定异常。以下三条是"安全多账号采集"的命脉，缺一条账号就危险。</span>**

| # | 命脉 | 要求 | 零依赖落地 | 关联文档 |
|:-:|------|------|-----------|---------|
| ① | **登录态隔离** | 每账号独立 user-data-dir + 独立 CDP 端口 | `browser_profiles.py`；独立扫码登录，互不串 Cookie | [[多并发池的批量化采集规则]] 5.1 |
| ② | **跨账号全局限速** | 全局 1 req/s 起步，跨账号共享漏桶 | `global_limiter.py`；测过安全 QPS 再放宽 | [[多worker并发池设计思路]] 红线 2 |
| ③ | **随机错峰启动** | 账号与账号之间随机延迟 20~60s | `runner.py` `one()` 开头 `time.sleep(random.uniform(20, 60))` | [[如何解决人机验证问题]] 第 7 章 |

> 📌 **<span style="color:#e67e22">可选项（P2+ 才上，仍非必需）：代理池（proxy_pool）、指纹浏览器（CloakBrowser/patchright/AdsPower）、验证码检测升级（URL+DOM 双重确认）。这些是"进一步降风控"的外挂，不是并发池的必需品。</span>**

> ⚠️ **<span style="color:#e74c3c">合规红线：降低触发概率 + 人工完成真验证可以，任何"自动破解验证码 / 硬扛风控"都禁止。MediaCrawler 已强制"自动求解禁用、人工处理"（[[0811-开发日志]] 第 12 章）。多账号并发把风控面放大了，更要把频率与隔离做到位，而不是去对抗平台。</span>**

| **P0** | 保持现状，零改动 | 不碰代码，先跑现有串行批采 | 连续 3 轮零崩溃、无锁冲突（当前已达标，勿破坏） |
| **P1** | 零依赖并发框架 + 每账号独立浏览器配置 | 建 `multi_account` 包（第 6 章 6 个模块）；`_collect_account` 加 profile 参数；config 加 4 项；start.ps1 改方案 A；db 加 account_tasks 表 | **2 账号并行 × 各 3 并发**跑 3 轮：无人机验证卡死、无 `database is locked`、登录态不串味（账号 A 请求绝不带账号 B Cookie） |
| **P2** | 全局限速 + 指数退避 + 断点续跑 | `global_limiter.acquire()` 接入每个账号请求前；`with_retry()` 包瞬态错误；`account_tasks` 登记状态支持断点 | 同一批账号重跑，已完成账号秒跳；偶发 429/超时自动退避成功；`account_tasks` 状态可恢复 |
| **P3** | 失败隔离汇总 + 前端账号级展示 | runner 汇总各账号成败清单；后端 API 返回 `account_tasks`，前端任务卡片加账号级状态徽标 | 单账号失败不影响其他账号；全局限速生效（日志可证）；前端可见每账号 pending/doing/done/failed |
| **P4（可选）** | 账号并发放开到 3~4 | 调 `MEDIACRAWLER_CONCURRENT_ACCOUNTS=3`（或 4） | 需 P1~P3 全绿才做；仍维持全局限速，日志无瞬时并发尖峰 |

### 10.1 每次放量前的安全自检（三组实验，来自 [[自研平台批量化处理路线]] 3 节）

1. **2 账号串行**（间隔 20~60s 随机）→ 成功？确认是"并发触发风控"还是"串行本身问题"；
2. **2 账号并发**（限速 1/s）→ 观察 429/403/验证码出现率；
3. **逐级放量**：2 → 3 → 4，每级稳定跑 2~3 轮再放宽，出现异常立即回退一级。
