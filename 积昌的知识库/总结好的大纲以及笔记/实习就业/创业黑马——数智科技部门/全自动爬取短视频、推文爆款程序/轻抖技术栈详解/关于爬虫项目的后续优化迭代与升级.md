# 📡 关于爬虫项目的后续优化迭代与升级：三大问题的可落地总方案

> [!summary] 概要
> 本文档解决本地部署抖音爬虫项目的三个根本痛点：**① 抖音 API 高频更新如何长期维护**、**② 本地部署无法像游戏一样强制更新、如何让用户知道有更新**、**③ 大体积项目如何只更新改动部分（类比王者荣耀增量更新）**。核心结论：**文件级差分 + 客户端自比对 + manifest 清单 + 三目录分离（program/data/models）+ ed25519 签名**，配合适配层隔离与多线路降级，形成一个"**服务端只管最新清单与全量文件、客户端逐文件自比对按需下载**"的增量更新体系；爬虫对抗走"**Provider 统一接口 + 多线路降级 + 签名算法不出包**"的维护架构。全程已由「代码总监」两轮质疑 + 终审，**判定通过**；并完成最小演练（改 1 文件→按需下载→升级→回滚，PASS）。

> ⚠️ **<span style="color:#e74c3c">安全声明（必须通读）：</span>**
> - 登录态/Cookie 目录唯一落点 `<DEPLOY_ROOT>\data\browser_data`（迁移前 `%LOCALAPPDATA%\MediaCrawler\browser_data`），**禁止提交 Git / 上传网盘 / 粘贴进工单**。
> - `.env.local` **只读密钥名、不读值、不外发**；密钥只存在于运行机的 `.env.local` 与站点运行时。
> - 更新通道具备**远程代码执行（RCE）**能力，**必须 ed25519 先验签再执行**；不执行任何未验签的代码/补丁。
> - MediaCrawler 为非商用学习许可；当前仅限内部非商用技术验证。**不实现任何"自动破解验证码"逻辑**。

## 1. 三大问题与总体解法

### 1.1 一句话版本

| 问题 | 本质 | 解法 |
|------|------|------|
| ① API 高频更新 | 反爬签名（X-Bogus / msToken / a_bogus）被频繁更新，爬取方法需要定期维护 | **适配层隔离**：所有采集能力收敛到统一接口 `Provider.collect_account(account, range_key)`；多线路降级（字幕直取→接口级→浏览器兜底）；签名算法**fork 内单文件、不出包** |
| ② 更新分发 | 本地部署无法强制更新 | **双通道告知**：launcher 启动检查 + 前端公告/可选推送（仅匿名元数据）；用户可主动"一键更新" |
| ③ 增量更新 | 大体积项目不能每次全量重装 | **文件级差分 + 客户端自比对**：服务端只维护最新 manifest + 全量文件，客户端逐文件比对按需下载单文件，天然断点续传 |

### 1.2 三层联动总图

```
┌────────────────────────── 服务端（你维护） ──────────────────────────┐
│  发布流水线：改代码 → 跑测试 → 打 manifest（sha256+ed25519签名）        │
│  → 上传到 Gitee Release / COS / 私有 OSS（组件包 ≤100M，断点续传）      │
└──────────────┬───────────────────────────────────────┬─────────────┘
               │ ① 发布清单+全量文件                        │ ② 可选：匿名元数据回传
               ▼                                          │ （版本号/错误码/成功率，用户同意）
┌────────────────────────── 客户端（小白用户机器） ─────────────────────┐
│  launcher（独立入口）→ 读本地 manifest → 拉远端 manifest → 验签        │
│  → 逐文件比对 sha256 → 只下载 changed/new 文件 → 全停→替换→回滚       │
│  目录结构：program（代码+venv）/ data（SQLite+Cookie+账号+.env.local） │
│            / models（ASR模型+Playwright浏览器）                       │
└─────────────────────────────────────────────────────────────────────┘
```

### 1.3 为什么这套方案对"本地部署 + 小白用户"成立

- 🎮 类比王者荣耀：客户端有"当前资源版本清单"，只拉增量资源包，本地校验合并——本方案是同一思想，但**服务端不预生成 diff 包**（那需要服务端持有所有历史版本），改为**客户端拿着自己的清单来比对**，服务端永远只维护"最新一份全量 + 最新清单"，实现与维护成本都最低。
- ✅ 天然断点续传：按单个文件下载，中断后已下的文件不重下（文件级 sha256 幂等）。
- ✅ 可回滚：每次更新前备份将被替换的文件 + 旧 manifest，失败一键还原。
- ✅ 可审计：每个文件的 sha256 都在 manifest 里，换包必被发现。

> 💡 **<span style="color:#2980b9">为什么放弃字节级差分（bsdiff）：</span>** 字节级差分要求服务端持有每个客户端的确切旧版本才能生成 diff，且客户端任一文件损坏就整包无法应用；文件级差分把"差异计算"下放到客户端（拿新旧两个 sha256 一比），服务端复杂度为零，容错性更高。30G 量级下，大多数更新只改几十个文件，文件级差分已足够小。

## 3. 问题一：抖音 API 高频更新与爬虫对抗

### 3.1 抖音反爬的现状

抖音网页/App 端通过 **webmssdk 动态下发** 的签名参数（X-Bogus / msToken / a_bogus）标记合法客户端，签名算法被逆向后**以周~月级频率更新**，配合接口字段增删、风控策略，导致爬取方法需要**周期性维护**。

> ⚠️ **<span style="color:#e74c3c">不自建签名服务：</span>** 把 X-Bogus/a_bogus 签名算法做成"云端签名服务"给所有用户调，等于把整套对抗能力做成一个随时可被吊销的高价值靶子，且签名 KEY 一旦泄露全盘皆输。**签名算法必须留在 fork 内、以单文件模块形式随包分发**，靠客户端自比对增量更新（见第 5 章）来升级——这正是"API 维护"与"增量更新"两个问题的耦合点。

### 3.2 适配层隔离（统一接口 `collect_account`）

所有采集能力统一实现 `Provider.collect_account(account, range_key) -> list[tuple[dict, dict]]`：

| Provider | 状态 | 说明 |
|---------|:--:|------|
| `MediaCrawlerProvider` | ✅ 活跃 | 走 MediaCrawler 子进程（浏览器兜底线路） |
| `DouyinOfficialProvider` | 🔴 未开通 | 官方开放平台，作品列表能力未申请；能力开通后可成为合规线路 |
| `ApiZeroVideoEnricher` | 🔴 未配置 | 仅作已知视频链接的补充源，不负责发现账号作品 |
| `SubtitleDirectProvider` | 🟡 待创建 | 线路1"字幕直取"（口播文案抓取，见 [[轻抖-如何快速实现口播稿件的抓取]]） |
| `ApiLevelProvider` | 🟡 待创建 | 线路2"接口级"（构造分享页/创作者页 API 直取） |
| `FailoverProvider` | 🟡 待创建 | 多线路降级调度：按线路优先级尝试，单条失败自动切下一条 |

> ✅ **<span style="color:#2980b9">为什么先立接口：</span>** API 更新时，维护者只需改对应 Provider 内部实现（或切换线路），`collection.py` 与前端一行不用动。这就是"适配层隔离"——把"抖音变了"的冲击限制在 Provider 内部。

### 3.3 多线路降级架构（待创建）

```
采集请求
  └─ FailoverProvider.run()
      ├─ 线路1 字幕直取（SubtitleDirectProvider）   ← 最快、最稳、最轻（口播文案）
      │     失败 ↓
      ├─ 线路2 接口级（ApiLevelProvider）           ← 构造 API 直取作品列表+指标
      │     失败 ↓
      └─ 线路3 浏览器兜底（MediaCrawlerProvider）    ← 最重、最接近真人，现有实现
            失败 → 记录失败原因，不静默吞
```

- **熔断策略**：单账号连续失败 N 次（建议 3）→ 切下一条线路；同线路全局失败率 > 阈值（建议 50%）→ 该线路整体熔断，避免僵尸重试放大风控。
- **状态展示**：每条线路的耗时/成败写入 `add_log`，前端可见"当前线路 = 字幕直取/接口级/浏览器兜底"。
- ⚠️ **<span style="color:#e67e22">与并发池的衔接：</span>** 并发池（[[多账号的并发池设计（Codex交付版本）]]）是"账号级并发"，这里是"单账号多线路降级"，两层正交，`collect_account` 接口同时承载两者。

### 3.4 签名与算法维护原则（fork 内单文件）

- 抖音相关算法（X-Bogus / msToken / a_bogus）**只放在 fork 内单文件模块**（如 `MediaCrawler/.../douyin/signature.py`），随包分发，不对外暴露接口。
- 升级路径：上游 MediaCrawler 社区更新 → 人工 merge 冲突区（通常就这一个文件）→ 走增量更新推给用户。
- **绝不**把算法做成 HTTP 服务、绝不把签名 KEY 写进明文配置、绝不贴进工单/日志。

### 3.5 监控与告警 SOP（问题①的运维闭环）

| 监控项 | 手段 | 触发动作 |
|--------|------|---------|
| 上游更新 | 订阅 MediaCrawler GitHub Release/commit | 收到通知 → 拉取 diff → 评估影响 |
| 采集成功率 | backend 已记录每任务 success/failed | 成功率 < 80% 且错误集中在"签名/参数/风控" → 判定 API 变更 |
| 错误特征码 | 采集失败日志按 `error` 分类计数 | 出现新错误码 → 建 case 定位 |
| 线路健康度 | FailoverProvider 记录每线路成功率 | 线路熔断告警 |
| 版本指纹探测 | 定时请求抖音页面/接口，比对签名参数结构 | 结构变化 → 提前预警，不等用户报障 |

> 📌 **<span style="color:#e67e22">建议的维护节奏：</span>** 每月固定一次"对上游 diff + 线路体检"；API 大规模变更时，用"升级包 + 更新日志"（第 4 章）推给用户，**不需要用户卸载重装**。

## 4. 问题二：更新分发——怎么让小白用户知道并拿到更新

### 4.1 为什么不能像游戏那样强制更新

游戏是中心化服务器，客户端连不上就玩不了，天然强制；本地部署的爬虫软件**不依赖你的服务器就能跑**，用户完全可以继续用旧版本。所以只能"**告知 + 引导**"，不能"**强制**"。

### 4.2 双通道告知机制

| 通道 | 实现 | 说明 |
|------|------|------|
| **launcher 启动检查**（主） | launcher 启动时 `GET` 远端 `latest.json`（含版本号+摘要+签名），与本地 manifest 比对 | 有新版 → 弹窗"发现新版本 vX.Y.Z：……（更新内容）【立即更新】【稍后】" |
| **应用内公告**（辅） | 前端首页顶部公告条，从 `latest.json` 拉取 | 用户已启动软件也能看到；支持纯文本更新说明 |
| **可选推送**（不强制） | 仅在用户**明确同意**后，回传匿名元数据（版本号/错误码/成功率），用于服务端统计哪些版本在崩溃 | 永不回传内容数据 |

> ⚠️ **<span style="color:#e74c3c">回传底线：</span>** 只回传"版本号 / 错误码 / 成功率"这类匿名元数据，**绝不回传任何采集到的内容数据**，且必须用户知情同意。合规红线见 [[#8. 安全边界]]。

### 4.3 更新通道 = 远程代码执行（RCE）风险，必须签名

更新通道有能力在你机器上写文件/执行命令，**等价于一个远程控制通道**。缓解措施：

1. **ed25519 签名**：服务端用私钥对 `manifest` 签名；客户端内嵌**公钥**，先验签、再校验每个文件 sha256，全部通过才写盘。
2. **HTTPS + 固定公钥**：即使域名被中间人劫持，没有私钥也伪造不了签名。
3. **不执行未验签代码**：任何补丁/脚本未过签名一律拒绝。
4. **最小权限运行**：更新进程建议以普通用户权限运行，不请求管理员权限（除非首次安装）。

> 💡 **<span style="color:#2980b9">私钥管理：</span>** 私钥按 3-2-1 原则备份（3 份拷贝、2 种介质、1 份离线）；泄露即轮换（生成新密钥对 + 重签全量 manifest）；客户端公钥通过**带外方式**（独立安全通道）更新，不走 HTTP。

### 4.4 渠道选择与容量约束

| 渠道 | 免费/费用 | 单文件上限 | 适合 |
|------|----------|-----------|------|
| **Gitee Release** | 免费 | ≈500M | 主要公开渠道（国内可达性好） |
| **腾讯云 COS / 阿里云 OSS** | 按量计费 | 大 | 私有分发 + 断点续传 + CDN |
| 私有内网 / 群文件 | — | — | 小范围种子用户 |

**组件包切分**：单个组件包 ≤ **100M**（对齐 Gitee 与弱网体验），支持断点续传；manifest 按组件列出文件清单，客户端逐文件下载即可（见 [[#5.3 manifest 清单结构]]）。

## 5. 问题三：增量更新——只更新改动部分（核心）

### 5.1 核心机制：文件级差分 + 客户端自比对

```
服务端（永远只维护一份）：
  latest/ 目录 = 当前全量文件 + manifest.json（含每个文件 sha256/大小/分类）+ manifest.sig（ed25519）

客户端（每次启动/手动检查时）：
  1. 读本地 manifest（上一版）→ 2. 拉远端 manifest + 验签
  3. 逐文件比对 sha256：
       本地无此文件        → 需下载（新增）
       本地 sha256 不同     → 需下载（改动）
       远端已无此文件       → 待删除
       其余               → 跳过（未变）
  4. 只下载需下载的文件（按需单文件，天然断点续传）→ 逐个校验 sha256
  5. 全停 → 替换 → 写回新 manifest → 启动
```

> ✅ **<span style="color:#2980b9">最小演练证据（2026-08-14 实测通过）：</span>** 构造 v1/v2 两个版本，改 1 个文件 + 新增 1 个文件；客户端自比对只检出 **2 个文件**下载，哈希校验通过，升级成功；`data/` 排除目录**未被误更新**；模拟失败**回滚后完整恢复 v1**。结论：机制可落地。

### 5.2 为什么这比"服务端生成补丁包"更好

| 对比项 | 服务端预生成 diff 包（bsdiff 思路） | 客户端自比对（本方案） |
|--------|--------------------------------|----------------------|
| 服务端复杂度 | 要持有所有历史版本才能算 diff | 只维护最新全量 + 最新清单 |
| 断点续传 | 整包或分块，块定位复杂 | 按文件天然续传 |
| 容错 | 任一文件损坏则补丁失败 | 按文件独立校验，坏哪个重下哪个 |
| 多版本兼容 | 每个旧版本要一个 diff | 一个清单兼容所有旧版本 |

### 5.3 manifest 清单结构

```json
{
  "version": "1.2.0",
  "compat": { "min_version": "1.0.0", "max_version": null },
  "components": [
    { "name": "program", "desc": "业务代码+配置模板", "policy": "replace" },
    { "name": "venv_patch", "desc": "依赖 wheel 增量", "policy": "merge" },
    { "name": "frontend_static", "desc": "前端构建产物", "policy": "replace" }
  ],
  "files": [
    { "path": "backend/app/config.py", "sha256": "…", "size": 1024,
      "category": "program", "policy": "replace", "min_version": null },
    { "path": "backend/app/providers/douyin.py", "sha256": "…", "size": 2048,
      "category": "program", "policy": "replace", "min_version": "1.1.0" },
    { "path": "backend/wheelhouse/f2-0.0.0-py3-none-any.whl", "sha256": "…",
      "size": 999999, "category": "venv_patch", "policy": "merge", "min_version": null }
  ],
  "exclude": [
    "data/**", "MediaCrawler/database/*.db", "MediaCrawler/database/*.db-wal",
    "MediaCrawler/database/*.db-shm", "MediaCrawler/browser_data/**",
    "backend/config/accounts.json", ".env.local", "logs/**",
    ".venv/**", "MediaCrawler/.venv/**", ".install-cache/**", ".pytest_cache/**", ".codex/**"
  ],
  "rules": [
    { "if": "files[category=program].size_sum > 200MB", "warn": "本次为大版本，建议保留备份" }
  ]
}
```

字段语义：
- `version`：语义化版本，`compat.min_version` 以下的旧客户端提示"需先升级到 X 版本"（避免跨太大版本）。
- `category`：组件归属，用于"先升级哪部分"（program 先于 venv_patch 后于 frontend_static）。
- `policy`：`replace`（整目录覆盖）/ `merge`（按文件合并，依赖类用 merge）。
- `exclude`：**永不参与更新的路径**（含通配），客户端比对时直接跳过。

### 5.4 客户端更新流程与断点续传

```
launcher（每次启动）
  └─ check_update():
       ├─ 本地有 manifest？ 无 → 首启，跳过更新，走初始化向导
       ├─ 拉 latest.json + manifest.sig → 验签（ed25519）
       │    失败 → 提示"更新源不可信"，沿用旧版
       ├─ 比对 → 有差异？
       │    无 → 正常启动
       │    有 → 弹窗询问（或按"自动更新"策略）：
       │         下载列表按 category 分组，逐文件下载（单个失败自动重试3次）
       │         下载进度 = 已下文件数/总文件数（断点续传：已完成文件写 .ok 标记）
       ├─ 全停（见 [[#7. Windows 文件锁与更新状态机]]）
       ├─ 备份待替换文件 + 旧 manifest → 替换/新增/删除 → 校验全部 sha256
       │    任一步失败 → 回滚（从备份还原）
       └─ 写回新 manifest → 启动服务
```

## 7. Windows 文件锁与更新状态机

### 7.1 问题：运行中的进程无法原子替换

Windows 下，正在运行的进程（uvicorn / npm / MediaCrawler 子进程 / ffmpeg / Redis）**锁住其加载的 .py/.exe/.dll 文件**，直接覆盖会报"文件被占用"。因此更新必须先"全停"。

### 7.2 更新状态机

```
IDLE ──发现更新──▶ DOWNLOAD（逐文件下载+校验）──全部就绪──▶ PRESTOP
                                                        │  向 backend 发"停机"信号
                                                        ▼
                ◀──失败回滚── FAILED                 REPLACE（备份→替换→新增→删除→全量校验）
                                                        │  成功
                                                        ▼
                                                     RESTART（launcher 拉起服务）
                                                        │
                                                        ▼
                                                      DONE（写回新 manifest）
```

- **全停顺序**：先停采集子进程（MediaCrawler）→ 停 backend（uvicorn）→ 停 frontend（npm）→ 再替换文件。
- **独立更新入口（launcher）**：launcher 是唯一有权限执行"停服务→替换→重启"的进程，**不依赖**正在运行的 backend（否则自己换自己会锁死）。
- **失败回滚**：替换前把待替换文件 + 旧 manifest 备份到 `<DEPLOY_ROOT>/data/.update_backup/`；任一步失败 → 还原 → 记录错误 → 提示用户重试。

### 7.3 launcher 自更新

- launcher 自身更新：下载新版到临时文件 → `os.replace` 原子替换 → 下次启动生效；不随程序整体更新，避免"换程序时把拉更新的人锁住"。
- launcher 版本独立于 `manifest.version` 区分；launcher 必须在"能读 manifest 且能启动服务"两个能力上保持向后兼容。

### 7.4 SQLite 迁移与一致性（配合更新）

- **可逆变更优先**：加表/加列（`ALTER TABLE ... ADD COLUMN` / `CREATE TABLE IF NOT EXISTS`）可逆；删表/改列需评估。
- **幂等**：迁移 SQL 全部 `IF NOT EXISTS`；重复执行不报错。
- **备份**：迁移前把 `radar.sqlite3` 复制一份 `.bak`（`data/` 内）。
- **门控**：业务库维护 `schema_version` 表，程序启动比对期望版本，低于则执行迁移脚本。
- **回滚语义**：SQLite 迁移与文件更新**解耦**——文件先回滚不影响库结构；库迁移失败则整次更新判失败并回滚文件（避免"半新半旧"）。

## 11. 决策记录与待确认项

### 11.1 已定决策（代码总监终审通过）

| 决策点 | 结论 | 理由 |
|--------|------|------|
| 增量更新算法 | **文件级差分 + 客户端自比对**，放弃 bsdiff | 服务端零复杂度、天然断点续传、多版本兼容、损坏可恢复 |
| 签名服务 | **不做云端签名服务**，算法 fork 内单文件随包分发 | 云端签名=高价值靶子，泄露全盘皆输 |
| 三目录分离 | program / data / models，`DEPLOY_ROOT` 驱动 | 增量更新的地基；登录态/数据零触碰 |
| 排除清单 | 通配 `MediaCrawler/database/*.db` + 真实路径清单 | 覆盖多账号独立库；目录含源码不可整排除 |
