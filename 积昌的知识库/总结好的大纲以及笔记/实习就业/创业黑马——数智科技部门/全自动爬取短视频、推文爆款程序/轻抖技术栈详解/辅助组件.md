## 1. 响应速度差距与目标

🔥 **<span style="color:#e74c3c">核心差距：轻抖对热门视频"3~10 秒出稿"，自家实证 30~100 秒、且有 120s 硬上限（见 [[0811-开发日志]]）。差距不在"采集能不能爬到"，而在"出稿速度引擎"——字幕直取、共享缓存、高速识别、并发服务这四件事自家还没落地。</span>**

- **目标**：把"链接 → 口播稿"的端到端响应从 30~100s 压到 **3~10s**，热门视频命中缓存 **<1s**
- **已有（不重复建设）**：采集三线路（[[3条线路设计]]）、达人账号字段（[[达人主页数据爬取]]）、字幕直取候选项目（douyin-mcp-server 等）
- **本文档补齐**：缓存服务、ASR 常驻服务、任务队列、API 服务化 —— 四块合称"**响应速度引擎**"

💡 **<span style="color:#2980b9">一句话结论：想达到轻抖速度，不是再堆"采集/识别"项目，而是把"结果复用 + 识别加速 + 并发调度 + 秒级返回"做成服务。字幕直取决定上限，缓存决定热门命中率，GPU 决定无字幕兜底下限，队列决定批量吞吐。</span>**

---

## 2. 端到端延迟拆解与杠杆模型

> 把"链接 → 口播稿"拆成四个延迟段，逐段看当前值与补齐组件后的目标值：

| 延迟段 | 当前（自家实证） | 补齐组件后 | 压缩杠杆 |
|------|:--:|:--:|------|
| ① 采集/解析 | 秒级~分钟级（易失败） | 秒级（接口层优先） | [[3条线路设计]] 三线路切换 |
| ② 缓存命中 | 无缓存，每次都全链路 | **<1s（热门秒回）** | 组件1 缓存服务 |
| ③ 音频识别 | CPU int8 small：分钟级 | **亚秒级~秒级（GPU 常驻）** | 组件2 ASR 服务 |
| ④ 排队/响应 | 串行处理、无流式 | **并发 + 流式首字** | 组件3 队列 + 组件4 API |

🔶 **<span style="color:#e67e22">杠杆结论：缓存（②）决定热门视频的"秒回"，GPU（③）决定无字幕视频的"兜底下限"，队列（④）决定批量请求的"吞吐上限"。三者叠加才能把"单条 30~100s"变成"批量平均 3~10s"。</span>**

## 3. 组件1：高速缓存服务（Redis / Dragonfly）

> 轻抖"热门秒回"的真正主力是**全用户共享缓存**：同一 `video_id` 第一次出稿后就写入缓存，之后任何人查都零网络请求（见 [[轻抖-如何快速实现口播稿件的抓取]]）。自家 [[3条线路设计]] 5.5 已设计"缓存层"接口，这里给出底层存储选型。

### 3.1 候选项目

| 项目 | ⭐ | 说明 | 选型建议 |
|------|:--:|------|---------|
| [redis/redis](https://github.com/redis/redis) | 68k+ | 行业标准内存数据库，生态最全 | **默认选择**：单机 SQLite 升级到 Redis，TTL + LRU 现成 |
| [dragonflydb/dragonfly](https://github.com/dragonflydb/dragonfly) | 30.2k | Redis/Memcached 替代品，多线程无共享，宣称吞吐数倍于 Redis | 缓存量大时替代 Redis（协议兼容，客户端可无缝切换） |
| [redis/redis-py](https://github.com/redis/redis-py) | — | Redis 官方 Python 客户端，asyncio 支持 | 自家技术栈接入用 |

### 3.2 落地要点

- **键设计**：`{video_id}` → `{text, source_line, ts}`；账号字段 → `{sec_uid}:profile`（见 [[达人主页数据爬取]]）
- **淘汰策略**：TTL（默认 7 天）+ LRU（内存上限），热门视频常驻
- **预取**：对榜单/热点视频后台主动预热，让"第一次请求"也命中缓存
- **降级**：Redis 挂了自动降级到 SQLite 落库，不阻塞主流程

💡 **<span style="color:#2980b9">缓存是"响应速度引擎"里性价比最高的一块：几乎零开发成本，却能把热门命中请求从几十秒压到 <1s。务必实现，且要做到"命中即返回、不触发任何采集线路"。</span>**

## 4. 组件2：高速 ASR 常驻服务（GPU）

> 无字幕视频必须走"下载→识别"。当前自家是 CPU int8 small 模型、进程内一次性调用（[[0811-开发日志]]），慢且每次冷启动。改为**GPU 常驻推理服务**（一次加载、反复推理），识别耗时可从分钟级压到亚秒级~秒级。

### 4.1 候选项目

| 项目 | ⭐ | 说明 | 选型建议 |
|------|:--:|------|---------|
| [fedirz/faster-whisper-server（speaches）](https://github.com/fedirz/faster-whisper-server) | — | faster-whisper 封装，**OpenAI API 兼容**、GPU/CPU 双 Docker、**SSE 流式**、WebSocket 实时、动态模型加载/卸载 | **首选**：现成常驻服务，接上就能用 |
| [nirnaim/faster-whisper-server](https://github.com/nirnaim/faster-whisper-server) | — | 生产级微服务：**Celery+Redis 后台队列**、模型池多副本、SSE+Webhook | 高吞吐批量转写 |
| [hwdsl2/whisper-server](https://github.com/hwdsl2/docker-whisper) | — | Docker 常驻，OpenAI API 兼容，`docker-compose.cuda.yml` 一键 NVIDIA GPU | 部署最省事 |
| [ggml-org/whisper.cpp](https://github.com/ggml-org/whisper.cpp) | 51k | 纯 C/C++ 极速推理，本地实时，多硬件加速（CUDA/Vulkan/OpenVINO） | 端侧/CPU 提速 |
| [modelscope/FunASR](https://github.com/modelscope/FunASR) | 15.2k | 阿里达摩院，Paraformer **GPU 上 120x 实时**，中文最强（含 VAD/标点/说话人分离） | **中文口播首选** |
| [FunAudioLLM/SenseVoice](https://github.com/FunAudioLLM/SenseVoice) | 9.1k | SenseVoiceSmall **10 秒音频约 70ms**，400k+ 小时训练，中/粤/英/日/韩 | 中文口播备选（与 Faster-Whisper 对比） |

### 4.2 落地要点

- **常驻化**：Docker 起 `speaches` 或 FunASR 服务，模型常驻显存，避免每次冷启动（自家有 RTX 5060 GPU）
- **接口统一**：暴露 OpenAI 兼容 `/v1/audio/transcriptions`，前端/采集层只认这一个接口
- **中文优先**：口播稿是中文场景，`FunASR/Paraformer` 或 `SenseVoiceSmall` 明显优于通用 Whisper
- **回退链**：GPU 服务挂了 → 降级到本地 CPU faster-whisper → 再不济走 [[3条线路设计]] 的字幕直取

🔥 **<span style="color:#e74c3c">GPU 常驻是把识别从"分钟级"变"亚秒级"的唯一杠杆。不上 GPU，无字幕视频永远慢；上了 GPU 并常驻，一次模型加载换来上千次秒级推理。</span>**

🔶 **<span style="color:#e67e22">中文口播别死磕 Whisper：FunASR/Paraformer 在中文上又快又准（120x 实时），SenseVoiceSmall 处理 10 秒音频约 70ms——这两个是中文场景的最优解，务必与 faster-whisper 一起纳入评测。</span>**

## 5. 组件3：异步任务队列（Celery / ARQ / RQ）

> 批量视频处理如果串行排队，队列长就是灾难。任务队列负责"来了就入队、多 worker 并发消费、失败重试"。社区实测（20 万任务/10 worker）：**Celery 完成 11.68s、ARQ 35.37s、RQ 51.05s**。

| 项目 | ⭐ | 说明 | 适用场景 |
|------|:--:|------|---------|
| [celery/celery](https://github.com/celery/celery) | 26k+ | 功能最全：路由/优先级/工作流/Flower 监控，批量吞吐最高 | **ASR/下载等 CPU/GPU 密集任务**（进程池） |
| [samuelcolvin/arq](https://github.com/samuelcolvin/arq) | — | 为 asyncio 从零构建，原生 async，内置 cron，基于 Redis Streams | **FastAPI/采集等 I/O 密集任务** |
| [rq/rq](https://github.com/rq/rq) | — | 极简，一个下午能上手，仅 Redis | 轻量任务、快速起步 |

🔶 **<span style="color:#e67e22">选型建议：不追求单队列，按任务类型分流——采集/下载（I/O 密集）走 ARQ，ASR 转写（算力密集）走 Celery 进程池，监控用 Flower。这样各自跑在擅长的模型上。</span>**

## 6. 组件4：API 服务化与流式响应

> 轻抖是"链接进来 → 结果出去"的服务，自家要让 Agent（Claude/Codex）或前端也能这样调。用 FastAPI 把整个链路包成一个 HTTP 服务，并支持**流式返回**（首字到达即推，不等全量完成）。

### 6.1 候选项目

| 项目 | ⭐ | 说明 |
|------|:--:|------|
| [fastapi/fastapi](https://github.com/fastapi/fastapi) | 82k+ | 现代高性能 Python Web 框架，自动生成 OpenAPI 文档，asyncio 原生 |
| [encode/httpx](https://github.com/encode/httpx) | 15k+ | 异步 HTTP 客户端，采集层并发请求、连接池复用 |
| [tiangolo/sqlmodel](https://github.com/tiangolo/sqlmodel) | 15k+ | SQLAlchemy+Pydantic，缓存/结果落库的 ORM 层 |

### 6.2 落地要点

- **统一入口**：`POST /transcript {share_url}` → 内部走 [[3条线路设计]] 调度器 → 返回 `{video_id, text, source_line, latency_ms}`
- **OpenAI 兼容**：识别端点暴露 `/v1/audio/transcriptions`，与 speaches/FunASR 服务一致，前端一套协议
- **流式返回**：长视频走 SSE，先推"已命中字幕"再推"识别结果"，用户侧首字更快
- **缓存头**：`ETag`/`Cache-Control`，热门结果让网关层也能缓存

💡 **<span style="color:#2980b9">服务化是"让速度被感知"的关键：即使内部 3 秒，如果 API 设计得让 Agent 等完整 JSON 才用，体验还是 3 秒；加上流式/渐进返回，体感可压到亚秒。响应速度 = 计算速度 × 返回方式。</span>**

## 8. 与现有体系的组件衔接

> 四个组件不是孤岛，而是串进已有链路的一条"速度流水线"：

```
  分享链接 ──► [①采集] 线路选择三线路 ──► 查缓存(组件1)
      │                                            │
      │             命中(<1s) ◄────────────────────┘
      ▼
  [字幕直取] 有字幕 ──► 写缓存(组件1) ──► 返回(组件4 API)
      │
      ▼ 无字幕
  [②识别] ASR常驻服务(组件2, GPU) ──► 写缓存 ──► 返回
      │
  队列(组件3) 并发消费 批量请求
      ▼
  [③监控] Prometheus/Grafana(组件5) 全程可观测
```

- **组件1 缓存**：是 [[3条线路设计]] 5.5 缓存层的落地存储（Redis/Dragonfly）
- **组件2 ASR**：是 [[轻抖相关的项目工具]] 第 3 类"本地 ASR 转写"的"常驻服务化"升级
- **组件3 队列**：让 [[3条线路设计]] 的调度器 + [[达人主页数据爬取]] 的采样任务并发跑
- **组件4 API**：把上面所有能力包成一个"链接→口播稿"服务，Agent/前端都能调

🔥 **<span style="color:#e74c3c">一句话串起来：输入链接 → 先查缓存（组件1，<1s）→ 有字幕就字幕直取、无字幕就丢给 GPU 常驻 ASR（组件2）→ 结果写缓存 → 通过 API 流式返回（组件4），全部排队走队列（组件3）并全程监控（组件5）。这就是"轻抖式速度"的完整拼图。</span>**

## 9. 给 Codex 的开发任务清单

### 9.1 模块拆分

1. **`speed/cache.py`** — 缓存层落地：Redis 客户端封装 + `video_id` 键 + TTL/LRU + SQLite 降级（对接 [[3条线路设计]] 调度器）
2. **`speed/asr_service.py`** — ASR 常驻服务客户端：统一 OpenAI 兼容接口，GPU（speaches/FunASR）→ CPU（faster-whisper）→ 字幕直取 三级回退
3. **`speed/queue.py`** — 任务队列接入：采集/下载走 ARQ，ASR 转写走 Celery 进程池 + Flower 监控
4. **`speed/api.py`** — FastAPI 服务：`POST /transcript`、`POST /v1/audio/transcriptions`、SSE 流式返回、缓存头
5. **`speed/metrics.py`** — Prometheus 指标：四段延迟直方图、缓存命中率、队列积压、失败率
6. **`main.py`** — 入口：FastAPI 应用装配，启动时加载缓存 + ASR 服务 + 队列 worker

### 9.2 实施顺序

1. **先做组件1 缓存 + 组件4 最小 API**（把现有 [[3条线路设计]] 最小闭环包成服务，热门命中即秒回）
2. **再加组件2 ASR 常驻**（Docker 起 speaches 或 FunASR，接 RTX 5060 GPU，替换进程内 CPU 调用）
3. **再接组件3 队列**（把采集/转写任务改入队并发，摆脱串行）
4. **最后补组件5 监控**（延迟/命中率/积压上大盘）

🔶 **<span style="color:#e67e22">优先交付"缓存 + API + GPU-ASR"三件套——这三件直接决定单条响应速度（3~10s）；队列和监控是批量与可观测性的增强，放后。</span>**

### 9.3 验收标准

- ✅ 同一 `video_id` 第二次请求命中缓存 → **<1s 返回，零网络调用**
- ✅ 无字幕视频走 GPU 常驻 ASR → 60s 音频识别耗时 **≤2s**
- ✅ 批量 100 条链接入队 → 队列并发消费，平均单条 ≤10s，无串行积压
- ✅ `POST /transcript` 返回含 `{video_id, text, source_line, latency_ms}`，SSE 流式首字 <1s
- ✅ 监控大盘显示四段延迟 P50/P95、缓存命中率、失败率
- ✅ GPU 服务/缓存/队列任一挂掉 → 自动降级，不阻塞主流程

🔥 **<span style="color:#e74c3c">最终验收：拿一条"有字幕的热门视频"测出 <1s，一条"无字幕视频"测出 ≤5s——达到轻抖的量级。</span>**

## 10. 风险与注意事项

- **算力成本**：GPU 常驻 ASR 需要显存常驻模型（RTX 5060 够跑 medium/large-v3-turbo 或 Paraformer），注意显存与功耗
- **依赖隔离**：ASR 服务（faster-whisper/FunASR）、缓存（Redis）、队列（Celery）依赖差异大，务必各自 Docker/venv 隔离（吸取 pyvideotrans Python 3.10 教训，见 [[0811-开发日志]]）
- **缓存一致性**：视频被删/字幕变更后缓存可能过期，TTL 别设太长，热门视频做主动刷新
- **接口兼容**：OpenAI 兼容端点是"双刃剑"——好接入但会锁死协议，升级模型时保持返回结构稳定
- **合规**：字幕直取仍属平台数据抓取，控制频率、接口层优先（与 [[3条线路设计]] 第8节一致）
- **不要过度设计**：单机场景 SQLite+进程内并发可能已够，先跑通"缓存+GPU+API"三件套，再决定是否上队列和 Redis 集群
