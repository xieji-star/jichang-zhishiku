# 🧭 线路选择：三线路采集通道 + 风控对抗 + 自动切换

> [!summary] 概要
> 本文档为数据采集/下载系统设计**三条互为备份的线路**，任一条被风控时立即切换下一条，并给每条线路搭配对应的风控对抗开源组件。核心设计依据：**轻抖能避开人机验证，是因为它走"服务端接口层"（只校验签名/频控），而自家 MediaCrawler 走"页面层"（专门检测模拟浏览器）**。因此三条线路按"接口层最优 → 接口层降级 → 页面层兜底"排成梯度：**线路1 字幕直取（最快）→ 线路2 接口级下载（接口层）→ 线路3 浏览器采集（页面层兜底）**，再由统一调度器做健康检测、熔断、冷却与自动切换。文末给出可直接交给 Codex 落地的开发任务清单。

## 1. 设计目标与总体架构

### 1.1 要解决的问题

🔥 **<span style="color:#e74c3c">核心痛点：自家 MediaCrawler 批量采集抖音时总是触发人机验证（Argus/滑块/行为验证），批量抓取极易失败（实证 5/12 账号失败）。原因见 [[轻抖VS我们的项目]]：自家走"页面/客户端层"（第①道防线），轻抖走"服务端接口层"（第②道防线）。</span>**

- **目标**：让"单条失败"不影响整体——一条线路被风控，立即自动切换另一条，保持采集/下载不中断
- **设计原则**：接口层优先（越接近轻抖越稳）、页面层兜底（能力最全但最容易触发风控）、统一调度（健康检测 + 熔断 + 冷却）
- **附加收益**：通过"字幕直取 + 缓存"顺带把体验拉向轻抖的十几秒

### 1.2 总体架构

```
                    ┌─────────────────────────────────────────┐
                    │         线路调度器（Router）              │
                    │  统一接口 fetch(link) → TranscriptResult  │
                    │  健康检测 / 熔断 / 冷却 / 优先级 / 缓存     │
                    └──────┬────────────┬────────────┬────────┘
                           ▼            ▼            ▼
                    ┌──────────┐  ┌──────────┐  ┌──────────┐
                    │  线路1    │  │  线路2    │  │  线路3    │
                    │ 字幕直取  │→ │ 接口级下载 │→ │ 浏览器采集 │
                    │ (最快)    │  │ (接口层)  │  │ (页面兜底) │
                    └──────────┘  └──────────┘  └──────────┘
```

### 1.3 三条线路总览

| 线路 | 名称 | 采集方式 | 风控等级 | 出稿速度 | 触发条件 |
|:--:|------|---------|:--:|:--:|------|
| ① | **字幕直取通道** | 调抖音 AI 字幕接口抄现成字幕 | 极低（接口层） | **~3 秒** | 视频有 AI 字幕 |
| ② | **接口级下载采集** | 第三方解析接口批量解析/下载无水印视频 | 低（接口层） | 秒级~分钟级 | 线路①无字幕 |
| ③ | **浏览器自动化采集** | MediaCrawler + yt-dlp（页面层） | 高（易触发人机验证） | 分钟级 | ①②都被风控 / 需主页批量 |

💡 **<span style="color:#2980b9">切换优先级固定为 ①→②→③：默认从最稳最快的线路开始，越靠后的线路越"重"，只作为兜底。</span>**

## 2. 线路1：字幕直取通道（最快最优，对标轻抖第⑤步）

> 直接调抖音**官方 AI 字幕接口**，把平台已生成的字幕"抄"回来，去时间轴就是口播稿。**零下载、零识别、零算力**——这正是轻抖十几秒出稿的核心（见 [[轻抖-如何快速实现口播稿件的抓取]] 第⑤步）。

### 2.1 采集方案

| 候选开源项目 | ⭐ | 说明 | 选型建议 |
|------------|:--:|------|---------|
| [yzfly/douyin-mcp-server](https://github.com/yzfly/douyin-mcp-server) | 1.2k | 提取抖音无水印链接 + 视频文案，MCP/Claude Skill | 首选：已封装成 MCP，可直接接入 Agent |
| [JNHFlow21/social-media-toolkit](https://github.com/JNHFlow21/social-media-toolkit) | 21 | Douyin SDK/CLI/MCP：提取元数据、文本、**带时间轴字幕**、评论 | 备选：明确输出带时间轴字幕，对应轻抖剥 `start` 字段的做法 |

### 2.2 风控对抗配置

- **签名合法化**：按项目文档维护接口签名/token，避免被判定为非法调用
- **低并发**：单条链接逐个处理，不批量并发打接口
- **缓存复用**：用 `video_id` 做唯一键落库，命中缓存直接返回（见第 5.5 节），热门视频对抖音几乎零请求
- **去时间轴**：拿到 `[{start, text}]` 后剥掉 `start`，拼接 `text` 即口播稿

### 2.3 适用场景与限制

- ✅ **适用**：真人出镜、有 AI 字幕的口播视频（爆款主流）
- ⚠️ **限制**：纯 BGM、纯画外音剪辑、无字幕搬运视频**无法使用**，此时切线路2
- 📌 **<span style="color:#e67e22">该线路同时解决了文章 7.1"第一优先：字幕直取"的改造目标，是性价比最高的一条。</span>**

## 3. 线路2：接口级下载采集（接口层，避开页面风控）

> 用第三方开源项目维护好的**接口级解析/下载服务**取数，不走浏览器、不模拟登录态，风控阈值比页面层高得多——是对标轻抖"接口层"思路的降级方案（对应文章 7.5"用专用解析接口替代维护账号登录态"）。

### 3.1 采集方案

| 候选开源项目 | ⭐ | 说明 | 选型建议 |
|------------|:--:|------|---------|
| [Evil0ctal/Douyin_TikTok_Download_API](https://github.com/Evil0ctal/Douyin_TikTok_Download_API) | 19.3k | 高性能异步抖音/快手/TikTok/B站数据爬取，API 调用 + 在线批量解析下载 | 首选：接口层、高星、能力全 |
| [JoeanAmier/TikTokDownloader](https://github.com/JoeanAmier/TikTokDownloader) | 15.4k | 抖音/TikTok 全量数据：发布/喜欢/收藏/视频/图集/直播/评论/账号/搜索/热榜 | 备选：采集面最全 |
| [Johnserf-Seed/TikTokDownload](https://github.com/Johnserf-Seed/TikTokDownload) | 8.8k | 抖音去水印批量下载用户主页作品 | 备选：轻量下载 |
| [5ime/video_spider](https://github.com/5ime/video_spider) | 3.0k | 短视频去水印，支持几十个平台 | 兜底：单链接解析 |

### 3.2 风控对抗配置

- **HTTP 指纹模拟**：[lexiforest/curl_cffi](https://github.com/lexiforest/curl_cffi)（6.3k⭐）——模拟浏览器 TLS/JA3/HTTP2 指纹，让请求"长得像"正常浏览器
- **IP 轮换**：[jhao104/proxy_pool](https://github.com/jhao104/proxy_pool)（23.6k⭐）——维护代理池，规避"同 IP 高频触发"
- **频控退避**：指数退避 + 随机延迟（如失败后 sleep 2s/4s/8s…），控制请求速率

### 3.3 适用场景与限制

- ✅ **适用**：线路1无字幕时的口播稿提取、批量下载、需要视频文件本身
- ⚠️ **限制**：仍是第三方接口，可能被接口频控；需要维护接口签名/参数
- 📌 **<span style="color:#e67e22">若接口返回"签名失效/频控"等异常，累计失败到阈值即熔断并切线路3。</span>**

## 5. 线路调度器：健康检测 / 熔断 / 冷却 / 切换

> 这是整个系统的"大脑"——保证一条线路被风控时**自动、无缝**切到下一条，并让被风控的线路冷却后自动恢复。

### 5.1 统一接口定义

```python
class TranscriptResult:
    video_id: str          # 抖音视频唯一 ID
    text: str              # 口播稿 / 文案
    source_line: str       # "line1" / "line2" / "line3"
    cached: bool           # 是否命中缓存
    latency_ms: int        # 耗时

class BaseLine(ABC):
    name: str
    @abstractmethod
    async def fetch(self, share_url: str) -> TranscriptResult:
        """输入分享链接，输出口播稿；失败抛 LineError"""
    @abstractmethod
    def health_check(self) -> dict:
        """返回线路健康度：success_rate / last_error / blocked"""
```

### 5.2 健康度指标

- **成功率**：近 N 次（如 20 次）请求成功比例
- **异常信号**：HTTP 状态码、验证码出现、接口报"签名失效/频控"、`httpx.ConnectError`、超时
- **延迟**：平均响应延迟，异常飙升记为降级信号
- **IP 标记**：代理池反馈该 IP 被墙则剔除

### 5.3 熔断与冷却

| 机制 | 规则 | 说明 |
|------|------|------|
| **熔断** | 连续失败 ≥ 5 次，或成功率 < 50% | 立即熔断该线路，切下一条 |
| **冷却池** | 熔断线路进入冷却（默认 10 分钟） | 冷却结束后自动重试，恢复则重新可用 |
| **半开探测** | 冷却结束后先放 1~2 条测试请求 | 成功则摘除熔断，失败则延长冷却 |
| **全线路熔断** | 三条都熔断 | 停止任务，飞书告警，人工介入 |

### 5.4 切换流程

1. 收到 `share_url` → 先查缓存（命中直接返回，不触发任何线路）
2. 按优先级 ①→②→③ 依次尝试：调 `fetch()`，成功即返回并写缓存
3. 某线路抛异常 → 记录失败、累计熔断计数、**立即**切下一条
4. 冷却池中的线路定期探测，恢复后回到可用队列

💡 **<span style="color:#e67e22">切换是"即时"的：一条线路异常不会阻塞整条请求，失败计数与切线路在同一毫秒内完成，用户侧无感知。</span>**

### 5.5 缓存层

- **键**：`video_id`（由分享链接解析得到）
- **存储**：Redis（生产）或 SQLite（单机，参考 [[mediacrawler_to_pyvideotrans.py]] 现有落库习惯）
- **写**：任何线路成功出稿后写入 `{video_id: text}` + 时间戳
- **读**：调度器入口先查缓存，命中则零网络请求——**这是轻抖"热门秒回"的隐形主力，务必实现**

💡 **<span style="color:#2980b9">缓存让"首次失败只发生一次"：一条视频哪怕第一次某线路失败，切换线路成功后缓存就绪，之后任何人查都秒回。</span>**

## 7. 给 Codex 的开发任务清单

### 7.1 模块拆分

1. **`lines/base.py`** — 抽象基类 `BaseLine` + `TranscriptResult` + `LineError`
2. **`lines/line1_subtitle.py`** — 字幕直取适配器（基于 douyin-mcp-server / social-media-toolkit）
3. **`lines/line2_api_download.py`** — 接口级下载适配器（基于 Douyin_TikTok_Download_API / TikTokDownloader）
4. **`lines/line3_browser.py`** — 浏览器采集适配器（MediaCrawler + CloakBrowser/patchright + proxy_pool）
5. **`router/scheduler.py`** — 调度器：优先级、熔断、冷却、半开探测
6. **`router/health.py`** — 健康度指标采集与统计
7. **`cache/cache.py`** — `video_id` 缓存层（Redis/SQLite）
8. **`main.py`** — 入口：接收分享链接 → 走调度器 → 返回口播稿
9. **`alert/wecom.py`** — 全线路熔断时企业微信/飞书告警

### 7.2 实施顺序

1. **先做线路2 + 缓存**（接口层最稳、收益最大）：`line2_api_download` + `cache` + 最小 `scheduler`
2. **再加线路1**（字幕直取）：`line1_subtitle`，优先从简单入口跑通
3. **最后接线路3**（浏览器兜底）：MediaCrawler + 指纹伪装 + 代理池 + 验证码
4. **补齐告警与监控**：熔断日志、切换记录、失败率统计

### 7.3 验收标准

- ✅ 单条线路故障 → 自动切换，**全程无人工干预**
- ✅ 被风控线路冷却后自动恢复，恢复后重新参与优先级排序
- ✅ 同一 `video_id` 重复请求 → 命中缓存，**零网络调用**
- ✅ 全线路熔断 → 触发告警，任务安全停止（不留下半截状态）
- ✅ 每条线路独立依赖环境，**互不污染**（吸取 pyvideotrans 需 Python 3.10 的教训，见 [[0811-开发日志]]）

🔥 **<span style="color:#e74c3c">优先交付"线路2 + 缓存 + 调度"的最小闭环——先让"被风控能自动切换"跑起来，再逐步叠线路1和线路3。</span>**

## 8. 风险与注意事项

- **合规风险**：批量抓取第三方平台数据可能违反平台服务条款，建议控制频率、仅采集授权/公开内容，接口方案优先（接口层对平台压力更小）
- **风控升级**：抖音风控随时变化，接口签名/解析规则可能失效，需要把"失效 → 切线路 → 告警"做成闭环，而不是硬编码
- **依赖隔离**：三条线路依赖差异大（接口库 / 浏览器 / 代理池），务必各自虚拟环境，避免版本冲突
- **账号安全**：线路3 涉及登录态，账号被封风险最高，建议用低权重账号 + 降低频率 + 及时告警
- **不要硬扛**：任何对抗组件都无法保证 100% 不被检测，设计上永远以"切换线路"为第一手段，对抗组件只是辅助
