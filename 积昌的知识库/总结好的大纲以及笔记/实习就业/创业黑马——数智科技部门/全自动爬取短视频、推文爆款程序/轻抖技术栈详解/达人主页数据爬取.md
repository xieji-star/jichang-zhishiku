## 1. 设计目标与总体架构

### 1.1 要解决的问题

🔥 **<span style="color:#e74c3c">核心痛点：MediaCrawler 采集达人主页，落库的只有"作品列表 + 昵称/头像"等基础字段；而粉丝量、获赞总数、作品总数、关注数、签名这些"账号级统计字段"缺失。下游爆款分析（[[矩阵号爆款数据分析与标准定义]]）需要这些字段做达人排序/筛选，但没有数据源。</span>**

- **目标**：输入达人主页链接 / 抖音号，一次性返回完整主页画像：`粉丝量 / 近1小时粉丝增长 / 总点赞数 / 可见作品总数 / 总关注数 / 主页签名`（+ 补充字段）
- **设计原则**：接口层优先（无登录、风控低、够快），浏览器层兜底（字段最全但需 Cookie），"近1小时粉丝增长"独立成模块（官方不提供）
- **附加收益**：把账号字段做成**时间序列表**后，不仅能看当前值，还能算"近24小时/近7天"增长趋势

### 1.2 总体架构

```
              ┌──────────────────────────────────────────┐
              │       达人主页数据采集层                  │
              │   统一接口 fetch_profile(sec_uid)         │
              │   缓存 → 接口层 → 浏览器层 → 粉丝增长计算  │
              └───────┬──────────────────┬──────────────┘
                      ▼                  ▼
            ┌────────────────┐  ┌───────────────────┐
            │  路线A 接口层   │  │  路线B 浏览器/登录  │
            │ 无登录/API 直取  │  │  逆向/自动化      │
            │ 风控低·字段部分  │  │  风控高·字段最全   │
            └────────────────┘  └───────────────────┘
                      │                  │
                      ▼                  ▼
            ┌──────────────────────────────────────────┐
            │   粉丝增长计算模块（Delta 采样差值）       │
            │   user_stats 时间序列表 → 近1小时/近24h     │
            └──────────────────────────────────────────┘
```

### 1.3 两条路线总览

| 路线 | 名称 | 代表项目 | 登录 | 风控 | 字段覆盖 |
|:--:|------|---------|:--:|:--:|------|
| A | **接口层** | redfox douyin-works-crawler / Evil0ctal API | 无需/部分 | 低 | 粉丝/获赞/作品数（部分缺关注/签名） |
| B | **浏览器/登录层** | TikTokDownloader / Douyin_Spider / mabotao8715 | 需 Cookie | 高 | 全字段 + 粉丝/关注列表 |

💡 **<span style="color:#2980b9">为什么两条路线都要？——接口层省事但字段可能不全（如 redfox 不返回关注数/签名），浏览器层字段全但有登录与风控成本。按"字段完整性 × 风控成本"权衡，接口层做主力、浏览器层做兜底，与 [[3条线路设计]] 的梯度思想一致。</span>**

## 2. 目标字段与抖音接口字段映射

> 抖音网页版用户详情接口（`.../aweme/v1/web/user/profile/other/`，需带 `a_bogus`/`msToken` 签名）返回的账号字段，本文档要采集的目标字段与之一一对应：

| 目标字段 | 抖音接口字段 | 说明 | 数据来源 |
|---------|------------|------|:--:|
| **目前粉丝量** | `follower_count` | 当前粉丝总数 | 接口直取 |
| **近1小时粉丝增长** | ❌ 无官方字段 | 需采样差值或第三方 | 计算/第三方 |
| **总点赞数** | `digg_count` | 获赞总数 | 接口直取 |
| **可见作品总数** | `aweme_count` | 可见作品数（部分接口另有 `total`） | 接口直取 |
| **总关注数** | `following_count` | 关注数 | 接口直取 |
| **主页签名** | `signature` | 个人简介 | 接口直取 |
| 昵称 | `nickname` | 达人昵称 | 接口直取 |
| 抖音号 | `unique_id` / `short_id` | 搜索用 ID | 接口直取 |
| 头像 | `avatar_uri` | 头像地址 | 接口直取 |
| IP 归属地 | `ip_location` | 部分接口返回 | 接口直取 |
| 认证信息 | `custom_verify` | 黄 V/蓝 V 等 | 接口直取 |

🔶 **<span style="color:#e67e22">注意 `aweme_count` 是"可见作品数"而非"历史全部作品数"——私密/下架/审核中的作品不计入，文档与统计口径必须标注清楚，否则下游分析会误读。</span>**

## 4. 粉丝增长的三种实现方案

> "近1小时粉丝增长"**没有官方接口字段**，只能通过以下三种方式之一获得。默认推荐 Delta 采样法。

### 4.1 Delta 采样法（推荐自研）

- **原理**：定时抓取 `follower_count`，存入时间序列表，`近1小时增长 = 当前值 − 1小时前的值`
- **实现**：调度器每 N 分钟抓一次 `user_stats` 落库，查询时算滑动窗口差值
- **参照**：`systemt1st/douyin` 的"轮询 + 记录"模式
- ✅ 优点：免费、可控、与采集同链路、可扩展出"近24h/近7天"
- ❌ 缺点：只能反映采样时刻的瞬时值，采样间隔内的波动被平均

### 4.2 第三方数据平台（红狐 / 蝉妈妈 / 抖查查）

- **红狐数据**：redfox douyin-works-crawler 的底层数据源，有指数评分
- **蝉妈妈 / 抖查查**：有粉丝增长曲线 API，付费
- ✅ 优点：有历史曲线、数据权威
- ❌ 缺点：付费、第三方依赖、合规授权需评估

### 4.3 增长排行思路（douyin-rise-ranking）

- 不做单账号"近1小时绝对值"，而是**跨账号对比增量**：同一时段内各达人粉丝增量排序
- 适用场景：找黑马账号、竞品监测（与 [[矩阵号爆款数据分析与标准定义]] 的达人排序需求对口）
- 若目标是单账号"近1小时增长"数值，Delta 法更直接

💡 **<span style="color:#2980b9">落地建议：默认用 Delta 采样法，采样间隔做成可配置（1分钟~1小时）。间隔设为 1 小时即可直接得出"近1小时增长"，设为更短间隔则能同时支持"近24h/近7天"趋势。</span>**

## 5. 与 MediaCrawler 的结合方案

> 现状：MediaCrawler 抖音模式采集达人主页 → 作品入库，账号表只有 `nickname/avatar` 等基础字段。改造方向：

1. **账号字段落库**：进入达人主页时调用户详情接口，把 `follower_count/digg_count/aweme_count/following_count/signature` 一并写入 `users` 表
2. **时间序列表**：新建 `user_stats(sec_uid, ts, follower_count, digg_count, following_count, aweme_count)`，支撑粉丝增长计算与趋势
3. **复用 [[3条线路设计]] 三线路调度**：账号字段也走"缓存 → 接口层 → 浏览器层"梯度，接口层（线路2）优先、浏览器层（线路3）兜底
4. **缓存策略**：粉丝量是慢变量，账号字段按 **10~30 分钟**缓存，命中即零请求

🔥 **<span style="color:#e74c3c">不要为"实时粉丝量"高频打接口——粉丝量变化很慢，10 分钟采样完全够用，高频只会白白触发风控。近1小时增长用差值算即可，不需要实时值。</span>**

## 6. 风控对抗配置

> 复用 [[3条线路设计]] 第6节组件（curl_cffi / proxy_pool / 指纹伪装），再针对账号字段接口做三条专门对策：

| 对策 | 做法 | 对应组件 |
|------|------|---------|
| **降频** | 账号字段 10~30 分钟缓存 + 采样间隔可配置 | 自研缓存层 |
| **轻量请求** | 账号字段走 GET 轻量接口，不启动浏览器 | curl_cffi（模拟 TLS/JA3 指纹） |
| **IP 轮换** | 多账号/多 IP 分散请求，避免同 IP 高频 | [jhao104/proxy_pool](https://github.com/jhao104/proxy_pool) |
| **签名维护** | a_bogus/msToken 过期即换线路，不硬编码 | [[3条线路设计]] 熔断/冷却机制 |
| **浏览器兜底** | 接口层失效切浏览器层，再配指纹伪装 | CloakBrowser / patchright |

💡 **<span style="color:#2980b9">账号字段是"慢变量"，风控对抗的核心是"降频 + 缓存"而非"高频硬扛"——把采样间隔调大、让请求少到不触发风控，比任何对抗组件都有效。</span>**

## 7. 给 Codex 的开发任务清单

### 7.1 模块拆分

1. **`profile/fields.py`** — 目标字段定义 + 抖音接口字段映射 + 数据口径说明（`aweme_count`=可见作品数）
2. **`profile/line_api.py`** — 接口层适配器（redfox douyin-works-crawler / Evil0ctal API / 自研用户详情接口）
3. **`profile/line_browser.py`** — 浏览器层适配器（TikTokDownloader / Douyin_Spider / MediaCrawler 增强）
4. **`profile/delta.py`** — 粉丝增长 Delta 计算（近1小时/近24h/近7天）
5. **`profile/store.py`** — `users` 表 + `user_stats` 时间序列表落库
6. **`router/profile_router.py`** — 账号字段调度：缓存 → 接口层 → 浏览器层 → 熔断切换
7. **`main.py`** — 入口：输入达人主页链接/抖音号 → 输出完整主页画像

### 7.2 实施顺序

1. **先做最小闭环**：`fields` + `line_api` + `delta` + `store`（字段映射 + 接口层 + 粉丝增长 + 落库）
2. **再加缓存与调度**：`profile_router`（10~30 分钟缓存 + 熔断切换）
3. **再接浏览器层兜底**：`line_browser`（字段不全/接口失效时启用）
4. **补齐监控告警**：采样日志、切换记录、失败率统计

🔶 **<span style="color:#e67e22">优先交付"接口层 + Delta + 落库"最小闭环——先用 redfox 或自研接口把账号字段跑通，再逐步叠缓存、调度与浏览器层。</span>**

### 7.3 验收标准

- ✅ 输入抖音号/主页链接 → 返回 粉丝量 / 获赞 / 作品数 / 关注数 / 签名（接口层可覆盖的字段）
- ✅ 近1小时粉丝增长 = 时间序列表两次采样差值，输出含采样时间与误差说明
- ✅ 账号字段 10 分钟缓存命中 → 零网络请求
- ✅ 接口层失败 → 自动切浏览器层，全程无人工干预
- ✅ `user_stats` 可查历史趋势（近24h/近7天增量）
- ✅ 各适配器独立依赖环境，互不污染（吸取 pyvideotrans Python 3.10 教训，见 [[0811-开发日志]]）

🔥 **<span style="color:#e74c3c">最终验收：一条命令拿到"达人主页完整画像"——不只是作品列表，而是含粉丝量、增长、点赞、作品数、关注、签名的结构化数据。</span>**

## 8. 风险与注意事项

- **合规风险**：粉丝增长监测属于对平台的监控行为，采集第三方账号数据可能违反平台条款，建议控制采样频率、仅用于授权/公开账号分析、接口方案优先（接口层对平台压力更小）
- **接口失效**：抖音 `a_bogus`/`msToken` 签名规则随时变化，接口层必须做成可替换（失效→切线路→告警闭环），禁止硬编码签名
- **数据口径**：`aweme_count` 是可见作品数；粉丝增长受"平台清理僵尸粉/账号限流"影响，差值可能为负或失真，需在文档中说明
- **依赖隔离**：接口层 / 浏览器层依赖差异大，务必各自虚拟环境，避免版本冲突
- **账号安全**：浏览器层涉及 Cookie 登录态，账号被封风险最高，用低权重账号 + 降低采样频率 + 及时告警
- **不要硬扛**：账号字段是慢变量，采不到就降频缓存，不必追求"实时"，对抗组件永远只是辅助
