## 三、做得好的地方（亮点）

1. **隔离工程化**〔多源证实〕：三个核心第三方全部"子进程 + 独立 venv/登录态/采集库 + 超时/暂停/取消/进程树终止"，故障隔离与升级边界清晰（mediacrawler.py:490-537、transcription.py:400-468）；
2. **数据层严谨**：同步幂等闭环（云端 (video_id, captured_at) 唯一索引 + DO UPDATE 重放、imported 数核对后才 mark_synced）、备份带 sha256 manifest 与恢复回滚、转录租约防旧尝试覆盖、WAL + busy_timeout=15000；
3. **测试体系是项目最强环节**：250 用例、247 个离线可跑，含 SSRF/Fake-IP 安全测试、真实 CLI 门禁、竞态与 TTL 边界、故障注入回滚；
4. **安全基线扎实**：SSRF 域名/IP 白名单成体系、日志凭据脱敏（含 URL 参数）、验证码自动求解被硬禁用（人工处理合规红线）、密钥集中 .env.local 且 gitignore 正确、CORS 与端口全回环绑定；
5. **转录临时文件三重防线**："先落库后删除"严格闭环、job 目录所有权签名、TTL + 心跳 + 每小时 janitor；
6. **文档体系罕见地"诚实"**：实测数据（5/12 失败、66.67% 转录率、误报分析）如实记录、合规风险章节坦诚披露、README 对未完成项明确标注"下一阶段"。

## 四、严重问题（7 项）

### 🔴 1. MediaCrawler「非商业学习许可」与默认商用启用正面冲突〔多源交叉证实〕

- 证据：MediaCrawler/LICENSE（NON-COMMERCIAL LEARNING LICENSE 1.1，明确"不得用于商业用途""不得大规模爬取"）；start.ps1:95 默认 COLLECTION_PROVIDER=mediacrawler；collection.py:100-137 mediacrawler 分支直接创建采集器；
- 影响：项目服务公司 12 个矩阵号运营，属商业场景；默认即启用意味着**商用侵权风险当前处于"开机即发生"状态**；抖音平台条款风险同向叠加；
- 修复：三选一（文档 7.1 节已给路径）——① 联系 NanmiCoder 取得书面商用授权；② 切换接口级采集替代（Evil0ctal API 已在 route2 下载链路接入，可扩展为采集源）；③ 借鉴思路自研（不复制代码）。**在授权落地前，建议将默认 provider 改回 demo 或显式加"商用授权确认"开关。**

### 🔴 2. 风控"三件套"接线空转：熔断器永远不熔断、错峰未启用、全局限速只管账号启动〔三源交叉证实〕

- 证据：
  - risk_control.py:104-117 的 RiskCircuitBreaker.record_failure **全项目无任何生产调用点**（仅单测调用），collection.py:428 只记 record_success → tripped() 恒 False，RISK_CIRCUIT_BREAKER=true 也是死开关；
  - runner.py:16-17,29-32 stagger 默认 False、collection.py:422-425 未传 stagger、risk_control.py:74-82 的 random_stagger() 无调用者 → 随机错峰（20~60s）从未生效；
  - collection.py:673 的 global_limiter.acquire() **每账号仅调一次**（限"账号启动"而非"平台请求"），子进程内 HTTP 请求不经漏桶；
  - mediacrawler.py:109 自认 request_budget_enforced=False，MEDIACRAWLER_BUDGET_* 环境变量在 MediaCrawler 目录 grep 零命中——**请求预算未被上游执行**；
- 影响：0815 文档"熔断器已接入生产、argus 触发仍 20/20 完成"的结论需要重新归因——当时靠的是请求节奏保守 + 退避重试，**不是熔断/错峰**；多账号并发一旦放量（并发默认目前仍为 1），风控保护弱于设计意图，封号风险被放大；
- 修复：在 runner.py 失败路径与 mediacrawler.py 风险信号检测处接入 record_failure；给 run_accounts 传 stagger；把漏桶下沉到请求层（或收紧并发默认并如实修订文档）。

### 🔴 3. 字幕直取命中后"成功被误判失败"：上线即踩的确定性缺陷

- 证据：douyin_subtitles.py:29（persists_result=True）+ douyin_subtitles.py:41-44（成功返回 srt_text=""）→ collection.py:154-162（持久化回调失败即抛 RuntimeError）→ db.py:1087-1090（srt_text 非空校验 return False）→ transcript_router.py:702-710（命中即触发回调）；
- 影响：SUBTITLE_DIRECT_ENABLED=true（当前默认 false，灰度/上线必开）后，**字幕直取成功也会被计为转录失败且口播稿丢失、缓存不写入**——第 0 顺位线路形同虚设；
- 修复：将 douyin_subtitle 从 _persisted_provider_names 排除（正文已存 videos.subtitle_text），或对 douyin_subtitle 来源做 SRT 空值容忍；并补 SUBTITLE_DIRECT_ENABLED=true 的端到端测试。

### 🔴 4. 云端同步写接口应用层零鉴权 + AuthN fail-open + RLS 敞开〔双源交叉证实〕

- 证据：radar.openapi.controller.ts:11-13 无任何守卫；radar.service.ts:400-421 importRows 不校验 token；本地 sync.py:49-53 发送的 x-sync-token/Authorization/OAI-Sites-Authorization 三个凭据在 server 代码中 **grep 零命中（没有任何消费点）**；@NeedLogin 守卫是 **fail-open**（loginUrl 为空即放行），身份信任可伪造的 x-larkgw-suda-webuser header；RLS 策略 USING (true) 实质敞开；
- 影响：若平台网关未对 /openapi/* 强制拦截，任何知晓地址者可向云端业务库**灌入伪造账号/视频/快照数据（数据投毒）**，污染 12 账号矩阵展示；
- 修复：为 OpenAPI 控制器补 token/API Key 校验守卫；**立即向妙搭平台确认 openapi 前缀的网关鉴权策略**；确认 FORCE_AUTHN_TOKEN 的强制开启路径。

### 🔴 5. 全项目无版本控制 + MediaCrawler 深 fork 不可追溯〔双源交叉证实〕

- 证据：根目录 git rev-parse 失败（无 .git，0811 文档亦自认）→ .env.local、数据库、登录态目录无版本保护、.gitignore 从未生效；MediaCrawler 目录无 .git 但已被深度本地修改（字幕直取模块、多账号环境变量消费、隐私列迁移、pyproject 镜像源）；
- 影响：误改/磁盘损坏恢复证据弱；MediaCrawler 上游更新无法 diff/merge，只能整包替换后手工重打 3+ 处补丁，极易回归；备份目录 122MB 也不受控；
- 修复：根目录 git init（按"后续优化迭代"文档的排除清单配置 .gitignore）；MediaCrawler 建立 git 基线 + 上游 remote + 本地补丁清单（或独立 overlay 目录）。

### 🔴 6. 爆款分析零落地："爆款程序"名不副实〔业务闭环 Agent + 本人核验〕

- 证据：矩阵号爆款数据分析与标准定义.md 的 S/A/B/C 分级、40/30/30 评分公式、校准表在 db.py/main.py/前端 **grep 零命中**（评分/score/calibration 无业务实现）；README 与前端对"爆款评分、飞书同步属下一阶段"如实标注（未造假，但项目名与能力脱节）；
- 影响：商业闭环断在分析层——采集→落库→云端查看→导出→转录已通，但**爆款判定、选题分析、脚本生产三环全断**；"爆款程序"当前实质是"数据采集 + 口播稿转录工作台"；
- 修复：将评分公式落地为 SQL 视图/服务函数（数据已够：点赞/评论/收藏字段齐全）；或明确更名与定位，避免预期错位。

### 🔴 7. 文档-代码大面积漂移 + 同步契约默认值陷阱〔多源交叉证实〕

- 证据：改良版介绍文档描述的评分/校准/DeepSeek 周报/飞书出口在代码零命中（属设计蓝图，不能当验收依据）；SYNC_PATH 默认 /api/sync（旧 Sites 契约）而云端真实路由为 /openapi/radar/sync——库中已实测 **16 条 rejected**；默认转录数文档称 10 而代码为 2（collection.py:84）；README 声称导出"三个工作表"而 export.py 仅两表；账号数存在 12/13/25 三种口径；人机验证判定已升级为"DOM 可见性 + 连续 2 次去抖"但文档仍写"URL 关键字误报"；
- 修复：建立"文档随代码"更新机制（本次报告落库后，逐一修订相关文档并标注"以代码为准"）；重跑 /api/sync/retry-rejected 恢复 16 条。

## 五、重要问题（17 项）

1. 🟠 **转录线程池无全局封顶**：collection.py:820,887 每账号 min(4, jobs)，账号并发 4 时最多 16 路下载+ASR 并行，超载风险（蓝图要求全局上限）；
2. 🟠 **自研 with_retry 成死代码**：retry.py:10-11 无任何调用点，且默认 retryable 不含 429/5xx；采集子进程瞬态失败直接判账号失败；
3. 🟠 **字幕"预期缺失"误计熔断**：transcript_router.py:488-491 仅 subtitle_unavailable 不计失败，无字幕/过短/BGM/标题不匹配均计入熔断失败 → 低覆盖率环境第 0 顺位长期熔断；
4. 🟠 **yt-dlp worker stderr 管道填满死锁风险**：platform_subtitles.py:150-193 stderr 用 PIPE 且不 drain，超 64KB 时子进程写阻塞被误杀；
5. 🟠 **ASR 兜底无 BGM 闸门**："BGM 歌词当口播稿"的历史事故在 ASR 路径仍可复发（闸门只用于字幕直取）；
6. 🟠 **备份运维闭环缺失**：backups 无保留/回收策略（线性膨胀）；radar_rN/mc_rN 无 manifest 无法校验恢复；云端恢复后无自动补发同步（仅人工端点）；7. 🟠 **wal_queue 静默丢失隐患**：wal_queue.py:13-47 无界队列 + daemon 线程 + 吞异常 + 不持久；当前仅承载计数（主写路径仍直写），若业务写入队则进程被杀丢数据；

## 九、总体评价

> [!tip] 一句话定性
> <span style="color:#2980b9">**工程素养强于业务完成度，稳定性强于安全性，采集转录强于爆款分析。**</span> 这套系统在"受控并发、幂等落库、安全下载、脱敏、测试"上达到了中大型自研项目的规范水准，10 轮实测 100% 采集正确率是硬成绩；但它目前是<span style="color:#e67e22">**"采集 + 口播稿转录工作台"**</span>，距离名字里的"爆款分析"还差一个评分体系，距"全自动推文爆款"还差选题与脚本生产两环，且 <span style="color:#e74c3c">**商用合法性（MediaCrawler 许可）与技术债务（风控空接线、云端零鉴权、无版本控制）必须在继续投入前解决**</span>。
