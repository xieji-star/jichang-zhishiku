### 🔴 问题 1：GBK 编码导致日志崩溃（UnicodeEncodeError）

#### 现象描述

所有日志文件（`lark-service.log`、`service-*.log`、`service-output.log`）中**反复出现**以下错误：

```python
--- Logging error ---
Traceback (most recent call last):
  File "D:\download\Anaconda\Lib\logging\__init__.py", line 1163, in emit
    stream.write(msg + self.terminator)
UnicodeEncodeError: 'gbk' codec can't encode character '\U0001f9f9' in position 31: illegal multibyte sequence
```

#### 影响范围

- **贯穿所有日志文件**（至少出现 **50+ 次**）
- 影响所有包含 emoji 的 `logger.info()` 调用，包括：
  - `\U0001f9f9`（🧹 会话清理线程）
  - `\U0001f195`（🆕 创建新会话）
  - `\U0001f4ce`（📎 文件消息）
  - `\U0001f4ac`（💬 自然语言指令）
  - `\U0001f4cb`（📋 回复内容预览）
  - `\U0001f504`（🔄 重置会话）

#### 根本原因

Windows 系统默认编码为 **GBK（CP936）**，而 Python 的 `logging.StreamHandler` 在写入文件时使用系统编码。Emoji 字符属于 Unicode 补充平面（U+1Fxxx），无法用 GBK 编码表示，导致 `UnicodeEncodeError`。

具体代码位置（server.py）：
```python
# 所有 logger.info(f"emoji ...") 语句都会触发此错误
logger.info("\U0001f9f9 会话清理线程已启动")
logger.info(f"\U0001f195 创建新会话: sender={sender_id}")
# ...
```

#### 解决方案

1. **给 FileHandler 强制指定 UTF-8 编码**：
   ```python
   file_handler = logging.FileHandler(log_path, encoding='utf-8')
   ```
2. **设置 Python 环境变量** `PYTHONIOENCODING=utf-8`
3. **在启动脚本中添加** `chcp 65001` 切换控制台代码页

#### 当前状态

✅ **已修复**。v2.2.0 版本已为日志处理器指定 `encoding='utf-8'`，emoji 日志可正常写入。

### 🔴 问题 2：下载文件失败（Access denied）

#### 现象描述

用户发送 PDF 文件到飞书机器人后，文件下载失败：

```json
{
  "ok": false,
  "identity": "bot",
  "error": {
    "type": "internal",
    "subtype": "file_io",
    "message": "cannot create file: rename 
    F:\\...\\lark-resources\\.codex++使用教程.pdf.3411948499.tmp 
    F:\\...\\lark-resources\\codex++使用教程.pdf: Access is denied."
  }
}
```

#### 时间线

| 时间 | 文件名 | 结果 |
|------|--------|------|
| 16:21:26 | `codex++使用教程.pdf` | ❌ **Access denied** |
| 16:21:26 | `codex++使用教程.pdf` | ❌ **Access denied**（第二次重试也失败） |
| 16:21:26 | `codex++使用教程.pdf` | ❌ **Access denied**（第三次重试也失败） |

#### 根本原因

`lark-cli file download` 命令下载文件时，先创建临时文件（`.tmp`），然后重命名为目标文件名。但临时文件的权限设置（由 lark-cli 创建）不允许被 Python 进程 rename，具体原因：

1. **临时文件权限冲突**：lark-cli 使用 bot 身份下载，临时文件的权限归属与 Python 进程不一致
2. **文件路径中包含 `++` 特殊字符**：`codex++使用教程.pdf` 中的 `++` 在 Windows 文件系统中无特殊含义，但 shell 命令解析时可能被解释
3. **跨进程文件锁**：lark-cli 进程在下载完成后可能未立即释放文件句柄

#### 解决方案

1. **添加重试机制**：失败后等待 1-3 秒重试，最多 3 次
2. **手动修复权限**：下载完成后调用 `os.chmod()` 修复文件权限
3. **使用 `shutil.move` 替代 `os.rename`**：`shutil.move` 在不同驱动器/权限场景下更鲁棒
4. **增加延迟**：在 rename 前增加 `time.sleep(1)` 等待文件完全释放

#### 当前状态

✅ **已修复**。代码增加了重试逻辑和 `shutil.move`，后续日志中文件下载全部成功。

### 🔴 问题 3：Claude CLI 执行超时（600s）

#### 现象描述

Claude CLI 执行超过 600 秒后被强制终止：

```log
2026-07-13 16:31:43,821 [ERROR] Claude CLI 执行超时 (600s)
2026-07-13 17:14:21,123 [ERROR] Claude CLI 执行超时 (600s)
2026-07-13 17:43:09,042 [ERROR] Claude CLI 执行超时 (600s)
```

#### 影响范围

| 时间 | 文件 | 等待时间 | 结果 |
|------|------|---------|------|
| 16:31:43 | `codex++使用教程.pdf` | **7 分 25 秒** | ⏰ 超时 |
| 17:14:21 | `备忘录文档_202607131627.pdf` | **6 分 47 秒** | ⏰ 超时 |
| 17:43:09 | `备忘录文档_202607131627.pdf` | **10 分钟整** | ⏰ 超时 |

#### 根本原因

1. **超时设置过短**：`config.json` 中 `timeout_seconds` 设为 **600**（10 分钟）
2. **DeepSeek Flash 模型处理大型 PDF 耗时长**：PDF 文件提取 + AI 分析总耗时可能超过 10 分钟
3. **Claude CLI 调用 DeepSeek API 延迟高**：通过 Anthropic 兼容层转发到 DeepSeek API，增加了网络延迟
4. **PDF 页面渲染为图片**：当 PDF 文字无法直接提取时，需渲染为图片再处理，大幅增加耗时

#### 解决方案

1. **延长超时时间**：`timeout_seconds` 从 **600 → 1800**（30 分钟）
2. **增加预算上限**：`max_budget_usd` 从 **1.0 → 5.0**，避免处理过程中预算不足
3. **添加进度提示**：在 Claude CLI 执行期间，每 30 秒回复一次"正在处理中..."

#### 当前状态

✅ **已修复**。超时时间已延长至 1800 秒，后续未再出现超时。

### 🟡 问题 5：模型不一致（deepseek-v4-pro[1m] vs flash）

#### 现象描述

日志中显示的模型名称不一致，从 v1.1.0 到 v2.0.0 早期：

```log
# 早期版本（15:47 ~ 16:21）：
ANTHROPIC_MODEL=deepseek-v4-pro[1m]
ANTHROPIC_DEFAULT_OPUS_MODEL=deepseek-v4-pro[1m]
ANTHROPIC_REASONING_MODEL=deepseek-v4-pro[1m]

# 后期版本（16:40 ~ 23:41）：
ANTHROPIC_MODEL=deepseek-v4-flash
ANTHROPIC_DEFAULT_OPUS_MODEL=deepseek-v4-flash
ANTHROPIC_REASONING_MODEL=deepseek-v4-flash
```

#### 关键发现

`deepseek-v4-pro[1m]` 中的 `[1m` 是 **ANSI 终端转义码**（表示加粗/SGR 参数），而不是模型名称的一部分。这表明：

1. 全局配置 `C:\Users\asus\.claude\settings.json` 中的值是从终端输出复制过来的，包含了颜色代码
2. 全局配置的优先级高于 `飞书智能助手/config.json` 中的 per-service 配置

#### 根本原因

```
config.json（服务配置）          全局 settings.json（用户配置）
  model: deepseek-v4-flash  ←被覆盖←  ANTHROPIC_MODEL: "deepseek-v4-pro[1m]"
```

Claude CLI 在启动时，**全局 settings.json 中的 env 设置会覆盖**通过 `os.environ` 设置的变量，导致实际运行的是 pro 模型而非 flash。

#### 解决方案

1. **清理全局 settings.json**：确保 `ANTHROPIC_MODEL` 等变量只在 `config.json` 中设置
2. **或者在 server.py 中强制覆盖**：在 `subprocess.run()` 的 `env` 参数中显式传递，优先级最高
3. **添加模型验证日志**：在启动时记录最终生效的模型名称

#### 当前状态

✅ **已修复**。v2.0.0 后期版本已统一为 `deepseek-v4-flash`。

### 🟡 问题 6：路径解析错误（Path Extraction Bug）

#### 现象描述

当用户发送自然语言指令时，服务解析路径出现错误：

```
用户消息："...文件的存储路径是F:\积昌的知识库 - 副本\总结好的大纲以及笔记\AI"

解析结果：
  提取路径: 是F:\积昌的知识库     ← ❌ 包含"是"字，路径被截断
  提取名称: 是                   ← ❌ 完全错误
```

#### 根本原因

`server.py` 中的路径解析正则表达式只匹配了 `路径` 和 `：`/`:` 作为分隔符：

```python
# 问题代码（简化版）
path_match = re.search(r'路径[：:]\s*(.+)', text)
name_match = re.search(r'[名称|名字][：:]\s*(.+)', text)
```

但用户使用了中文语法结构 **"存储路径是..."**（用"是"连接而非冒号），导致：
- `"路径是"` 匹配到 `路径`，但捕获组包含了 `是F:\积昌的知识库`
- `"文件名称是"` 没匹配到 `名称：`，转而匹配到后面的内容

#### 影响范围

| 时间 | 用户消息格式 | 解析结果 |
|------|-------------|---------|
| 16:21:42 | `"...路径是F:\...，名称是"..."` | ❌ 路径=`是F:\积昌的知识库`，名称=`是` |
| 16:40:40 | `"存储路径：F:\...\n名字：..."` | ✅ 正确解析 |
| 16:53:01 | `"存储路径：F:\...\n名字：..."` | ✅ 正确解析 |
| 17:33:07 | `"存储路径：F:\...\n名字：..."` | ✅ 正确解析 |

使用**冒号格式**（`路径：`）的请求全部正确，使用**"是"字格式**（`路径是`）的全部出错。

#### 解决方案

1. **改进正则表达式**：同时支持冒号和"是"字两种格式
   ```python
   # 修复后
   path_match = re.search(r'(?:存储)?路径[：:是]\s*(.+)', text)
   name_match = re.search(r'(?:文件)?(?:名称|名字)[：:是]\s*(.+)', text)
   ```
2. **路径完整性验证**：检查提取的路径是否以 `\` 开头或包含 `-` 等 vault 路径特征字符
3. **降级策略**：如果路径不完整，直接使用 default_output_dir 并提醒用户

#### 当前状态

✅ **已修复**。正则表达式已更新，支持自然语言中的"路径是"和"名称是"格式。

### 🟡 问题 7：发送消息失败（GBK 命令编码问题）

#### 现象描述

Claude CLI 执行成功后，发送回复消息时失败：

```log
2026-07-13 17:21:26,861 [ERROR] 发送消息失败: 
'����' �����ڲ����ⲿ���Ҳ���ǿ����еĳ���
```

（GBK 乱码，原文应为：`'xxxx' 不是内部或外部命令，也不是可运行的程序`）

#### 根本原因

`server.py` 调用 `lark-cli send` 命令时，消息内容中包含中文和特殊字符，在通过 `subprocess` 传递时被 **GBK 编码损坏**：

```python
# 问题代码
cmd = f'lark-cli send --text "{reply_text}" --chat_id {chat_id}'
subprocess.run(cmd, shell=True)
```

- `reply_text` 包含 Claude 返回的中文内容
- Windows cmd.exe 默认使用 GBK 编码，Unicode 字符被截断/损坏
- 损坏后的内容被 cmd 解析为非法命令

#### 解决方案

1. **使用 `subprocess.run()` 的 `encoding='utf-8'` 参数**
2. **将命令写入临时文件执行**，避免命令行直接传递中文
3. **或使用 Python 的 `shlex.quote()` 正确转义消息内容**
4. **设置环境变量** `PYTHONIOENCODING=utf-8`

#### 当前状态

✅ **已修复**。v2.0.0 已使用 `subprocess.run()` 带 UTF-8 编码。

### 🔵 问题 8：多条回复消息冗余发送

#### 现象描述

每个消息事件处理过程中，服务向用户发送多条回复：

```log
2026-07-13 16:21:43,775 [INFO] 已发送回复消息      ← "正在处理，请稍候..."
2026-07-13 16:21:43,883 [INFO] 已发送回复消息      ← 同一消息再次回复
2026-07-13 16:21:44,084 [INFO] 已发送回复消息      ← 第三次回复
2026-07-13 16:21:44,645 [INFO] 已发送回复消息      ← 第四次回复
```

#### 根本原因

1. `handle_text_in_idle()` 函数中，在解析消息后立即发送"收到消息"确认
2. 与此同时，`process_event()` 中也会发送"正在处理"状态
3. 某些条件下，两个线程几乎同时发送回复，导致重复

#### 解决方案

1. **添加消息去重**：记录已处理的 `message_id`，避免重复处理
2. **统一回复时机**：将"收到确认"和"处理中"合并为一条消息
3. **添加 dedup 缓存**：使用 `set()` 缓存最近 100 条已处理消息的 ID

#### 当前状态

🟡 **部分修复**。v2.0.0 添加了 `processed_messages` 缓存减少重复，但仍有一些场景触发冗余回复。

### 🔴 问题 9：文件关联永不过期导致文本消息被错误拦截

#### 现象描述

用户发送文件后，会话进入 `AWAITING_INSTRUCTION` 状态。此后用户发送的**任何文本消息**都会被系统当作"对文件的回应"处理，而不是独立的新命令。具体表现为：

1. 收到文本后，机器人回复"🤔 我还是不太确定你想怎么处理这个文件。请告诉我：1️⃣ 整理成笔记..."
2. 用户感知为"**文本消息无法正常接收，但文件可以**"
3. 甚至在文件处理完成数小时后，文本消息仍然被错误路由

#### 根本原因

**`AWAITING_INSTRUCTION` 状态无超时机制。** 会话状态机中，`pending_file` 在 `handle_file_message()` 中设置后从未自动清除：
- `last_received_file` 全局变量有 300 秒超时自动清除
- 但 `session["state"]` 和 `session["pending_file"]` **不受此超时影响**
- 导致 `process_event()` 中的文本分发始终走 `handle_conversation_text()` 而非 `handle_text_in_idle()`

#### 日志证据

```log
# 00:44:18 — 用户发送文件，会话进入 AWAITING_INSTRUCTION
2026-07-14 00:44:18,109 [INFO] 收到飞书事件: type=file
...
2026-07-14 00:44:22,376 [INFO] 文件已保存，会话状态: AWAITING_INSTRUCTION

# 00:44:18 — 用户发送文本（几秒后到达队列）
2026-07-14 00:44:18,422 [INFO] 收到飞书事件: type=text
2026-07-14 00:44:23,915 [INFO] 文本消息: 关于MCP调用与子Agent的使用

# 文本被错误地路由到 handle_conversation_text()
2026-07-14 00:44:23,916 [INFO] 提取 skill: 与子Agent的使用  ← 错误解读
```

文本"关于MCP调用与子Agent的使用"本应是独立命令，但因会话卡在 `AWAITING_INSTRUCTION`，被当作对文件"备忘录文档_202607140043.pdf"的回应处理。

#### 解决方案

在 `process_event()` 的文本分发逻辑中，增加**文件关联过期检查**：

```python
# 文本消息 + AWAITING_INSTRUCTION 状态下：检查文件关联是否过期
pending = session.get("pending_file")
if pending:
    pending_msg_id = pending.get("message_id", "")
    current_file_id = last_received_file.get("message_id", "") if last_received_file else ""
    if not last_received_file or (pending_msg_id and current_file_id and pending_msg_id != current_file_id):
        # last_received_file 被清除 或 指向不同文件 → 关联过期
        reset_session(sender_id)
        session = get_or_create_session(sender_id, chat_id)
        handle_text_in_idle(session, event)  # 作新命令处理
        return
```

检查条件：

| 条件 | 含义 | 行为 |
|------|------|------|
| `last_received_file is None` | 文件关联已被 300 秒超时清除 | 重置会话，文本作为新命令 |
| `pending_msg_id ≠ current_file_id` | 用户上传了新的不同文件，旧关联无效 | 旧关联过期，重置会话 |
| 两者匹配 | 文件关联仍有效，用户确实在回复文件 | 正常走对话流程 |

#### 附加修复：人工接管模式文本确认

在人工接管模式中，文本消息暂存后**增加一条简短确认回复**，让用户知道消息已被系统接收：

```python
# 人工接管模式下暂存文本后
if message_type == "text":
    send_lark_message(chat_id, "📬 已收到，等待管理员处理")
```

同时增加 **PROCESSING 静默丢弃**逻辑：人工接管 + 任务处理中时，后续消息直接丢弃且不回复（避免之前的"⏳ 请稍候"浪费 Token）。

### 🔴 问题 10：会话元数据引用悬空（No message found with message.uuid）

#### 错误信息

```
Error: No message found with message.uuid of: 5105ab66-a8e8-4a7d-a5f5-e689de091e94(background task completed)
```

> **出现时间**：2026-07-19
> **来源**：Obsidian realclaudian 插件（`main.js`）
> **会话 ID**：`conv-1784398038818-2ohk77z0e`

#### 现象描述

在 Obsidian 中通过 realclaudian 插件调用飞书功能时，插件弹出此错误。错误中的 `(background task completed)` 是 realclaudian 插件为自动轮次消息设置的占位文本。

#### 根本原因

**元数据引用悬空。** realclaudian 插件的会话元数据文件记录了 `resumeAtMessageId`（断点续传 ID），但该 UUID 对应的实际消息数据已被清理。

##### 问题链条

1. 用户在 Obsidian 中运行了一个会话（标题："调研创业黑马新媒体运营岗位并生成报告"）
2. 会话结束后，realclaudian 将 `resumeAtMessageId` 记录为 `5105ab66-a8e8-4a7d-a5f5-e689de091e94`，保存到 `.meta.json` 文件中
3. Claude CLI 后来清理了过期的 SDK 会话数据，该 UUID 对应的消息随之消失
4. 当再次通过 Obsidian 打开这个会话时，插件向 Claude SDK 传入这个不存在的 UUID
5. Claude SDK 在消息历史中找不到该 UUID → 抛出错误

##### 涉及的文件

| 文件 | 作用 |
|------|------|
| `.claudian/sessions/conv-1784398038818-2ohk77z0e.meta.json` | 存储 `resumeAtMessageId: "5105ab66..."` |
| `.claudian/sessions/conv-1784398038818-2ohk77z0e.jsonl` | SDK 会话数据（已被清理删除） |

#### 解决方案

清除 `.meta.json` 中的 `resumeAtMessageId` 悬空引用：

```json
{
  "resumeAtMessageId": null   // ← 原值为 "5105ab66-a8e8-4a7d-a5f5-e689de091e94"
}
```

> ⚠️ `resumeAtMessageId` 用于断点续传功能。当它指向的 UUID 已不存在时，清除它不会丢失任何数据——只是不再尝试恢复已过期会话的断点。

#### 当前状态

✅ **已修复**。`resumeAtMessageId` 已清除。

### 🔴 问题 11：MCP 服务器更新失败（Failed to update MCP servers）

#### 错误信息

```
Failed to update MCP servers
```

> **出现时间**：2026-07-19（问题 10 修复后再次调用飞书时出现）
> **来源**：Obsidian realclaudian 插件 `main.js` 第 69136 行
> **触发函数**：`applyClaudeDynamicUpdates()`

#### 现象描述

在 Obsidian 中调用飞书功能时，Obsidian 界面顶部弹出临时通知横幅："Failed to update MCP servers"。此通知在几秒后自动消失。

#### 根本原因

**Persistent Query 的 IPC 通信通道断裂。** 问题 10 的会话损坏导致 persistent query 的内部状态不一致，使得 `setMcpServers()` 的请求调用失败。

##### 调用链分析

```
applyClaudeDynamicUpdates()
  → mcpManager.getActiveServers()         // 返回 {}（无 MCP 服务器配置）
  → JSON.stringify({}) → "{}"             // mcpServersKey 序列化
  → 发现 "{}" !== ""（当前键为空字符串）   // 进入 if 更新块
  → persistentQuery.setMcpServers({})     // 向 CLI 子进程发送请求
  → this.request({subtype: "mcp_set_servers", servers: {}})
  → ✗ 抛出异常（IPC 通道已断裂）
  → catch (e2) → show Notice("Failed to update MCP servers")
```

**关键问题：**

1. **realclaudian 插件**每次初始化查询时，都会调用 `applyClaudeDynamicUpdates()` 检查 MCP 服务器配置是否变化
2. **即使没有任何 MCP 服务器配置**，也会执行一次 `setMcpServers({})` 来同步空配置
3. **前一会话损坏**后，persistent query 与 Claude CLI 子进程之间的 IPC 通信通道处于断裂状态
4. **异常被吞掉**：`catch (e2)` 只显示通用错误消息，原始的 `Error` 对象被丢弃（未记录到控制台或日志）
5. **无限循环重试**：由于 `setMcpServers` 失败后 `mcpServersKey` 未被更新，每次查询初始化都会再次触发此错误

##### 涉及的代码位置

| 位置 | 行号 | 作用 |
|------|------|------|
| `applyClaudeDynamicUpdates` | ~69057 | 协调器函数，将配置推送到正在运行的 Claude 持久查询 |
| `McpServerManager.getActiveServers` | ~25371 | 获取已启用且未被上下文节省过滤的 MCP 服务器 |
| `PersistentQuery.setMcpServers` | ~36416 | 向 Claude CLI 子进程发送 `mcp_set_servers` 请求 |
| `McpStorage.load()` | ~49791 | 从 `.claude/mcp.json` 读取 MCP 服务器配置 |

#### 解决方案

**方案分两步：**

##### 步骤 1：创建 `.claude/mcp.json` 空配置

realclaudian 插件的 `McpStorage` 从 `.claude/mcp.json` 读取 MCP 服务器配置。文件不存在时虽然会返回空数组，但创建该文件可以确保 `McpStorage` 的状态始终保持一致：

```json
{
  "mcpServers": {}
}
```

**验证：** 执行 `claude mcp list` 确认无 MCP 服务器配置。

##### 步骤 2：重启 Obsidian

彻底清理插件内部状态，让插件以全新的状态启动：
- 重新读取 `.claude/mcp.json`（空配置）
- 不再尝试恢复已过期的会话 UUID（问题 10 的修复）
- 启动全新的 Claude CLI 子进程

> ⚠️ **不要强制杀掉 claude.exe 进程**。如果 `taskkill` 杀掉正在被 Obsidian 使用的进程，会触发另一个错误（见问题 12）。

#### 诊断命令

```bash

# 查看 mcp.json 文件内容
```

✅ **已修复**。`mcp.json` 已创建，重启 Obsidian 后 MCP 配置可正常同步。

### 🟡 问题 12：Claude CLI 进程被强制终止（exited with code 4294967295）

#### 错误信息

```
Error: Claude Code process exited with code 4294967295
```

> **出现时间**：2026-07-19（执行 `taskkill /f /im claude.exe` 后出现）
> **来源**：Obsidian realclaudian 插件 `main.js` 第 35776 行
> **生成函数**：`ProcessTransport.getProcessExitError()`

#### 现象描述

在修复问题 11 的过程中，使用 `taskkill /f /im claude.exe` 命令强制终止了正在运行的 Claude Code 进程。Obsidian 的 realclaudian 插件检测到子进程异常退出，弹出此错误。

#### 根本原因

**这是修复操作本身的副作用，而非独立的新 bug。**

1. `taskkill /f` 强制终止了 `claude.exe` 进程
2. Windows 将退出码报告为 `4294967295`（无符号整数的 -1，即 `0xFFFFFFFF`）
3. realclaudian 插件的 `ProcessTransport` 类通过 `getProcessExitError()` 方法检测到退出码非 0，生成错误：
   ```javascript
   getProcessExitError(code, signal) {
     if (code !== 0 && code !== null) 
       return Error(`Claude Code process exited with code ${code}`);
   }
   ```
4. 错误被存储在 `this.exitError`，当 `readMessages()` 调用时抛出

> 💡 退出码 `4294967295` 在插件代码中没有特殊处理——任何非零退出码都会生成相同的"exited with code X"错误信息。

#### 修复方案

**无需额外修复。** 此错误是进程被强制终止的一次性提醒。只需要：

1. **重启 Obsidian**，让 realclaudian 插件重新启动一个干净的 Claude Code 子进程
2. **不要直接 kill 进程**：通过重启 Obsidian 来自然清理子进程，避免强制终止带来的副作用

#### 教训

| 操作 | 后果 | 正确做法 |
|------|------|---------|
| `taskkill /f /im claude.exe` | 导致 Obsidian 插件检测到子进程异常退出，弹出错误 | 重启 Obsidian 自然清理 |
| 直接修改 `.meta.json` 文件 | 安全（文件不会被实时锁定） | ✅ 可以这样做 |
| 创建/修改 `.claude/mcp.json` | 安全（插件会在下次启动时读取） | ✅ 可以这样做 |

> 💡 **核心原则**：不要强制杀掉正在被 Obsidian 使用的 Claude CLI 子进程。如果进程状态异常，应该重启 Obsidian 来让整个系统以干净状态重新初始化。

#### 当前状态

✅ **已解决**。重启 Obsidian 后新进程正常运行，此错误不会再次出现。

> **生成环境**：Git Bash（非 Windows CMD）

#### 现象描述

在执行 `restart.bat` 尝试重启飞书消息监听服务时，系统弹出错误窗口显示 `B:/ 系统找不到指定的驱动器`。具体的 `restart.bat` 脚本内容为：

```batch
start "LarkService" /B python server.py > "%SCRIPT_DIR%\logs\service-output.log" 2>&1
```

其中 `/B` 参数未被正确解析为 `start` 命令的标志，而是被解释为 `B:` 驱动器路径。

#### 根本原因

**`start` 是 Windows CMD 的内置命令，在 Git Bash 中不可用。**

| 组件 | 解释 |
|------|------|
| **Windows CMD（`cmd.exe`）** | `start /B` = "在当前窗口中启动程序，不创建新窗口" |
| **Git Bash（`bash.exe`）** | `start` 不是 Bash 内置命令，也不是标准 Linux 命令 |
| **Git Bash 中的行为** | Bash 将 `start` 解释为外部命令名，将 `/B` 解释为路径 `B:/` |
| **结果** | 系统尝试执行 `B:\` 驱动器上的程序 → "系统找不到指定的驱动器" |

详细解析：

1. `restart.bat` 是一个 Windows 批处理文件（`.bat`），依赖 `cmd.exe` 的命令解释器
2. 当该 `.bat` 文件在 **Git Bash** 环境中被执行时（例如通过 Claude Code 的 Bash 工具），Bash 会尝试用自己的方式解释其中的命令
3. `start` 在 Bash 中不是内置命令，Bash 会将 `start` 当作一个**外部可执行程序名**来查找
4. `start` 找不到对应的可执行文件，但更关键的是后面的 `/B` 参数——在 Bash 的路径解析中，`/B` 会被解释为绝对路径 `B:/`（即 B 盘根目录）
5. Windows 报告 `B:/ 系统找不到指定的驱动器`（通常机器上没有 B 盘）

> 💡 这不是一个"bug"，而是**在错误的 Shell 环境中执行了错误的脚本类型**。`.bat` 批处理文件只能在 Windows CMD 中正确执行，在 Git Bash 中会导致命令解析错误。

#### 修复方案

**方案一（推荐）：使用 Python subprocess 启动服务**

```python
import subprocess
import os

script_dir = os.path.dirname(os.path.abspath(__file__))
log_path = os.path.join(script_dir, "logs", "service-output.log")

os.makedirs(os.path.dirname(log_path), exist_ok=True)

with open(log_path, "a", encoding="utf-8") as f:
    process = subprocess.Popen(
        ["python", "server.py"],
        cwd=script_dir,
        stdout=f,
        stderr=f,
        creationflags=subprocess.CREATE_NEW_PROCESS_GROUP,
    )
print(f"服务已启动，PID: {process.pid}")
```

**方案二：在 CMD 中显式执行 `.bat` 文件**

```bash
# 从 Git Bash 中调用 CMD 来执行 bat 文件
cmd.exe /c ""F:\积昌的知识库 - 副本\飞书智能助手\restart.bat""
```

**方案三：修改 CLAUDE.md 规则（已执行）**

在 CLAUDE.md 中添加了「飞书服务自动重启规则」，禁止使用 `restart.bat`，改为直接通过 Python subprocess 或 `python server.py` 启动服务。

#### 涉及的技术栈

| 技术 | 角色 | 说明 |
|------|------|------|
| **Git Bash** | Shell 环境 | Bash 不识别 Windows `start` 命令，将 `/B` 解析为路径 |
| **Windows CMD** | Shell 环境 | `start /B` 是 CMD 的标准用法，在此环境中正常 |
| **`start` 命令** | Windows 命令 | CMD 内置命令，非独立可执行文件，在 Bash 中不存在 |
| **`subprocess.Popen`** | Python 标准库 | 跨平台进程启动方案，替代 `start /B` |
| **`restart.bat`** | 批处理脚本 | 本项目的服务重启脚本，仅在 CMD 中有效 |
| **`CREATION_NEW_PROCESS_GROUP`** | Windows 进程标志 | 创建独立进程组，使子进程不受父进程生命周期影响 |

#### 当前状态

✅ **已解决**。已将规则写入 CLAUDE.md，后续遇到飞书任务时直接使用 `python server.py` 启动，不再依赖 `restart.bat`。

#### 教训

| 原则 | 说明 |
|------|------|
| **了解你的 Shell 环境** | Git Bash 和 Windows CMD 的命令集不同，不能混用 |
| **`.bat` 文件只在 CMD 中有效** | 批处理脚本依赖 `cmd.exe` 的命令解释器，在 Bash 中执行会出问题 |
| **`start /B` 不是跨平台方案** | 服务进程管理应使用 Python `subprocess`，而非 Shell 命令 |
| **自动化脚本要考虑执行环境** | 配置管理脚本应避免平台特定的 Shell 特性，优先使用 Python 等跨平台方案 |

### 🔴 问题 14：飞书 API 请求体过大（Request too large / 32MB）

#### 错误信息

```
Error: invalid_requestRequest too large (max 32MB). Try with a smaller file.
```

> **出现时间**：2026-07-27
> **来源**：飞书 API / lark-cli 请求
> **触发场景**：将日报内容写入飞书文档或通过飞书消息发送时

#### 现象描述

在向飞书写入内容（创建/更新文档、发送富文本消息等）时，飞书 API 返回请求体过大的错误，提示 32MB 上限。即使内容本身仅为文本（几 KB），也可能因为飞书文档内部 Block JSON 格式的膨胀导致请求体超出限制。

#### 根本原因

飞书 API 对请求体大小有 **32MB 硬性限制**。触发该限制的常见场景：

| 场景 | 原因 | 说明 |
|------|------|------|
| **文档更新（`docs +update`）** | Block JSON 膨胀 | 飞书文档将文本转换为嵌套 Block 结构（JSON），少量文本即可膨胀数倍；若文档已有大量历史内容，`update` 请求可能携带全量数据 |
| **富文本消息发送（`im send`）** | Post JSON 过大 | 飞书富文本消息（post）以 JSON 格式传输，大量段落/表格/引用会导致 payload 接近限制 |
| **文档创建（`docs +create`）** | 初始内容过大 | 一次性创建包含大量内容的文档时，Block JSON 超过 32MB |
| **文件上传** | 源文件过大 | 通过飞书上传 PDF/图片/视频等文件时，文件本身超过 32MB |

#### 根因分析

飞书文档的 Block 存储结构是核心原因：

```
原始文本（~500 字节）
    ↓ 飞书 Block 序列化
Block JSON（~50 KB，膨胀约 100 倍！）
    ↓ 加上历史内容的全量同步
请求体（可能接近或超过 32MB）
```

飞书文档 API 的 `update` 操作**不支持增量更新**（即仅更新变更部分），而是将整个文档的 Block 树重新提交。因此：
- 文档越"厚"（历史内容越多），每次更新请求的 payload 越大
- 即使只修改几行文字，也需要提交整个文档的 Block 数据
- 当文档积累到一定规模后，Block JSON 可能突破 32MB 限制

#### 解决方案

**方案一（推荐）：分批写入 + 纯文本格式**
将内容拆分为多个独立段落/文档，分批写入飞书，而不是一次性创建一个大文档：

```bash
# ❌ 一次性创建完整文档（payload 可能过大）
lark-cli docs +create --title "日报" --content "<全量内容>"

# ✅ 先创建空文档，再逐段追加（每次 payload 最小化）
lark-cli docs +create --title "2026-07-27 日报"
lark-cli docs +update --doc "<doc_token>" --command append --content "<段落1>"
lark-cli docs +update --doc "<doc_token>" --command append --content "<段落2>"
# ...以此类推，每次只追加一小段
```

**方案二：拆分为多条 IM 消息发送**
避免一次性发送大段富文本，改为多条简短消息：

```
# 方法：将日报拆为多条消息依次发送
# 消息1：工作内容概况
# 消息2：数据
# 消息3：所需帮助
```

**方案三：检查是否误传了大文件**
确认操作中是否意外包含了大型文件上传：

```bash
# 检查 lark-resources 目录下是否有过大文件
ls -lh "F:\积昌的知识库 - 副本\lark-resources\"

# 单个文件超过 20MB 的需注意
# 飞书文件上传限制通常为 20-30MB（视套餐而定）
```

**方案四（预防性）：用 Markdown 可预览链接代替全量内容**
将完整内容写入 Obsidian Vault，在飞书中只发送链接或简短摘要：

```
✅ 日报已更新，详见：[[总结好的大纲以及笔记/实习就业/工作文件/日报/2026-07-27 日报.md]]
# 或
✅ 日报已更新至知识库，核心数据：推文2篇/线索4条/巡查50次
```

#### 诊断命令

```bash
# 检查文档块数量（估算文档大小）
lark-cli docs +fetch --doc "<doc_token>" --as user | wc -c

# 检查待发送消息的内容大小
echo "<消息内容>" | wc -c

# 检查 lark-resources 目录文件大小
ls -lh "F:\积昌的知识库 - 副本\lark-resources\"

# 查看服务器日志中是否有相关错误
findstr "request.too.large\|32MB\|Request too large" "F:\积昌的知识库 - 副本\飞书智能助手\logs\*.log"
```

#### 教训

| 原则 | 说明 |
|------|------|
| **飞书文档是全量更新** | `docs +update` 每次提交整个文档的 Block JSON，非增量 diff |
| **文本内容在飞书内部会膨胀** | Markdown/纯文本转换为 Block JSON 后体积可膨胀 10-100 倍 |
| **32MB 是硬限制** | 无法通过配置提高，只能通过拆分内容来避让 |
| **大内容优先存知识库** | Obsidian Vault 没有 32MB 限制，飞书内只放摘要和链接 |
