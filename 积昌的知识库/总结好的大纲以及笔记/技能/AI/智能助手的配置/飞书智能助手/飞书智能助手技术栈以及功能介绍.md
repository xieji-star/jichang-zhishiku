## 一、系统概述

### 1.1 系统定位

飞书智能助手是一个 **Python 编写的本地服务**，通过飞书官方 CLI 工具 `lark-cli` 监听飞书即时消息，将用户发送的消息和文件交由 **Claude CLI（实际调用 DeepSeek API）** 处理，最终将处理结果写入 **Obsidian Vault** 并通过飞书回复用户。

### 1.2 核心架构

```
飞书 (Feishu) → lark-cli event consume (WebSocket 长连接) → Python 服务 → Claude CLI → Obsidian Vault
                                                                    ↓
                                                          lark-cli im send (回复用户)
```

### 1.3 架构核心特点

| 特点 | 说明 |
|------|------|
| 🔌 **无内网穿透** | lark-cli 主动连接飞书服务器建立 WebSocket，无需暴露本地端口 |
| 🧵 **多线程协作** | 6 个线程各司其职，通过 Queue 解耦 |
| 🗣️ **多轮对话** | 会话状态机实现文件→询问→追问→执行的完整流程 |
| ⚡ **本地快速响应** | 问候/帮助/模式切换等简单请求由 Python 直接回复（<1 秒） |
| 🎛️ **双模式接管** | 自动处理 / 人工接管，可在飞书中随时切换 |
| 🔐 **管理员远程控制** | admin.py 允许 Claude Code 远程查看和操控飞书助手 |

### 2.2 lark-cli 详解

#### 2.2.1 核心命令

| 命令 | 用途 | 关键参数 |
|------|------|---------|
| `lark-cli event consume im.message.receive_v1` | 建立 WebSocket 长连接，实时接收消息事件 | `--as bot` 使用应用身份 |
| `lark-cli im +messages-send` | 发送文本消息 | `--chat-id` / `--content`（JSON 格式） |
| `lark-cli im +messages-resources-download` | 下载消息中的文件 | `--message-id` / `--file-key` / `--output`（**必须使用相对路径**） |
| `lark-cli auth status` | 验证当前认证状态 | - |

#### 2.2.2 事件格式（NDJSON）

lark-cli 的 `event consume` 输出 **NDJSON（Newline Delimited JSON）** 流，每行一个事件：

```json
{"message_id": "om_xxxxx", "message_type": "text", "content": "/帮助", "chat_id": "oc_xxxxx", "sender_id": "ou_xxxxx", "chat_type": "p2p"}
```

#### 2.2.3 重要路径

```
.exe 路径: C:\Users\asus\AppData\Roaming\npm\node_modules\@larksuite\cli\bin\lark-cli.exe
.cmd 路径: C:\Users\asus\AppData\Roaming\npm\lark-cli.cmd（不要使用！）
```

> [!CAUTION] 🔴 .cmd 与 .exe 的区别
> **必须直接使用 `.exe` 路径**，不能使用 `.cmd` 批处理。`lark-cli.cmd` 经过 Windows `cmd.exe` 转发时，会**错误解析**包含空格、换行符或特殊字符的长参数，导致消息发送失败。这是 v2.0.0 中"请求超时"（实际上是发送回复失败）的**根本原因**。

#### 2.2.4 事件消费者进程管理

`event_consumer()` 使用 `subprocess.Popen` 启动 lark-cli 事件消费进程，配置行缓冲 (`bufsize=1`) 确保逐行读取 NDJSON 事件流：

```python
process = subprocess.Popen(
    consume_cmd,
    stdin=subprocess.PIPE,
    stdout=subprocess.PIPE,
    stderr=subprocess.PIPE,
    text=True,
    encoding="utf-8",
    errors="replace",
    bufsize=1,  # ★ 行缓冲：确保 readline 逐行返回
)
```

当进程意外退出时，外层 `while True` 循环在 3 秒后自动重启，**无需手动干预**。

### 2.3 Claude CLI + DeepSeek API 详解

#### 2.3.1 架构关系

```
Claude CLI (客户端，作为 AI 代理层)
    │  通过 ANTHROPIC_BASE_URL 重定向 API 请求
    ▼
DeepSeek API (服务端，兼容 Anthropic 接口)
    │  执行模型推理
    ▼
deepseek-v4-flash (模型)
```

Claude CLI 本身不运行任何 Claude 模型，而是作为**文件系统交互的代理层**，将 prompt 发送给 DeepSeek 后端模型处理。

#### 2.3.2 环境变量配置

```json
{
  "ANTHROPIC_BASE_URL": "https://api.deepseek.com/anthropic",
  "ANTHROPIC_AUTH_TOKEN": "sk-xxxxx",
  "ANTHROPIC_MODEL": "deepseek-v4-flash",
  "ANTHROPIC_DEFAULT_HAIKU_MODEL": "deepseek-v4-flash",
  "ANTHROPIC_DEFAULT_OPUS_MODEL": "deepseek-v4-flash",
  "ANTHROPIC_DEFAULT_SONNET_MODEL": "deepseek-v4-flash",
  "ANTHROPIC_REASONING_MODEL": "deepseek-v4-flash"
}
```

> [!WARNING] ⚠️ 环境变量优先级陷阱
> Claude CLI 启动时会读取 `C:\Users\asus\.claude\settings.json` 中的 `env` 配置，**该文件中的环境变量优先级高于 `config.json` 中设置的进程环境变量**。这就是此前反复修改 `config.json` 中的模型名为 `deepseek-v4-flash` 却始终不生效的原因。

#### 2.3.3 Claude CLI 调用参数

```python
cmd = [
    claude_config.get("cli_path"),  # Claude CLI 可执行文件路径
    "-p", prompt,                    # prompt 字符串
    "--settings", settings_path,    # 权限配置文件
    "--output-format", "text",      # 纯文本输出
    "--max-budget-usd", "5.0",      # 预算上限 $5.0
    "--no-session-persistence",     # 不持久化会话
]
```

### 2.4 PyMuPDF (fitz) 可选加速

#### 2.4.1 功能描述

当安装了 PyMuPDF 时，服务会在**调用 Claude CLI 之前**预先提取 PDF 文本内容，直接嵌入 prompt 中。这样 Claude 启动后无需花时间读取 PDF 文件，大幅节省处理时间。

#### 2.4.2 实现逻辑

```python
try:
    import fitz
    HAS_PDF_SUPPORT = True
except ImportError:
    HAS_PDF_SUPPORT = False
```

#### 2.4.3 各情况行为

| 情况 | 行为 |
|------|------|
| ✅ PyMuPDF 已安装 | 自动预提取 PDF 文本，Claude 直接使用 |
| ❌ PyMuPDF 未安装 | 优雅降级，Claude 自己使用 Read 工具读取 |
| 📄 PDF 为扫描件（无文本层） | 预提取返回空，Claude 自行处理 |
| ✂️ 文本超过 80000 字符 | 自动截断，末尾添加截断说明 |

### 2.5 Obsidian realclaudian 插件与 MCP（当通过 Obsidian 调用飞书时）

当用户通过 **Obsidian 的 realclaudian 插件**（非 `server.py` 服务）调用飞书时，涉及以下额外技术组件：

#### 2.5.1 realclaudian 插件

| 项目 | 说明 |
|------|------|
| 📦 插件名称 | realclaudian（Obsidian 社区插件） |
| 📄 主文件 | `.obsidian/plugins/realclaudian/main.js`（~100,000+ 行打包代码） |
| 🔗 用途 | 在 Obsidian 中集成 Claude Code，提供持久化会话管理 |
| 🗂️ 会话存储 | `.claudian/sessions/` 目录 |
| ⚙️ MCP 配置 | `.claude/mcp.json` |

#### 2.5.2 MCP（Model Context Protocol）管理

realclaudian 插件内置了 MCP 服务器管理功能，相关组件架构如下：

```
McpStorage（存储层）
  └─ 从 .claude/mcp.json 读写 MCP 服务器配置
     └─ 格式：{"mcpServers": {"name": {"command": "...", "args": [...]}}}
     
McpServerManager（管理层）
  ├─ loadServers()    → 从 McpStorage 加载配置
  ├─ getActiveServers() → 获取已启用且未被上下文节省过滤的服务器
  └─ 返回 {serverName: config} 对象，供 applyClaudeDynamicUpdates 使用

applyClaudeDynamicUpdates（推送层）
  └─ 在查询初始化时，通过 persistentQuery.setMcpServers() 将配置推送到 CLI
     └─ 即使没有服务器，也会同步空配置 {}
```

**关键组件位置（main.js）：**

| 组件 | 行号（约） | 作用 |
|------|-----------|------|
| `McpServerManager` 类 | 25348-25436 | MCP 服务器管理 |
| `McpStorage` 类 | 49787-49883 | MCP 配置持久化 |
| `applyClaudeDynamicUpdates` | 69057-69156 | 动态配置推送 |
| `getProcessExitError` | 35775-35779 | 子进程退出码处理 |

#### 2.5.3 会话持久化机制

realclaudian 插件将会话数据存储在 `.claudian/sessions/` 目录中：

```
.claudian/sessions/
├── conv-xxxxxxxxxxxx-xxxxx.meta.json   ← 会话元数据（标题、模型、断点续传 ID）
└── conv-xxxxxxxxxxxx-xxxxx.jsonl       ← SDK 会话数据（消息历史，会被 CLI 自动清理）
```

**met.json 文件关键字段：**

| 字段 | 说明 | 问题场景 |
|------|------|---------|
| `resumeAtMessageId` | 断点续传 UUID | 如果指向已删除的消息 → "No message found with message.uuid" |
| `title` | 会话标题 | - |
| `selectedModel` | 使用的模型 | - |
| `providerState` | 提供者状态 | - |

> ⚠️ **注意**：会话数据（`.jsonl`）由 Claude CLI 的会话保留机制自动管理，会定期清理过期数据。但元数据（`.meta.json`）中的 `resumeAtMessageId` 不会自动清除，可能导致"引用悬空"问题。

#### 2.5.4 典型错误场景

当用户在 Obsidian 中通过 realclaudian 插件调用飞书时，可能遇到以下错误链：

```
会话元数据损坏（resumeAtMessageId 悬空）
  └─→ "No message found with message.uuid of: xxxx"
        └─→ Persistent Query IPC 通道断裂
              └─→ "Failed to update MCP servers"
```

| 错误 | 触发时机 | 修复方式 |
|------|---------|---------|
| UUID 悬空 | 恢复已过期的会话 | 清除 `resumeAtMessageId` |
| MCP 更新失败 | 查询初始化时同步配置 | 创建 `mcp.json` + 重启 Obsidian |
| 进程退出码 4294967295 | 进程被强制终止 | 重启 Obsidian |

详细分析见 [[飞书智能助手报错日志]] 中的问题 10-12。

### 3.2 v1.0.0 — 初始版本

**功能**：
- 基础飞书消息接收与回复
- Claude CLI 调用 DeepSeek API 处理任务
- 文件下载与保存

**问题**：
- 所有消息（包括问候）都调用 Claude CLI，响应时间 6-9 秒
- 使用 `lark-cli.cmd` 而非 `.exe`，导致消息发送失败
- 无多轮对话，文件消息直接自动处理

### 3.3 v2.0.0 — 多轮对话

**新增功能**：
- 🗣️ **会话状态机**：IDLE → AWAITING_INSTRUCTION → CLARIFYING → PROCESSING
- 📎 **文件消息询问意图**：收到文件后先问用户"怎么处理？"
- 🔍 **意图提取**：从自然语言中提取路径、名称、意图
- 🔄 **看门狗线程**：每 60 秒检查 lark-cli 进程健康

**架构变更**：从单线程变为 **3 线程**（主线程 + task_worker + watchdog）

### 3.4 v2.1.0 — 本地加速 + PDF 预提取

**新增功能**：
- ⚡ **本地命令处理器**：问候/帮助/模式切换由 Python 直接回复（<1 秒）
- 📄 **PDF 预提取**：使用 PyMuPDF 提取文本嵌入 prompt
- ⏱ **超时提升**：600s → 1800s（30 分钟）
- 🔧 **lark-cli.cmd 修复**：消除消息发送失败的根本原因

**架构变更**：从 3 线程变为 **4 线程**（新增 admin_monitor 实际到 v2.2.0 全功能）

### 3.5 v2.2.0 — 双模式接管 + 管理员 CLI

**新增功能**：
- 🎛️ **双模式接管**：自动 / 人工，可在飞书中随时切换
- 🛠️ **admin.py**：Claude Code 远程查看和控制飞书助手
- 🔐 **管理员监控线程**：每 2 秒轮询 admin_state.json 远程指令
- 📬 **消息排队**：人工接管模式下消息暂存，管理员可逐一处理

**架构变更**：从 4 线程变为 **6 线程**（新增 admin_monitor + cleanup_stale_sessions）

### 3.6 v2.2.1 — 文本接收修复 + 人工接管优化

### 3.7 v3.0.0 — 纯接收模式（禁用自动处理）（当前版本）

**核心变更**：

| 变更 | 说明 |
|------|------|
| 🔇 **禁止自动发信** | 移除所有自动回复机制，飞书助手不再发送任何消息 |
| 📥 **纯接收模式** | 所有消息静默排队等待管理员处理 |

**修改涉及文件**：
- `飞书智能助手/server.py`：重写 `process_event()` 为纯接收逻辑，移除 `handle_local_command()` 等自动处理函数
- `飞书智能助手/admin.py`：更新文档和状态显示，移除模式切换功能

**修复的 BUG**：

| 严重程度 | 问题 | 根因 | 修复 |
|---------|------|------|------|
| 🔴 P0 | 文本消息"无法接收"（被文件会话拦截） | `AWAITING_INSTRUCTION` 状态无超时 | 增加文件关联过期检查 |
| 🔴 P0 | 人工接管模式下文本无反馈 | 静默保存不回复 | 增加确认回复 "📬 已收到" |
| 🔴 P0 | 接管模式在文件损坏时静默回退到 auto | `_get_mode()` 无内存缓存 | 增加 `_cached_mode` 兜底 |
| 🟡 P1 | 切到人工接管后旧 PROCESSING 状态残留 | `_set_mode()` 不同步会话 | 会话全部重置为 IDLE |
| 🟡 P1 | 人工接管 + 处理中时回复"⏳ 请稍候" | PROCESSING 检查先于 manual 检查 | 交换检查顺序，静默丢弃 |

**架构变更**：
- 新增 `_cached_mode` / `_mode_cache_lock` 内存缓存
- `process_event()` 检查顺序重排：manual → PROCESSING → dispatch
- 文本分发增加文件关联过期检查

## 四、核心功能详解

### 4.1 多轮对话系统（v2.0.0+）

#### 4.1.1 会话状态机

```
收到文件                 用户说明意图
IDLE ─────────→ AWAITING_INSTRUCTION ────────→ CLARIFYING
 ↑                     │ 取消                       │ 信息齐全
 │                     ▼                            ▼
 │                   IDLE ────────────────────→ PROCESSING
 │                     ↑                             │
 │                     └──── 取消 ──────────────────┘ │
 └───────────────────────────────────────────────────←┘
                    Claude 执行完毕
```

#### 4.1.2 会话数据模型

```python
{
    "sender_id": "ou_xxxxx",           # 用户唯一标识
    "chat_id": "oc_xxxxx",             # 会话 ID
    "state": "IDLE",                   # 当前状态
    "pending_file": {                  # 待处理的文件
        "path": "lark-resources/xxx.pdf",
        "name": "文件名.pdf",
        "message_id": "om_xxxxx"
    },
    "context": {                       # 多轮对话积累的上下文
        "storage_path": "AI/学习笔记",   # 存放路径
        "note_name": "学习笔记",         # 笔记名称
        "intent": "organize",           # 意图
        "custom_instruction": "...",    # 原始指令
        "skill_name": "meeting-summary" # 指定 skill
    },
    "awaiting_field": "note_name",     # 当前追问字段
    "conversation_count": 2,           # 对话轮次
    "last_activity": 1234567890        # 最后活动时间
}
```

#### 4.1.3 意图提取

从用户自然语言中通过正则表达式提取：

| 信息类型 | 关键词模式 | 示例 |
|---------|-----------|------|
| 📁 存放路径 | `放在`、`存到`、`路径`、`目录`、`文件夹` | "放在 AI/学习笔记" |
| 📝 笔记名称 | `名字`、`名称`、`叫`、`标题`、`命名为` | "名字叫知识点总结" |
| 🎯 处理意图 | `整理`、`总结`、`提取`、`搜索` | "整理成笔记" |
| ❌ 取消操作 | `取消`、`不用了`、`算了`、`cancel` | "算了" |

#### 4.1.4 服务启动验证

服务启动时自动验证 lark-cli 的可用性和认证状态，验证失败则退出：


#### 4.1.7 文件关联超时与会话重置（v2.2.1 修复）

**🔴 BUG：** 接收文件后，会话进入 `AWAITING_INSTRUCTION` 状态且**永不过期**。后续用户发送的任何文本消息都会被 `handle_conversation_text()` 错误地当作文件处理的对话继续（追问"你想怎么处理这个文件？"），而非独立的新命令。用户感知为"文本消息无法正常接收，但文件可以"。

**修复方案：** 在文本消息分发时，检查 `last_received_file` 是否与 `pending_file` 匹配。如果不匹配（超时清除或被新文件覆盖），重置会话到 IDLE，将文本作为新命令处理：

```python
# 文件关联过期检查
pending = session.get("pending_file")
if pending:
    pending_msg_id = pending.get("message_id", "")
    current_file_id = last_received_file.get("message_id", "") if last_received_file else ""
    if not last_received_file or (pending_msg_id and current_file_id and pending_msg_id != current_file_id):
        # last_received_file 被超时清除 或 指向不同文件 → 关联过期
        reset_session(sender_id)
        session = get_or_create_session(sender_id, chat_id)
        handle_text_in_idle(session, event)  # 作为新命令处理
        return
```

**关联文件超时机制：** `last_received_file` 同时拥有 300 秒（5 分钟）超时自动清除机制，与此修复配合确保文件关联不会永久残留。

### 4.4 消息去重

飞书可能因网络抖动重复推送同一事件，服务通过 `message_id` 去重：

```python
processed_message_ids: set = set()

if message_id in processed_message_ids:
    return  # 跳过重复消息
processed_message_ids.add(message_id)
# 控制集合大小，避免内存泄漏
if len(processed_message_ids) > 1000:
    processed_message_ids.clear()
```

> [!WARNING] ⚠️ 清空策略的局限
> 当集合超过 1000 条时使用 `clear()` 完全清空，这意味着之前的 message_id 全部丢失。如果飞书在清空后立即重推旧事件，将被视为新消息处理。此设计优先考虑**内存安全**而非**绝对去重**——1000 条的上限确保不会内存泄漏，而清空后重复的概率较低。

> 看门狗仅负责**监控和日志记录**，实际的进程自动重启由 `event_consumer()` 函数的 `while True` 外层循环处理。

### 4.6 会话清理机制

每 5 分钟清理 30 分钟无活动的会话，防止内存泄漏：

```python
SESSION_TIMEOUT = 30 * 60       # 30 分钟
SESSION_CLEANUP_INTERVAL = 300  # 每 5 分钟

def cleanup_stale_sessions():
    while True:
        time.sleep(SESSION_CLEANUP_INTERVAL)
        stale_ids = [sid for sid, s in sessions.items()
                     if now - s["last_activity"] > SESSION_TIMEOUT]
        for sid in stale_ids:
            del sessions[sid]
```

## 六、管理员远程控制 admin.py

### 6.1 概述

| `pending` | 查看待处理消息列表 | `python admin.py pending` |
| `process <ID> [指令]` | 处理指定待处理消息 | `python admin.py process 0 "整理成笔记"` |

### 6.5 admin.py 关键技术机制

#### 6.5.1 服务 PID 检测（get_service_pid）

admin.py 通过 PowerShell WMI 查询定位运行中的 server.py 进程 PID，而非依赖 PID 文件：

```python
def get_service_pid() -> int:
    result = subprocess.run(["powershell", "-Command",
        "Get-CimInstance Win32_Process -Filter \"Name='python.exe' AND CommandLine LIKE '%server.py%'\" | Select-Object -ExpandProperty ProcessId"],
        capture_output=True, text=True, timeout=10)
    pid_str = result.stdout.strip()
    if pid_str:
        return int(pid_str.split('\\n')[0])
    return 0
```

> 使用 WMI 查询而非 `tasklist` 命令，因为 WMI 可以同时过滤进程名和命令行参数，避免误匹配其他 Python 进程。

#### 6.5.2 最近用户检测（get_default_chat_id）

`reply` 命令通过反向扫描日志文件，查找最近出现 `chat_id=oc_` 的记录，实现"回复最近发消息的用户"：

```python
def get_default_chat_id() -> str:
    log_file = LOG_DIR / "lark-service.log"
    for line in reversed(f.readlines()):
        if "chat_id=oc_" in line:
            idx = line.index("chat_id=oc_")
            return line[idx:idx + 36]  # oc_ + 32 chars
    return ""
```

> 此方法仅在服务运行期间有日志记录时才有效。如果刚重启且日志被清空，`reply` 将无法找到目标 chat_id。

#### 6.5.3 `admin_chat_id` 的设置

`admin_chat_id` 是 admin_state.json 中的一个关键字段，指定**管理员所在的飞书会话 ID**。当管理员通过 `override` 注入覆盖指令时，服务会向此 chat_id 发送确认消息：

```json
{
  "admin_chat_id": "oc_xxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
}
```

**设置方式**：管理员先手动向飞书机器人发送一条消息，然后通过 `admin.py sessions` 或查看日志找到自己的 chat_id，手动写入 `admin_state.json`。

### 6.4 管理员监控线程

服务端的 `admin_monitor()` 线程每 2 秒轮询 `admin_state.json`，检测指令：

| 指令 | 处理方式 |
|------|---------|
| `cancel` | 释放处理锁，使执行中的 Claude CLI 在下一次检查时退出 |
| `override` | 将管理员的指令作为最高优先级事件注入任务队列 |
| `pause` | 设置暂停标志，跳过队列中的消息 |
| `resume` | 清除暂停标志 |

### 7.9 接管模式内存缓存（v2.2.1 新增）

**解决 BUG**：`admin_state.json` 文件损坏或并发读写时，`_get_mode()` 静默返回 `"auto"`，导致人工接管模式丢失。

**模式**：文件持久化 + 内存缓存双重保障。读操作优先走文件（同步到缓存），文件失败时回退到缓存：

```python
_cached_mode = "auto"          # 内存缓存，启动时默认 auto
_mode_cache_lock = threading.Lock()  # 读写锁

def _get_mode() -> str:
    global _cached_mode
    try:
        if ADMIN_STATE_PATH.exists():
            state = json.loads(ADMIN_STATE_PATH.read_text(encoding="utf-8"))
            mode = state.get("mode", "auto")
            with _mode_cache_lock:
                _cached_mode = mode       # ★ 同步到缓存
            return mode
    except Exception:
        logger.warning(f"⚠️ 读取失败，使用内存缓存: {_cached_mode}")
    with _mode_cache_lock:
        return _cached_mode                # ★ 文件失败时回退缓存

def _set_mode(mode: str):
    global _cached_mode
    # ...写入文件...
    with _mode_cache_lock:
        _cached_mode = mode                # ★ 写入文件后同步缓存
    # ★ 切到 manual 时重置所有会话
    if mode == "manual":
        with sessions_lock:
            for sid in list(sessions.keys()):
                sessions[sid].update({"state": "IDLE", ...})
```

**关键点**：
- 写入操作：先写文件，再同步缓存
- 读取操作：先读文件（同步缓存），失败回退缓存
- 切换 manual 时：重置所有会话，防止旧 PROCESSING 状态残留

### 7.10 禁止使用 `start /B` — 用 Python subprocess 替代（2026-07-26 新增）

**背景**：CLAUDE.md 中配置了飞书服务自动重启规则，最初通过 `restart.bat`（含 `start /B` 命令）来重启服务。但在 Git Bash 环境中执行时，弹出 `B:/ 系统找不到指定的驱动器` 错误。

**错误分析**：

| 组件 | 说明 |
|------|------|
| ❌ 错误命令 | `start "LarkService" /B python server.py > logs\service-output.log 2>&1` |
| 🔍 执行环境 | Git Bash（Claude Code 的 Bash 工具默认使用 Git Bash） |
| 🎯 根因 | `start` 是 Windows CMD 内置命令，Git Bash 不识别。`/B` 被 Bash 解析为 B: 盘路径 |

**正确做法**：永远使用 Python `subprocess.Popen` 来管理后台进程：

```python
import subprocess
import os

def start_service(script_dir: str) -> subprocess.Popen:
    """启动飞书消息监听服务（替代 start /B）"""
    log_path = os.path.join(script_dir, "logs", "service-output.log")
    os.makedirs(os.path.dirname(log_path), exist_ok=True)
    
    with open(log_path, "a", encoding="utf-8") as f:
        process = subprocess.Popen(
            ["python", "server.py"],
            cwd=script_dir,
            stdout=f,
            stderr=f,
            creationflags=subprocess.CREATE_NEW_PROCESS_GROUP,
        )
    return process
```

**关键参数说明**：

| 参数 | 作用 | 替代的 CMD 行为 |
|------|------|----------------|
| `cwd=script_dir` | 设置工作目录 | 替代 `cd /d "%SCRIPT_DIR%"` |
| `stdout=f, stderr=f` | 重定向输出到日志文件 | 替代 `> logfile 2>&1` |
| `CREATION_NEW_PROCESS_GROUP` | 创建独立进程组，不受父进程生命周期影响 | 替代 `start /B` 的后台运行效果 |

**为什么 `subprocess.Popen` 优于 `start /B`？**

1. **跨平台**：在 Windows/Linux/macOS 上都能工作
2. **不依赖 Shell 环境**：无论是 CMD、Git Bash 还是 PowerShell，行为一致
3. **可控性强**：可以通过 `process.pid` 获取进程 ID，通过 `process.terminate()` 优雅关闭
4. **错误可捕获**：Python 异常机制可以捕获启动失败的错误，而非弹窗

**相关规则**：参见 CLAUDE.md 中「飞书服务自动重启规则」。

## 📌 总结

### 架构亮点

1. **零内网穿透**：lark-cli 通过 WebSocket 主动连接飞书服务器，无需暴露本地端口，比企业微信方案更简单安全
2. **纯标准库**：服务仅依赖 Python 标准库，PyMuPDF 为可选加速，部署极其轻量
3. **双模式灵活切换**：用户可在飞书中随时切换自动/人工模式，无需修改配置或重启服务
4. **管理员远程控制**：admin.py 通过 JSON 文件 IPC 通信，架构简单可靠，Claude Code 可远程操控
5. **多轮对话体验**：收到文件后先询问用户意图，通过自然语言理解提取路径/名称/意图，减少误操作
