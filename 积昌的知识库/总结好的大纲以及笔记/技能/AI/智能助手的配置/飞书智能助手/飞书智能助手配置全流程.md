## 一、概述

### 1.1 系统架构

```
飞书 (Feishu/Lark) → lark-cli event consume → Python 服务 → Claude CLI → Obsidian Vault
                                          ↓
                                   lark-cli im send (回复用户)
```

### 1.2 数据流

1. **📱 用户在飞书** 中给机器人发送消息/文件
2. **🔄 lark-cli event consume** 通过 WebSocket 长连接实时接收消息事件
3. **⚙️ Python 服务** 解析事件、下载文件（支持 **PDF 预提取**）、**通过多轮对话明确用户意图**
4. **⚡ 本地命令处理器** 对问候、帮助、模式切换等简单请求**直接回复（<1 秒）**，无需调用 Claude CLI
5. **🧠 Claude CLI**（实际调用 DeepSeek API）处理复杂任务
6. **💾 处理结果** 写入 Obsidian Vault + 通过 `lark-cli im send` 回复用户
7. **🔄 双模式运行**：可随时在「自动接管」和「人工接管」模式间切换
8. **🛠️ 管理员 CLI（admin.py）**：Claude Code 可通过命令行远程查看和控制飞书助手

### 1.3 技术栈

| 技术 | 用途 | 版本 |
|------|------|------|
| 🐍 Python | 服务端编程 | 3.13 |
| 🛠️ lark-cli | 飞书官方 CLI 工具（事件监听/消息收发） | npm 包 |
| 🤖 Claude CLI | AI 任务执行引擎 | Anthropic 官方 |
| 🧠 DeepSeek API | AI 模型后端 | deepseek-v4-flash |
| 📄 PyMuPDF (fitz) | PDF 文本预提取（可选加速） | pip 包 |
| 📒 Obsidian | 知识库 | - |

### 1.4 与企业微信方案的区别

| 对比项 | 企业微信 | 飞书 |
|--------|---------|------|
| 消息获取方式 | HTTP 回调（被动推送） | WebSocket 长连接（主动监听） |
| 通信协议 | HTTP POST（XML 加密） | NDJSON 流式事件 |
| 内网穿透 | 需要（LocalTunnel） | **不需要**（lark-cli 主动连接飞书服务器） |
| 服务框架 | FastAPI + uvicorn | 纯 Python 脚本（无 Web 服务） |
| Windows 服务管理 | nssm | 可选（目前用 restart.bat 管理） |
| 消息加解密 | AES 加解密（wechatpy） | lark-cli 自动处理 |
| 文件下载 | 企业微信 Media API | lark-cli messages-resources-download |
| 快速命令响应 | 全部走 Claude CLI | **本地命令处理器**（问候/帮助/状态 <1秒） |
| 接管模式 | 仅自动处理 | **双模式**（自动/人工 + 管理员 CLI 远程控制） |
| 远程管理 CLI | 无 | **admin.py**（Claude Code 可查看消息、发送回复、取消/覆盖任务） |

> [!TIP] 💡 核心优势
> 飞书方案**不需要内网穿透**，因为 lark-cli 主动连接飞书服务器建立 WebSocket 长连接，企业微信方案需要 LocalTunnel 暴露本地端口到公网。

## 四、核心代码解析

### 4.1 架构设计

服务由 **6 个线程**协作运行（v2.2.0 新增管理员监控和本地命令处理）：

```
┌─ 主线程 ─────────────────────┐
│  event_consumer()             │
│  → lark-cli event consume     │
│  → 读取 NDJSON 事件流         │
└────────┬──────────────────────┘
         │ put(event)
┌────────▼──────────────────────┐
│     任务队列 (Queue)           │
└────────┬──────────────────────┘
         │ get()
┌────────▼──────────────────────┐
│  task_worker() (工作线程)      │
│  → 会话分发 (状态机)           │
│  → 多轮对话 / 解析意图         │
│  → 下载文件 → 调用 Claude      │
│  → 处理管理员覆盖指令           │
└───────────────────────────────┘

┌─ 看门狗线程 ──────────────────┐
│  watchdog()                   │
│  → 每60秒检查 lark-cli 进程    │
└───────────────────────────────┘

┌─ 会话清理线程 ────────────────┐
│  cleanup_stale_sessions()     │
│  → 每5分钟清理30分钟超时会话   │
└───────────────────────────────┘

┌─ 管理员监控线程 (v2.1.0 新增) ──┐
│  admin_monitor()               │
│  → 每2秒轮询 admin_state.json   │
│  → 支持: cancel / override /   │
│    pause / resume 指令          │
└────────────────────────────────┘
```

### 4.2 事件消费（event_consumer）

使用 `lark-cli event consume` 建立长连接，实时接收消息事件：

> [!WARNING] ⚠️ 重要修复
> 必须直接使用 `lark-cli.exe` 而非 `lark-cli.cmd`，因为 .cmd 批处理经过 Windows cmd.exe 转发时会**截断或错误解析长参数**，导致消息发送失败（见 [[#七、常见问题]] Q6）。

```python
# ★ 直接使用 .exe 路径，避免 .cmd 批处理的 cmd.exe 参数解析问题
exe_path = r"C:\Users\asus\AppData\Roaming\npm\node_modules\@larksuite\cli\bin\lark-cli.exe"

def event_consumer():
    while True:
        process = subprocess.Popen(
            [exe_path, "event", "consume",
             "im.message.receive_v1", "--as", "bot"],
            stdin=subprocess.PIPE,    # 保持 stdin 打开，防止进程退出
            stdout=subprocess.PIPE,
            stderr=subprocess.PIPE,
            text=True, bufsize=1,
        )
        # 逐行读取 NDJSON 格式事件流
        line = stdout_fd.readline()
        if not line:  # EOF = 进程退出
            break
        event = json.loads(line)
        task_queue.put(event)
```

事件 JSON 示例：

```json
{
  "message_id": "om_xxxxx",
  "message_type": "text",
  "content": "/帮助",
  "chat_id": "oc_xxxxx",
  "sender_id": "ou_xxxxx",
  "chat_type": "p2p"
}
```

### 4.3 消息发送（send_lark_message）

> [!WARNING] ⚠️ 重要修复
> 使用 `--content` 传递 JSON 而非 `--text`，避免 Windows cmd 处理多行参数时截断。

```python
def send_lark_message(chat_id, content):
    content_json = json.dumps({"text": content}, ensure_ascii=False)
    result = lark_cli([
        "im", "+messages-send",
        "--chat-id", chat_id,
        "--content", content_json,   # ★ 使用 JSON 而非 --text
        "--as", "bot",
    ])
```

### 4.4 文件下载（download_lark_file）

> [!WARNING] ⚠️ 重要修复
> lark-cli 不接受绝对路径的 `--output` 参数，必须使用相对路径。

```python
def download_lark_file(message_id, file_key, vault_root, relative_dir, file_name):
    # ★ 使用相对路径（相对于 vault_root）

         "--output", relative_path,
         "--as", "bot",
        ],
        cwd=vault_root,  # 工作目录设为 vault 根目录
    )
```

### 4.6 Prompt 生成

Prompt 生成分为两种模式：

#### 模式一：已知命令 → generate_claude_prompt()

| 消息类型 | 命令 | 行为 |
|---------|------|------|
| text | `整理笔记 [文件夹] [名称]` | 调用 meeting-summary skill 处理关联文件 |
| text | `/帮助` | 生成本机器人帮助信息 |
| text | `/搜索 [关键词]` | 在 Vault 中搜索内容 |
| text | `总结 [内容]` | 直接总结一段文字 |
| text | 自然语言 | 理解意图并执行（创建笔记、搜索、调用 skill 等） |

#### 模式二：多轮对话 → build_session_prompt()

当用户在 **AWAITING_INSTRUCTION** 或 **CLARIFYING** 状态时，服务会积累对话上下文，然后调用 `build_session_prompt()` 构建包含完整上下文的 prompt：

| 上下文字段 | 来源 | 说明 |
|-----------|------|------|
| pending_file | 用户上传的文件 | 文件路径和名称 |
| storage_path | 用户告知的存放路径 | 笔记在 Vault 中的位置 |
| note_name | 用户告知的笔记名称 | .md 文件名 |
| intent | 从对话中推断的意图 | organize / summarize / extract / search |
| custom_instruction | 用户原始指令 | 完整的自然语言描述 |

> [!TIP] 💡 PDF 预提取（v2.1.0 新增）
> 当用户发送 PDF 文件并通过多轮对话确认意图后，`build_session_prompt()` 会在**调用 Claude CLI 之前**使用 PyMuPDF（`fitz`）预先提取 PDF 文本内容，直接嵌入 prompt 中。这样 Claude 启动后无需花时间读取 PDF 文件，大幅节省处理时间。
>
> ```python
> # server.py 中的 PDF 预提取逻辑
> if file_name.lower().endswith('.pdf') and HAS_PDF_SUPPORT:
>     doc = fitz.open(file_path)
>     for i in range(doc.page_count):
>         text = doc[i].get_text('text')
>         if text.strip():
>             texts.append(f"=== Page {i+1} ===\n{text}")
>     doc.close()
>     # 嵌入 prompt，限制 80000 字符避免超长
>     lines.append(f"\n以下是 PDF 文件内容（预提取）：\n\n{pdf_extracted_text}")
> ```
>
> | 情况 | 行为 |
> |------|------|
> | ✅ PyMuPDF 已安装 (`pip install pymupdf`) | 自动预提取 PDF 文本，Claude 直接使用 |
> | ❌ PyMuPDF 未安装 | 优雅降级，Claude 自己使用 Read 工具读取 |
> | 📄 PDF 为扫描件（无文本层） | 预提取返回空，Claude 自行处理 |
> | ✂️ 文本超过 80000 字符 | 自动截断，末尾添加截断说明 |

### 4.10 会话管理与多轮对话（v2.0.0 新增）

v2.0.0 引入**会话状态机**，支持与用户进行多轮对话，明确意图后再执行任务。

#### 会话状态定义

```python
# 每个用户一个会话，按 sender_id 索引
SESSION_STATES = {
    "IDLE":                # 默认状态，等待用户输入
    "AWAITING_INSTRUCTION": # 收到文件，等待用户说明意图
    "CLARIFYING":          # 正在追问缺失信息
    "PROCESSING":          # Claude CLI 正在执行
}
```

#### 状态转换图

```
    收到文件                 用户说明意图
IDLE ─────────→ AWAITING_INSTRUCTION ────────→ CLARIFYING
 ↑                     │ 取消                       │ 信息齐全
 │                     ▼                            ▼
 │                   IDLE ────────────────────→ PROCESSING
 │                     ↑                             │
 │                     └──── 取消 ──────────────────┘ │
 └───────────────────────────────────────────────────←┘
                    Claude 执行完毕
```

#### 核心流程

```python
def process_event(event):
    session = get_or_create_session(sender_id, chat_id)
    
    if session["state"] == "PROCESSING":
        send_lark_message(chat_id, "⏳ 正在处理上一个任务...")
        return
    
    if message_type == "file":
        handle_file_message(session, event)  # 下载+询问
    elif message_type == "text":
        if session["state"] == "IDLE":
            handle_text_in_idle(session, event)     # 已知命令/自然语言
        else:
            handle_conversation_text(session, event)  # 多轮对话
```

#### 文件消息处理（新流程）

```python
def handle_file_message(session, event):
    # 1. 下载文件
    downloaded = download_lark_file(...)
    # 2. 保存到会话
    session["pending_file"] = {"path": downloaded, "name": file_name}
    session["state"] = "AWAITING_INSTRUCTION"
    # 3. 询问用户意图（不自动处理！）
    send_lark_message(chat_id, f"✅ 已接收文件\n请问你想怎么处理？\n"
                               "1️⃣ 整理成笔记\n2️⃣ 总结内容\n"
                               "3️⃣ 提取关键信息\n4️⃣ 其他用途")
```

#### 对话文本处理

```python
def handle_conversation_text(session, event):
    content = event.get("content", "")
    
    # 取消操作
    if content in ("取消", "不用了", "算了"):
        reset_session(sender_id)
        return
    
    # 从消息中提取上下文（路径、名称、意图）
    extract_context_from_text(session, content)
    
    # 检查信息是否齐全
    missing = is_session_ready_to_execute(session)
    if not missing:
        # 信息齐全 → 执行
        prompt = build_session_prompt(session)
        execute_and_reply(chat_id, prompt, sender_id)
    else:
        # 信息不全 → 继续追问
        session["state"] = "CLARIFYING"
        ask_missing_info(chat_id, missing)
```

#### 会话管理关键函数

| 函数 | 作用 |
|------|------|
| `get_or_create_session()` | 按 sender_id 获取/创建会话 |
| `reset_session()` | 将会话重置为 IDLE |
| `extract_context_from_text()` | 从用户消息中提取路径、名称、意图 |
| `is_session_ready_to_execute()` | 检查是否已收集足够信息 |
| `build_session_prompt()` | 从会话上下文构建执行 prompt |
| `cleanup_stale_sessions()` | 定期清理 30 分钟无活动的会话 |

#### 上下文提取示例

```python
# 用户说："整理成笔记放在 AI 目录，名字叫学习笔记"

extract_context_from_text(session, content)
# → context["intent"] = "organize"
# → context["storage_path"] = "AI 目录"
```

#### 4.10.3 文件关联超时修复（v2.2.1）

> [!WARNING] 🔴 BUG 描述
> 接收文件后，会话进入 `AWAITING_INSTRUCTION` 状态且**永不过期**。用户后续发送的任何文本消息都会被错误地当作"对文件的回应"处理，触发"你想怎么处理这个文件？"追问。用户感知为"文本消息无法正常接收，但文件可以"。

**根因：** 文本消息进入 `handle_conversation_text()` 而非 `handle_text_in_idle()`，因为会话卡在 `AWAITING_INSTRUCTION` 状态。

**修复：** 在 `process_event()` 的文本分发逻辑中增加文件关联过期检查。通过比对 `session.pending_file.message_id` 与 `last_received_file.message_id`：

| 条件 | 判断 | 行为 |
|------|------|------|
| `last_received_file` 已被超时清除（None） | 关联过期 | 重置会话到 IDLE，作为新命令处理 |
| `pending_file.message_id ≠ last_received_file.message_id` | 指向不同文件 | 旧关联过期，重置会话 |
| 两者匹配 | 关联有效 | 正常走 `handle_conversation_text()` |

```python
# 文件关联过期检查
pending = session.get("pending_file")
if pending:
    pending_msg_id = pending.get("message_id", "")
    current_file_id = last_received_file.get("message_id", "") if last_received_file else ""
    if not last_received_file or (pending_msg_id and current_file_id and pending_msg_id != current_file_id):
        reset_session(sender_id)
        session = get_or_create_session(sender_id, chat_id)
        handle_text_in_idle(session, event)
        return
```

同时关联 `last_received_file` 已有的 **300 秒超时自动清除**机制，双重保障防止文件关联永久残留。

### 5.4 自动重连机制

服务启动后，`event_consumer()` 主线程建立 WebSocket 连接并持续监听。当连接意外断开或 lark-cli 进程崩溃时，**自动在 3 秒后重试**：

```
服务启动 → lark-cli auth status 验证
             ↓
        event_consumer() 启动 lark-cli event consume（WebSocket）
             ↓
        while True 读取 NDJSON 事件流
             ↓
        连接断开/lark-cli 崩溃 → 等待 3 秒 → 自动重连
             ↓
        看门狗线程每 60 秒检查一次进程健康
             ↓
        会话清理线程每 5 分钟清理过期会话
```

此机制确保服务在无需人工干预的情况下持续运行。

> [!WARNING] 🔴 重要变更
> 飞书智能助手 v3.0.0 已**永久禁用**自动消息处理和自动回复功能，改为**纯接收模式**。此变更不可在运行时切换。

   - 移除所有本地命令处理器（问候、帮助、状态、版本查询等）

   - 不维护多轮对话状态机

   - 所有任务必须由 Claude Code 通过 `admin.py` 触发
   - 管理员使用 `admin.py override` 或 `admin.py process` 触发处理

4. **🤐 完全静默**
   - 在飞书中不做任何自主响应
   - 用户发送任何消息（包括"你好"、"帮助"）都不会得到回复
   - 用户感知为"机器人不说话了"，但实际上消息已被排队等待

## 九、常见问题

> [!QUESTION] ❓ Q1: 收到的回复只有"📋 处理完成:"没有内容？

**原因**：`--text` 参数在 Windows cmd 中处理包含换行符的内容时被截断。

**解决**：改用 `--content` + `json.dumps()` 传递完整 JSON，已修复。

> [!QUESTION] ❓ Q2: 文件下载失败（"absolute paths are not allowed"）？

**原因**：lark-cli 不允许绝对路径的 `--output` 参数。

**解决**：使用相对路径 + 设置 `cwd=vault_root`，已修复。

> [!TIP] ❓ Q3: 服务收不到消息？

排查步骤：
1. 检查 lark-cli 进程是否存活（看门狗会自动恢复）
2. 检查 lark-cli 认证状态：`lark-cli auth status`
3. 确认是 bot 身份：`lark-cli config default-as`
4. 查看日志 `lark-service.log`

> [!WARNING] ❓ Q4: lark-cli 进程反复退出？

看门狗线程每 60 秒检查一次，如果进程退出会自动记录日志。`event_consumer` 的 `while True` 循环会自动重启进程。如反复退出，检查：
- 网络连接是否稳定
- lark-cli 认证是否过期（重新运行 `lark-cli auth login`）
- 企业防火墙是否阻止了 WebSocket 连接

> [!CAUTION] ❓ Q5: 修改 config.json 后模型仍为旧版本（pro）？

> [!CAUTION] 🔴 全局 settings.json 覆盖问题
> Claude CLI 启动时会读取 `C:\Users\asus\.claude\settings.json` 中的 `env` 配置，**该文件中的环境变量优先级高于 `config.json` 中设置的进程环境变量**。如果只修改了服务 `config.json` 但未更新全局 settings.json，模型将不会生效。
> - **解决方法**：同步更新 `C:\Users\asus\.claude\settings.json` 中的 `ANTHROPIC_MODEL` 为 `deepseek-v4-flash`
> - **验证方法**：启动服务后查看日志中 `ANTHROPIC_MODEL=` 的输出值（应显示 `deepseek-v4-flash`）

> [!CAUTION] ❓ Q6: 发送消息失败（"'...' 不是内部或外部命令"）？

> [!CAUTION] ❓ Q8: 调用飞书时出现"Failed to update MCP servers"或"Claude Code process exited with code 4294967295"？

**错误一："Failed to update MCP servers"**

| 项目 | 内容 |
|------|------|
| ❓ 现象 | Obsidian 界面弹出"Failed to update MCP servers"通知 |
| 🔍 根因 | Persistent Query 的 IPC 通信通道因前一会话损坏而断裂 |
| 🔗 关联 | 通常与 `.claudian/sessions/` 中的 `resumeAtMessageId` 悬空有关 |
| 🛠️ **修复** | **方案分两步**：① 创建 `.claude/mcp.json`（空配置）② 重启 Obsidian |

**原因详解：**
- realclaudian 插件的 `McpStorage` 从 `.claude/mcp.json` 读取 MCP 服务器配置
- 即使没有配置任何服务器，插件也会调用 `setMcpServers({})` 向 CLI 子进程同步空配置
- 如果前一会话损坏导致 IPC 通道断裂，此调用会抛出异常，异常被 catch 后显示通用错误
- 参考 [[飞书智能助手报错日志#🔴 问题 11：MCP 服务器更新失败（Failed to update MCP servers）]] 获取完整分析

**排查命令：**
```bash
# 检查 MCP 配置
claude mcp list
cat "F:\积昌的知识库 - 副本\.claude\mcp.json"

# 检查会话元数据中是否有悬空引用
grep "resumeAtMessageId" ".claudian/sessions/"*.meta.json | grep -v '"pattern"'
```

**解决步骤：**
```bash
# 1. 确保 .claude/mcp.json 存在（如不存在则创建）
echo '{"mcpServers": {}}' > ".claude/mcp.json"

# 2. 检查并清理悬空的 resumeAtMessageId
#    编辑 .claudian/sessions/*.meta.json，将 resumeAtMessageId 设为 null

# 3. 重启 Obsidian（必须！否则插件内部状态不会刷新）
```

**错误二："Claude Code process exited with code 4294967295"**

| 项目 | 内容 |
|------|------|
| ❓ 现象 | 显示"Claude Code process exited with code 4294967295" |
| 🔍 根因 | Claude CLI 子进程被外部强制终止（如 taskkill、任务管理器） |
| ⚠️ 性质 | **修复操作的副作用**，非独立 bug |
| 🛠️ **修复** | 重启 Obsidian 即可 |

**原因详解：**
- 退出码 `4294967295` 是 Windows 无符号整数的 `-1`（`0xFFFFFFFF`）
- 当使用 `taskkill /f /im claude.exe` 强制终止进程时，Windows 报告此退出码
- realclaudian 插件的 `ProcessTransport.getProcessExitError()` 检测到非零退出码则生成错误
- **无需额外修复**，重启 Obsidian 后新进程可正常运行

**重要教训：不要直接 kill 正在被 Obsidian 使用的 Claude CLI 进程！**

| 错误操作 | 正确操作 |
|---------|---------|
| `taskkill /f /im claude.exe` | **重启 Obsidian** 自然清理子进程 |
| 直接结束任务管理器中的 claude.exe | 关闭 Obsidian，让插件自己管理进程生命周期 |

参考 [[飞书智能助手报错日志#🟡 问题 12：Claude CLI 进程被强制终止（exited with code 4294967295）]] 获取完整分析。

> [!CAUTION] ❓ Q9: 执行 restart.bat 时弹出 "B:/ 系统找不到指定的驱动器"？

**原因**：`restart.bat` 中的 `start /B` 命令在 Git Bash 环境中被误解析为 B 盘路径。

**详细分析：**

| 组件 | 解释 |
|------|------|
| ❓ 错误命令 | `start "LarkService" /B python server.py > logs\service-output.log 2>&1` |
| 🔍 执行环境 | Git Bash（而非 Windows CMD） |
| 🎯 根因 | `start` 是 Windows CMD 的内置命令，在 Git Bash 中不存在。Bash 将 `/B` 解释为路径 `B:/` |
| ⚠️ 结果 | 系统尝试访问 B 盘 → 弹出 "系统找不到指定的驱动器" |

**为什么 `start /B` 在 Git Bash 中会失败？**

- `start` 是 `cmd.exe` 的内置命令，不是独立可执行文件
- Git Bash 中没有 `start` 命令，Bash 将它当作外部程序名查找
- 找不到 `start` 后，Bash 将参数 `/B` 解析为绝对路径 `B:/`
- Windows 报告 B 盘不存在（通常没有 B 盘）

**解决方案：使用 Python subprocess 代替 `start /B`**

```python
import subprocess, os

script_dir = r"F:\积昌的知识库 - 副本\飞书智能助手"
log_path = os.path.join(script_dir, "logs", "service-output.log")
os.makedirs(os.path.dirname(log_path), exist_ok=True)

with open(log_path, "a", encoding="utf-8") as f:
    subprocess.Popen(
        ["python", "server.py"],
        cwd=script_dir,
        stdout=f, stderr=f,
        creationflags=subprocess.CREATE_NEW_PROCESS_GROUP,
    )
```

### 13.2 🔴 关键发现：全局 settings.json 覆盖问题

> [!CAUTION] **根因分析**
> Claude CLI 启动时会读取 `C:\Users\asus\.claude\settings.json` 中的 `env` 配置，**该文件中的环境变量优先级高于服务 `config.json` 中设置的进程环境变量**。此前虽然反复修改了 `飞书智能助手/config.json` 中的模型名为 `deepseek-v4-flash`，但由于全局 settings.json 仍然指向 `deepseek-v4-pro[1m]`，导致每次 Claude CLI 启动时都会覆盖进程中的环境变量。

| 排查步骤 | 结果 |
|---------|------|

| ③ 检查 `C:\Users\asus\.claude\settings.json` | ❌ **仍为 pro，此为根因** |
| ④ 修改后重启服务验证 | ✅ 日志显示 `ANTHROPIC_MODEL=deepseek-v4-flash` |
