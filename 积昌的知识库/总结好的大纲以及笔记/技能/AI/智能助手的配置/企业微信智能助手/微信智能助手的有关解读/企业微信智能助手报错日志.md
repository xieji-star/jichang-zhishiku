### 🔴 问题 1：服务频繁无故崩溃（严重）

> 已有记录，本文补充根本原因分析。

#### 现象描述

服务在 **3 小时 42 分钟**内（11:47 ~ 15:29）崩溃至少 **12 次**，具体表现：

| 序号 | 时间 | 运行时长 | Tunnel URL |
|------|------|---------|-----------|
| 1 | 11:47 | 首次启动 | `literacy-aqua-celtic-bibliography.trycloudflare.com` |
| 2 | 11:53 | 重启（切换 LocalTunnel） | `silent-cups-chew.loca.lt` |
| 3 | 12:08 | 运行约 **15 分钟**后崩溃 | `shy-olives-report.loca.lt` |
| 4 | 12:09 | 仅 **1 分钟**后再次崩溃 | `tricky-bulldog-75.loca.lt` |
| 5 | 12:10 | 仅 **1 分钟**后再次崩溃 | `tasty-bulldog-61.loca.lt` |
| 6 | 12:11 | 仅 **1 分钟**后再次崩溃 | `lucky-rat-23.loca.lt` |
| 7 | 12:14 | 获得**固定子域名** | `jichang-vault-0a9bccb4e4.loca.lt` |
| 8 | 12:45 | 运行约 **31 分钟**后崩溃 | 同上 |
| 9 | 12:54 | 运行约 **9 分钟**后崩溃 | 同上 |
| 10 | 12:57 | 子域名被占用 | `bitter-snake-40.loca.lt` |
| 11 | 12:58 | 手动重启恢复固定子域名 | `jichang-vault-0a9bccb4e4.loca.lt` |
| 12 | 14:54 | 运行约 **2 小时**后崩溃（最长） | 同上 |
| 13 | 15:25 | **本次修复重启** | 同上 |

#### 根本原因

**缺少顶层异常捕获机制：**

```python
# server.py 问题代码（简化）
if __name__ == "__main__":
    uvicorn.run(app, host="127.0.0.1", port=8800)
    # ❌ 没有 try/except 包裹
    # ❌ 任何未捕获异常直接导致进程退出
    # ❌ 退出时不留任何错误日志
```

日志中崩溃前后没有任何 ERROR 记录，说明异常发生在 Python 虚拟机层面（如 Segmentation Fault、系统级错误），或者 uvicorn 工作进程被操作系统直接终止。

**可能的触发原因（无法确定具体哪个）：**
1. `subprocess.run()` 调用 Claude CLI 时，子进程僵尸化导致主进程死锁
2. `httpx` 网络请求超时导致 asyncio 事件循环崩溃
3. Windows 下 `signal.signal()` 处理不当导致进程被 kill
4. LocalTunnel 的 node.js 进程异常退出触发连锁反应

#### 解决方案

1. **添加全局异常捕获钩子**：
   ```python
   import sys, traceback
   def global_excepthook(exc_type, exc_value, exc_traceback):
       with open("crash.log", "a", encoding="utf-8") as f:
           traceback.print_exception(exc_type, exc_value, exc_traceback, file=f)
   sys.excepthook = global_excepthook
   ```

2. **在 `uvicorn.run()` 外层包裹 `try/except`**
3. **使用 nssm 注册为 Windows 服务**（已提供 `install-service.bat`），崩溃后自动重启
4. **添加看门狗进程**：监控主进程是否存活

#### 当前状态

✅ **部分修复**。已添加 nssm 服务安装脚本，但全局异常捕获尚未实施。

### 🔴 问题 2：模型不一致（deepseek-v4-pro[1m] vs flash）（严重）

> 🆕 **补充问题** — 原有文档未记录。

#### 现象描述

所有 Claude CLI 调用日志中，模型名称显示为 `deepseek-v4-pro[1m]`，而非预期的 `deepseek-v4-flash`：

```log
# 全部 20+ 次 Claude CLI 调用（11:47 ~ 15:29）都使用 pro 模型
2026-07-13 11:56:06,385 [INFO] ANTHROPIC_MODEL=deepseek-v4-pro[1m]      ← 含 ANSI 转义码
2026-07-13 12:04:20,051 [INFO] ANTHROPIC_MODEL=deepseek-v4-pro[1m]      ← 同上
2026-07-13 12:54:26,229 [INFO] ANTHROPIC_MODEL=deepseek-v4-pro[1m]      ← 同上
# ... 全部调用均如此
```

而 `config.json` 中实际配置的是：
```json
{
  "claude": {
    "env": {
      "ANTHROPIC_MODEL": "deepseek-v4-flash"
    }
  }
}
```

同时 `[1m` 是 **ANSI 终端转义码**（SGR 参数，表示加粗），说明值是从终端输出中复制而来。

#### 根本原因

**全局 settings.json 覆盖 per-service 配置：**

```
配置文件优先级链：
1. C:\Users\asus\.claude\settings.json（全局）← 优先级最高
   → 包含 ANTHROPIC_MODEL=deepseek-v4-pro（带 ANSI 转义码 [1m）
   
2. F:\积昌的知识库 - 副本\总结好的大纲以及笔记\技能\AI\智能助手的配置\企业微信智能助手\微信智能助手\config.json（服务配置）
   → 包含 ANTHROPIC_MODEL=deepseek-v4-flash
   ← 被全局配置覆盖，未生效
```

#### 影响

1. **费用增加**：pro 模型单价远高于 flash，增加 API 调用成本
2. **响应变慢**：pro 模型推理速度低于 flash
3. **ANSI 码污染**：`[1m` 作为模型名的一部分，可能在某些 API 调用中导致错误
4. **误导用户**：用户以为使用的是 flash 模型，实际使用的是 pro

#### 解决方案

1. **清理全局 settings.json**：移除或修正 `ANTHROPIC_MODEL` 等变量
2. **在 server.py 的 `subprocess.run()` 中强制覆盖**：通过 `env` 参数显示传递，优先级最高
   ```python
   env = os.environ.copy()
   env["ANTHROPIC_MODEL"] = "deepseek-v4-flash"
   subprocess.run(cmd, env=env, ...)
   ```
3. **添加启动验证**：在服务启动时，对比 config.json 与全局配置的差异并记录警告

#### 当前状态

✅ **已修复**。迁移至 `F:\积昌的知识库 - 副本\总结好的大纲以及笔记\技能\AI\智能助手的配置\企业微信智能助手\微信智能助手\` 后，模型配置已统一。

### 🔴 问题 3：Cloudflare Tunnel + WARP 冲突（严重）

> 🆕 **补充问题** — 原有文档未记录。

#### 现象描述

服务首次启动时使用 Cloudflare Tunnel（`cloudflared`），结果如下：

```log
11:47:44 - 启动 Cloudflare Tunnel: C:\Program Files (x86)\cloudflared\cloudflared.exe
11:47:49 - ✅ Tunnel URL: https://literacy-aqua-celtic-bibliography.trycloudflare.com
```

仅运行约 **5 分钟**后，服务崩溃。随后立即迁移到 LocalTunnel：

```log
11:53:01 - 启动 LocalTunnel (via: lt.cmd)
11:53:04 - ✅ Tunnel URL: https://silent-cups-chew.loca.lt
```

#### 根本原因

用户电脑同时运行 **Cloudflare WARP**（VPN/代理软件），导致以下冲突：

1. **WARP 劫持 DNS 解析**：Cloudflare Tunnel 依赖 DNS 解析到 Cloudflare 边缘网络，但 WARP 篡改了 DNS 响应
2. **端口冲突**：`cloudflared` 在本地创建代理端口时，WARP 可能拦截了流量
3. **路由冲突**：Tunnel 流量经过 WARP 加密隧道又经过 cloudflared 隧道，形成嵌套隧道，导致连接不稳定

**典型症状：** Tunnel 连接反复断开重连 → 企业微信回调失败 → 服务异常退出

#### 解决方案

1. **切换到 LocalTunnel**（`lt.cmd`）：LocalTunnel 通过 **HTTPS WebSocket** 直接连接公网服务器，不受 WARP DNS 劫持影响
2. 在 server.py 中添加 `--with-tunnel` 模式，默认使用 LocalTunnel
3. 添加启动日志确认隧道类型

#### 当前状态

✅ **已修复**。LocalTunnel 运行稳定，最长运行 **2 小时**未崩溃。

### 🟡 问题 4：Tunnel 子域名竞争（中等）

> 已有记录，补充技术细节。

#### 现象描述

```log
2026-07-13 12:57:58,963 [WARNING] 子域名 jichang-vault-0a9bccb4e4 被占用，将使用随机子域名
2026-07-13 12:57:58,964 [INFO] 当前 Tunnel URL: https://bitter-snake-40.loca.lt
```

子域名变更后，企业微信管理后台配置的回调 URL **立即失效**，用户必须手动更新。

#### 根本原因

1. **旧 Tunnel 进程未完全释放子域名**：`server.py` 启动时会先执行 `taskkill /f /im node.exe`，但旧 LocalTunnel 进程释放子域名需要 **3-5 秒**
2. **新进程抢先启动**：旧进程的 node.exe 被 kill 后，新进程立即尝试申请同一子域名，但 loca.lt 服务端尚未释放该子域名
3. **缺少重试机制**：服务在子域名申请失败后，直接使用随机子域名，不等待重试

#### 解决方案

1. **增加等待时间**：kill 旧进程后等待 5 秒再启动新 Tunnel
2. **添加子域名重试机制**：失败后每 2 秒重试一次，最多重试 5 次
3. **记录旧 Tunnel URL 并自动更新回调 URL**（需企业微信 API 支持）

#### 当前状态

🟡 **部分修复**。添加了 waiting 逻辑，但自动更新回调 URL 尚未实现。

### 🟡 问题 6：不支持 file 类型消息回调（中等）

> 🆕 **补充问题** — 原有文档未记录。

#### 现象描述

用户通过企业微信发送 PDF 等文件时，服务可以通过 `file` 类型的回调收到消息：

```xml
<MsgType><![CDATA[file]]></MsgType>
```

但日志中**没有 file 类型的处理记录**，说明：

1. 用户发送的 PDF 文件，企业微信服务器可能没有以 `file` 类型触发回调
2. 或者 `file` 类型的回调被服务器的错误处理捕获
3. 用户在后续文本消息中说"已发送"，说明文件发送和文本消息是**分开发送的**

#### 根本原因

**企业微信的消息回调机制与飞书不同：**

| 平台 | 文件通知方式 |
|------|-------------|
| 飞书 | 直接推送 `file` 类型事件到 WebSocket（含下载链接） |
| 企业微信 | 推送加密 XML 回调到 HTTP URL，`file` 类型包含 MediaId（需额外调用 API 下载） |

企业微信的 `file` 回调需要：
1. 从 XML 中提取 `MediaId`
2. 调用企业微信 API `GET /cgi-bin/media/get` 下载文件
3. 将文件保存到本地

**当前 server.py 并未实现 file 消息的处理逻辑**，只处理了 text 和 event 类型。

#### 解决方案

1. **添加 file 消息处理**：提取 `MediaId` 并通过 WeCom API 下载
2. **添加文件关联逻辑**：将文件与用户的后续文本消息关联
3. **实现文件下载功能**：使用 `httpx` 调用 WeCom 媒体文件 API

#### 当前状态

🟡 **未修复**。file 类型消息尚未实现处理逻辑。

### 🟡 问题 7：进程清理过于粗暴（中等）

> 已有记录，补充影响分析。

#### 现象描述

`restart-service.bat` 和 `fix-all.bat` 中使用：

```batch
taskkill /f /im python.exe   ← 杀死所有 Python 进程
taskkill /f /im node.exe     ← 杀死所有 Node.js 进程
```

#### 风险

1. **误杀飞书服务**：飞书智能助手（PID 60116）也使用 `python.exe`，会被同时杀掉
2. **误杀其他 Node.js 服务**：可能误杀其他运行的 Node 应用
3. **数据丢失**：被杀进程正在写入的数据可能损坏

#### 解决方案

1. **记录具体 PID**：启动服务时保存 PID 到 `server_pid.txt`
2. **精确 kill**：只 kill 记录的 PID：
   ```batch
   if exist "%SCRIPT_DIR%\server_pid.txt" (
       set /p PID=<"%SCRIPT_DIR%\server_pid.txt"
       taskkill /f /PID !PID! 2>nul
   )
   ```
3. **同样记录 Tunnel PID**：`tunnel_pid.txt`

#### 当前状态

🟡 **未修复**。仍使用粗暴的 `taskkill /im` 方式。

🟡 **部分修复**。固定子域名已实现，但 URL 变化后仍需手动更新企业微信后台。

### 🔵 问题 12：claude-settings.json 权限过大（轻微）

> 🆕 **补充问题** — 原有文档未记录。

#### 现象描述

`claude-settings.json` 中设置了通配权限：

```json
{
  "permissions": {
    "allow": ["*"]
  }
}
```

#### 风险

1. **Claude 可执行任意系统命令**：包括文件删除、网络请求等
2. **安全边界缺失**：虽然当前环境是本地运行，但 `*` 权限不符合最小权限原则
3. **潜在误操作**：Claude 可能在处理任务时执行意外命令

#### 解决方案

```json
{
  "permissions": {
    "allow": [
      "Read",
      "Write",
      "Edit",
      "Bash(git:*)",
      "Bash(mkdir:*)",
      "Bash(ls:*)",
      "Bash(python:*)",
      "Grep",
      "Glob"
    ]
  }
}
```

#### 当前状态

🟡 **未修复**。仍使用 `["*"]` 通配权限。

### 4.3 教训与改进措施

1. **架构健壮性**
   - 任何 Web 服务必须添加全局异常捕获
   - 关键服务应使用 nssm 或同类工具注册为系统服务
   - 进程管理应使用 PID 文件而非 `taskkill /im`

2. **配置管理**
   - 全局 settings.json 会无条件覆盖 per-service 配置
   - 服务应通过 `subprocess.run(env=...)` 强制覆盖关键变量
   - 最小权限原则：`claude-settings.json` 不应使用 `["*"]`

3. **内网穿透选择**
   - 如果使用 Cloudflare WARP，必须使用 LocalTunnel 而非 Cloudflare Tunnel
   - 固定子域名对生产环境至关重要
   - 应实现 Tunnel URL 的自动检测和回调 URL 更新

4. **消息类型覆盖**
   - 企业微信支持 text、file、image、link、event 等多种消息类型
   - 所有类型都应有对应的处理逻辑或友好提示
   - `file` 类型的 MediaId 下载是企业微信文件处理的核心
