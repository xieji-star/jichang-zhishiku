## 一、系统概述

### 1.1 系统定位

企业微信智能助手是一个 **Python FastAPI Web 服务**，通过**内网穿透工具**暴露本地端口到公网，接收企业微信推送的 HTTP 回调消息，将用户从微信/企业微信发送的消息和文件交由 **Claude CLI（实际调用 DeepSeek API）** 处理，最终将处理结果写入 **Obsidian Vault** 并通过企业微信 API 回复用户。

### 1.2 核心架构

```
微信 (WeChat) → 企业微信 (WeCom) → LocalTunnel → Python FastAPI 服务 → Claude CLI → Obsidian Vault
                                                    ↓
                                          企业微信 API (回复用户)
```

### 1.3 架构核心特点

| 特点 | 说明 |
|------|------|
| 🔌 **被动推送** | 企业微信通过 HTTP POST 回调推送消息，服务无需主动轮询 |
| 🛡️ **AES 加密通信** | 所有回调消息使用 AES 加密，需 wechatpy 解密 |
| 🌐 **内网穿透必需** | 回调 URL 必须公网可达，需要 LocalTunnel 或 Cloudflare Tunnel |
| ⚡ **FastAPI 异步** | 基于 FastAPI + Uvicorn 的异步 Web 服务器 |
| 🔒 **单实例并发控制** | processing_lock 确保 Claude CLI 单实例运行 |
| 🏗️ **Windows 服务管理** | 使用 nssm 注册为 Windows 服务，实现开机自启 |

## 三、系统架构与数据流

### 3.1 完整数据流

```
微信用户发送消息
       │
       ▼
┌─────────────────────────────────────┐
│          企业微信服务器                │
│  接收消息 → 调用回调 URL             │
│  ↓                                  │
│  回调 URL: https://xxx.loca.lt/     │
│           wecom/callback            │
└──────────────┬──────────────────────┘
               │ HTTPS POST（XML 加密）
               ▼
┌─────────────────────────────────────┐
│        LocalTunnel 隧道              │
│  公网 → 本地端口 8800 转发           │
└──────────────┬──────────────────────┘
               │ 本地转发
               ▼
┌─────────────────────────────────────┐
│      FastAPI 服务 (localhost:8800)    │
│                                      │
│  POST /wecom/callback:               │
│   ├── 接收加密 XML                    │
│   ├── WeChatCrypto 解密              │
│   ├── parse_xml_message() 解析       │
│   ├── 判断 MsgType(text/file/event)  │
│   ├── 加入 task_queue (Queue)        │
│   └── 返回 "success" (避免重试)       │
│                                      │
│  task_worker() (后台线程):            │
│   ├── 文件消息 → download_media()    │
│   ├── 生成 prompt                    │
│   ├── run_claude_task()              │
│   │   └── Claude CLI → DeepSeek API  │
│   └── send_text_message() 回复用户    │
└──────────────────────────────────────┘
```

### 3.2 消息类型处理

| 消息类型 (MsgType) | 处理方式 |
|-------------------|---------|
| `text` | 解析命令（整理笔记/搜索/帮助）或自然语言 → 调用 Claude |
| `file` | 下载文件到 wecom-resources → 调用 Claude 处理 |
| `event` | 暂不处理，仅记录日志 |
| 其他（link 等） | 记录日志，回复"暂不支持" |

## 四、核心功能详解

### 4.1 URL 验证（GET /wecom/callback）

企业微信在配置回调 URL 时发送 GET 请求验证：

```python
@app.get("/wecom/callback")
async def wecom_verify(msg_signature, timestamp, nonce, echostr):
    decrypted = crypto.check_signature(
        msg_signature, timestamp, nonce, echostr
    )
    return PlainTextResponse(content=decrypted)
```

### 4.2 消息接收与解密（POST /wecom/callback）

```python
@app.post("/wecom/callback")
async def wecom_callback(request, msg_signature, timestamp, nonce):
    # 1. 获取原始 XML
    raw_body = await request.body()
    xml_str = raw_body.decode("utf-8")

    # 2. AES 解密
    decrypted_xml = crypto.decrypt_message(
        xml_str, msg_signature, timestamp, nonce
    )

    # 3. XML 解析
    msg_data = parse_xml_message(decrypted_xml)

    # 4. 加入任务队列
    task_queue.put(task)

    # 5. 必须返回 "success"
    return PlainTextResponse(content="success")
```

### 4.3 文件下载

通过企业微信 Media API 下载文件：

```python
def download_media(media_id: str) -> Optional[bytes]:
    token = get_access_token()
    url = f"https://qyapi.weixin.qq.com/cgi-bin/media/get?access_token={token}&media_id={media_id}"

    response = http_client.get(url)
    # 检查 Content-Type 判断是否返回了错误 JSON
    if "application/json" in response.headers.get("Content-Type", ""):
        error_data = response.json()
        logger.error(f"下载媒体文件失败: {error_data}")
        return None
    return response.content  # 保存到 wecom-resources/
```

> [!NOTE] 文件下载限制
> - 企业微信媒体文件**有效期 3 天**，过期后无法下载
> - 文件大小限制：**20MB**（企业微信）/ **10MB**（微信互通）
> - 下载后保存在 `wecom-resources/` 目录，不自动清理

### 4.4 Prompt 生成

| 消息类型 | 命令 | 行为 |
|---------|------|------|
| text | `整理笔记 [文件夹] [名称]` | 调用 meeting-summary skill 处理关联文件 |
| text | `/帮助` / `帮助` | 生成机器人帮助信息 |
| text | `/搜索 [关键词]` | 在 Vault 中搜索内容 |
| text | 自然语言 | 理解意图并执行 |
| file | - | 下载文件并分析内容（询问用户用途） |

### 4.5 任务队列与并发控制

```python
task_queue: queue.Queue = queue.Queue()
processing_lock = threading.Lock()

# 后台工作线程
worker_thread = threading.Thread(target=task_worker, daemon=True)
worker_thread.start()

def task_worker():
    while True:
        task = task_queue.get(timeout=1)
        process_task(task)  # 单线程处理，保证顺序

def process_task(task):
    with processing_lock:  # 🔒 确保 Claude CLI 单实例
        is_processing = True
        claude_output = run_claude_task(prompt)
        is_processing = False
```

> [!WARNING] ⚠️ 无多轮对话
> 与飞书方案不同，企业微信版**没有多轮对话机制**。文件消息直接自动处理，收到文本命令也立即执行。这是因为企业微信回调是无状态的 HTTP 请求模型。

### 4.6 配置状态自检（is_configured）

服务启动时自动检测企业微信配置完整性，通过 `is_configured` 全局变量跟踪状态：

```python
is_configured = not wecom_config.get("corp_id", "").startswith("YOUR_")

# 影响以下行为：
# - 加密模块初始化（crypto）
# - API 客户端初始化（wecom_client）
# - 健康检查返回值（wecom_configured 字段）
# - 消息解密（未配置则跳过）
# - 文件下载（未配置则无法获取 access_token）
```

> [!NOTE] 配置未完成时
> 即使 `config.json` 未填写，服务也能启动。健康检查返回 `wecom_configured: false`，所有需要企业微信 API 的功能（消息解密、文件下载、回复用户）会自动跳过并记录警告，方便先启动服务再逐步配置。

### 4.8 文件关联机制

当用户先发送文件、再发送文字指令时，通过 `last_received_file` 全局变量关联。文件消息的处理流程如下：

```
用户发送文件 → last_received_file 保存 media_id/title/timestamp
                   ↓
用户发送文字命令 → 检查 last_received_file 是否为空
                   ↓
非空 → task["file_path"] 指向 last_received_file["local_path"]
  空 → 纯文字命令（无关联文件）
                   ↓
处理完成后 → 清理 last_received_file（避免重复关联）
```

```python
last_received_file: Optional[dict] = None

# 收到文件时保存（仅保存元数据，文件在 task_worker 中下载）
last_received_file = {
    "media_id": media_id,
    "title": title,
    "from_user": from_user,
    "timestamp": time.time(),
    "local_path": None,  # 在 process_task() 中下载后更新
}

# 收到文字命令时检查关联
if last_received_file:
    task["file_path"] = last_received_file.get("local_path", "")
    task["file_info"] = last_received_file

# 处理完成后清理关联（避免重复使用）
if last_received_file and task.get("file_path") == last_received_file.get("local_path"):
    last_received_file = None
```

> [!NOTE] ⚠️ 无自动超时清理
> 与飞书方案不同，企业微信版 **没有 5 分钟超时自动清理** `last_received_file` 的机制。文件关联仅在处理完成后主动清除。这意味着用户在发送文件后的任意时间内发送"整理笔记"命令，都可能关联到之前收到的文件。

## 五、内网穿透方案

### 5.1 为什么需要内网穿透？

企业微信回调 URL **必须是公网可访问的地址**。本机开发环境在局域网内，无法直接接收来自企业微信服务器的 HTTPS 请求，需要通过内网穿透工具将本地端口暴露到公网。

### 5.2 方案选择

| 方案 | 工具 | 适用场景 | 固定子域名 | 与 WARP 兼容 |
|------|------|---------|-----------|-------------|
| **方案 A（备用）** | Cloudflare Tunnel (`cloudflared`) | 默认场景 | ❌ 每次重启变化 | ❌ 冲突 |
| **方案 B（主力）** | LocalTunnel (`lt`) | 启用 WARP 时 | ✅ 通过 CorpID 哈希生成 | ✅ 兼容 |

### 5.3 方案 A：Cloudflare Tunnel

```bash
# 安装
winget install Cloudflare.cloudflared

# 启动
cloudflared tunnel --url http://localhost:8800
# 输出：https://xxxxx.trycloudflare.com
```

> ⚠️ **已知问题**：Cloudflare WARP 会劫持 cloudflared 的 DNS/流量，导致无法连接。已因此方案迁移至 LocalTunnel。

### 5.4 方案 B：LocalTunnel（主力）

#### 启动方式

```bash
# 手动启动
lt --port 8800 --subdomain jichang-vault-xxxxxxxxxx

# 通过服务启动（添加 --with-tunnel 参数）
python server.py --with-tunnel
```

#### 固定子域名生成

```python
corp_id = wecom_config.get("corp_id", "default")
subdomain_hash = hashlib.sha256(corp_id.encode()).hexdigest()[:10]
desired_subdomain = f"jichang-vault-{subdomain_hash}"
# 结果示例：jichang-vault-0a9bccb4e4
```

#### 自动检测 Tunnel URL

服务启动后，会等待 LocalTunnel 输出 URL（最长 60 秒），然后保存到 `current-tunnel-url.txt`：

```python
for i in range(60):
    time.sleep(1)
    with open(tunnel_log, "r") as f:
        for line in f:
            if "your url is:" in line.lower():
                match = re.search(r"https://[a-zA-Z0-9-]+\.loca\.lt", line)
                if match:
                    tunnel_url = match.group(0)
                    break
```

### 5.5 子域名被占用时的降级行为

当期望的固定子域名（如 `jichang-vault-0a9bccb4e4`）被其他 LocalTunnel 实例占用时，服务不会报错退出，而是自动降级使用随机子域名：

```python
if desired_subdomain not in tunnel_url:
    logger.warning(f"子域名 {desired_subdomain} 被占用，将使用随机子域名")
```

此时 Tunnel URL 变为随机字符串（如 `bitter-snake-40.loca.lt`），需要手动更新企业微信后台的回调 URL。重启服务并确保旧进程已完全退出即可恢复固定子域名。

### 7.1 回调端点必须返回 "success"

### 7.9 Windows 无窗口启动进程

当启动 LocalTunnel 子进程时，使用 `CREATION_NO_WINDOW` 标志防止弹出控制台窗口：

```python
tunnel_process = subprocess.Popen(
    [lt_path, "--port", str(port), "--subdomain", subdomain],
    stdout=open(tunnel_log, "a"),
    stderr=subprocess.STDOUT,
    creationflags=subprocess.CREATE_NO_WINDOW  # Windows 无窗口标志
)
```

> 如果不加此标志，LocalTunnel 的 Node.js 进程会在每次启动时弹出一个控制台窗口，影响用户体验。

### 7.10 优雅关闭与信号处理

服务启动时注册 `SIGTERM` 和 `SIGINT` 信号处理器，在退出时自动清理 Tunnel 子进程：

```python
def cleanup():
    logger.info("正在关闭服务...")
    if tunnel_process:
        tunnel_process.terminate()
        logger.info("Tunnel 进程已终止")

signal.signal(signal.SIGTERM, lambda s, f: cleanup())
signal.signal(signal.SIGINT, lambda s, f: cleanup())

try:
    uvicorn.run(app, host=host, port=port)
finally:
    cleanup()  # 确保即使 uvicorn 异常退出也清理
```

> 此机制确保通过 `nssm stop` 或 `Ctrl+C` 停止服务时，LocalTunnel 子进程不会残留。

### 12.2 架构差异的本质

```
企业微信:                        飞书:
┌──────────┐     ┌──────────┐   ┌──────────┐
│ 企业微信   │────▶│ LocalTun │   │ 飞书     │─────┐
│ 服务器    │     │ nel(公网) │   │ 服务器   │     │ WebSocket
└──────────┘     └──────────┘   └──────────┘     │
      ↑               │                      ┌───▼──────────┐
      │  HTTPS 回调    │                      │ lark-cli     │
      │               ▼                      │ event consume│
┌─────┴──────────────┐                       └───┬──────────┘
│ FastAPI (local:8800)│                           │ stdin/stdout
└────────────────────┘                           ▼
                                           ┌──────────────┐
                                           │ Python 脚本   │

```

企业微信方案需要**公网可达的回调 URL**，因此必须依赖内网穿透；飞书方案中 lark-cli 主动连接飞书服务器建立 WebSocket 长连接，**不需要任何内网穿透**。

### 12.3 功能差异总结

| 飞书有 / 企业微信无 | 影响 |
|---------------------|------|
| 多轮对话 | 企业微信：文件直接自动处理；飞书：先问用户"怎么处理？" |
| 本地命令处理器 | 企业微信：问候也要 6-9 秒；飞书：<1 秒 |
| 双模式接管 | 企业微信：只有自动模式；飞书：可随时切换人工接管 |
| admin.py 远程控制 | 企业微信：无法远程查看状态；飞书：Claude Code 可远程管理 |
| 看门狗自动恢复 | 企业微信：崩溃后需手动重启；飞书：3 秒自动重连 |
| PDF 预提取加速 | 企业微信：Claude 自行读取；飞书：PyMuPDF 预提取嵌入 prompt |

## 📌 总结

### 架构亮点

1. **企业微信原生集成**：通过 HTTPS 回调 + AES 加密通信，符合企业微信官方标准
2. **异步 Web 框架**：FastAPI + Uvicorn 提供高性能异步请求处理
3. **Windows 服务化**：通过 nssm 注册为系统服务，实现开机自启
4. **固定 Tunnel 子域名**：基于 CorpID 哈希生成，重启后 URL 不变
5. **单实例并发控制**：processing_lock 确保 Claude CLI 单实例运行，避免资源竞争

### 技术栈核心关系

```
Obsidian Vault（知识存储）
     ↑
Claude CLI（AI 代理层）→ 实际调用 DeepSeek API（模型推理）
     ↑ subprocess
Python FastAPI 服务（业务逻辑层）
     ↑ wechatpy 解密 + httpx 下载
LocalTunnel（内网穿透层）
     ↑ HTTPS 回调
企业微信服务器
     ↑
用户（微信 App）
```

### 与飞书方案的选择建议

| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| 日常使用微信沟通 | **企业微信** | 微信互通，无需额外 App |
| 复杂文件处理 | **飞书** | 多轮对话 + PDF 预提取体验更好 |
| 需要远程管理 | **飞书** | admin.py 提供完整的远程控制能力 |
| 追求低延迟 | **飞书** | 本地命令处理器 <1 秒 |
| 追求稳定性 | **飞书** | 看门狗 + 自动重连，无需手动干预 |
| 简单文件传输解析 | **企业微信** | 直接自动处理，无需多轮对话 |
