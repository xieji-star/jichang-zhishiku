# 0801请求过大：Read 工具读取 PDF 报错（Request too large）修复日志

> [!summary] 概要
> 2026-08-01 晚，让 AI 深度阅读大创项目的路演 PPT PDF（`智灌云联——AI硬件驱动玉米水肥引领者.pdf`）时触发报错：`Error: invalid_request Request too large (max 32MB)`，任务直接终止。排查后发现**<span style="color:#e74c3c">三层根因</span>**：① 该 PDF 是纯图片拼合型（26 页、内嵌图片总像素 103.9MP、最大图宽 2666px），渲染成图片后单次请求体积超过 32MB 上限；② 机器未安装 poppler（pdftoppm 命令行工具），Read 工具的 PDF 渲染管线本身故障；③ 本会话还存在图片投递受限的现象（连 181 字节的 PNG 都无法投递）。修复方案：**<span style="color:#2980b9">重渲染压缩 + 拆分成 4 个分卷</span>**（每卷渲染体积 5.5–6.7MB，远低于上限），并用 winget **<span style="color:#2980b9">安装 Poppler 25.07.0</span>** 修复环境依赖，原文件已备份至 `原始文件备份/`，重启会话后生效。

## 1. 报错概况

### 1.1 报错场景

- 触发指令：让 AI 深度阅读 `已整理好的文件/学校文件/大创与国创` 文件夹下的项目文件，以"中国国际创新大赛国赛主评委"角色评审项目。
- 读取顺序：`智灌云联计划书（终版）.pdf` → `网评版本.pdf` → `智灌云联——AI硬件驱动玉米水肥引领者.pdf`。
- 🔥 **<span style="color:#e74c3c">第 3 个文件读取时直接报错终止任务</span>**，AI 无法继续评审。

### 1.2 原始报错信息与变体

本次排查过程中，同一根因在不同场景下表现出 4 种不同的报错形态：

| # | 报错信息 | 出现场景 |
|---|---------|---------|
| 1 | `Error: invalid_request Request too large (max 32MB). Try with a smaller file.` | 用户原会话：读取路演 PPT 原文件（12.4MB） |
| 2 | `invalid_request`（截断形态） | 本会话：读取 960px 重渲染单文件（5.0MB） |
| 3 | `pdftoppm failed: Command 'pdftoppm' not found or is in an unsafe location` | 本会话：任何 PDF 使用 `pages` 参数分段读取时 |
| 4 | `[Unsupported Document]` / `[Unsupported Image]` | 本会话：读取 PDF / 图片时内容无法投递 |

> [!warning] 结论
> 这 4 种报错形态**同源**：Read 工具处理 PDF 依赖本机 PDF 渲染管线，而管线缺失（缺 poppler）+ 文件渲染体积超限，共同导致读取失败。⚠️ 不要被不同报错文案误导，修复方向只有一个：**修环境 + 减体积**。

## 2. 根因分析

### 2.1 直接根因：请求体积超过 32MB 上限

- 💡 **<span style="color:#2980b9">Read 工具读 PDF 的机制</span>**：先把 PDF 每页渲染成图片，再一次性放入请求中发送给 AI 模型。
- 📊 **<span style="color:#e67e22">单次请求体积上限 32MB</span>**，且图片在请求中还要经过 base64（把二进制数据转成文本的编码方式，体积约增加 33%）编码，实际"可用"的图片体积约只有 24MB。
- 路演 PPT 渲染后的图片总量远超此上限，请求直接被 API 拒绝。

### 2.2 文件根因：图片拼合型 PDF 体积巨大

- 该 PDF 是 **PPT 导出型**：26 页全部是整页图片（每页 1 张），**<span style="color:#e67e22">无任何可选中文字</span>**。
- 内嵌图片最大宽 **<span style="color:#e67e22">2666px</span>**，图片总像素 **<span style="color:#e67e22">103.9MP</span>**——照片级内容 PNG 压缩率极低，渲染体积按像素数量近似平方增长。
- 对比：40 页的网评版本（66.5MP）能读、61 页的计划书终版（110.8MP 但都是小图 + 大量文字页）能读，唯独它失败——**<span style="color:#e74c3c">问题不在页数，而在每页的像素密度与内容复杂度</span>**。

### 2.3 环境根因：机器缺少 poppler（pdftoppm）

- 💡 **<span style="color:#2980b9">poppler</span>**：开源的 PDF 渲染工具库，提供 `pdftoppm`（把 PDF 页面转成图片的命令行工具）等命令。
- Read 工具的分段读取（`pages` 参数）和部分渲染路径依赖 `pdftoppm`，而本机**未安装**，导致 PDF 渲染管线整体不可用。
- 排查确认：`where pdftoppm` 无结果，全盘搜索无 `pdftoppm.exe`，本机无 Chocolatey，有 scoop 与 winget 包管理器。

### 2.4 环境观察：本会话图片投递受限

- 测试发现：即使 **<span style="color:#e67e22">181 字节的微型 PNG</span>** 也无法投递（返回 `[Unsupported Image]`），而同目录的文本文件读取完全正常。
- 说明本会话的 Read 工具对"视觉类文件"（PDF/图片）整体无法投递内容——与文件大小无关，属会话环境限制。

## 4. 修复过程

### 4.1 第一步：备份原文件

- 将原文件（12.4MB）复制到 `已整理好的文件/知识库报错日志/原始文件备份/`，确保可随时还原。
- 📌 **<span style="color:#e67e22">先备份、后改动</span>**——修复全程不丢任何原始数据。

### 4.2 第二步：重渲染压缩 1400px（不达标）

- 用 PyMuPDF 将 26 页重渲染为 1400px 宽、JPEG 质量 85，文件降到 7.3MB。
- ❌ 验证：1.46x 渲染仍达 **<span style="color:#e67e22">44.3MB</span>**，超限——压缩不到位。

### 4.3 第三步：重渲染压缩 960px（仍超限）

- 从备份重渲染为 960px 宽、JPEG 质量 90，文件降到 5.0MB，1.0x 渲染 23.1MB。
- ❌ 实测读取仍报 `invalid_request`——**<span style="color:#e74c3c">base64 编码后约 30.8MB 仍逼近 32MB 上限</span>**，且 26 页单次请求没有任何安全余量。

### 4.4 第四步：拆分 4 个分卷（达标 ✅）

- 核心思路：💡 **<span style="color:#2980b9">把"单次请求的像素总量"作为硬约束</span>**——拆小文件，而不是只压体积。
- 从备份以 1120px 宽、JPEG 质量 90 重渲染，按页拆成 **<span style="color:#e67e22">4 个分卷（7/7/6/6 页）</span>**：

| 分卷 | 页数 | 文件大小 | 1.0x 渲染 PNG | base64 后估算 |
|------|------|---------|--------------|--------------|
| 第 1 部分 | 7 页 | 1.7MB | 6.1MB | ~8.1MB |
| 第 2 部分 | 7 页 | 1.7MB | 6.7MB | ~8.9MB |
| 第 3 部分 | 6 页 | 1.4MB | 5.5MB | ~7.4MB |
| 第 4 部分 | 6 页 | 1.5MB | 5.7MB | ~7.6MB |

- ✅ 每卷渲染体积 5.5–6.7MB，**<span style="color:#e74c3c">远低于 32MB 上限，留足安全余量</span>**。

### 4.5 第五步：安装 poppler（winget）

- scoop 安装失败（main 桶损坏，见第 6 章问题 6）→ 改用 **<span style="color:#2980b9">winget</span>** 安装 `oschwartz10612.Poppler 25.07.0` 成功。
- 安装位置：`C:\Users\asus\AppData\Local\Microsoft\WinGet\Packages\oschwartz10612.Poppler_...\poppler-25.07.0\Library\bin`。
- ✅ 该路径已写入用户 PATH 注册表（`HKCU\Environment`）——**重启 Claude Code 后 pdftoppm 即可被找到**。

### 4.6 最终文件状态

- `大创与国创/PPT/路演PPT/`：4 个分卷（总计约 6.6MB，取代原单文件）。
- `知识库报错日志/原始文件备份/`：原始 PDF（12.4MB）完整保留。
- `网评PPT/`、`计划书/`：未做改动。

| 技术/工具 | 版本 | 用途 |
|-----------|------|------|
| Python | 3.13.12 | 脚本编写与运行 |
| PyMuPDF（fitz） | 1.28.0 | PDF 页数/图片分析、重渲染、JPEG 压缩、拆分 |
| pypdf | 6.1.3 | 备用检测（本修复主要用 PyMuPDF） |
| winget | Windows 自带 | 安装 Poppler（`oschwartz10612.Poppler 25.07.0`） |
| scoop | 已装 | 首次尝试安装 poppler（失败，桶损坏） |
| PowerShell | Windows 自带 | 查询用户 PATH 注册表 |
| Git Bash | 随 Git | 文件检索、环境检查 |
| Poppler | 25.07.0 | 提供 `pdftoppm`，修复 Read 工具 PDF 渲染依赖 |

> [!note] 专业名词
> - **<span style="color:#2980b9">poppler / pdftoppm</span>**：开源 PDF 渲染工具库 / 其 PDF 转图片命令行工具（Read 工具分段读取 PDF 的依赖）。
> - **<span style="color:#2980b9">base64</span>**：把二进制数据编码成文本的方式，图片进请求前会经过它，体积约增加 33%。
> - **<span style="color:#2980b9">渲染体积</span>**：PDF 被转成图片后的总字节量，决定请求是否会超限。
> - **<span style="color:#2980b9">JPEG 质量 q85/q90</span>**：JPEG 压缩参数，数值越高画质越好、文件越大。

## 6. 遇到的问题与解决

1. 🕳️ **1400px 压缩不达标**：文件压到 7.3MB 但渲染仍有 44.3MB → 意识到关键变量是**像素总量**而非文件大小，改走"低分辨率重渲染 + 拆分"组合。
2. 🕳️ **960px 单文件仍报 `invalid_request`**：实测读取失败 → 计算出 base64 后仍逼近上限，**单文件方案必须放弃**，改为拆分。
3. 🕳️ **拆分后 Read 仍返回 `[Unsupported Document]`**：1.7MB 的小分卷按体积论不该失败 → 深挖发现环境另有问题（缺 poppler、图片投递受限），不是文件能单独解决的。
4. 🕳️ **`pages` 参数分段读取硬报错**：`pdftoppm failed: Command 'pdftoppm' not found` → 确认本机未装 poppler，任何 PDF 分段读取都不可用。
5. 🕳️ **连 181 字节 PNG 都返回 `[Unsupported Image]`**：用微型图片 + 文本对照测试，确认本会话图片投递整体受限（与大小无关）→ 记录为环境限制，验证策略改为"体积数学验证 + 重启后终验"。
6. 🕳️ **scoop 安装 poppler 失败**：安装过程被杀（exit 137），且 scoop 自动更新时 main 桶转换损坏（`'main' bucket not found`）→ 放弃 scoop，切换 winget 一次成功。
7. 🕳️ **winget 安装后当前会话 PATH 不生效**：进程环境在会话启动时已固化，注册表已更新但当前会话仍找不到 pdftoppm → **重启 Claude Code 后生效**（已写入日志）。
8. 🕳️ **中文控制台乱码**：PyMuPDF 脚本输出在 GBK 控制台乱码 → 脚本加 `PYTHONIOENCODING=utf-8` 解决。

## 8. 使用建议与后续操作

- 🔥 **<span style="color:#e74c3c">重启 Claude Code 会话</span>**，让 Poppler 的 PATH 生效，再尝试读取路演 PPT 分卷验证修复效果。
- 📌 **读 PDF 规范**：
  - 单次读取控制在 **<span style="color:#e67e22">≤10 页</span>** 或渲染体积 **<span style="color:#e67e22">≤20MB</span>**（base64 后 ≤27MB），留足余量；
  - 大 PDF 先拆分成小文件再读（可用 PyMuPDF 脚本，见备份脚本思路第 4 章）；
  - 读取 PDF 时优先使用不带 `pages` 参数的方式（本机分段读取依赖 poppler，重启后可用）。
- ⚠️ **监测对象：`网评版本.pdf`**（9.7MB / 40 页，1.0x 渲染约 30MB，已达上限 94%）——若后续读取报同样错误，用同样的"重渲染 + 拆分"方法处理。
- 📌 **原始文件还原**：如需还原路演 PPT 原文件，从 `已整理好的文件/知识库报错日志/原始文件备份/` 复制回原目录即可。
- 💡 **经验沉淀**：PPT 导出的 PDF 往往是"图片拼合型"，体积大且无文字层，是 Read 报错的高发区；比赛材料建议同时保留一份"转图片分卷"版本供 AI 读取。
