# 知识库报错修复

把"报错"当作一次性事件处理（修完就忘）是最大的浪费——同一个根因会以 4 种不同的报错文案出现（见速查表），修一次只能解决表面问题。本 skill 的核心价值：**每次报错都走完整的"复现 → 三层诊断 → 备份 → 修复 → 验证 → 日志"闭环**，把根因、修复过程和经验沉淀到 `总结好的大纲以及笔记/知识库FAQ/`（2026-08-04 起统一存放地），让下次报错有据可查、同类问题直接命中。**同时每次修复必须更新报错统计台账（`00-报错统计台账.md`），按根因累计类型与次数**（2026-08-12 新增固定规则），让高频报错一目了然。**每份 FAQ 报错文档顶部还需常驻「📊 报错统计速览」块**（2026-08-13 新增固定规则，规则见第六步），把本文档累计报错总数放到标题下方最显眼处，与台账同步更新。**报错发生时先查 FAQ 再诊断**（2026-08-04 用户确认的固定规则）：优先阅读 `总结好的大纲以及笔记/知识库FAQ/` 的往期报错记录，按关键词命中后直接采用文档记载的根因与修复方案，未命中再走完整三层诊断。**写日志前必须先查重**：知识库内已有相关记录的报错 → 补充进对应文档对应位置，不新建文档；未记录过的 → 在 `知识库FAQ/` 新建（命名参考该文件夹既有报错文档格式）。

本 skill 由 [[references/0801请求过大案例.md]] 提炼而来（该案例是完整的实战记录，含全部数据与踩坑过程，遇到陌生情况时先读它）。

## 工作流程

### 第一步：记录时间并优先查阅 FAQ（快速定位）

1. 先运行 `date` 记录当前时间（精确到分钟）——日志需要时间戳，这也是知识库每日首条指令的规则。
2. **优先查阅 `总结好的大纲以及笔记/知识库FAQ/` 的往期报错记录**（2026-08-04 用户确认的固定规则）：用当前报错文案的**关键词**匹配 FAQ 文档（见下表），命中后**完整阅读对应文档**，按其中记载的根因与修复方案快速定位、照方处理，可跳过或大幅简化后续三层诊断；未命中 → 进入完整三层诊断。

3. 复现报错：用与用户相同的操作尝试读取报错对象，拿到**精确的报错原文**。
4. 关键认知：⚠️ 同一个根因会有 4 种不同报错形态（见速查表），**以诊断结果为准，不要被报错文案误导**。如果无法复现（文件现在能读），检查"会话上下文累积"因素——同一次会话里已读过多个大文件时，请求体是累计的。

### 第二步：三层诊断（核心，决定修复方向）

报错必然落在以下三层之一，逐层排查：

**① 文件层（报错对象本身）**
- 是 PDF 时运行 `python scripts/pdf_diagnose.py <pdf路径>` 体检：页数、文字层字符数、内嵌图片像素总量、最大图宽、1x/1.5x/2x 渲染 PNG 体积。
- 判据：💡 Read 工具读 PDF 是先把每页渲染成图片再整体发送，**单次请求上限 32MB**，图片经 base64 编码还有约 +33% 开销，所以"可用"渲染体积实际约 24MB。
- 高危特征：纯图片拼合型 PDF（无文字层、每页一张整页图、图宽 2000px+）——这类文件渲染体积按像素量平方级增长，是最常见的爆雷对象。

**② 环境层（机器依赖）**
- 检查 poppler：`where pdftoppm`；若找不到，再查用户 PATH 注册表（PowerShell：`[Environment]::GetEnvironmentVariable('Path','User')`）与 WinGet Packages 目录。
- 判据：Read 工具的 PDF 渲染依赖 poppler 提供的 `pdftoppm`（PDF 转图片命令行工具）。缺失时：`pages` 参数读取硬报错 `pdftoppm failed`，整份读取软失败返回 `[Unsupported Document]`。

**③ 工具/会话层（当前会话能力）**
- 对照测试：在报错文件同目录放一个 txt 文件和一个几 KB 的小 png，分别用 Read 读取。
- 判据：txt 能读而 png 不能读（返回 `[Unsupported Image]`，哪怕 181 字节）→ 本会话图片投递受限，任何视觉类文件（PDF/图片）都无法投递内容，与文件大小无关。

### 第三步：备份（先备份后改动）

- 修改任何原文件之前，先把原件复制到 `总结好的大纲以及笔记/知识库FAQ/原始文件备份/`（保持原名；同名已存在时加日期后缀）。
- 这是硬性安全底线：修复过程绝不丢失原始数据，日志里也要写明备份位置。

### 第四步：修复（按诊断结果选择）

**A. 文件层渲染体积超限 → `python scripts/pdf_fix_split.py <pdf路径>`**
- 默认参数：目标宽 1120px、JPEG 质量 90、每卷 7 页。产物为 `原名_第N部分.pdf` 分卷，输出在源文件同目录。
- 设计理由：**把"单次请求的像素总量"当作硬约束**。只压缩不拆分（如压到 960px）仍会因 base64 开销逼近上限；拆分让每次请求的像素量直接减半以上，无论工具内部如何缩放都安全。
- 安全线：单卷 1x 渲染 PNG ≤ 10MB（base64 后 ≤ 13MB，对 32MB 上限留足余量）。
- 修复后原单文件可删除（内容已由分卷替代，备份仍在）。

**B. 环境层缺 poppler → winget 安装**
- 执行：`winget install --id oschwartz10612.Poppler --accept-package-agreements --accept-source-agreements -h --disable-interactivity`
- scoop 也可用（`scoop install poppler`），但 main 桶可能损坏（报 `'main' bucket not found`），损坏时不要修桶，直接切 winget。
- 装完验证：检查用户 PATH 注册表是否包含 `...\WinGet\Packages\oschwartz10612.Poppler_...\poppler-xx\Library\bin`。
- ⚠️ 当前会话的 PATH 是启动时固化的——**必须明确提示用户重启 Claude Code 后生效**，不要在当前会话里反复重试同一操作。

**C. 会话层图片投递受限 → 本会话无法彻底修复**
- 完成文件层的体积数学验证 + 环境层检查，把"重启后终验"写进日志和汇报，如实说明，不编造成功。

### 第五步：验证

- 数学验证：分卷脚本输出的验证表（每卷 1x 渲染 PNG ≤ 10MB、页数合计 = 原页数、备份存在）。
- 实测读取：Read 读取分卷第 1 部分；能读到内容即通过；若仍返回 `[Unsupported Document]`，如实记录为"会话环境限制，待重启后终验"。
- 诚实记录未能验证的项——日志的价值在于真实，不在于好看。

### 第六步：写报错日志 + 更新报错统计台账（必须执行，先查重再落盘）

**查重规则**（2026-08-04 用户确认的固定规则）：
- **规则 1（已有记录 → 补充）**：若本次报错类型在知识库内已有相关文档记录（重点查 `总结好的大纲以及笔记/知识库FAQ/`，按报错类型关键词匹配，如「会话ID未找到」对应 `03-Claudian会话ID未找到（双机同步）.md`），则**将本次内容补充进该文档的对应位置**（按文档既有的"复发记录"格式追加，并同步更新 frontmatter 的 `updated` 字段），**不新建文档**。
- **规则 2（无记录 → 新建）**：若知识库内无任何相关记录，则新建文档，**位置固定为 `总结好的大纲以及笔记/知识库FAQ/`**，命名参考该文件夹既有报错文档的格式：`NN-报错类型简短描述.md`（两位数字序号递增 + 具体报错类型，如 `01-Obsidian反复报错Request too large.md`；**禁止**用笼统的"报错"二字代替类型）。
- 查重判据：以报错类型的**根因/现象**为准（如"会话ID未找到"、"Request too large"），不完全相同的报错文案不算重复记录。
- 与第一步的关系：**第一步的优先查阅**用于快速定位修复方案（命中即照方处理）；**第六步的查重**用于归档落盘（决定补充还是新建）。两者共用同一套关键词匹配。

**排版**：调用 `/文档转换+排版` skill 排版（功能四：Obsidian 笔记排版规则），输出必须包含：
  - frontmatter（title / type / date / tags / source）；
  - 概要 callout、相关笔记、emoji 索引（`[[#章节]]` 锚点）；
  - 正文分章节：报错概况（原文与变体）、根因分析、诊断数据、修复过程、技术栈、遇到的问题、验证结果、使用建议与遗留事项；
  - 红/橙/蓝三色重点标记（≥10 处）、专业名词括号解释、附件超链接（备份与分卷）。
- 内容要求：日志是"案例沉淀"，数据要完整（文件大小、页数、渲染体积、脚本参数、安装命令），后人（包括未来的 AI）能照着复现。
- 参考：`references/0801请求过大案例.md` 就是标准样板。

**更新报错统计台账**（2026-08-12 新增固定规则）：写完日志后，打开 `总结好的大纲以及笔记/知识库FAQ/00-报错统计台账.md`，按本次报错的**主根因**更新统计：
- **找到对应类型行** → 该行"累计次数" +1，更新"最近发生时间"与"最近一次事件"（wikilink 锚点指向本次日志所在 FAQ 文档的复发记录），同步 frontmatter `updated` 为当天日期；
- **未找到对应类型** → 在对应分类（📊 网络/代理类 或 🧾 文件/环境类）表格末尾**新增一行**：编号递增（N/F + 序号）、类型命名遵循"根因优先"原则（参考速查表，禁止用笼统的"报错"二字）、次数=1、关联本次 FAQ 文档、最近一次事件=本次摘要；
- **多根因**：一次修复覆盖多个根因时，每个根因各 +1，并在对应行"最近一次事件"注明；
- 同步更新文档底部"📈 汇总统计"表的"累计修复事件"（各类型次数求和）与"最近更新时间"；
- 统计口径：**根因类型**，与第六步查重规则（以根因/现象为准）一致，确保台账与 FAQ 文档分类可对账。

**维护文档顶部「📊 报错统计速览」块**（2026-08-13 新增固定规则）：**每份 FAQ 报错文档的顶部（`#` 标题之下、结论摘要/快速索引之前）必须常驻一个 `> [!summary] 📊 报错统计速览（截至 YYYY-MM-DD）` callout**，与台账同步维护，让用户"一眼看到该文档累计报错总数"：
- **内容三要素**：① **总事件数**（原始事件 N 次 + 复发 M 次，数字用 `<span style="color:#e74c3c">` 红色加粗）；② **根因拆分表**（列：根因 / 台账累计 / 主要发生地，只列该文档涉及到的根因，次数取台账权威值）；③ 末尾固定一行 `📊 完整统计口径见 [[00-报错统计台账]]`。
- **更新时机**：**每次写复发记录时同步更新**（与台账更新同时进行）——总事件数 +1、根因表数字与台账保持一致；新建 FAQ 文档时也要一并创建该块。
- **数据口径**：根因拆分表的"台账累计"以 `00-报错统计台账.md` 为准（文档内不另行累计全局数）；"总事件数"以本文档自身的原始+复发记录计数。
- **样板**：`04-Codex桌面端反复重新连接（公司环境）.md` 顶部的速览块即为标准模板；`00-报错统计台账.md` 本身不加此块（它是全局统计源）。

### 第七步：汇报

按用户习惯汇报（默认双语：英文在前、中文在后），结构：
1. 根因（表格，三层）；
2. 修复内容（文件层/环境层分别做了什么）；
3. 遗留事项（重启、监测对象——如渲染体积接近上限但还能读的文件，列为监测项）；
4. 日志位置（wikilink 格式便于点击；若为"补充式"记录，指明补充到了哪份文档、哪个位置）。

## PDF 报错速查表

| 报错形态 | 根因 | 处理 |
|---------|------|------|
| `Request too large (max 32MB)` / `invalid_request` | 渲染体积超请求上限（多为图片拼合型 PDF） | 备份 → pdf_fix_split.py → 验证 → 日志 |
| `pdftoppm failed: Command 'pdftoppm' not found` | 机器缺 poppler | winget 安装 → 提示重启会话 |
| `[Unsupported Document]` | PDF 渲染管线故障（缺 poppler）或会话图片投递受限 | 三层诊断定位：环境缺失→装 poppler；会话受限→分卷+重启终验 |
| `[Unsupported Image]` | 会话图片投递受限（与文件大小无关） | 对照测试确认 → 重启会话；本会话内只做数学验证 |
| 其他文件类报错 | 文件损坏 / 格式不支持 | 检查文件头与完整性、格式转换、备份后重新导出 |

## 网络延迟/连通性类报错速查表

| 报错形态 | 根因 | 处理 |
|---------|------|------|
| 国外网站访问慢 / 延迟大（浏览器），但 Codex 正常 | 所有国外流量共用一个慢速"保 Codex 节点"（如美国-IEPL 02），或浏览器未走系统代理 | 查 `/configs` mode 与节点 → 节点 delay 体检 → 分流：OpenAI 域名走美国节点，其余 `MATCH` 走香港/日本快节点 → 热加载 |

## 常见坑（写日志时务必记录遇到的任何新坑）

- 压缩参数不达标：只压到 1400px 时渲染仍可能 40MB+；**分卷才是根治**。
- base64 开销：渲染体积 24MB 的文件，base64 后可能刚好卡在 32MB 上限外。
- scoop main 桶损坏是常见环境坑，直接切 winget 更快。
- 中文控制台乱码：Python 脚本输出前 `sys.stdout.reconfigure(encoding="utf-8")`。
- 图片投递受限时连 181 字节 PNG 都失败——用它做"最小对照测试"成本为零，很划算。
- **mihomo 规则指向具体节点时，代理名必须带完整前缀（含国旗/emoji）**：如 `- MATCH, 🇭🇰|香港-IEPL 01`，写成 `香港-IEPL 01` 会报 `proxy [香港-IEPL 01] not found`，热加载 400 失败。
- **"Codex 能用" ≠ "节点快"**：保 Codex 节点（美国-IEPL 02）是唯一过 CF 风控的节点但慢；浏览器重页面会被它拖垮。先做节点 delay 体检（`/proxies/{name}/delay`），再按域名分流，不要直接换节点把 Codex 弄坏。
