## 2. 项目总览（大白话）

### 2.1 这个项目是做什么的
你有一个 Obsidian 知识库，里面堆着大量笔记：实习求职的方法论、短视频运营笔记、一个叫"智灌云联"的水肥一体机项目资料、科研/学术裁缝的课程笔记、电脑工具报错记录（知识库FAQ）等等。

笔记越来越多，如果只是往里堆，很快就**找不到、对不上、互相矛盾**。这个项目做的事情是：**请 AI（Claude Code）当一名"有纪律的图书管理员"**，按 LLM Wiki 方法论把散装笔记整理成一套结构化的知识库，并让 AI **以后能持续维护**（新笔记进来就整理、定期体检、随时可查）。

### 2.2 为谁做、解决什么问题
- **为谁做**：知识库主人（谢积昌）自己日常用——查资料、做决策、写脚本、准备面试、研究项目时能快速找到沉淀过的知识。
- **解决什么问题**：① 笔记找不到（现在有 index 索引）；② 知识点没关联（现在有双向链接）；③ 整理完一次就没人管（现在有 log 日志 + hook 定期迭代机制）；④ 新知识进来不知怎么归档（现在有 ingest 工作流）。

### 2.3 三层架构（本项目的核心设计）
整个知识库被分成三层，各司其职：

| 层 | 实际位置 | 角色 | 权限 |
|----|---------|------|------|
| **原始层** | `总结好的大纲以及笔记/` | 装"原材料"：直播课总结、笔记、PDF、报错记录等，**不可修改** | 只读 |
| **Wiki 层** | `自动维护知识库/` | AI 整理出的成品页：索引、日志、实体页、概念页 | AI 可自由写 |
| **契约层** | `.claude/` | 规定"怎么维护"的规则文件（CLAUDE.md、LLM-WIKI-SCHEMA.md） | 与用户共同演进 |

## 3. 背景与来龙去脉

### 3.1 项目怎么来的
- 2026 年 7 月，知识库主人决定按照 Andrej Karpathy 的《LLM Wiki》方法论（原文见 `自动维护知识库/LLM Wiki.md`）整理自己的 Obsidian 知识库。
- **LLM Wiki 的核心思想**：让大语言模型（LLM）当"有纪律的图书管理员"，按固定规则维护一个 wiki——它不只是被动回答问题，而是**主动把读过的内容整理成结构化页面、建索引、记日志、做交叉引用**，让知识"复利积累"。
- 2026-07-11 完成初始化（建 CLAUDE.md / index.md / log.md + 20 个页面），之后 07-11 至 08-17 持续 ingest / lint / update 迭代，页面从 20 个涨到 61 个。

### 3.2 关键约束与用户偏好
- **原始层只读**：`总结好的大纲以及笔记/` 里的源文件绝不改动（这是"不可变的原始来源"）。
- **Wiki 层可自由维护**：`自动维护知识库/` 由 AI 全权负责。
- **`已整理好的文件/` 是用户只读归档区**：只有用户明确指令才动。
- **规则与用户最新指令冲突时，以用户指令为准**。
- **语言偏好**：知识库文档以简体中文为主；代码、命令、专有名词保留原文。
- **自动迭代机制**：`.claude/hooks/` 里的 hook 会在每条新消息到达时自动检查时间——每 3 天提醒做一轮 wiki 迭代、每周一提醒上传 GitHub 备份（仓库 `xieji-star/jichang-zhishiku`）。

### 3.3 和团队/其他事情的关系
- 知识库是个人知识库，但里面沉淀了大量求职/实习/自媒体/项目材料，是日常工作决策的"第二大脑"。
- 它与多个自动化服务相关：飞书智能助手（`飞书智能助手/`）、企业微信智能助手（`微信智能助手/`）、Codex 会话（`.codex/`）等，它们都会往知识库写东西，所以知识库的整理工作会持续有新输入。

| 术语（英文/缩写） | 一句话大白话解释 |
|------------------|-----------------|
| **Obsidian** | 一款本地 Markdown 笔记软件，笔记是普通 `.md` 文件，支持双向链接、图谱、插件。本项目就是整理一个 Obsidian 知识库（也叫 **vault**，即"笔记仓库"）。 |
| **知识库 / Vault** | 指整个笔记仓库，本项目的知识库根目录是 `F:\积昌的知识库 - 副本`。 |
| **LLM Wiki** | Andrej Karpathy 提出的一套"让大模型当有纪律的图书管理员来维护知识库"的方法论。核心：分三层（原始层/Wiki层/契约层）+ 固定工作流（ingest/query/lint）+ 索引 + 日志。 |
| **三层架构** | 原始层（原材料，只读）→ Wiki 层（AI 整理出的成品页）→ 契约层（规则文件）。 |
| **ingest（摄取）** | 把新来的原始材料读进来、提炼、写成 Wiki 页面、更新索引和日志的过程。**"把书放进图书馆并编好目录"。** |
| **query（查询）** | 在知识库里找答案的过程：先查 index 索引定位页面，再深入读页面，综合回答。**"去图书馆查资料"。** |
| **lint（体检）** | 定期给知识库做健康检查：找矛盾、过时说法、孤儿页、缺失页、缺失的交叉引用等。**"给图书馆做盘点"。** |
| **index.md（索引）** | Wiki 层的目录文件，列出所有页面（链接 + 一句话简介 + 来源数 + 更新时间），按分类组织。查资料先看它。 |
| **log.md（日志）** | Wiki 层的操作日志，每次 ingest/query/lint 都追加一条，格式 `## [YYYY-MM-DD] 动作 | 标题`，可用命令 grep 出来看。 |
| **实体页 / 概念页 / 来源页** | Wiki 页面的类型：实体页讲"一个具体的东西"（如"Claude Code"）；概念页讲"一个抽象概念"（如"MQTT 协议"）；来源页保留原始内容只加 frontmatter。 |
| **frontmatter** | Markdown 文件最顶部用 `---` 包起来的一段 YAML 元信息（如 title、tags、source、created、updated）。Obsidian 的 Dataview 插件靠它自动生成表格。 |
| **双向链接** | Obsidian 的 `[[页面名]]` 语法，两个页面互相能跳转。它让知识不是孤岛，而是连成网。 |
| **孤儿页** | 没有任何其他页面链接进来的页面（没有入站链接），等于"知识孤岛"，lint 时会找出来修复。 |
| **hook（钩子）** | Claude Code 的一种自动化机制：在某个时机（如用户发消息时）自动执行一段脚本。本知识库用它做"定期维护提醒"。 |
| **知识库FAQ** | `总结好的大纲以及笔记/知识库FAQ/` 文件夹，专门存放各种使用报错的排查记录（如网络故障、报错修复）。 |
| **MediaCrawler** | 一个开源的短视频/小红书爬虫框架，本项目里用于采集抖音数据做"爆款分析"（见 `wiki/自媒体运营/短视频爆款采集系统.md`）。 |
| **A→B 接力** | 交接的核心概念：A（前任）没做完的事 = **接力棒**；B（接手者）要做的 = **接力任务**。两者一一对应。 |

## 10. 关键决策与踩坑记录

> [!note] 这些是最值钱的经验，能帮你少走弯路。

### 10.1 关键决策（为什么这么选）
- **选 LLM Wiki 而非普通笔记整理**：因为知识库是"活的"、会持续有新输入；LLM Wiki 让 AI 可维护、可复利，而不是整理完一次就废。
- **分三层 + index/log 双骨架**：原始层只读保证源文件安全；index 负责"找到"，log 负责"记账"；两者是 wiki 的骨架，任何写入后必须同步维护。
- **来源页保持原样、只加 frontmatter**：避免改动原始资料；改写/综合内容放独立 wiki 页。
- **页面粒度"一页一主题"**：一个页面 ≈ 一个实体/概念/方法论，便于互链和检索。
