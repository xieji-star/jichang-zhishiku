## 2. 项目总览（大白话）

- **这个项目是做什么的**：每周一，公司销售和运营团队需要一份"客户运营周报"，内容包括这周新增了多少客户、流失了多少客户、客户复购率怎么样、不同标签的客户分布如何。以前这些是运营专员手工从企业微信后台导出数据、在 Excel 里手动算，**又慢又容易算错**。我做了一个自动化程序：让电脑自动从企业微信拉数据 → 自动算各项指标 → 自动生成 Excel 报告 → 自动通过群机器人发到"销售运营群"。整个过程约 5 分钟，人不用动手。
- **为谁做**：销售团队（约 15 人）和运营主管看；直接使用者是运营负责人王姐。
- **解决什么问题**：省时间（3-4 小时 → 5 分钟）、避免算错、让管理层每周一早上就能看到数据。
- **项目价值**：一句话——让"周报"从一件每周都要做的麻烦事，变成一件全自动、不用人盯的事。
- **整体完成度估算**：约 **75%**。主体功能（取数 → 算数 → 出报告 → 发送）已全部跑通，并且真实发出过两期周报；还剩"数据看板、历史数据迁移、客户流失预警、操作手册、脚本容错优化"这些后续工作没做完。

## 3. 背景与来龙去脉

- **项目怎么来的**：2026 年 6 月底，运营负责人王姐在周会上提出来——现在每周手工做周报太耗时，而且上个月有一次数据算错了被经理批评，希望能有更省事、更可靠的办法。经理刘总拍板："能不能做成自动的？"正好我 7 月入职实习，这个任务就交给了我。
- **为什么这样做**：我调研后发现，企业微信官方提供了"客户联系""会话存档"等接口，可以直接拿到客户数据；再加上公司本来就用企业微信办公，不需要额外买工具。于是确定方案：用 Python 写脚本自动取数、自动生成 Excel、用企业微信"群机器人"自动发送。
- **关键约束和前置信息**：
  - 数据口径以王姐定的为准（什么叫"流失客户""新增客户"等），具体见 `docs/数据字典.md`；
  - 公司 IT 对权限管得比较严：企业微信应用的密钥、CRM 只读账号、服务器申请都要走 IT 审批，周期可能以"周"计——这也是部分工作没做完的原因；
  - 只能用公司内网/已授权账号访问相关后台，**不要用自己的私人账号去调接口**。
- **和公司/团队其他事的关系**：
  - 与"客户标签体系"有关：新增/流失判断依赖客户身上的标签和互动记录；
  - 与"会话存档"项目有关：聊天互动统计依赖会话存档是否开通（目前只开了部分员工）；
  - 与 CRM 有关：历史数据迁移需要从 CRM 导出（目前没有权限）。

> 规则：下面都是项目里会遇到的词。哪怕你觉得基础，也请看一眼——在这个项目里它们有特定含义。

| 术语（英文/缩写） | 大白话解释 |
|---|---|
| 企业微信（WeCom） | 公司用来和客户、内部同事沟通的软件，相当于微信的企业版 |
| 客户联系 | 企业微信里"员工添加客户微信、和客户聊天"的功能模块，客户就是员工微信里的好友，但用的是公司企业微信 |
| 外部联系人 | 员工用企业微信加的客户（不是公司内部同事），**本项目的统计对象** |
| 会话存档 | 企业微信官方功能，可以把员工和客户的聊天内容保存下来（需要开通权限），用于统计互动 |
| 标签 | 给客户打的分类标记，比如"已成交""高意向""已流失"，周报按标签分组统计 |
| 接口（API） | 企业微信对外开放的"取数窗口"，程序通过这些窗口拿数据，窗口地址是一串网址 |
| access_token | 程序访问接口的"临时门禁卡"，每次调用都要带，约 2 小时（7200 秒）过期，过期要重新换 |
| secret（应用密钥） | 换门禁卡的"原始钥匙"，只能配一次，保管在配置文件里（已脱敏） |
| webhook（群机器人） | 企业微信群里的"机器人"，给它一个网址，程序就能往群里自动发消息，本项目的"自动发送"靠它 |
| 周报 | 每周一生成的客户运营数据报告，本项目的产出物 |
| 指标/口径 | 指标的"定义和算法"。比如"流失客户 = 90 天以上无互动的客户"就是一个口径；口径定错了，数字就对不上 |
| 流失客户 | 超过 90 天没有互动（没聊过天）的外部联系人 |
| 新增客户 | 本周新添加的外部联系人 |
| 复购率 | 老客户中再次购买的占比（具体口径见 `docs/数据字典.md`） |
| 数据看板（Dashboard） | 把数据做成图表、集中在一个网页上实时看的页面，本项目未完成项之一 |
| 定时任务（Cron/任务计划程序） | 让电脑到点自动运行程序，不用人守着，本项目用于每周一 9:00 自动发周报 |
| Python | 写本脚本用的编程语言 |
| requests 库 | Python 里用来访问网页接口（API）的常用工具包 |
| pandas 库 | Python 里用来处理表格数据的常用工具包，本项目用它算周报数字 |
| CSV | 一种简单的表格文件格式（用逗号分隔），程序中间数据存在这里 |
| Excel（.xlsx） | 微软的表格文件，周报最终产出格式 |
| CRM | 公司用的"客户关系管理系统"，存客户全量资料，历史数据迁移要从它导出 |
| UTF-8 编码 | 文字在文件里的保存格式；Windows 下 Excel 读中文要带 BOM（即 utf-8-sig），否则会乱码 |
| 时区（Asia/Shanghai） | 服务器默认是 UTC（世界标准时间），不指定时区的话定时任务会按 UTC 跑，导致 9:00 变 8:00 |

## 9. 下一步怎么做（手把手）

> 以下每一步都写成"普通人能照做"的指令：**做什么 → 打开哪个文件/用什么工具 → 看到什么结果算做对 → 卡住了怎么办**。

### 立即做（第一周内）

**第 1 步：把项目跑起来（环境搭建）**
- 做什么：在自己的电脑上装好运行环境。
- 具体动作：① 装 Python 3.10+（公司电脑如果没有，找 IT 小李要安装包，勾选"Add to PATH"）；② 打开命令行，进入项目文件夹，运行 `pip install -r requirements.txt` 安装依赖；③ 把 `config/config.json` 里的密钥（secret）用从 A 或公司密码库拿到的真实值填进去。
- **看到什么算做对**：命令行不报错，`pip list` 里能看到 requests、pandas、openpyxl 等包。
- **卡住怎么办**：看 `README.md` 的"安装"章节；还不行就企业微信找 A（实习结束前会把联系方式给你）或 IT 小李。

**第 2 步：跑一次取数，确认能拿到数据**
- 做什么：运行取数脚本。

- **看到什么算做对**：终端打印"取数完成，共 XX 条"，`data/raw/` 下出现以当周编号命名的 CSV，用 Excel 打开中文正常。
- **卡住怎么办**：若报"token 过期 / 40014"等错，说明密钥没填对或权限没通，找 IT 确认应用权限。

**第 3 步：生成一期周报，核对数字**

## 10. 关键决策与踩坑记录

> 这是最值钱的部分：我踩过的坑，你直接避开。

### 关键决策（为什么这么选）

- **为什么用 Python 而不是现成报表工具（如 FineReport）**：FineReport 要买授权、审批流程长；Python 免费、我会写，而且取数要调的接口用 Python 最方便。试过 FineReport 试用版，部署权限拿不到，放弃。
- **为什么先做"周报"而不是先做"数据看板"**：王姐说周报最急（每周都要用），看板是锦上添花，所以把周报排在前面。这也解释了为什么看板现在还没做。
- **为什么用 webhook 群机器人发报告而不是用企业微信 API 发文件**：机器人最简单，不用申请消息推送权限；缺点是消息有大小限制（见踩坑 3）。
- **为什么指标口径都写进数据字典**：防止"你以为的流失"和"王姐以为的流失"不是一个意思，先定死口径再写代码。

### 踩过的坑（现象 → 根因 → 怎么避开）

- **踩坑 1：access_token 过期报 40014**
  - 现象：跑取数脚本报错"40014, invalid access_token"。
  - 根因：企业微信的 token 每 7200 秒（2 小时）过期，之前是每次手动复制，一过期就报错。
  - 怎么避开：已封装在 `utils/wecom_auth.py` 自动刷新；你以后改代码不要再直接硬编码 token。
- **踩坑 2：Excel 中文乱码**
  - 现象：生成的 xlsx 打开后中文是"口口口"。
  - 根因：CSV 中间文件用了 UTF-8，Excel 打开 CSV 时认不出来。
  - 怎么避开：写 CSV 时用 `encoding='utf-8-sig'`（带 BOM）；最终 xlsx 用 openpyxl 直接写，不受影响。
- **踩坑 3：群机器人消息太长发不出**
  - 现象：`send_report.py` 报错，消息没发出去。
  - 根因：企业微信群机器人单条消息上限 4096 字节；周报内容一多就超。
  - 怎么避开：把长报告拆成"文字摘要 + 附件文件"两条发；附件用发送文件接口，不塞在文本里。
- **踩坑 4：定时任务时间差 1 小时**
  - 现象：本该 9:00 发的周报，8:00 就发了。
  - 根因：公司那台 Windows 机器时区被设成 UTC，任务计划程序按系统时间跑。
  - 怎么避开：任务计划程序里指定时区 Asia/Shanghai，并检查机器时区是"北京时间"。
- **踩坑 5：密钥差点被提交到代码库**
  - 现象：config 里的 secret 一度写死在脚本里。
  - 根因：图省事直接硬编码。
  - 怎么避开：已挪到 `config/config.json` 并加入 `.gitignore`；你的代码里不要再出现明文密钥。

### 试错过但放弃的方案

- **FineReport 报表工具**：要钱、要权限，放弃。
- **手工每周从后台导出**：太慢、易错，被自动化取代。
- **企业微信"数据看板"官方内置功能**：公司没开通这个服务，放弃，改自建。

## 11. 风险与求助点

> 逐条标 ❓ 的是需要人工确认/存在隐患的地方，务必留意。

- **❓ 密钥交接**：`config/config.json` 里的 secret 值是 **<已脱敏>**。实际值请交接时当面向 A 要，或去公司内部密码库取；交接后建议自己重新生成一个 secret 并撤销旧的（找 IT 在管理后台操作），防止旧权限泄漏。
- **❓ 企业微信应用权限**：如果交接后应用被停用或权限变更，取数会失败。现象：`fetch_data.py` 报"未授权"。处理：找 IT 确认"企微周报"这个应用的客户联系/会话存档权限还在。
- **❓ CRM 只读账号（事项 2 的前置）**：至今没批，卡在 IT 小李，需要你接力推进，最好面对面找他一次。
- **❓ 服务器审批（事项 1 的前置）**：IT 张工那边还在流程里，尽早催，别等到最后。
- **⚠️ 风险：周一漏发周报**。如果周一早上定时任务没跑，周报就会漏发（销售会来问）。兜底办法：每周一早上看一眼群里有没有报告；没有就手动跑一次并查 `logs/` 日志。
- **⚠️ 风险：口径被随意改**。数据口径别自己改，任何指标定义要改先找王姐确认，再改 `docs/数据字典.md`，否则历史数字会"对不上"，后果是管理层质疑数据可信度。
- **遇到问题找谁（按优先级）**：

  - 服务器/部署 → **IT 张工**
  - 原始手工周报流程、业务细节 → 销售部 **陈哥**（最懂业务的人）
  - 项目方向、优先级 → 经理 **刘总**
