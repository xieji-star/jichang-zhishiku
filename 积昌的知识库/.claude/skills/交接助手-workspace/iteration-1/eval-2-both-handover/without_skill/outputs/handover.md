# Part 1 给同事看的说明文档

## 1.1 项目背景与定位

这是一个**个人知识管理库（Obsidian Vault）**，位于 `F:\积昌的知识库 - 副本`。它不是一个单纯的笔记仓库，而是一个**「由 AI 半自动维护的知识系统」**，严格遵循 Andrej Karpathy《LLM Wiki》方法论运行（原文见 `自动维护知识库/LLM Wiki.md`）。

其核心思想是三层架构：

| 层级 | 本知识库落点 | 角色 | 权限 |
|---|---|---|---|
| 原始层 Raw Sources | `总结好的大纲以及笔记/` | 不可变的源文件（文章、笔记、PDF、图片） | 只读，绝不修改 |
| Wiki 层 The Wiki | `自动维护知识库/` | Claude 生成的结构化 Markdown 页面（61 页） | AI 自由读写 |
| 契约层 The Schema | `.claude/CLAUDE.md` + `.claude/LLM-WIKI-SCHEMA.md` | 规定结构、约定与工作流 | 与用户共同演进 |

这个知识库同时承载了两大自动化业务助手：
- **飞书智能助手**（`飞书智能助手/server.py`）：监听飞书消息，自动处理文档总结、文件落盘、脚本上传等。
- **企业微信智能助手**（`微信智能助手/server.py`）：通过企业微信接收自动化任务并处理。

以及 **26 个已安装的 Agent Skill**（位于 `.claude/skills/`），覆盖简历/求职、脚本撰写、会议纪要、PPT/PDF 排版、知识库报错修复等日常场景。

## 1.3 两大自动化机制（Hook 驱动）

知识库的维护是**自动化触发**的，触发源是 `.claude/settings.json` 中配置的 `UserPromptSubmit` hook，每次用户发送新消息时自动运行 `kb-maintenance-check.sh`，到期即提示 AI 执行：

1. **LLM Wiki 迭代（每 3 天）**：依据 LLM Wiki 方法论对全库执行一轮 ingest / query / lint，同步维护 `自动维护知识库/index.md` 与 `log.md`，完成后更新标记文件 `.last-wiki-maintain`。
2. **GitHub 备份（每周一 或 ≥7 天）**：将整个知识库上传至 GitHub 仓库 `https://github.com/xieji-star/jichang-zhishiku`（账号 `xieji-star`），每次新建日期文件夹 `积昌的知识库<MMDD>`，只保留最近 10 个版本，完成后更新 `.last-github-backup`。

> 目的：让知识库持续"进化"（新内容不断被吸收进 wiki）并拥有异地备份，不依赖人工记忆。

## 1.4 关键运行规则（同事须知）

- **全权限模式**：知识库对 AI 永久开放全部权限（等同 `claude --dangerously-skip-permissions`），AI 执行任何操作都不应再询问用户授权。
- **文件夹 vs 文档**：两者是不同概念——"创建文件夹"= 建真实目录；"创建文档"= 建 `.md` 文件，禁止混淆。
- **权限分级**：`自动维护知识库/` 与 `.claude/skills/` 可自由修改；`总结好的大纲以及笔记/` 只读；临时文件清理遵循明确规则（下详）。
- **文档查询顺序**：先查 `自动维护知识库/index.md` 定位页面，再深入对应笔记，禁止全库扫描。
- **文档创建/编辑排版**：一律调用 `/文档转换+排版` Skill 完成。
- **飞书身份**：文档增删改查用个人账号「落日」（`--as user`）；文档总结/读书笔记用 bot「谢积昌的飞书CLI」（`--as bot`）。
- **每日首次指令**：每天第一条指令时先运行 `date` 读取当前时间并显示。

## 1.5 常见任务 SOP

- **整理新来源**：原始文件进 `总结好的大纲以及笔记/` → AI 读取 → 写入/更新 `自动维护知识库/wiki/` 页面 → 更新 `index.md` → 在 `log.md` 追加 `ingest` 条目。
- **知识库查询**：读 `index.md` → 定位 → 读页面 → 综合回答并给引用。
- **报错修复**：优先查 `总结好的大纲以及笔记/知识库FAQ/`（00 台账 + 01~11 编号记录）按关键词匹配历史修复方案，再复现→三层诊断→备份→修复→验证，最后回写 FAQ 与统计台账。
- **短视频脚本撰写**：按「华哥脚本撰写」Skill 流程，<10 条须先问内容线（技术痛点40%/方向判断25%/案例故事20%/筛选劝退15%），≥10 条自动按配比分配。

## 1.6 注意事项与已知"坑"

1. **盘符不一致**：所有 CLAUDE.md 规则文件里写的根路径是 `E:\积昌的知识库 - 副本`，但**实际物理路径是 `F:\积昌的知识库 - 副本`**。所有命令请用 `F:\`，遇到规则文件中的 `E:\` 应理解为同一库的旧写法。
2. **规则中提到的 `收件箱/` 与 `已整理好的文件/` 文件夹当前并不存在**：真正的原始来源在 `总结好的大纲以及笔记/`。新增来源时若规则要求放收件箱，需按需创建。
3. **根目录有大量 `_` 开头临时文件**（`_*.txt`、`_test*.pdf` 等），属于可清理的中间产物，但删除非明确三类临时文件前仍需用户确认。
4. **`.yolov8m-seg.pt.*.part`** 是一个未下载完的模型残片，可忽略或清理。
5. 服务目录 `飞书智能助手/` 下有一个名为 `⚠️` 的文件夹与 `积昌` 文件，属历史遗留，勿动。

## 2.4 必须遵守的硬性规则（速查）

1. **永不询问权限**：库已永久开放全部权限，任何操作直接执行，禁止请求授权或等待确认。
2. **文档查询窄路径**：先 `自动维护知识库/index.md` → 定位 → 深入；禁止全库 find/ls/grep 扫描。
3. **文件夹≠文档**：创建"文件夹"建目录，创建"文档"建 `.md` 文件，禁止混淆、禁止猜测——含糊时先问。
4. **只读区**：`总结好的大纲以及笔记/`（原始层）与 `自动维护知识库/CLAUDE.md` 中的源文件绝不修改。
5. **文档创建/编辑**：一律走 `/文档转换+排版` Skill。
6. **临时文件清理**：`_`/`temp_`/`tmp_` 开头脚本、`test_*.png`、`benchmark.json` 等可直接删；其他文件删除必须先问用户。
7. **每日首条指令读时间**：先 `date` 再干活。
8. **企微自动化任务**：prompt 以「🔴 自动化任务 — 来自企业微信」开头时，**禁止任何飞书/lark 操作**，直接按内容执行。
9. **飞书自动化任务**：prompt 以「🔴 自动化任务 — 来自飞书」开头时，先确保飞书服务在运行。
10. **规则冲突**：规则与用户最新指令冲突时，以用户最新指令为准；拿不准立即停下问"做什么/怎么做"。

## 2.5 常见任务处理流程

| 任务 | 流程 |
|---|---|
| 整理新来源 | 读源 → 写入/更新 `自动维护知识库/wiki/` → 更新 `index.md` → 追加 `log.md` ingest 条目 |
| 知识库查询 | `index.md` 定位 → 读页 → 综合回答 → 有价值答案存回 wiki 并记 query 条目 |
| 报错修复 | 先查 `知识库FAQ/00-报错统计台账.md` 与编号记录 → 复现 → 三层诊断（文件/环境/工具；网络类：代理/线路/环境）→ 备份 → 修复 → 验证 → 回写 FAQ + 台账 |
| 写短视频脚本 | 按「华哥脚本撰写」Skill；<10 条先问内容线，≥10 条按 40/25/20/15 自动分配 |
| 会议/课程纪要整理 | 用「会议笔记整理」或「文档转换+排版」Skill，产出 Obsidian 笔记 |
| 工作总结/SOP | 用「工作SOP与业务线整理」Skill |
