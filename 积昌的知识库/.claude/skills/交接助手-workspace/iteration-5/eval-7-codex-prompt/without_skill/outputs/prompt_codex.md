# 给 Codex 的提示词（可直接复制粘贴使用）

> 用法：复制下方代码块中的全部内容，粘贴到 Codex 对话框中发送即可。Codex 拿到后会自己回溯聊天记录、核查项目文件，然后写出一份"给人看的交接文档"。

```text
你是一个「交接文档撰写助手」。你之前通过 Codex 帮用户完整开发了一个「短视频爬虫项目」。现在用户要离职了，需要把这个项目交接给一位完全没参与过的实习生。请基于你自己的聊天记录（会话历史）+ 项目真实文件，写一份【给人看的、极其详细的交接文档】——目标读者是真人新手实习生，不是给 AI 的，所以要用大白话、手把手、把来龙去脉讲清楚。

════════════════════════════════════
第一步：信息收集（按顺序执行，全部信息必须真实）
════════════════════════════════════

1. 回溯你的会话历史：检索 `C:\Users\asus\.codex\sessions\*.jsonl` 中与「短视频爬虫」项目相关的全部对话，逐条还原：
   - 项目目标、要解决什么问题
   - 技术选型与架构（用什么语言/框架/库、为什么这么选）
   - 已完成的功能模块（每条对应哪个文件）
   - 关键代码/函数所在位置
   - 踩过的坑：现象、根因、怎么避开的
   - 没做完的事：差什么、为什么没做完（阻塞原因）
   - 关键决策：做过哪些选择、为什么选 A 不选 B、试错过但放弃的方案

2. 核查项目真实文件：定位项目目录，用文件读取逐项核实——每个文件的真实路径、作用、当前状态（新建/修改/已完成/未动/临时）、产出物在哪、配置文件、启动方式、依赖环境。

3. 真实纪律（硬性）：
   - 能核实的一定核实；核实不了的标「❓需人工确认」，严禁编造路径/命令/结论。
   - 每条路径、命令、数字都要真实可查。

════════════════════════════════════
第二步：目标读者与写作要求
════════════════════════════════════

读者 = 一个完全没参与过、对项目零背景的实习生。因此：
- 大白话：能不用术语就不用；非用不可必须进术语表解释。
- 手把手：每一步写到"照做就能做"的程度。
- 讲来龙去脉：为什么做这个项目、业务背景、为什么这么选型。
- 宁可多写不可简略：每个条目都按下面字段标准写满。禁止出现「等等」「下次继续」「详见以前的记录」「后续再说」这类一笔带过。
- 详细度自检：如果你觉得"这份文档太啰嗦"，那说明写漏了——给人看的交接文档就是要啰嗦、要全、要能让没参与过的人也能看懂并照做。

════════════════════════════════════
第三步：文档结构（必须覆盖"四要素"，按以下 12 节完整输出）
════════════════════════════════════

四要素（缺一不可）：①当前已经做了什么 ②还有什么没做的 ③接下来要接着做什么 ④接下来该怎么做。其中 ②③ 必须一一对应（编号一致），并用一张「A→B 接力总览表」钉在一起。

【0. 元信息】
项目名 / 交接对象（人：实习生）/ 交接日期（用今天）。

【1. 这份文档是给谁看的】
- 写这份文档的背景（谁交接给谁、为什么交接）。
- 读者读完应达到的效果（能独立接手哪些事）。

【2. 项目总览（大白话）】
- 项目是做什么的、为谁做、解决什么问题。
- 一句话讲清项目价值。
- 整体完成度估算（如"约 70%"）＋判断依据。

【3. 背景与来龙去脉】
- 项目怎么来的、为什么做（业务背景、触发原因）。
- 关键约束、用户偏好、前置信息。
- 和公司/团队其他事情的关系。

【4. 术语表】
- 把项目里出现的专业词、缩写、黑话、内部代号逐条解释。
- 格式：`术语（英文/缩写）＝ 一句话大白话解释`。
- 哪怕你觉得"这很基础"也写——读者可能不懂。

【5. 当前进度（用"人话"讲）】
- 整体做到哪一步、处于什么阶段。
- 最后一次停在什么位置（以非技术读者能懂的方式描述）。

【6. 已完成工作（全量逐条，每条写满 4 个字段）】
- 做了什么：一句话说清成果。
- 产出物在哪：相对路径＋一句话用途。
- 怎么验证有效：可复现的验证方法（命令输出/文件内容/运行结果）。
- 关键数据/效果：能写数字就写数字（条数、时长、通过率、性能等）。
- 按时间或模块分组逐条列出。

【7. A 没做完的事 = 前任留给实习生的"接力棒"（全量逐条，每条写满 7 个字段）】
- 还差什么：具体到差哪一块、缺哪个功能/数据/步骤。
- 为什么没做完：阻塞原因（时间不够/技术难题/等依赖/等决策）。
- 前置条件：做这件事之前必须满足什么。
- 优先级：紧急 / 重要 / 一般。
- 做到什么算完成：可验收的定义（可检验，不只说"做完"）。
- 从哪开始：入口（文件:行号 / 函数名 / 命令 / 找谁）。
- 验证信号：看到什么现象算真正完成/接上。
- 开头点明：这些是前任（A）留下的"接力棒"，是实习生的起点，不是他的过错。

【8. A→B 接力总览（读到就能开工，核心）】
把第 7 节的"没做完的事"和第 9 节的"实习生接下来要做的"用一张表钉在一起，每条一行：

| # | A 没做完的（接力棒） | 你（实习生）接下来要做什么 | 从哪开始（文件/工具/找谁） | 做到什么算完成（怎么验证） |
|---|---------------------|--------------------------|--------------------------|---------------------------|

表末给出「接力开工第一步」：具体动作 → 出现什么现象算正式接上。
这张表就是实习生的"开工地图"：照着 #1 做即可。

【9. 下一步怎么做（手把手，每条写满 5 个字段）】
- 接哪个遗留项：对应第 7 节的哪条（编号一致）。
- 具体步骤：展开成 1-N 步，每步可照做（不写"做一下"这种空话）。
- 从哪开始：第一个动作（打开哪个文件 / 跑哪条命令 / 找谁）。
- 做到什么算完成：可观察的完成信号。
- 卡住了找谁/看哪：求助路径（文档/人/工具）。
- 区分"立即做"与"之后做"。

【10. 关键决策与踩坑记录】
- 做过的选型、为什么这么选（用大白话讲理由）。
- 踩过的坑：现象、根因、怎么避开（这是给后人最值钱的部分）。
- 试错过但放弃的方案及原因。

【11. 风险与求助点】
- 不确定处、需要人工确认的点，逐条标「❓」。
- 可能翻车、有隐患的地方。
- 遇到问题找谁：责任人、关联文档、常用工具位置。

【12. 常用资源清单】
- 关键文件/产出物位置（相对路径＋一句话用途）。
- 账号、密钥、工具的存放位置（密钥/token 值一律脱敏为 `<已脱敏>`，只写存放位置）。
- 相关文档/链接清单。

════════════════════════════════════
第四步：路径与命令风格
════════════════════════════════════

- 因为最终读者是人（实习生），路径统一给「相对路径＋一句话用途」；命令给 Windows/PowerShell 风格、可直接复制的命令（如 `.\start.ps1`、`tasklist`、`python xxx.py` 等）。
- 命令要写清"输入什么、预期看到什么输出"。

════════════════════════════════════
第五步：输出要求
════════════════════════════════════

1. 将交接文档保存为 Markdown 文件，保存到项目根目录（文件名如 `交接文档_MMDD.md`），并在回复中完整输出全文，方便用户复制。
2. 文档开头保留元信息：项目名、交接对象（人：实习生）、交接日期。
3. 写完全文后自行检查（交付前自查）：
   - 四要素是否齐全？②③ 是否成对一一对应、都写满了字段？
   - 接力总览表是否存在？是否每条都含"从哪开始"与"做到什么算完成"？
   - 「接力开工第一步」是否明确到具体动作＋现象？
   - 一个完全没参与过的实习生，能否【不问任何人、不查任何东西】，就照着第 8 节的 #1 动手第一步？能 → 合格；不能 → 继续补写 ③④。
   - 是否出现「等等/下次继续/详见以前记录/后续再说」等一笔带过？出现则必须展开。
4. 全文用清晰 Markdown 排版：标题层级、表格、要点列表、关键信息用醒目提示（如引用块/callout/加粗）。
```
