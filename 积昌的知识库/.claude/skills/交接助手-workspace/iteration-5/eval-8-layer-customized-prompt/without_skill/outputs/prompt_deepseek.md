# 交接提示词 · DeepSeek Harness 版

> 使用说明：把下面 ```text 代码块里的全部内容整体复制，粘贴到 DeepSeek Harness 的对话框里，按其中的要求与它对话即可。它产出的《交接文档》是给 Codex 继续干项目用的。

```text
# 你的任务：写一份《交接文档》，让 Codex 无缝接手我们的知识库自动化整理项目

## 一、你的身份与硬约束（先记住这四条）

你正在参与一个「知识库自动化整理项目」（一个 Obsidian 知识库 + 自动化整理脚本的项目，之前由 Claude Code 做了一半，现在要交给 Codex 继续干）。

你现在的任务：**仅凭我们这段聊天记录里你掌握的全部信息**，产出一份《交接文档》，交给另一个 AI 智能体 **Codex**，让 Codex 读完就能直接开工、继续把项目干完。

你的硬约束（必须全程遵守，这是你能不能把事办成的关键）：
1. **你读不到本地文件系统、也跑不了本地命令**。你唯一的依据是这段聊天记录里出现过的一切（对话内容、用户贴过的内容、你确认过的信息）。
2. **自包含**：凡是关键内容——代码片段、配置、命令、路径、数据——一律**直接贴进文档正文**，绝对不允许只写"在 xxx 文件里"这种让 Codex 自己去查的话（因为你连自己写的路径都可能记错）。
3. **证据分级**：文档里每一条信息都要标注 ✅确定 / 🔶推断 / ❓待确认。聊天里明确出现过的标 ✅；你凭推理补的标 🔶；你记不清、聊天里没明说的标 ❓。**绝不装确定。**
4. **验证靠人代跑**：你不能执行命令，所以文档里所有验证步骤都必须写成"请用户运行 XX 命令，看到 YYY 输出即成功"这种形式，不能写"你跑一下试试"。

## 二、输出的文档必须回答四个问题（四要素，缺一不可）

1. **当前已经做了什么**：已完成工作的全量清单，每一条含 4 个字段——做了什么 / 产出物在哪 / 怎么验证有效 / 关键数据（能写数字就写数字）。
2. **还有什么没做**：未完成工作的全量清单（这就是交给 Codex 的"接力棒"），每一条必须写满 **7 个字段**：还差什么 / 为什么没做完(阻塞原因) / 前置条件 / 优先级(紧急/重要/一般) / 做到什么算完成(可验收) / 从哪开始 / 验证信号。
3. **接下来要接着做什么**：Codex 要接的每件事（接力任务），与第 2 点的每一条**一一对应、编号一致**。
4. **接下来该怎么做**：把第 3 点展开成 1-N 步，每步只做一件事、每步可照做、每步有验证信号、卡住了找谁。

> 最容易翻车的写法（绝对禁止）："还有几件事没做完，下次继续""你接手后把剩下的做一下""详见之前的记录""等等/后续再说"。只要出现这类一笔带过，就是不合格，必须展开成上面带字段的条目。

## 三、目标读者 Codex 是什么水平（决定你该写到多细）

- Codex 是 **L1 自治型智能体**：能读本地文件、能跑 Windows PowerShell 命令、模型强、上下文大。
- 所以文档里**凡是你能确定的入口**，直接给"文件路径:行号 / 函数名 / PowerShell 命令"，Codex 自己能读文件补细节；
- 但**凡是你不确定的入口**，就不要硬给路径——把你记得的关键内容（代码/配置片段）直接贴出来，并标 ❓，让 Codex 或用户去核对；
- 命令统一用 **Windows PowerShell** 风格。你记不清确切命令时，就写"大致是……请用户核对"，**绝对不许编造命令**。

## 四、文档骨架（照这个写，结构不许乱）

- **0. 交接摘要（启动包）**：300–500 字，放在最前面。讲清楚：项目是做什么的 / 当前做到哪一步 / 最关键的三件事（①已完成什么 ②A没做完的接力棒 ③Codex 下一步第一件事）。
- **1. 项目总览与验收标准**：一句话定位 + 最终目标 + 做到什么程度算完成（可检验）。
- **2. 文件地图**：逐个列出你记得的文件/文件夹——路径、作用、当前状态（新建/修改/已完成/未动/临时）。**记不清路径的，把你知道的线索（文件名、大概位置、内容）写出来并标 ❓。**
- **3. 已完成工作（全量逐条）**：按第 2 点四要素的第①条写，每条 4 个字段，含关键代码/函数位置。
- **4. 当前精确进度**：聊天记录里最后一次有效操作是什么？停在哪个文件/哪一步？代码/文档/数据当前处于什么状态？
- **5. A 没做完的事（接力棒，全量逐条）**：按四要素第②条写，每条 7 个字段。开头点明：**这些是前任留下的接力棒，是 Codex 的起点。**
- **6. A→B 接力总览表（核心，把 ⑤ 和 ⑦ 钉在一起）**：

  | # | A 没做完的（接力棒） | Codex 要做什么 | 从哪开始（路径:行号/函数名/命令/贴内容） | 做到什么算完成（验证信号） |
  |---|--------------------|----------------|--------------------------------------|---------------------------|

  - "从哪开始"列：能确定就写入口；不确定就把关键内容直接贴进这一行。
  - "做到什么算完成"列：写"用户帮跑什么命令、看到什么输出"。
  - 表末给一句"接力开工第一步"：让用户帮跑哪条命令 → 看到什么现象算正式接上。
- **7. 下一步行动计划（命令级）**：按四要素第③④条写。每步只做一件事；每步都写"用户代跑验证信号"。区分"立即做 / 之后做"。
- **8. 环境与配置依赖**：模型/工具/软件及版本、端口、环境变量、依赖库、密钥/token 的**存放位置**（值一律脱敏为 `<已脱敏>`）。关键配置项直接贴出脱敏值，不要只写"在 .env 里"。
- **9. 数据与状态快照**：涉及的数据/文件/接口当前状态；临时数据、测试数据是否要清理；哪些中间产物要保留。
- **10. 关键决策与踩坑记录**：做过的选型及原因、踩过的坑（现象+根因+怎么规避）、试错过但放弃的方案及原因。
- **11. 风险与待确认项**：逐条标 ❓，不确定处、需人工确认的点全列出来。
- **12. 续作启动手册**：如何验证"续上了"——写成"请用户代跑 XX，看到 YYY 输出即成功"，并附上给用户的核对清单（见第 13 条）。
- **13. 给用户的核对清单（必须放最后）**：因为你读不到文件、可能记错路径/命令/状态，请用户逐条核对或代跑后回填。格式示例：
  - ☐ 请核对以下路径是否真实存在：`<路径1>`、`<路径2>`
  - ☐ 请代跑命令 `<命令>`，把输出贴回，确认是否与文档描述一致
  - ☐ 请确认项目当前是否停在我说的这个状态：<状态描述>

## 五、写作风格与硬性要求（违反即重写）

1. **宁可写长，不可省略**；每条细节写透，禁止"等等/后续再说"。
2. **不要猜**：任何可能产生歧义的地方（路径、函数名、命令、验收口径）都直接写出来，拿不准就标 ❓ 并附你记得的线索。
3. 每步**只做一件事**，降低 Codex 一次理解太多、以及你一次写太多的负担。
4. 全程使用**简体中文**；技术标识符（文件名、命令、参数名）保持原名。
5. 写完对照下面的自查清单，全部勾选后才算完成。

## 六、完成自查（交稿前逐条对照）

- [ ] 四要素齐全：①已做了什么 ②还没做什么(每条7字段) ③接下来做什么(与②编号一一对应) ④怎么做(展开成可照做的1-N步)
- [ ] 关键代码/配置/命令已**贴进正文**，不是只给路径
- [ ] 每条信息都有证据分级标记（✅ / 🔶 / ❓）
- [ ] 所有验证步骤都写成"请用户代跑 XX，看到 YYY"
- [ ] 末尾附了「给用户的核对清单」
- [ ] 全文没有"等等/详见以前记录/后续再说"这类一笔带过
- [ ] 没有编造任何路径、命令、函数名
```
