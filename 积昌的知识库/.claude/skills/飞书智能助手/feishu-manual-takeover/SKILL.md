# 🤖 飞书人工接管工作流

将飞书智能助手人工接管模式下收到的课堂笔记、会议记录等文件，处理为结构化的 Obsidian 笔记并存入知识库。

---

## 📂 Skill 职责说明

本 skill 是一个**编排层（Orchestration Layer）**，不直接处理内容提取和结构化。职责划分如下：

| 层级 | Skill | 职责 |
|------|-------|------|
| 🎯 **编排层** | `feishu-manual-takeover`（本 skill） | 文件发现 → 飞书消息检索 → 路径规划 → 调用处理 → 链接建立 → 验证清理 |
| 🛠️ **处理层** | `会议笔记整理` | PDF 文本提取 → 字幕修正 → 去重 → 结构化输出 → 写入磁盘 |

> [!IMPORTANT]
> 处理内容时**必须调用 会议笔记整理 skill**，不要自己实现内容整理逻辑。会议笔记整理 负责全部内容处理工作，本 skill 只负责任务编排。

---

## ⚙️ 核心工作流

### 单文件模式

```
用户通过飞书发送文件
       │
       ▼
  Step 1: 扫描 中间文件/lark-resources/ ──► 列出待处理文件（按时间排序）
       │
       ▼
  Step 1.2: 飞书聊天检索 ──► 搜索P2P聊天中的文件名/指令（lark-im）
       │
       ▼
  Step 2: 分析文件内容 ──► 快速预览 PDF → 判断内容类型
       │
       ▼
  Step 3: 确认存储目标 ──► 路径 + 文件名（优先用飞书消息中的名称）
       │
       ▼
  Step 4: 检查目标目录 ──► 查看已有附件/笔记
       │
       ▼
  Step 5: 调用 会议笔记整理 ──► 传递完整参数 → 内容处理 → 写入磁盘
       │
       ▼
  Step 6: 验证输出 ──► 确认文件存在、frontmatter 完整
       │
       ▼
  Step 7: 建立双向链接 ──► 搜索相关笔记 → 正向链接 → 反向链接
       │
       ▼
  Step 8: 报告完成 ──► 向用户汇总处理结果
```

### 多文件批处理模式

```
用户通过飞书发送多个文件
       │
       ▼
  Step 1: 批量扫描 中间文件/lark-resources/ ──► 识别所有新文件 → 创建处理队列
       │
       ▼
  Step 1.2: 飞书聊天检索 ──► 搜索P2P聊天获取文件名映射/指令
       │
       ▼
  Step 1.5: 批量命名映射 ──► 将文件名与用户指定的名称一一映射
       │
       ▼
  Step 2: 批量预览 ──► 依次快速预览各文件 → 判断内容类型
       │
       ▼
  Step 3: 统一确认存储目标 ──► 同系列则同目录，不同系列则分目录
       │
       ▼
  Step 4: 检查目标目录 ──► 检查目录结构和已有笔记
       │
       ▼
  Step 5: 循环处理 ──► 对每个文件依次调用 会议笔记整理（串行处理）
       │    ├── 文件 1 → 会议笔记整理 → 输出笔记 1
       │    ├── 文件 2 → 会议笔记整理 → 输出笔记 2
       │    └── ...
       ▼
  Step 6: 批量验证 ──► 确认所有文件存在、frontmatter 完整
       │
       ▼
  Step 7: 批量双向链接 ──►
       ├── 系列内链接（新文件之间互相链接）
       └── 全库链接（链接到已有笔记 + 反向链接）
       │
       ▼
  Step 8: 合并报告 ──► 一张总表汇总所有处理结果
```

## 🧭 信息源优先级

在开始处理前，明确各信息源的**优先级顺序**。文件相关的指令可能来自多个渠道：

| 优先级 | 信息源 | 说明 | 示例 |
|:------:|--------|------|------|
| 🥇 **最高** | **飞书P2P聊天文本消息** | 用户上传文件后，紧随文件发送的文本消息 | `"关于MCP调用与子Agent的使用"`（跟在 PDF 文件后面的文字消息） |
| 🥈 **高** | **Claude 对话消息** | 用户在此对话中直接告诉你的 | `"存储路径：F:\...\AI"` |
| 🥉 **中** | **飞书P2P聊天上下文** | 同一聊天中较早期的消息 | 用户之前说过的路径 |
| 🏁 **最低** | **内容推断** | 根据PDF内容自行推断 | 用户说"你定"或未提供时 |

> [!WARNING] 🔴 **核心原则：先查飞书，再问用户**
> 当发现 中间文件/lark-resources/ 中有新文件，但 Claude 对话中未提供文件名或指令时，**不要立即询问用户**——先去飞书 P2P 聊天中搜索是否有文本消息。用户很可能已经通过飞书将文件名附在文件后面发送了。

## 处理模式判断

在开始处理前，根据以下条件判断使用单文件模式还是多文件批处理模式：

| 判断条件 | 模式 |
|---------|:----:|
| `中间文件/lark-resources/` 中只有 **1 个**新文件 | 📄 **单文件模式** |
| `中间文件/lark-resources/` 中有 **2 个以上**新文件 | 📦 **多文件批处理模式** |
| 用户消息中明确为 **多个文件指定了多个名称** | 📦 **多文件批处理模式** |
| 用户说"分别总结"、"逐个处理"、"每个文件一份" | 📦 **多文件批处理模式** |
| 飞书聊天消息中为 **多个文件指定了多个名称** | 📦 **多文件批处理模式** |

### Step 1: 扫描资源目录

检查 `中间文件/lark-resources/` 目录（相对 vault 根目录），列出所有待处理文件：

```bash
ls -la "中间文件/lark-resources/"
```

> [!TIP] 💡 按上传时间识别最新文件
> 文件名通常包含上传时间戳（如 `备忘录文档_202607140012.pdf` 表示 2026-07-14 00:12 上传）。按时间从新到旧排列，优先处理最新的文件。

重点关注以下文件类型：
- 📄 **PDF 文件**（最常见）→ 调用 会议笔记整理 处理
- 🖼️ **图片文件**（png/jpg/webp）→ 调用 会议笔记整理（支持 OCR）
- 📝 **文本文件**（txt/md）→ 直接读取内容后调用 会议笔记整理

> [!NOTE] 📌 上次处理过的文件
> 如果 `中间文件/lark-resources/` 中有已被处理过的旧文件（如 `备忘录文档_202607131627.pdf`），忽略它们，只处理最新的未处理文件。

#### 批量检测（多文件模式）

当扫描发现多个新文件时，按上传时间从新到旧排列，创建**处理队列**：

```bash
# 列出所有 PDF 文件，按时间排序
ls -la "中间文件/lark-resources/" | grep ".pdf" | sort -k6,7
```

记录以下信息到处理队列：
```
处理队列:
  [1] 备忘录文档_202607140043.pdf (上传时间: 2026-07-14 00:43, 大小: 573KB)
```

> [!IMPORTANT]
> 创建处理队列后，在后续步骤中要**按队列顺序**逐个处理文件。每次处理完一个文件后，将其标记为"已处理"。

### Step 1.2: 飞书聊天消息检索 ⭐（新增/重要）

**这是从本次实战中总结出的关键步骤。** 用户可能通过飞书 P2P 聊天发送文件名和处理指令，而不是在 Claude 对话中告知。

#### 1.2.1 为什么要检索飞书聊天

用户的常见操作模式：
1. 在飞书中发送一个 PDF 文件（文件消息）
2. **紧接着发送一条文本消息**，内容就是希望保存的文件名（如"关于MCP调用与子Agent的使用"）
3. 然后在 Claude 对话中只告诉存储路径

如果不检索飞书聊天，会遗漏文件名信息——这正是上次实战中的教训。

#### 1.2.2 检索方法

扫描完 中间文件/lark-resources/ 后，使用 `lark-im` 检索飞书 P2P 聊天中的最近消息：

```bash
# 第一步：确保使用用户身份（飞书消息搜索需要 user 身份）
lark-cli config default-as user

# 第二步：列出最近的 P2P 聊天消息，查看文件附近是否有文本消息
lark-cli im +chat-messages-list --user-id {{用户open_id}} --page-size 20 --sort desc
```

> [!NOTE] 📌 查找与文件关联的文本消息
> 在返回的消息列表中，找到文件消息（`msg_type: "file"`），然后查看：
> - 该消息**之后**的第一条文本消息——可能是文件名
> - 该消息**之前**的上下文——可能是存储路径
> - 文本消息如果是回复（`reply_to`）该文件消息的，则是明确关联

#### 1.2.3 消息类型识别

在飞书 P2P 聊天中，可能出现的消息类型：

| 消息类型 | `msg_type` | 内容 | 在本工作流中的用途 |
|---------|:----------:|------|:----------------:|
| 📄 **文件** | `file` | PDF、图片等 | 需要处理的源文件 |
| 💬 **文本** | `text` | 文字内容 | **文件名**、处理指令、路径说明 |
| 🤖 **交互卡片** | `interactive` | 机器人的交互选择 | 确认/选择操作 |
| 🖼️ **图片** | `image` | 图片消息 | 可调用 会议笔记整理 OCR |
| 🔗 **链接** | `link` | 分享链接 | 可能是文档链接 |

> [!TIP] 💡 **文本消息是最关键的信息载体**
> 用户发送文件后紧随的文本消息，**极大概率就是文件名**。

#### 1.2.4 从飞书消息中提取信息

根据检索结果，提取以下信息：

| 信息 | 飞书消息中的位置 | 示例 |
|------|----------------|------|
| **文件名** | 文件消息之后的文本消息内容 | `"关于MCP调用与子Agent的使用"` |
| **存储路径** | Cluade 对话消息 或 飞书聊天上下文 | `"存到AI目录"` |
| **处理方式** | 文本消息中的指令 | `"整理成笔记"`、`"总结内容"` |
| **多个文件名映射** | 按队列顺序对应多条文本消息 | `"1.3如何定科研方向"`, `"1.4定科研基础"` |

#### 1.2.5 搜索特定关键词

如果聊天消息较多，直接用关键词搜索：

```bash
lark-cli im +messages-search --query "文件名|路径|存到|整理" --page-size 10
```

#### 1.2.6 多文件模式的聊天检索

**仅多文件模式时**，飞书聊天检索更为重要——用户可能一次性发送：
1. 文件 1（PDF）
2. 文件 2（PDF）
3. 文本消息："文件1→名称A，文件2→名称B"

从消息列表中按时间顺序关联文件和文本消息。

> [!CAUTION] 🔴 **多条消息的顺序关联**
> 飞书消息的 `create_time` 字段标识时间。按时间顺序：
> ```
> T1: 文件1 (PDF)
> T2: 文件2 (PDF)
> T3: "文件1→名称A，文件2→名称B" (文本)
> ```
> 队列中排第1的文件 → 名称A，排第2的文件 → 名称B。

#### 1.2.7 当飞书聊天中也没有文件名时的处理

如果在飞书聊天中也没有找到文件名信息，**再回退到 Step 3 的确认流程**——在 Claude 对话中询问用户。

### Step 1.5: 批量命名映射（多文件模式专用）

**仅在多文件批处理模式时执行此步骤。**

当用户一次性指定了多个文件名时，需要将 中间文件/lark-resources/ 中的文件与用户指定的名称一一对应。

#### 1.5.1 解析用户提供的名称映射

名称可能来自两个渠道：
- **Claude 对话消息** —— 用户直接在此对话中告知
- **飞书聊天文本消息** —— 从 Step 1.2 中检索到的消息

用户可能以以下格式提供名称：

| 格式 | 示例 | 解析方式 |
|------|------|---------|
| **有序列表** | "文件1→1.3如何定科研方向，文件2→1.4定科研基础" | 按队列顺序一一对应 |
| **逗号分隔** | "1.3如何定科研方向, 1.4定科研基础" | 按队列顺序一一对应 |
| **分行** | "第一个叫A，第二个叫B" | 按语义对应 |
| **分别指定** | "文件1叫XX，文件2叫YY" | 直接映射 |
| **飞书文本紧随文件** | 在文件消息之后发送文本"关于MCP调用与子Agent的使用" | 文本即为对应文件的名称 |

#### 1.5.2 创建文件-名称映射表

```markdown
文件-名称映射表:
  | 队列# | 源文件                            | 笔记名称              | 目录       | 名称来源     |
  |:-----:|-----------------------------------|----------------------|-----------|-------------|
  |   1   | 备忘录文档_202607140025.pdf       | 1.3如何定科研方向     | 学术裁缝   | Claude对话   |
  |   2   | 备忘录文档_202607140028.pdf       | 1.4定科研基础         | 学术裁缝   | Claude对话   |
  |   3   | 备忘录文档_202607140043.pdf       | 关于MCP调用与子Agent的使用 | AI    | 飞书文本消息 |
```

> [!NOTE] 📌 系列判断
> 如果多个文件属于同一系列（如学术裁缝 1.3、1.4），目录一致。如果来自不同系列，则分目录存储。

#### 1.5.3 当名称对应不明确时的处理

| 情况 | 处理方式 |
|------|---------|
| 用户说"两个文件名字一样，加序号区分" | 询问具体命名规则 |
| 用户说"你定" | 根据内容推断后逐一确认 |
| 用户只说了部分名称 | 明确名称的部分先映射，缺失的部分询问用户 |
| 用户按队列顺序提供名称 | 按时间排序后一一对应（最常见） |
| **飞书聊天有文本，但 Claude 对话没有** | **直接用飞书文本作为文件名（Step 1.2 已检索）** |
| **飞书聊天和 Claude 对话都有名称** | **优先使用飞书聊天中的名称（信息源优先级最高）** |

> [!TIP] 💡 按序映射是最常见场景
> 用户通常会说"文件1→XXX，文件2→YYY"，直接按 中间文件/lark-resources/ 中的时间顺序从新到旧对应即可。

### Step 2: 分析文件内容

在确认存储目标之前，先快速了解文件内容，以便准确判断内容类型。

#### 2.1 快速预览 PDF

使用 PyMuPDF 提取前几页，快速了解内容概要：

```bash
python3 -X utf8 -c "
import fitz, sys
sys.stdout.reconfigure(encoding='utf-8', errors='replace')
doc = fitz.open('F:/积昌的知识库 - 副本/中间文件/lark-resources/{{文件名}}')
print(f'总页数: {doc.page_count}')
for i in range(min(3, doc.page_count)):
    text = doc[i].get_text('text')
    if text.strip():
        print(f'=== Page {i+1} ===')
        print(text[:500])
    else:
        print(f'=== Page {i+1} === [无文本内容]')
doc.close()
"
```

#### 2.2 批量预览（多文件模式）

**仅多文件模式时**，依次预览队列中每个文件的前3页，快速了解各文件的内容概要。无需一次性提取全文，先预览了解内容类型即可。

```
预览 文件1 → 判断内容类型
预览 文件2 → 判断内容类型
...
```

如果预览不足以判断（如文字提取不完整），再提取全文。

#### 2.3 判断内容类型

根据预览内容判断：

| 特征 | 类型 | 标签 |
|------|------|------|
| 有讲师讲解、知识点教学、案例演示 | 🎓 **听课笔记** | `#听课记录` |
| 有参与人讨论、决策、待办事项 | 🗣️ **会议记录** | `#会议记录` |
| 同时包含笔记文本 + PDF 讲义引用 | 🧬 **混合材料** | 按主类型选择 |

#### 2.4 判断是否属于已有系列

检查 `总结好的大纲以及笔记/` 下已有目录结构。如果是续集（如第 2 讲），应存入**同一目录**，文件名遵循系列编号规则（如 `1.1` → `1.2`）。

**多文件模式：** 如果多个文件属于同一系列（如 1.3、1.4），确认它们存入**同一目录**，文件名按系列编号有序排列。

### Step 3: 确认存储目标

收集三个关键信息。**注意各信息源的优先级（参考上方"信息源优先级"章节）。**

| 确认项 | 说明 | 优先级来源 | 示例 |
|--------|------|-----------|------|
| **存储路径** | 存放在 `总结好的大纲以及笔记/` 下的哪个子目录 | Claude 对话中提供 | `学术裁缝`、`AI` |
| **文件名** | 笔记的文件名（不含 .md） | **🥇飞书文本消息** > 对话消息 | `关于MCP调用与子Agent的使用` |
| **内容来源** | 简短说明来源（用于 frontmatter） | 根据内容推断 | "AI工具使用教程视频转录" |

#### 路径处理规则

```bash
# 基本路径
总结好的大纲以及笔记/{{子目录}}/{{文件名}}.md

# 如果子目录不存在，先创建
mkdir -p "总结好的大纲以及笔记/{{子目录}}/"
```

> [!TIP] 💡 如果用户说"你定"或"随便"
> 根据文件内容推断：看内容主题匹配已有目录，看是否属于系列（检查编号），按推断结果建议给用户确认。

#### 多文件模式的确认策略

| 情况 | 处理方式 |
|------|---------|
| **同系列多文件**（用户已指定所有名称） | 一次性确认目录，然后逐个处理 |
| **同系列多文件**（用户未指定名称） | 先确认目录，再逐个确认文件名 |
| **不同系列多文件** | 分别确认每个文件的目录和名称 |

### Step 5: 调用 会议笔记整理 skill

这是核心处理步骤。使用 Skill 工具调用 会议笔记整理 skill。

#### 5.1 单文件调用

```markdown
Skill: 会议笔记整理
Args: 
  处理文件: F:\积昌的知识库 - 副本\中间文件/lark-resources\{{文件名}}
  存储位置: F:\积昌的知识库 - 副本\总结好的大纲以及笔记\{{子目录}}
  文件名称: {{文件名}}
  内容来源: {{说明}}
```

#### 5.2 多文件顺序调用（批处理模式）

**仅多文件模式时**，按处理队列顺序，**依次串行调用** 会议笔记整理。每次只处理一个文件，完成后才开始下一个。

```
循环队列:
  ┌─────────────────────────────────────────┐
  │  文件 1 → 调用 会议笔记整理         │
  │         → 等待完成 → 验证通过          │
  │         → 标记为"已处理"               │
  ├─────────────────────────────────────────┤
  │  文件 2 → 调用 会议笔记整理         │
  │         → 等待完成 → 验证通过          │
  │         → 标记为"已处理"               │
  ├─────────────────────────────────────────┤
  │  ... (重复直到队列为空)                 │
  └─────────────────────────────────────────┘
```

> [!WARNING] 🔴 **串行而非并行**
> 不要同时调用多个 会议笔记整理。由于 Skill 调用是同步的，必须等前一个完成后再调用下一个。串行处理可以避免上下文混淆和资源冲突。

每次调用时，参数中的文件名和内容来源要对应到当前处理的文件：

```markdown
# 第 1 次调用
Skill: 会议笔记整理
Args: 
  处理文件: F:\积昌的知识库 - 副本\中间文件/lark-resources\{{文件1}}
  存储位置: F:\积昌的知识库 - 副本\总结好的大纲以及笔记\{{子目录}}
  文件名称: {{文件名1}}
  内容来源: {{来源1}}

# 完成后 → 第 2 次调用
Skill: 会议笔记整理
Args: 
  处理文件: F:\积昌的知识库 - 副本\中间文件/lark-resources\{{文件2}}
  存储位置: F:\积昌的知识库 - 副本\总结好的大纲以及笔记\{{子目录}}
  文件名称: {{文件名2}}
  内容来源: {{来源2}}
```

> [!CAUTION] 🔴 **上下文管理**
> 每次调用 会议笔记整理 后，要等它完全执行完毕（返回结果）再继续下一个。不要在前一个 会议笔记整理 尚未完成时就发起新的调用。

#### 5.3 参数传递要点

> [!WARNING] 🔴 **参数传递要点**
> 1. **必须使用完整绝对路径**（如 `F:\积昌的知识库 - 副本\...`），不要用相对路径
> 2. 路径中的反斜杠 `\` 会由系统自动处理，直接写 Windows 路径格式即可
> 3. 调用后 会议笔记整理 会执行其 Step 0（前置询问三个问题），**你需要提前帮用户回答这三个问题**，让 会议笔记整理 跳过提问直接处理：
>    - 存储位置 → 已在 Args 中提供
>    - 文件名 → 已在 Args 中提供
>    - 内容来源 → 在 Args 中补充 `内容来源: {{说明}}`

#### 5.4 等待 会议笔记整理 完成

会议笔记整理 会自动执行：
1. Step 0.5: PDF 文本提取
2. Step 1-2: 识别类型、清理预处理（字幕修正 + 去重）
3. Step 3: 结构化输出并写入磁盘
4. Step 6: 建立双向链接（基础版）

#### 5.5 处理 会议笔记整理 的 Step 0 询问

如果 会议笔记整理 因为缺乏上下文而发起 Step 0 的三个问题，直接给出答案让其继续：

> "这三个信息用户已经提供了：路径是 `总结好的大纲以及笔记/{{子目录}}`，名称是 `{{文件名}}`，来源是 PDF 文件，请直接处理。"

### Step 7: 建立双向链接（增强版）

会议笔记整理 的 Step 6 已经做了一次基础链接搜索，但**本 skill 需要额外做一次更全面的链接建立**，特别是：

#### 7.1 检查 会议笔记整理 已添加的链接

读取笔记末尾的 `## 🔗 相关笔记`，看是否已有链接。如果有，在此基础上补充而不是覆盖。

#### 7.2 补充系列链接

如果当前笔记属于某个系列（如 `学术裁缝` 系列），**必须**添加：

```markdown
- [[{{子目录}}/{{前序笔记}}]] — 上一讲/相关主题说明
```

#### 7.3 多文件交叉链接（批处理模式核心）

**仅多文件模式时，这是最关键的一步！** 同批次处理的多文件之间，应当建立**互相链接**的关系。

假设同批次处理了 1.3 和 1.4 两个文件：

```
文件 1.3 的 🔗 相关笔记:
  - [[学术裁缝/1.1读书的目的与未来方向的锚定]] — 第一讲（已有链接）
  - [[学术裁缝/1.2如何选导师]] — 第二讲（已有链接）
  - [[学术裁缝/1.4定科研基础]] — 下一讲：科研基础分类 ← 新增交叉链接

文件 1.4 的 🔗 相关笔记:
  - [[学术裁缝/1.1读书的目的与未来方向的锚定]] — 第一讲（已有链接）
  - [[学术裁缝/1.2如何选导师]] — 第二讲（已有链接）
  - [[学术裁缝/1.3如何定科研方向]] — 上一讲：如何选择科研方向 ← 新增交叉链接
```

**交叉链接规则：**

| 情境 | 操作 |
|:----:|------|
| 同系列、编号连续的多个新文件 | 建立"上一讲/下一讲"形式的系列链接 |
| 同系列但不连续（如同时处理 1.1 和 1.3） | 用"相关主题"说明建立链接 |
| 不同系列的文件（如同时处理学术裁缝和实习训练营） | 不建立交叉链接 |
| 新文件之间有主题关联（如 1.3 讲选方向、1.4 讲基础） | 用说明文字体现关联 |

#### 7.4 全库搜索相关笔记

使用 Grep 在 `总结好的大纲以及笔记/` 下搜索：

```
Grep pattern="关键词1|关键词2|关键词3|关键词4" path="总结好的大纲以及笔记/" glob="*.md" output_mode="files_with_matches"
```

关键词选择策略：
- 从 tags 中提取 2-3 个
- 从核心章节标题中提取 2-3 个
- 专有名词（课程名、讲师名等）

**多文件模式：** 每个文件独立搜索，独立匹配。不要用一个搜索词覆盖所有文件。

#### 7.5 正向链接 + 反向链接

| 步骤 | 操作 | 说明 |
|:----:|------|------|
| 1 | 选择 3-5 篇最相关笔记 | 排除当前笔记自身和 PDF 文件 |
| 2 | 添加到当前笔记 `## 🔗 相关笔记` | 每个链接带简短说明 |
| 3 | 追加反向链接到相关笔记 | 在目标笔记末尾添加 `- [[{{子目录}}/{{当前笔记名}}]]` |

#### 7.6 反向链接追加规则

- 如果目标笔记已有 `## 🔗 相关笔记` 列表 → 在列表中添加一项
- 如果目标笔记没有 → 在文件末尾添加 `## 🔗 相关笔记` 段落
- 避免重复添加：检查目标笔记是否已包含当前笔记的链接

**多文件模式：** 所有新文件都完成链接添加后，再统一做反向链接追加。这样可以避免反复读写同一文件。

## 🧩 边界情况处理

| 情况 | 处理方式 |
|------|---------|
| **中间文件/lark-resources/ 为空** | 告知用户没有找到待处理文件，请先通过飞书智能助手发送文件 |
| **有旧文件和新文件混在一起** | 按上传时间排序，只处理最新的未处理文件 |
| **文件不是 PDF 而是图片** | 直接调用 会议笔记整理，它支持图片 OCR |
| **单个新文件** | 走单文件模式标准流程 |
| **多个新文件（2个以上）** | 走多文件批处理模式流程 |
| **用户已指定完整路径和文件名** | 跳过 Step 3 确认，直接使用 |
| **用户为多个文件指定了多个名称** | 建立文件-名称映射表，按队列顺序对应 |
| **用户只说了部分文件的名称** | 明确的部分先映射，缺失的部分询问用户 |
| **⭐ 文件名在飞书聊天中（不在Claude对话中）** | **使用 Step 1.2 检索飞书 P2P 聊天中的文本消息作为文件名** |
| **⭐ 飞书聊天中有多条文本消息** | 按时间顺序关联：文件消息之后最近的文本消息即为文件名 |
| **⭐ 飞书聊天文本消息是回复某文件消息的** | 使用 `reply_to` 字段关联文件消息和文本消息 |
| **⭐ 飞书聊天搜索无结果（也没有文件名）** | 回退到 Step 3，在 Claude 对话中询问用户 |
| **会议笔记整理 执行失败或未生成文件** | 回退方案：手动 PyMuPDF 提取 → 手动整理 → 手动写入。**多文件：单个文件失败不影响其他文件的处理** |
| **目标目录已有同名文件** | 询问用户是否覆盖，或在文件名后添加时间戳 |
| **多个新文件属于不同系列** | 分目录存储，分别处理，不建立交叉链接 |
| **多个新文件属于同一系列** | 同目录存储，文件名连续编号，建立交叉链接 |
| **内容来源不是飞书而是企业微信** | **不触发**本 skill（企业微信走 wecom-summary 流程） |
| **笔记内容与现有笔记高度重叠** | 考虑合并而非创建新笔记，询问用户意见 |
| **会议笔记整理 发起 Step 0 询问** | 直接替用户回答三个问题，让其继续处理 |
| **当前笔记是某个系列的一部分** | 必须存入同一目录，文件名按系列编号规则命名 |
| **PDF 有文字但质量差（大量 Y=了 等）** | 会议笔记整理 会自动修正，无需额外操作 |
| **用户要求跳过某一步** | 尊重用户意愿，直接执行要求的步骤 |
| **批处理中某一文件处理时间过长** | 先完成该文件，再继续下一个（串行确保稳定性） |
| **批处理完成后发现某个文件内容有误** | 单个修复，不影响其他已经处理好的文件 |
