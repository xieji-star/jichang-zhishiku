# 文档转换+排版 Skill

## 概述

本 skill 提供两大功能：

### 功能一：AI 味道去除 + 文档排版转换
用户粘贴一段文字（带有明显的 AI 生成痕迹），需要：
1. **去 AI 味** — 将生硬、啰嗦、模板化的 AI 语言改写为自然、简洁、专业的人类写作风格
2. **排版美化** — 将处理后的文本按固定模板转换为精美的 PDF 文档

### 功能二：创业黑马工作文档排版优化
用户提供创业黑马数智科技部门的工作文档，需要：
1. **清理格式** — 去除冗余格式，统一排版风格
2. **应用模板** — 按蓝色渐变背景模板输出 PDF

### 功能三：短视频脚本诱饵资料PDF生成
用户提供短视频/抖音脚本（如论文辅导类、学术干货类脚本），每个脚本末尾通常带有诱饵引导（评论关键词 + 资料包承诺）。需要：
1. **理解脚本内容** — 识别每个脚本的主题、类型、诱饵关键词和应包含的内容清单
2. **设计资料内容** — 为每个脚本设计充实可用的资料内容（模板类、清单类、范例类、工具类）
3. **排版生成PDF** — 按固定模板为每个脚本生成独立的诱饵资料PDF

### 功能四：会议/课程纪要整理成 Obsidian 笔记
用户发送原始材料（会议纪要、课程纪要等，大部分为 PDF，也可能是 Word、TXT、图片等格式），需要整理成**全面、详细、完整**的 Obsidian 笔记；也用于对已有文档进行**排版**（重新格式化、美化布局、统一样式）和建立**知识库双向链接**。核心流程：读全文 → 同音字纠错 → 理顺逻辑顺序 → 去重 → 去口水话 → 按模板输出（概要、带 emoji 图标和一句话说明的索引、红/橙/蓝三色+emoji 重点标记、专业名词括号解释、知识库双向链接、附件超链接、源文档配图按对应位置就地插入——推广/装饰图自动剔除）。支持一次发送多份文件：按文件名中的段标记（上/中/下及中1、中2等）自动合并整理。任务入口智能判断：输入未整理的原始材料走完整整理流程；输入已整理的文档跳过整理、只做美化排版；双向链接在任何场景都执行。

> ⚠️ **两个排版体系的区分（重要）：** 本技能包含两套排版规则，按输出目标区分使用——
> - **PDF 排版**（功能一/二/三）：遵循下方"固定排版模板参数"与"Markdown 格式规范"（蓝色渐变背景、`--` 副标题标记、`>highlight` 高亮框、`---` 写作提醒等），输出精美 PDF；
> - **Obsidian 排版**（功能四）：遵循"第二部分"的"文档排版规则"（Markdown 结构排版、callout、红橙蓝三色重点标记），输出 Obsidian 笔记，不硬编码字体字号。
> 两者不可混用：PDF 模板参数仅用于 markdown_to_pdf.py 渲染；Obsidian 笔记排版靠 Markdown 结构实现。

## Markdown 格式规范（重要！）

解析器按照严格的规则解析 Markdown。以下规范必须在构建 Markdown 时严格遵守：

### 标题区格式（#）—— ⚠️ 最容易出错的地方

标题块由三部分连续构成，**中间不能有空行**（解析器只检查 i+1 紧邻行）：

```
✅ 正确写法：
# 文档标题
-- — 副标题文字 —           ← -- 是解析器标记，其后才是正文，em dash 放在 -- 后面
作者：姓名                   ← 紧接副标题，不能有空行

✅ 或使用"著作人/编著"前缀：
# 文档标题
-- — 副标题文字 —
著作人：姓名                 ← 紧接副标题
```

**注意副标题的对称性：** `-- ` 前缀是解析器标记，会被自动去除。如果副标题本身带有装饰符号（如 em dash `—`），必须放在 `-- ` 的后面：

| 写法 | 解析后结果 | 说明 |
|------|-----------|------|
| `-- 副标题` | `副标题` | 无装饰符号 |
| `-- — 副标题 —` | `— 副标题 —` | ✅ 两边对称的 em dash |
| `— 副标题 —` | ❌ 不被识别为副标题 | 解析器只认 `-- ` |

**常见错误：**

```
❌ 错误1：用了长破折号 — 而不是 --（解析器不识别）
# 文档标题
— 副标题文字 —            ← 解析器不认，当作普通正文

❌ 错误2：标题/副标题/作者之间有空行（解析器只检查 i+1 紧邻行）
# 文档标题
                          ← 空行导致副标题识别失败
-- 副标题文字 —
                          ← 空行导致作者识别失败
作者：姓名

❌ 错误3：标题行后有空格或其他字符
# 文档标题 -- 副标题       ← 副标题不能跟在 # 后面，必须单独一行
```

**验证方法：** 检查生成的 PDF 中：
1. 副标题是否为 **12pt 黑色加粗居中**，作者是否为 **16pt 灰色居中**。如果是 11pt 黑色左对齐 → 有空行导致识别失败
2. 副标题两端的装饰符号（em dash `—` 等）是否**左右对称**。如果仅一侧有 → `-- ` 标记后的内容需要补全

### 作者前缀说明

| 前缀 | 渲染效果 | 说明 |
|------|---------|------|
| `作者：` | 只显示姓名（如"科研华哥"） | 兼容旧文档 |
| `著作人：` | 显示"著作人：姓名"（如"著作人：科研华哥"） | 保留前缀 |
| `编著：` | 显示"编著：姓名"（如"编著：科研华哥"） | 保留前缀 |

### 写作提醒格式（---）

```
✅ 正确写法：
---

写作提醒
正文内容...
正文内容...

❌ 错误写法（标题后跟空行）：
---

                          ← 空行！标题行变成空，文字"写作提醒"被当正文
写作提醒
正文内容...
```

**原因：** 解析器把 `---` 后的第一行作为标题行。如果有空行，空行被当作标题（变成空白），实际的"写作提醒"文字被吞进正文，导致标题和正文都出现"写作提醒"（重复）。

### 标题层级

```
# 文档大标题           → 22pt 深蓝加粗居中
## 第1部分 一级标题    → 16pt 深蓝加粗
### 1.1 二级标题       → 13pt 中蓝加粗
```

- 一级标题支持 `第1部分`、`第一部分`、`1.` 等编号前缀
- 二级标题支持 `1.1`、`2.3` 等编号前缀

### 其他格式

| 格式 | 语法 | 渲染效果 |
|------|------|---------|
| 正文 | 普通文字，相邻行自动合并 | 11pt 黑色 |
| 加粗标签 | `**标签名：**` | 11pt 黑色加粗 |
| 要点列表 | `- 要点内容` | 11pt 黑色，缩进 + ● 符号 |
| 编号列表 | `1. 内容` / `2. 内容` | 11pt 黑色，独立段落不合并 |
| 数学公式 | `$$ 公式 $$`（支持同行或跨行） | 20pt 居中，matplotlib 渲染 |
| 高亮框 | `>highlight 文字` | 蓝底蓝框 |
| 写作提醒 | `---` + 标题行 + 正文行 | 红色标题居中 + 红色正文 |

## 执行步骤

### 步骤 1：理解输入并预处理

- 如果是粘贴的文字：先判断是否带有 AI 味（空泛的总结、重复的句式、过度使用"首先/其次/最后"、"值得注意的是"等模板化表达）
- 如果是创业黑马工作文档：识别文档类型（周报、SOP、方案等），保持专业正式风格
- 如果是学术/技术资料：保持原文风格，重点在排版美化
- 如果是短视频/抖音脚本文档（如论文辅导类、学术干货类）：识别每个脚本的主题、类型、末尾的诱饵引导（评论关键词 + 资料包承诺），进入功能三工作流
- **输入预处理：** 无论输入的是什么格式（Markdown、纯文本、富文本等），都先将其转换为普通结构化文本。清除原文中残留的 Markdown 语法符号（`**`、`` ` ``、`*` 等），只保留干净的文字内容。数学公式保留用 `$$` 包裹以便后续渲染。

### 步骤 2：去 AI 味处理（仅功能一）

对 AI 痕迹明显的文本做以下处理：
- ❌ 删除 "首先/其次/最后"、"值得注意的是"、"总的来说" 等空泛过渡词
- ❌ 删除 "在当今这个…的时代"、"随着…的发展" 等废话开头
- ❌ 删除每个段落末尾的 "总之/因此，…非常重要" 式总结句
- ❌ 合并过于细碎的短句
- ❌ 把 "我们应当/需要/可以" 改成直接陈述
- ✅ 保持专业术语和技术细节不变
- ✅ 保持数字、公式、代码不变
- ✅ 保持原文的逻辑结构和核心信息

### 步骤 3：构建 Markdown 内容

按以下结构组织处理后的文本，**严格遵循上面的格式规范**：

```markdown
# 文档标题
-- — 副标题 —
作者：姓名

## 第1部分 章节名

### 1.1 小节标题

正文内容...

**加粗标签：** 重点内容...

- 要点内容

$$ 数学公式 $$

>highlight 关键解读内容

---

写作提醒
正文内容...
```

### 步骤 4：生成 PDF

使用 `scripts/markdown_to_pdf.py` 脚本生成 PDF：

```bash
python "<skill_path>/scripts/markdown_to_pdf.py" \
  --input "<临时 markdown 文件路径>" \
  --output "<输出 PDF 路径>"
```

脚本会自动：
- 解析 markdown 中的标题层级
- **自动清除内联 Markdown 语法符号**（`**`、`` ` ``、`*` 等），输出纯文本
- 添加蓝色渐变背景
- 应用所有排版参数
- 渲染数学公式为透明 PNG
- 输出成品 PDF

**脚本清洗机制：** `clean_inline_markdown()` 函数会在解析后自动去除所有文本中的：
- `**bold**` → bold（加粗符号）
- `` `code` `` → code（行内代码符号）
- `*italic*` → italic（斜体符号）
- `**标签：** 内容` → 标签： 内容（标签行内的加粗符号，通过精确查找 `**` 关闭位置处理）

这意味着原文中有任何 Markdown 格式符号，最终 PDF 中都不会出现这些符号本身，只有干净的纯文本。

### 步骤 5：清理中间文件

**PDF 生成完成后，必须立即执行以下清理操作：**

1. **删除中间生成的 .md 文件** — 无论它被保存在哪个目录
2. **删除任何其他中间产物**（如临时 PNG 公式图片、临时配置文件等）
3. **仅保留最终 PDF 文件**

```bash
# 删除中间 markdown 文件（如果存在）
if [ -f "<临时 markdown 文件路径>" ]; then
  rm -f "<临时 markdown 文件路径>"
fi
```

> ⚠️ **规则：** 除非用户**在本次任务中明确申明**需要保留某些类型的文件（例如"帮我保留 md 文件"），否则一律只保留 PDF，删除所有中间文件。

### 步骤 6：错误总结与自动归档（新增 — 防止重复踩坑）

**每次调用完成后，必须执行以下操作：**

1. **回顾本次任务**：检查是否遇到了任何问题、Bug 或用户投诉（包括但不限于内容缺失、格式错乱、渲染异常、用户要求反复修改等）。
2. **判断是否需要归档**：如果本次任务中：
   - 修复了某个 Bug → 记录修复方案
   - 用户指出了某个错误 → 记录错误根因
   - 发现某个渲染异常 → 记录触发条件和规避方法
   - 用户提出了新的格式要求 → 记录新规则
3. **更新 SKILL.md**：将以上内容追加到「已知问题与注意事项」章节末尾，格式为：
   ```
   ### N. 问题标题（案例日期）
   
   **问题描述：** ...
   **根因：** ...
   **修复方案：** ...
   **相关文档：** ...
   ```
4. **更新 cases/ 案例库**：如果本次生成的是有代表性的文档，将最终正确的 Markdown 源码保存到 `cases/` 目录作为参考。
5. **更新描述字段**（如需要）：如果技能的行为或限制发生了实质性变化，同步更新 SKILL.md 开头的 `description` 字段，确保下一次调用时能正确触发。

> ⚠️ **核心原则：不让同一个错误出现两次。每次调用都是一次学习机会，必须把教训固化到技能文件中。**

### 步骤 7：返回结果

告知用户 PDF 已生成，给出最终 PDF 文件路径。如果用户有进一步调整要求（字体大小、颜色、行距等），修改脚本中的对应常量后重新生成。

### 步骤 8：功能三专属工作流——短视频脚本诱饵资料PDF生成

当步骤1识别到输入是短视频/抖音脚本文档时，执行以下专属工作流。

#### 8.1 分析脚本内容

读取每个脚本，提取以下信息：
- **脚本标题**：脚本的标题和副标题，后续用作PDF主标题
- **类型**：干货型或流量型，影响内容设计风格
- **诱饵引导**：每个脚本末尾的评论区关键词（如「返修」「图表」「叙事」等）和承诺的资料包内容
- **资料包内容清单**：脚本末尾承诺了哪些模板、清单或工具，必须全部覆盖

> 注意用户可能说"X份脚本"但实际数量可能不同，以实际读取到的脚本数量为准，不要被用户说的数字限制。

#### 8.2 设计资料包内容

根据脚本内容，为每个脚本设计充实可用的资料内容，确保用户拿到就能直接用。内容分为四大类：

- **模板类**：话术模板、句式模板、结构模板、Response Letter模板
- **清单类**：自检表、分类表、步骤清单、检查清单
- **范例类**：错误vs正确写法对比、改写前后对比、好/坏范例
- **工具类**：追踪表、操作模板卡、工作表示例

设计原则：每份资料包至少包含3-4个部分，每个部分有干货内容，不能凑数。

#### 8.3 构建Markdown内容

严格遵循本技能的全部Markdown格式规范，特别注意以下规则：

**标题区规则：**
```
# 主标题（基于脚本原标题，去掉营销词汇）
-- — 副标题 —
作者：姓名
```
- **主标题**：使用脚本原标题或基于脚本标题创作。禁止带品牌前缀（如"华哥·"），禁止带"资料包""大礼包"等营销词汇。直接用脚本原标题如"论文返修四步法""论文图表叙事法""创新不足破局三招"等
- **副标题**：简短（4-12字），能总领全文。禁止使用"评论XX免费领取""评论区扣XX领取"等引导语。使用如"论文返修通关指南""图表叙事指南""让创新被看见"等概括性短句
- 标题/副标题/作者三行**连续无空行**

**内容结构建议：**
- 每个资料包分为3-4个部分，用 `## 第X部分` 组织
- 每部分用 `### X.X` 细化小节
- 关键内容用 `>highlight` 高亮框突出
- 要点用 `-` 列表
- 步骤或编号内容用 `1.` `2.` 编号列表

## 已知问题与注意事项

### 1. 副标题必须使用 `-- ` 前缀

解析器通过 `startswith('-- ')` 检测副标题。**不能使用长破折号 `—`（U+2014）**，必须用两个连字符加空格：

```
-- 这是副标题    ✅ 正确
— 这是副标题    ❌ 错误（不会被识别）
```

### 2. 标题区不能有空行

解析器只检查**紧挨着的下一行**（`i+1`）来寻找副标题和作者。空行会导致识别失败。标题、副标题、作者三行必须连续无空行。

### 3. 写作提醒 `---` 后不能有空行

`---` 后的第一个非空行作为标题。如果紧跟着空行，标题会变成空字符串（fallback 为"写作提醒"），而实际的文字会被当作正文内容。**正确做法：** `---` 后直接写标题，不留空行。脚本已加入自动跳过空行的保护逻辑，但最佳实践仍是不要留空行。

### 4. fpdf2 的 cell() 渲染注意事项

`cell()` 方法在**常规字重 + 小字号（12pt）+ 无边框**的组合下，fpdf2 可能不渲染文字（已知 bug）。解决方案：
- 副标题等需使用 `multi_cell()` 代替 `cell()`
- 如果需要精确控制位置，可配合 `border=1` 调试（开启边框观察位置），确认后再关闭

### 5. 作者前缀可选

- `作者：姓名` → 渲染为"姓名"（灰色，16pt）
- `著作人：姓名` → 渲染为"著作人：姓名"（灰色，16pt，保留前缀）

### 6. 公式解析

`$$` 公式支持两种格式：
- 同行：`$$ 公式 $$`
- 跨行：
  ```
  $$
  公式行1
  公式行2
  $$
  ```

### 7. matplotlib 字体警告

生成 PDF 时控制台可能出现 "MERG NOT subset" 警告。这是 matplotlib 的字体子集化警告，**不影响 PDF 输出效果**，可以忽略。

### 8. `-- ` 前缀被剥离导致副标题不对称

**问题：** 副标题行 `-- 摆脱中式流水账，打造顶级学术叙事流 —` 解析后变为 `摆脱中式流水账，打造顶级学术叙事流 —`，右侧有 em dash 但左侧没有，看起来不对称。

**根因：** `-- `（两个连字符+空格）是解析器标记，会被 `[3:]` 完全剥离。如果装饰符号写在 `-- ` 的**前面**（如 `— 副标题`），解析器不认；如果写在 `-- ` 的**位置**上（即用 `—` 替代 `--`），解析器同样不认。只有放在 `-- ` 的**后面**才会保留：

| 原始行 | 解析后副标题 | 结果 |
|--------|-------------|------|
| `-- 副标题` | `副标题` | 无装饰，内容正确 |
| `-- — 副标题 —` | `— 副标题 —` | ✅ 两边对称 |
| `— 副标题 —` | ❌ 不被识别，降级为普通正文 | 格式错误 |

**修复前写法：**
```markdown
# 文档标题
-- 副标题 —           ← 右侧有 em dash，左侧没有
```

**修复后写法：**
```markdown
# 文档标题
-- — 副标题 —         ← em dash 放在 -- 后面，两边对称
```

### 9. 内联 Markdown 符号（`**`、`` ` ``）残留

**问题：** 正文中的 `**加粗**` 和 `` `代码` `` 符号会直接出现在 PDF 中，影响美观。

**解决方案：** 脚本已内置 `clean_inline_markdown()` 自动清洗函数：
- `**bold**` → bold
- `` `code` `` → code  
- `*italic*` → italic
- `**标签：** 内容` → 标签： 内容

清洗在解析之后、渲染之前执行，不影响 Markdown 的结构解析，只去除输出中的语法符号。

### 10. 标签行 `**` 的精确解析

**问题：** 原标签解析器用 `strip('*')` 暴力清除头尾星号，导致 `**低阶：** However...` 处理成 `低阶：** However...`（内层 `**` 残留）。

**解决方案：** 改为查找 `close_pos = line.find('**', 2)` 精确定位关闭标记位置，只去除第一对 `**`，保留其后所有内容。

### 11. 编号列表 `1. 2. 3.` 的独立段落支持

**问题：** 原解析器不识别 `1. ` `2. ` 等编号前缀，将编号行当作普通正文（相邻行自动合并），导致多个编号点连成一段。

**解决方案：** 解析器已增加 `\d+\. ` 正则检测，匹配到编号前缀时作为独立 `numbered` 类型处理，不参与相邻行合并。同时 `clean_content` 会对其内容执行内联 Markdown 清洗。

**用法示例：**
```markdown
1. **尊重的姿态，明确的事由：** 邮件开篇必须清晰给出 Manuscript ID 与 Full Title。
2. **给编辑台阶，不直接责备：** 将延迟归因于"审稿专家寻找困难"。
3. **主动提供帮助：** 表达愿意补充数据、提供潜在审稿人名单的意愿。
```

**注意：** 编号后必须紧跟空格（`1. 内容`）。编号行与下一编号行之间**不**需要空行，解析器会自动将它们分别作为独立段落。

### 12. 写作提醒 `---` 吞噬后续所有内容（案例分析）

**问题：** 当 `---` 出现在文档**中间**时，解析器的写作提醒处理循环会一直收集到文件末尾，把后续所有章节标题和正文全部吞入写作提醒正文。这导致：
- 章节结构完全丢失（所有内容被渲染为红色正文）
- 长文本被 `multi_cell()` 在奇怪位置截断，出现"随意分行"现象
- 写作提醒以外的所有格式（标题、列表、高亮框）全部失效

**表现为用户反馈：** "被拒稿后的三大底层认知 1. 盲目改投...看到同样的问 题再拒你一次" — 章节标题消失、文字断在不合理的位置。

**根因：** 解析器第 437-441 行原始代码：
```python
while i < len(lines):
    line = lines[i].strip()
    if line:
        body_lines.append(line)
    i += 1
```
循环不检测任何终止条件，一路消费到 EOF。

**修复方案：** 在循环中添加标题边界检测，遇到 `#` 或 `---` 时停止收集，让外层主循环处理：
```python
while i < len(lines):
    line = lines[i].strip()
    if not line:
        i += 1
        continue
    if line.startswith('#') or line == '---':
        break
    body_lines.append(line)
    i += 1
```

**最佳实践（供创作者参考）：**
- ✅ `---` 写作提醒**推荐放在文档末尾**（如自查清单、注意事项等），这样即使不加边界检测也能正确工作
- ✅ 如果需要在文档中间使用写作提醒（如强调核心观点），确保解析器已应用上述修复
- ✅ 写作提醒每行正文控制在 **45 个汉字以内**（约 180mm），优先保持单行显示
- ❌ 不要在写作提醒后面紧接章节标题而不加空行 — 虽然修复后能正确截断，但空行有助于可读性

**案例验证：** `SCI拒稿信号分析与修改策略对照表` 文档在修复前：第1部分的写作提醒吞掉了第2~5部分所有内容，导致全部内容堆在红色正文中，章节结构消失。修复后：写作提醒止于三大底层认知，后续章节正常解析。

### 13. 写作提醒正文智能换行

**问题：** 原实现直接使用 `multi_cell()` 渲染写作提醒正文，即使文字刚好能一行显示也按多行逻辑处理，且缺乏宽度预检机制。

**解决方案：** 脚本已改为"先测宽、再渲染"——`writing_reminder()` 对每行正文先用 `get_string_width()` 检测文字宽度：
- ✅ **宽度 ≤ 180mm** → 使用 `cell()` 单行渲染，行距紧凑
- ✅ **宽度 > 180mm** → 使用 `multi_cell()` 自动换行，内容不丢失

**原则：** 写作提醒正文渲染遵循"迫不得已才换行，能一行显示绝不打断"。这确保短文本紧凑、长文本完整。

**内容建议（供创作者参考）：** 写作提醒每行正文控制在 **45 个汉字以内**（约 180mm），优先保持单行显示。如果信息较多，拆分为多行正文，每行独立：

```markdown
---

写作提醒
邮件模板不是万能药，使用时根据情境调整语气措辞，催稿勿超1次/月。
Rebuttal 的核心原则是"尊重但坚定"——既要承认审稿人的贡献，也要有理有据地捍卫自己的工作。
```

### 14. ASCII 下划线 `_` 渲染异常导致文本框错位（案例分析）

**问题：** 文档中使用 `【__________________】`（ASCII 下划线 `_`, U+005F）作为填空文本框时，fpdf2 渲染出现文本流错位，表现为：
- "文本框与整个文本错位"
- 文本框区域出现空白，文字跑到错误位置
- 长串连续下划线导致 `multi_cell()` 行宽计算异常

**根因：** ASCII 下划线 `_` 是窄字符（约 2mm/字符），在 fpdf2 的 `multi_cell()` 中，连续下划线被当作一个不可断开的"单词"。当这个"单词"宽度超过行宽时，`multi_cell()` 无法正确断行，导致整行渲染偏移或跳过。

**修复方案：** 将 ASCII 下划线替换为**全角下划线 `＿`（U+FF3F）**，它在 CJK 字体中与普通汉字等宽（约 3.88mm/字符 @ 11pt），`multi_cell()` 能正确处理其换行位置。

| 写法 | 渲染结果 |
|------|---------|
| `【__________________】`（ASCII `_` × 18） | ❌ 渲染错位，出现空白 |
| `【＿＿＿＿＿＿＿＿＿＿＿＿】`（全角 `＿` × 18） | ✅ 正常显示，与文字对齐 |

**修复前后对比（三遍过滤法操作模板卡）：**
```markdown
# ❌ 修复前（ASCII 下划线）
- 新 Idea 雏形：将本文的【】模块/公式，跨领域引入到【】任务中，用来解决【__________________】问题。

# ✅ 修复后（全角下划线）
- 新 Idea 雏形：将本文的【】模块/公式，跨领域引入到【】任务中，用来解决【＿＿＿＿＿＿＿＿＿＿＿＿】问题。
```

**适用范围：** 文档中所有填空/待填写区域，包括：
- `记录：＿＿＿＿＿＿＿＿＿＿＿＿`（思考记录区）
- `迁移方向：＿＿＿＿＿＿＿＿＿`（填写区域）
- `【＿＿＿＿＿＿＿＿】`（填空文本框）

### 15. 写作提醒禁止随意分行——内容未填满时禁止手动换行（重要规则）

**问题：** 写作提醒正文中，人为将长句拆分为多行（每行 ≤45 字符）会导致"内容未填充满就换行"的现象。例如：

```
盲目改投是最大的时间浪费：不处理审稿意见直接投下一个期刊，    ← 约31字，行未满就换行
大概率换一批审稿人，看到同样的问题再拒你一次。               ← 约22字，行未满
```

这种行为导致 PDF 中出现大量半空行，视觉上参差不齐，阅读体验差。

**根因分析：** 此前的错误修复方案要求"手动将写作提醒正文拆分为 ≤45 字符的短行"，但该方案治标不治本——它虽然避免了 `multi_cell()` 在字符中间断开的问题，却引入了更严重的新问题：**内容未填满就换行**。

**正确方案：** 不要手动断行！保持每个完整句子为一行，让 PDF 引擎的 `multi_cell()` 自然处理换行。即使 `multi_cell()` 可能在字符中间断开（如"问/题"分处两行），这也是 PDF 引擎的标准换行行为，比人为制造半空行更可接受。

```markdown
# ❌ 错误做法（手动断行，行未满就换）
---

写作提醒
被拒稿后的三大底层认知
盲目改投是最大的时间浪费：不处理审稿意见直接投下一个期刊，
大概率换一批审稿人，看到同样的问题再拒你一次。

# ✅ 正确做法（保持完整句子为一行，引擎自然换行）
---

写作提醒
被拒稿后的三大底层认知
盲目改投是最大的时间浪费：不处理审稿意见直接投下一个期刊，大概率换一批审稿人，看到同样的问题再拒你一次。
审稿人是你最便宜的顶级顾问：别人花几个小时免费帮你找论文的死穴，把意见用透，这篇论文就成了。
区分"执行问题"与"选题问题"：技术细节没做好可以补实验，如果是底层逻辑或选题立意出问题，盲目改投毫无意义。
```

**核心规则（必须遵守）：** ⚠️ **当一行内容未填充满时，禁止随意换行！**
- 写作提醒的正文行应以"完整语义单元"为单位（一个完整的句子或分句）
- 不限制每行的字符数，即使超过 45 字也不手动断行
- 排版引擎的 `multi_cell()` 会自动处理换行，无需人工干预
- 如果担心 `multi_cell()` 断行位置不理想，应通过调整页面边距或字体大小解决，而不是手动断行

### 16. `>highlight` 解析器缺陷——同行文本被丢弃（严重 Bug 修复记录）

**问题等级：** 🔴 **严重 Bug — 内容完全丢失**

**问题：** 所有 `>highlight` 高亮框的内容均为空。具体表现为：
- 蓝色矩形框正常绘制（位置正确）
- 但框内**没有任何文字**
- 用户反馈："万能模板部分连内容都没有了"

**根因：** 解析器第 414-424 行的 `>highlight` 处理逻辑存在致命缺陷：

```python
# ❌ 有问题的代码（v1）
if line.startswith('>highlight'):
    texts = []          # texts 初始为空
    i += 1              # ← 直接跳到下一行，丢弃了 >highlight 同行的文本！
    while i < len(lines):
        line = lines[i].strip()
        if not line or line.startswith('#'):
            break
        texts.append(line)   # 只收集后续行，不收集 >highlight 同行的内容
        i += 1
    content.append({'type': 'highlight', 'text': ''.join(texts)})
    continue
```

`i += 1` 直接跳过了当前行，而 `texts` 初始为空列表。后续的 while 循环只收集 `>highlight` **之后**的行。这意味着：
- 单行写法 `>highlight 文字内容` → `texts = []` → 高亮框为空 ❌
- 多行写法无法生效，因为后续行要么是空行要么是标题，循环立即 break

	>>> 修复后（v2）完整代码：
```python
if line.startswith('>highlight'):
    text_after = line[len('>highlight'):].strip()  # 抓取同行文本
    texts = [text_after] if text_after else []     # 作为初始内容
    i += 1
    while i < len(lines):
        line = lines[i].strip()
        if not line or line.startswith('#'):
            break
        texts.append(line)
        i += 1
    content.append({'type': 'highlight', 'text': '\n'.join(texts)})
    continue
```

**注意事项（v2 版本包含两个修复）：**
1. `text_after` 捕获 `>highlight` 同行的文本 → 修复内容完全丢失
2. `'\n'.join(texts)` 替换了原来的 `''.join(texts)` → 修复多行文本被无间隔拼接

**第二个 Bug 详解：** `''.join(texts)` 会将多行高亮文本拼接为无间隔的一整段。例如：
```markdown
>highlight 第一行内容。
第二行内容。
```
用 `''.join` → `"第一行内容。第二行内容。"`（两句话连在一起，`multi_cell()` 仍然被迫在字符中间断行）
用 `'\n'.join` → `"第一行内容。\n第二行内容。"`（`multi_cell()` 在 `\n` 处分行，每个自然句独立一行）

**最佳实践（多行高亮）：** 当高亮文本较长（超过约 45 个汉字）时，应在自然断句处拆分为多行：
```markdown
# ✅ 正确做法：在自然句号/分号处换行
>highlight 【华哥寄语】不要等待灵感砸到头上，高手发论文靠的是 SOP（标准作业程序）。
每次读文献，老老实实把这三步走完，Idea 就会自然出来！
```

**验证方法：** 拆分后每行应 ≤ 45 个汉字（约 174mm），这样 `multi_cell()` 渲染时每行正好占满一行，不会再次断行。

**影响范围：** 该 Bug 影响了所有使用了 `>highlight` 语法的文档，包括：
- `三遍过滤法操作模板卡.pdf` — 【华哥寄语】高亮框为空
- `SCI拒稿信号分析与修改策略对照表.pdf` — 万能模板高亮框为空

**教训：** 在修复解析器 Bug 之前，上述两个文档的高亮框在所有迭代中都是空白的。AI 在排查时错误地将原因归咎于 em dash `—` 等特殊字符（见第 16 条的初版记录），而非定位到解析器本身的逻辑缺陷。

> ⚠️ **排查原则：当内容完全不显示时，优先怀疑解析器/渲染管线的上游（数据是否被正确提取），而非下游（渲染细节）。**

### 17. 排版时随意删除原文内容导致信息丢失（错误案例警示）

**问题等级：** ⚠️ **严重错误** — 内容完整性事故

**错误行为：** 在执行"学术/技术资料排版美化"时，AI 在"去 AI 味"的名义下**自行删除了原文中的重要内容**，包括：

| 删除的内容 | 所属文档 | 影响 |
|-----------|---------|------|
| "拆论文核心：你不是在读别人的论文，你是在拆零件拼你自己的东西！" | 三遍过滤法 | 丢失了背面的核心指导思想 |
| 【直接扔掉】的方括号格式（改为普通文字"直接扔掉"） | 三遍过滤法 | 丢失了原文的视觉强调效果 |
| PAGE 5 完整流程图（改为一行概括文字） | SCI拒稿 | 丢失了完整的 SOP 可视化结构 |
| 自查清单的 `[ ]` 复选框符号 | SCI拒稿 | 丢失了可勾选的交互提示 |
| "（影响因子）""（审稿范围）""（参考公式模板）"等括号注 | SCI拒稿 | 丢失了对术语的补充说明 |
| 华哥寄语标题（仅保留寄语正文） | 三遍过滤法 | 丢失了寄语出处标识 |

**根因分析：**
1. **混淆了"去 AI 味"与"内容精简"** — 技能的去 AI 味只应删除模板化过渡词（首先/其次/值得注意的是），不应用于删除事实性内容、结构元素或格式标记
2. **擅自重写原文结构** — 将原本清晰的层级结构（如 PAGE 1 ~ PAGE 5）重新编号为"第1部分~第5部分"，过程中遗漏了部分内容
3. **误删格式标记** — 认为方括号 `【】`、复选框 `[ ]`、箭头 `►` 等是"格式噪音"而删除，实际上它们是原文的**语义组成部分**

**修复方案：**
1. **忠实还原**：对照原文逐行检查，确保 PDF 中的每一句话在原文中都有对应
2. **保留格式语义**：方括号、复选框、箭头等格式标记属于内容的一部分，必须保留

**评审清单（供创作者参考）—— 排版前自问：**
- [ ] 我是否删除了原文中的任何一句话？—— 如果是，必须确认该句不是重要内容
- [ ] 我是否改变了原文的结构层级？—— 如果是，必须确认新结构覆盖了全部原内容
- [ ] 我是否删除了任何格式符号（【】、[ ]、→ 等）？—— 如果是，这些符号可能有语义功能
- [ ] 我是否用自己的话重新表述了原文？—— 如果是，原文的精确信息可能已丢失

> ⚠️ **核心原则：排版美化的目的是让内容更好看，不是让内容变少。对学术/技术资料，保持原文完整是最高优先级。**

### 18. 诱饵资料PDF的主标题禁止品牌前缀和营销词汇（实战规则 2026-07-29）

**问题：** 生成诱饵资料PDF时，主标题使用了"华哥·论文返修资料包"格式，包含品牌前缀"华哥·"和营销词汇"资料包"，用户反馈"营销味道太大了"。

**根因：** 诱饵资料是用于评论区引导用户领取的PDF，用户希望它看起来像一份正经的学术参考资料，而不是营销物料。品牌前缀和"资料包"容易让人联想到商业推广。

**修复方案：**
- 主标题直接使用脚本原标题，如"论文返修四步法""论文图表叙事法""创新不足破局三招"
- 禁止在标题中出现品牌名（如"华哥·""XX老师·"）
- 禁止在标题中出现"资料包""大礼包""福利"等营销词汇

### 19. 诱饵资料PDF的副标题禁止使用评论区引导语（实战规则 2026-07-29）

**问题：** 副标题使用了"评论「返修」免费领取"格式，用户反馈"像营销号"。

**根因：** 评论区引导语虽然在脚本中提到了，但放在PDF副标题上显得过于营销化。用户希望副标题能概括资料核心价值。

**修复方案：**
- 副标题改为简洁的、能总领全文的短句，如"论文返修通关指南""图表叙事指南""数据到叙事的跃迁"
- 禁止使用"评论XX领取""评论区扣XX"等评论区引导语
- 副标题控制在4-12字之间，尽量精简

# 第二部分：会议/课程纪要整理成 Obsidian 笔记（功能四）

> 本部分由原「笔记整理」skill 整合而来，功能四的完整执行规范。以下流程适用于：用户发送原始材料（会议纪要、课程纪要等，多为 PDF，也可能是 Word、TXT、图片等格式）要求整理成 Obsidian 笔记、或对已有文档排版美化、或建立知识库双向链接。

## 核心原则 / Core Principles

1. **全面详细，绝不精炼**：用户明确要求"内容全面而非大幅精炼"。整理后的文档必须保留原始材料中的**所有实质内容**（观点、数据、事实、案例、决定、行动项），可以改写语言使其通顺，但**绝不可以随意删减内容**。宁长勿短。
2. **忠实原文**：不添加原文没有的观点或事实；改写的目的是让语句通顺，不是创作。
3. **处理顺序**：读全文 → 同音字纠错 → 理顺逻辑顺序 → 去重 → 去口水话 → 结构化成稿。先纠错、再捋顺、再去重，顺序不能颠倒。
4. **一文档一课程（硬性规则）**：一篇文档只存储一节课（一次会议）的内容，绝不把多节课的内容混入同一篇文档。一次整理了多节不同的课时，必须按课分开输出多篇文档，每篇只对应一节课。
5. **内容完整性可核查（硬性规则）**：整理稿必须覆盖原始材料的**全部信息点**——所有观点、数据、数字、案例、例子、操作步骤、注意事项、金句、老师口头反复强调的内容，一律保留。**整理完成后必须重新通读原始材料，逐段核对是否有遗漏**，确保"课堂上讲过的内容，笔记里都能找到"。宁可多写，不可漏写。

## 任务入口判断：缺少哪一步就从哪一步开始 / Entry Point: Start Where It's Missing

本部分包含两个主要功能：**① 整理**（原始材料 → 结构化完整笔记）和 **② 美化排版**（已整理文档 → 美化布局、统一样式），外加一个**独立步骤：知识库双向链接**（任何场景都要执行）。接到任务后**先判断输入材料处于什么状态，再决定从哪一步开始**——已做完的步骤跳过，缺哪一步就补哪一步，绝不重复劳动。

1. **判断输入材料状态**（开工前第一件事）：
   - **未整理**：输入是原始材料（PDF、Word、TXT、录音转写稿、会议/课程纪要、图片等，没有 frontmatter 和结构化章节）→ 需要**整理 + 排版**两步；
   - **已整理**：输入已是 Obsidian 笔记（有 frontmatter、有章节结构、内容完整，只是格式/排版/元素不理想）→ **跳过整理步骤**，只做**美化排版**；
   - **只要求双向链接**：用户只说"补个链接""建立双向链接""和知识库关联"等 → 只做**双向链接**步骤，不动文档其他内容。
2. **按状态执行**：
   - 未整理 → 完整流程：整理（工作流程第一~五步）→ 排版（输出模板 + 文档排版规则）→ 双向链接 → 质量检查清单；
   - 已整理 → 只做排版：按"文档排版规则"和"输出模板"补齐缺失元素（概要、索引、重点标记、分点等），**只改呈现形式，绝不删改实质内容**；然后执行双向链接。
3. **双向链接是独立步骤，任何场景（整理或排版）完成后都要执行**：扫描知识库，按"真实关联"标准建立/更新相关笔记区块、**正文就地链接（主要跳转入口）**与互链。用户明确会使用本技能的双向链接功能。
4. **对照检查清单补缺**：无论任务从哪一步进入，完成后对照"质量检查清单"逐项自查，**发现哪一项缺失就补哪一项**（缺概要补概要、缺索引补索引、缺重点标记补重点标记、缺链接补链接），已有且达标的项目不动。

## 多文件合并 / Merging Multiple Files

用户可能一次发送多份文件：它们可能属于同一堂课（会议）的多段纪要，也可能包含多节不同课（会议）的纪要。处理前先完成分组、排序、合并。

1. **识别文件名标记**：文件名结构为"课程/会议名 + 段标记"，段标记位于文件名的**末尾**：
   - 括号形式（全角（）或半角()）：`实习面试课（上）`、`实习面试课（中）`、`实习面试课（下）`
   - 不带括号直接跟在后面：`实习面试课上`、`实习面试课中`、`实习面试课下`
   - 带数字序号（中间段太长拆成多份时）：`实习面试课（中1）`、`实习面试课（中2）`，或 `实习面试课中1`、`实习面试课中2`
   - 含义：**上** = 该堂课的上半部分；**中** = 中间段；**中1** = 中间段第 1 部分、**中2** = 中间段第 2 部分（以此类推）；**下** = 下半部分
2. **按课程/会议分组**：去掉段标记后剩下的部分就是课程/会议名（如 `实习面试课`）。把课程/会议名相同的文件归为一组；一次发送多节不同课（会议）的纪要时，分别归入不同组。
3. **组内排序**：按 `上 → 中 → 中1 → 中2 → … → 下` 的顺序排列（数字序号决定段内先后；没有序号的中排在 中1 之前）。
4. **合并再整理**：把组内文件按排序后的顺序合并成一份完整内容，再进入"工作流程"进行后续整理。合并时先通读全部文件，再判断整体逻辑顺序，不要机械按文件顺序输出。
5. **分组输出（硬性规则）**：每个课程/会议生成**一篇独立文档**，文档标题用课程/会议名。**一篇文档只存储一节课（一次会议）的内容**，绝不将不同课程的内容混入同一篇文档；即使没有明确要求分开，也必须分开输出。单文件场景同理：一个文件 = 一节课 = 一篇文档。
6. **文档元数据**：frontmatter 的 `source` 字段列出全部原始文件名（如 `实习面试课（上）、实习面试课（中）、实习面试课（中1）`）。
7. **拿不准就问**：如果文件名无法识别（没有段标记、段标记不认、同一课程出现两个相同段标记如两个"上"、或排序矛盾），立即停下来向用户确认，不要自行猜测顺序或归属。

## 工作流程 / Workflow

> 进入本流程前先按"任务入口判断"确定输入状态：以下第一~五步针对**未整理**的原始材料；若输入**已整理**（或用户只要排版/补链接），跳过对应步骤，直接从"文档排版规则"（或"知识库双向链接"）开始——**缺少哪一步就从哪一步开始**。

多文件场景先按"多文件合并"完成分组、排序、合并，再进入以下步骤。

### 第一步：读取并理解全部内容

1. 用 Read 工具读取用户发送的文件：
   - **PDF**：用 Read 读取；超过 10 页必须用 `pages` 参数分页读取（每页 1-20 页），确保**读完全部内容**。
   - **Word/其他**：Read 直接读取，无法读取的格式先转换。
2. 通读全文，先弄清这份纪要讲的主题、涉及的话题有哪些、整体结构应该是什么。

### 第二步：同音字纠错（语音转写错别字修正）

纪要大多来自录音转写（语音识别），机器经常把读音相同或相近的字写成错别字——**同音字/音近字错误**（如"视觉锤"被写成"视觉吹"、"完播率"被写成"晚波率"、"小红书"被写成"小红叔"、"涨粉"被写成"掌粉"）。这类错字不改，整理出来的笔记内容就是错的，会误导后续阅读和使用。第一步已经通读全文、掌握了话题背景，这一步正好利用这份上下文判断正误。

1. **以纪要的具体内容为依据，不凭空猜**：同一个读音在不同语境对应不同汉字（如"shì lì"可能是"实力"也可能是"视力"），必须结合全文话题、前后文、举例和专名线索判断正确写法；读不通的地方往往是同音字错误的信号，结合上下文重读往往就能还原出正确的词。
2. **重点排查对象**（转写最容易出错的类型）：
   - 专业名词、术语、概念（如"完播率"→"晚波率/玩波率"、"私域"→"思域"、"视觉锤"→"视觉吹"）；
   - 人名、地名、品牌名、平台名（如"小红书"→"小红叔/小虹书"、"周鸿祎"→"周鸿一"）；
   - 中英混读、数字单位（如"AI"→"哎爱"、"1 万"→"1 碗"、"20 块"→"20 筷"）；
   - 同音近义词混用（如"涨粉"→"掌粉"、"带货"→"代货"、"预算"→"玉算"）。
3. **纠错原则**：
   - 只修正**确定无疑**的同音字错误——修正后的词必须能被上下文直接支撑；拿不准的**宁可不改**，保持原文（改错比不改更糟）；
   - 只替换错字，不顺手改写其他正常内容，不改变原意；
   - 同一错字全文反复出现时**全部修正**；发现一处同音字错误后，往往同篇还有成批的类似错误，顺带排查全文；
   - 说话人故意的谐音梗、双关语、口头梗（如"恰饭"、"起飞"）不是错误，**不要改**；
   - 人名、品牌名等专名实在无法确定正确写法时，保留原样并在首次出现处用括号标注疑似写法，留待确认，不瞎猜。
4. **时机**：本步在理解全文之后、理顺顺序之前执行——先读懂全文才能判断正误，纠正后再理顺逻辑顺序、去重、去口水话，后续所有步骤都基于纠错后的正确文本进行。

### 第三步：判断并理顺内容顺序

由于录音转写的原因，纪要内容可能乱序：**开头在最后面，内容和结尾在最前面**。

1. 判断是否乱序：观察内容间是否存在逻辑断裂、时间线错乱、话题中途被截断又接上、开头语出现在文末等情况。
2. 重构逻辑顺序，常见正确顺序：
   - **会议纪要**：开场/会议主题 → 议程/背景 → 主体内容（按话题分组）→ 讨论/问答 → 总结/结论 → 行动项/下一步计划。
   - **课程纪要**：课程主题 → 概念讲解 → 内容展开 → 案例/演示 → 总结要点。
3. 按**话题（topic）**重组而非机械按原文顺序排列；重组后保证上下文衔接自然。拿不准顺序时，以时间先后和话题完整性为第一依据。

### 第四步：删除重复内容

1. 找出重复内容（同一观点、同一段话、同一信息反复出现）。
2. 只保留一次**最完整、最清晰**的表述，删除其余重复部分。
3. 注意：相似但不完全相同的表述要保留（例如先简单提一句、后面详细展开的，保留详细版本；前后口径不同的，全部保留并标注差异）。

### 第五步：删除口水话和语气词

1. 删除语气词、口头禅：哦、啊、嗯、呃、emmm、就是说、然后（口语连接）、那个、这个、是吧、对吧、好不好、对不对、其实吧、反正、那啥、咱就是说 等。
2. 删除口语重复（"就是就是""对对对"）、没说完的碎片（除非能从上下文补全其意思）。
3. **保留所有实质内容**：观点、数据、事实、案例、决定、行动项一律保留，只删修饰性语气，不删信息。

### 举例与类比保留（硬性规则）/ Keeping Examples & Analogies

1. **课程/会议中的举例是理解的钥匙，必须保留**：讲师在讲观点时使用的**类比、比喻、举例、案例、故事、场景**（如"私厨宫保鸡丁""志愿填报""创业选赛道""太阳从东边升起"等），是帮助读者理解抽象观点、让内容"落地"的关键，**整理时一律保留，不得删除**。
2. **例子紧跟观点就地放置**：把例子放在它所解释的观点/概念旁边，用"类比""举例""比如"等标识引出，让读者读到观点时就能看到例子。
3. **例子要简洁（硬性要求）**：只保留例子的**核心比喻与关键信息**，点到为止、能看明白即可；**不展开人物、场景、动作、结果等细节，不重复讲师原话**（仍遵守"去口水话"规则）。判断标准：读者能看懂"这个例子在说明什么观点"即可，不需要还原完整场景。
4. **例外**：纯粹为了活跃气氛、与主题无关的闲聊段子可酌情精简；**只要例子在解释观点，就必须保留（但按第 3 条保持简洁）**。

### 分点方式 / Point Structuring

> 决定正文如何划分章节（分点）的规则。**用户指令中给出的分点方式优先于任何默认规则。** 分点只决定正文的 `##` 章节如何组织，不改变其余排版要求（概要、索引、重点标记、双向链接等照常执行）。

1. **用户未给分点方式 → 自行规划（默认）**：当用户没有明确要求按什么分点、分几部分时，默认根据原始材料内容**自行规划分点**——按话题、逻辑结构或时间顺序划分章节，章节数量不限，以"内容全面、结构清晰、分类合理"为准。
2. **用户已给分点方式 → 严格照做（硬性规则）**：当用户在指令中**明确给出了分点方式**（如给出章节标题列表、或指定"分几点/分几部分"）时，必须**严格按照用户给出的分点来组织文档**：
   - 分点的标题、顺序、数量一律以用户给的为准，**不得自行增删、改名、调序**；
   - 每个分点下的内容从原始材料中提取对应部分填充，内容仍须**全面详细**，不得因有固定分点就缩减内容；
   - 用户给的分点是总纲时（如只给了几个大类标题），大类下可再按内容自然细分小节（`###`），但**大类标题必须与用户给的一致**。
3. **判断依据**：从用户指令中识别是否包含"分点/分几部分/按以下分类/按照下面的格式/按照下面的要求"等字眼，以及是否列出了一组明确的标题或数字（如"1、xxx　2、xxx　3、xxx"）。**列出了 → 按用户分点执行；没有 → 自行规划。**
4. **分点与章节的对应**：用户给出的每个分点对应正文的一个 `##` 章节（分点标题即为章节标题）；自行规划分点时，每个话题/大类对应一个 `##` 章节。索引、重点标记、双向链接等其余排版要求不变。

## 输出模板 / Output Template（Obsidian 笔记）

整理结果必须是 Obsidian 笔记，遵循此模板：

```markdown
---
title: <文档标题>
type: 会议纪要 / 课程纪要 / 其他
date: <会议或课程日期；不知道则用整理日期>
tags:
  - <相关标签>
source: <原始文件名>
---

# <文档标题>

> [!summary] 概要
> <高度总结本纪要大概讲了什么：主题、主要结论、关键要点，2-5 句话>

## 相关笔记

- [[相关笔记1名]] — 关联说明
- [[相关笔记2名]] — 关联说明

## 索引

- 🎯 [[#1. <章节名>]] — <一句话说明本章讲什么>
- 📊 [[#2. <章节名>]] — <一句话说明本章讲什么>
- 💡 [[#3. <章节名>]] — <一句话说明本章讲什么>

## 1. <章节名>

<正文>

## 2. <章节名>

<正文>
```

### 模板说明 / Template Notes

1. **概要（必须）**：放在文档开头（frontmatter 之后、索引之前），用 callout `> [!summary] 概要`，高度总结文档大概讲了什么，让用户看一眼就知道内容。
2. **索引（必须）**：放在概要（及"相关笔记"区块）之后、正文之前，列出所有章节，**必须使用 Obsidian wikilink 锚点格式**跳转，保证在 Obsidian 中点击一定能跳转：
   ```markdown
   ## 索引

   - 🎯 [[#1. 章节名]] — 一句话说明本章讲什么
   - 📊 [[#2. 章节名]] — 一句话说明本章讲什么
   - 💡 [[#3. 章节名]] — 一句话说明本章讲什么
   ```
   - **每条索引 = emoji 图标 + wikilink + 一句话说明**（用户明确要求：第一眼就知道每条索引在讲什么内容）：
     - **图标**放在链接**前面**（链接外，不影响跳转），选与该章节内容匹配的 emoji（如 🎯 选题、🏭 生产线、🍡 信息点、🧲 勾人、📋 作业）；
     - **一句话说明**放在链接后面：`— <10-20 字概括该章节内容>`。
   - wikilink 内的标题必须与正文 `##` 标题**逐字完全一致**（包括序号、冒号、标点）。
   - **禁止**使用 `[文字](#锚点)` 这种 markdown 锚点格式——中文标题、冒号、句点等标点在 Obsidian 中会生成错误锚点，导致索引无法跳转。
   - 输出后核对一遍：把索引的 `[[#...]]` 与正文 `##` 标题逐一比对（可用脚本 diff），确保逐字一致、每条都能跳。
3. **正文**：
   - 按话题划分 `##` 章节，章节内用 `###` 小节组织。
   - 内容完整详细，宁长勿短；合理使用分段、列表、表格、加粗增强可读性。
   - 每个话题下先写核心结论，再展开细节。
   - **正文中每讲到一处与知识库其他文档关联的内容（案例、概念、人名、项目、素材），就在该处就地插入 `[[相关笔记名]]` 或附件链接**（规则见"知识库双向链接"章节第 2 节）——让读者在正文中直接点击跳转，不是只在开头/结尾集中堆链接。

## 范例文档 / Example Note

> 整理前先用 Read 打开范例文档，直观理解所有要求的最终效果，输出向它看齐（范例本身即质量标准）。

- **范例**：`总结好的大纲以及笔记/浪尖训练营/自媒体训练营/浩源自媒体课1.0/浩源自媒体课1.0第二节/浩源自媒体课1.0第二节.md`（若路径变动找不到，用 Glob 按文件名搜索）
- 重点看它的：
  - **索引**：每条带 emoji 图标 + `— 一句话内容说明`；
  - **重点标记**：红/橙/蓝三色 span + emoji + 加粗的组合方式；
  - **正文**：多级嵌套列表的分点方式、表格用法；
  - **结构**：概要 callout、"相关笔记"区块、wikilink 索引、文末"原始材料"附件链接；
  - **正文就地链接**：注意正文中"（第一天的课见 [[01 浩源自媒体课1.0第一节]]）""明天（[[03 浩源自媒体课1.0第三节]] 拍摄与剪辑课）"这类写法——链接嵌在相关内容旁边、读到即可点击跳转，这就是"就地插入"的标准形态（见"知识库双向链接"章节）。

## 文档排版规则 / Document Formatting Rules（Obsidian 笔记排版）

当用户要求**排版**（说"排版""重新排版""美化""调整格式"等），或整理时发现文档本身格式混乱，除按上述模板输出外，遵循以下排版规范：

> ⚠️ 本节是 **Obsidian 笔记**的排版规则（Markdown 结构排版）；**PDF 渲染**的排版规范见第一部分的"固定排版模板参数"与"Markdown 格式规范"，两者不可混用。

1. **标题层级统一**：按 `#` 文档标题 → `##` 章节 → `###` 小节 → `####` 细节依次递进，不跳级、不随意乱用层级。
2. **段落划分合理**：按话题/逻辑分段，每段聚焦一个意思，避免大段文字堆砌（一段以不超过 5-6 行为宜）。
3. **列表与表格规范**：并列内容用无序列表，步骤/顺序用有序列表，对比或数据用表格；同一文档内同类内容格式保持一致。
4. **强调样式统一**：加粗用于重点，斜体用于补充说明/引用；颜色标记只用于真正的重点（见"重点内容标记"），不混用、不滥用。
5. **中英文与标点规范**：中文正文使用全角标点，中文与英文、数字之间留一个空格，保持混排整齐。
6. **引用与 callout**：他人的话、原文引用用 `>` 引用块；提示、注意事项、总结用 callout（如 `[!tip]`、`[!note]`、`[!warning]`）。
7. **不硬编码字体字号行距**：Obsidian 由主题统一渲染，排版靠 Markdown 结构（标题、列表、表格、引用块）实现；不要用 HTML 强制字体大小、行距、对齐（重点颜色标记除外）。
8. **图片与附件位置**：图片、附件嵌入位置与描述文字相邻，必要时在图下加一行说明文字。
9. **排版不删内容**：排版只改变呈现形式，不删除、不改写任何实质内容（口水话按"第五步"规则处理）。若用户只说"排版"，同样按模板输出概要、索引与重点标记；只有用户明确说"只要排版、不要其他元素"时才简化输出。
10. **分点明确（硬性规则）**：正文必须多级分点呈现，**禁止"一大坨"文字堆砌**：
    - 能用列表表达的（并列项、要点、特征、步骤）一律用列表：无序列表 `-`，有序列表 `1. 2. 3.`；
    - 层级嵌套用缩进（`-` 下再缩进 `  -`，可继续嵌套）；
    - 每个分点只讲一个意思，一句话说不清就拆成多个分点；步骤/顺序用有序列表，对比或数据用表格；
    - 连续文字超过 5-6 行必须拆分成分点或列表；宁可多分点，不要大段堆砌。

## 重点内容标记 / Highlighting Key Points

1. 重点内容用 **图标（emoji）+ 文字颜色 + 加粗** 三种手段标记，确保重点一眼可见（用户明确要求重点必须突出）：
   - **图标**放在重点内容最前面，起视觉提示作用：
     - 🔥 最重要结论、决定、核心观点
     - ⚠️ 底线、禁忌、警示、不能做的事
     - 📊 重要数据、数字、指标
     - 💡 关键概念、定义、方法、原则
     - ⭐ 金句、老师的原话强调
     - 📌 注意事项、操作提醒
   - **文字颜色**（Obsidian 支持 HTML span）：
     - 红色 `#e74c3c`：最重要结论、决定、警示
     - 橙色 `#e67e22`：重要数据、数字、指标
     - 蓝色 `#2980b9`：关键概念、定义
   ```markdown
   🔥 **<span style="color:#e74c3c">最重要结论</span>**
   ⚠️ **<span style="color:#e74c3c">训练期写稿不要用 AI</span>**
   📊 **<span style="color:#e67e22">小红书基础浏览量 100</span>**
   💡 **<span style="color:#2980b9">PASS = 地点 + 动作 + 话术 + 内心所想</span>**
   ⭐ **<span style="color:#e74c3c">"时效性才是爆款视频的本质"</span>**
   ```
2. 重点内容同时用**加粗**辅助强调（见上示例）。
3. **只标记真正的重点**，不要给全文染色——但重点处**必须标记，宁可略多不可漏标**：每篇文档的重点标记不应少于 10 处（视内容量增减）。
4. 用户提供了图像/素材（图表、截图等）时，在对应内容处插入：
   - 已在知识库内：`![[图片文件名.png]]`
   - 在知识库外：先下载/复制到知识库附件位置，再 `![[图片文件名.png]]` 嵌入。
5. **写完必须验证颜色标签真实存在**：整理完成后用 Grep 检查文档中 `<span style="color:` 的出现次数（应 ≥10 处）并确认红/橙/蓝三种颜色都有。原因是：只写 emoji 和加粗、却漏掉 HTML 颜色标签，是整理时的常见失误，会导致整篇文档在 Obsidian 中渲染成统一颜色、重点完全不突出（用户踩过的坑）。

## 专业名词解释 / Explaining Jargon

1. 文档中的专业名词、英文缩写（如 ROI、KPI、SOP、OKR、DAU 等），在名词旁加括号解释：
   ```
   ROI（投资回报率，即投入的钱赚回来的比例）
   ```
2. **先根据文档内容判断该名词在此处的含义**，再解释。同一名词在不同语境意思不同，例如 ROI 在营销语境是"投资回报率"，在医学语境可能是"感兴趣区域"（Region of Interest）。以文档内容为准判断。
3. 解释要简单易懂、生活化，不要用更复杂的术语解释术语。
4. 只在名词第一次出现时解释，后续出现不重复解释。

## 知识库双向链接 / Bidirectional Links

> 双向链接的核心原则（用户明确要求，硬性规则）：**只有"真实关联"才建链；链接必须"就地插入"正文中与内容直接相关的句子旁**——读者在正文读到某个案例、概念、人名、项目、素材时，旁边就有可直接点击的 [[链接]]，点一下就能跳去关联文档查看详细内容。"相关笔记"区块（或 📎 行）只是文末的集中汇总，**正文就地链接才是主要跳转入口**。**严禁只在文档开头或结尾集中插入一堆链接**（读者读正文时看不到、点不到，等于白建）。

### 1. 只对"真实关联"建链，禁止"为了添加而添加"（硬性规则）

- **真实关联的判定标准**：两篇文档存在**实质内容上的关联**，读者从 A 跳到 B 能看到相关内容。常见真实关联：
  - 同一课程/系列的其他节课笔记（如第二节 ↔ 第一节、第三节）——自动互链，无需额外判断；
  - 同一项目的不同材料（如项目创新点文档 ↔ 该项目文件读取报错的日志，日志内容确实在讲这个项目的文件）；
  - 素材与使用该素材的文档（如学员案例素材库 ↔ 引用学员案例写成的脚本）；
  - 文档与其描述/引用的附件（PDF、Word、Excel 等）；
  - 文档与其所属的技能/规则（如日志所属的报错修复技能）。
- ❌ **禁止的链接类型**（用户踩过的坑）：
  - **"排版风格参照范例"类元关联**：A 文档排版参照了 B 文档的样式，这只是格式层面的参照、不是内容关联，**不建链**；
  - **仅凭关键词/主题沾边**：如两篇文档同属"农业"领域但内容互不引用、互相没有阅读跳转价值，**不建链**；
  - 任何"单纯为了添加而添加"的链接。
- **拿不准就删**：说不清"读者从 A 跳到 B 能看到什么相关内容"的链接，一律不建。

### 2. 链接必须"就地插入"正文中与内容相关的位置（硬性规则）

**链接的最终形态：链接是"嵌在正文里"的，不是"堆在文外"的。** 读者从正文开头读到结尾，每遇到一个与知识库其他文档关联的内容（案例、概念、人名、项目、素材），它的旁边就有 [[链接]] 可以直接点击跳转——读完正文，等于把整个关联网都走了一遍。

- **就地插入的规则**：
  - 讲到某个话题、案例、人名、项目、概念、素材时，若知识库中有对应笔记或附件内容，**在该内容所在的句子旁/段落处直接插入** `[[相关笔记名]]` 或附件链接，让链接与所讲内容紧贴在一起；
  - **一处关联加一处链接**：正文中每个有关联的地方都要加，同一素材在正文出现几次就插几次（如三个案例分别对应三份素材，就分别在三个案例处各插一个链接）；
  - **严禁只在文档开头或结尾集中插一堆链接**：把链接全部堆在开头"相关笔记"区块（或文末），读者读到正文时看不到也点不到，等于白建。
- **标准笔记（有 frontmatter）**：概要之后的"**相关笔记**"区块只作为**集中汇总清单**保留，**正文中的就地链接才是主要跳转入口**——两者都要有，正文就地链接尤其必须存在，缺一不可。
- **非标准文档的就地形式**（无 frontmatter 的脚本、日志等生产文档）：
  - 不单独设文末"相关笔记"区块（堆在末尾、阅读时看不见，等于白建）；
  - 在**正文开头元信息之后**加一行 `📎` 开头的集中链接行（如"📎 相关素材：…"）作为汇总，把关联文档与附件列在这里：
    ```markdown
    - 7个高流量标签：#论文标题 #SCI写作 #科研 #顶会 #研究生 #学术写作 #论文发表

    📎 相关素材：[[学员感悟]]（案例素材库）· [[0802脚本2]]（同系列脚本）· [结构模板：xxx.xlsx](../参考的资料/xxx.xlsx)
    ```
  - 📎 行只是汇总清单，**正文中遇到具体关联处仍必须就近插入链接**——如正文讲到某个学员案例时，就在该案例处插入 `[[学员感悟]]`；正文讲某条选题方向时，就插入 `[[受众报告]]`。

**就地插入的写法示例**（把链接嵌进正文句子里，读到即点即跳）：

```markdown
❌ 错误示范：链接全堆在开头/结尾，正文里一个都没有
📎 相关素材：[[学员感悟]] · [[受众报告]] · [[0802推文2]]

（正文一整段……全程没有任何可点击的链接……）

✅ 正确示范：每个关联处都就地插入链接
我有个学员，做家禽目标检测（案例细节见 [[学员感悟]]），手里只有 500 来张图，
跑出来的效果稀烂……
第一步，看量。500 张图对目标检测来说连热身都不够……（这条讲的是 [[受众报告]]
技术痛点型内容线）
三步查完，问题全在数据上——和 [[0802推文2]] 讲的是同一个坑。
```

- 就地链接写法灵活：可以直接 `[[链接]]` 嵌在句子里，也可以 `（相关：[[链接]]）` 跟在句尾；**只要链接出现在相关内容旁边即可**。

### 3. 双向互链的建立流程

1. 扫描知识库中已有的全部笔记（用 Glob 列出全库 .md 文件，再 Grep 搜索与本文内容相关的关键词：主题词、人名、项目名、概念名等），按第 1 条标准筛出**真实关联**的笔记；
2. **就地插入（核心步骤）**：写作/整理正文时，每写到一处与关联笔记相关的案例、概念、人名、项目、素材，**就在该处插入** `[[相关笔记名]]`（不带 .md 后缀的 Obsidian wiki-link）——一处关联一处链接，边写边插，不是最后集中加；
3. **通读补链**：正文成稿后通读一遍，逐段自问"这里提到的东西，知识库里有对应文档吗？"——有就补插就地链接，确保每个关联点都有链接可点；
4. 在相关笔记中对应位置加入返回链接 `[[本文档名]]`，实现**双向**；
5. 最后才在本文档概要之后、索引之前添加"**相关笔记**"区块（标准笔记）或开头 📎 行（非标准文档），把全部关联笔记集中汇总——**汇总 ≠ 替代正文就地链接**。

### 4. 删除/修改链接时的要求

- 删除某一对关联时，**双向都要删**——本文档的相关链接 + 对方文档中的返回链接一起移除，不能只删一边留下"单向断链"；
- 已建链接若重新判断不符合"真实关联"标准，同样双向清理。

### 5. 附件文档也是双向链接对象

- 文档与附件（PDF、Word、Excel、图片等）有关联时，同样要在有关联的正文位置建立链接（见"附件超链接"章节）——文档 ↔ 附件同样是双向链接，按第 2 条"在有关联的地方"就近放置。

### 6. 没有关联就不强建

- 没有关联就不强建；不要为了链接而链接。

## 附件超链接 / Attachment Links

> 附件链接是"文档 ↔ 附件"双向链接的一部分：只要文档与附件有关联，就必须在**有关联的正文位置就地插入**链接（用户明确要求），文末可另设"附件"汇总区，但正文就近链接必须有。

1. 如果用户提供了附件（PDF、Word、Excel、图片等），先理解附件内容，判断它与文档内容的对应关系。
2. **在文档中与附件内容相关的位置就地插入超链接**（每个有关联的地方加一处，不只在文末集中列一遍），让用户**从文档点击直接跳入附件的相关内容**查看详情：
   ```markdown
   [查看附件：<附件名>](<附件路径>)
   ```
3. 附件是 PDF 且能定位到具体页时，用 `#page=N` 定位（Obsidian 会跳转到该页）：
   ```markdown
   [查看附件：<附件名>（第 3 页）](<附件路径>#page=3)
   ```
4. 附件在知识库内的用相对路径；在知识库外的用绝对路径。无法定位具体页时，注明附件中大概位置（如"第 2 章"）。

## 图片插入规则 / Image Insertion Rules（功能四）

> 当源文档带有一组配图（微信公众号文章、长图、PPT、PDF 里的截图，常见为 `img_1.png`、`img_2.png`… 或按内容命名的截图/示意图），整理成 Obsidian 笔记时**必须把这些图片按对应位置插入**，让读者看到内容就能看到图。图片插入遵循以下硬性规则。**注意：图片用 `![[...]]` 内嵌（可直接显示），与"附件超链接"用 `[文字](路径)`（点击跳转）不同，两者别混。**

### 1. 先清点源文档全部图片（一张不漏）

- 读取源文档时，先**逐张列出所有图片**及其存储路径（如 `附件资源/<文章名>/img_2.png`）。
- 用 Glob 核对图片目录，确认每张都存在、知道每张的文件名。
- 清点后**数清总数**，之后插入时对照这一总数，确保一张不漏（漏图是最常见错误）。

### 2. 图片必须"就地插入"对应位置，不集中堆放

- 每张图片插在**它所配的内容旁边**：官网截图紧跟该网站介绍、课程/章节截图紧跟该节内容、文末推广码放文末。
- **一处内容对应一张图**，图与内容紧贴；**不要**把所有图集中堆在开头或结尾（和"就地链接"同理）。
- 图下（或旁）最好加一行说明（如"××官网截图"），让读者不点开也知道图里是什么。

### 3. 用 `![[...]]` 内嵌，且必须带**完整相对路径**

- 图片在知识库内：`![[路径/图片名.png]]`
- **必须写完整路径**（如 `![[微信公众号文章/黑大百科/附件资源/黑龙江大学常用网站及APP汇总/img_2.png]]`）。因为通用文件名（`img_x.png`）在全库可能重名，Obsidian 的"最短路径"会解析到错误的图。
- 支持 PNG / JPG / JPEG / GIF / WebP，GIF 动图也能内嵌。

### 4. 只引用、不复制、不移动源文件

- 源图片保留在原发布/附件目录，笔记**只做 `![[...]]` 引用**，不复制到笔记目录，避免重复占空间。
- **禁止删除、移动、重命名源图片**（源目录按"保留目录/只读"对待）。

### 5. 推广/装饰类图片：默认剔除，拿不准就问用户

- 对**推广二维码、公众号/群二维码、宣传海报、纯装饰性动图**（如星星、横幅、贴纸动图）这类"营销/纯装饰"图，**默认不插入、直接剔除**。
- 若无法判断某图是否属推广图，**询问用户**后再决定，不擅自插入。
- 用户明确要删除某图时，**连同该图上下文的说明文字、配图标题一起删除**，不能留下"孤图"或空标题/空段落（如整块"附：关联推广"段落一并删掉）。

### 6. 插入/删除后必须验证

- 用 Grep 核对笔记中所有 `![[...]]` 引用：
  - 每个引用都指向**真实存在的图片文件**（否则 Obsidian 显示空白/警告）；
  - 该插的都已插、无遗漏；该删的都已删、无残留图注。
- 用户要求"只保留截图类、删推广类"时，逐一核对该要求已落实（如只留 img_2~img_15 官网截图，删掉 img_1 群二维码、img_16 装饰动图、img_17 推广码）。

## 保存规则 / Saving Rules

1. **保存位置**：以用户指定的位置为准。用户说保存到哪就保存到哪；用户没说时，默认放到用户提供文件所在目录，或在可自行决定时放到知识库 `总结好的大纲以及笔记/` 下与主题对应的子文件夹（如 `总结好的大纲以及笔记/浪尖训练营/`）。
2. **文档命名**：按以下优先级确定——
   - **用户已明确给出名字** → 用用户给的名字；
   - **用户没给出名字、但有明确的存储目录** → **参考该存储目录下已有文档的命名格式来命名**：先列出该目录下现有文档，观察它们的命名规律（如 `术语-通俗解释.md`、`主题-副标题.md`、`英文缩写-中文全称.md` 等），再按同样的格式与风格为本文档命名，保持整目录一致性；
   - **既没给名字、也无既定格式可参考**（如目标目录为空）→ 才由你按通用规范自行命名（如 `主题-说明.md`）。
   - ⚠️ **注意**：参考的是"同目录文档的**命名格式**（结构与风格）"，不是照搬某个具体文件名；也不要误解为只能沿用已有的名字。
3. 整理完成后向用户报告：文档保存路径、文件名、整理了哪些内容。
